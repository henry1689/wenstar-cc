## 二、为什么需要豁免（背景）

### 缺陷实证

`_rebuildMemoryAnchors()`（`SQLiteAdapter.ts:2437`，调用点 `:719`）每次 `init()` 末端执行：先无条件 `DELETE` 全部 `%_ANCHOR`，再从 `conversations` 按 `dialog_group_id` 聚合重建，**循环里没有归属存在性检查**。

2026-10-10 户籍清理实测：8 个 uuid 的 **92 条锚点**离线删除后重启 → `memories` 9852 → 9944（正整 92），且 **id 集合与备份 100% 相同**（物理复原，非重新生成）。源为 `conversations` **384 行 / 92 个对话组**，全库 1583 组中恰 92 组属「源还在而无人认领」。

### S4 独立评审打回（`a96fae73e09447fa8`）

初版改动被评审**打回**，两条 P0：

- **P0-1 判据真源选错**：只用 `entities` 会**误杀活着的实体**。FG 73 个 uuid vs `entities` 70 个，其中 3 个 active 实体因同名行持别的 uuid 而永远进不了 `entities`：
  - `TXS-000000026` 警幻仙姑 → entities 同名行持 `027`
  - `TXS-000000028` 崔莺莺 → 持 `554`
  - `TXS-000000029` 陈都灵 → 持 `030`
  - 后果：锚点先被 DELETE 摧毁、再被判据拒收 → **永久消失且不可恢复**
  - 时序放大：`storage.initialize()` 在 `server.ts:496`，FG→entities 同步在 `:549` —— 判据每次都在同步之前评估
- **P0-2 fail-open 方向错**：判据故障会退化成原缺陷本身（复活），且 `us.length===0` 分支静默无告警

### 修订方案（本次豁免要落地的内容）

1. 判据真源改为 **`entities` ∪ FG nodes**（新增 `_fgUuids` 实例字段，由 `init()` 在重建**之前**异步载入）
2. 判据构建**移到无条件 DELETE 之前**；构建失败或可用集为空 → **`return 0` 不 DELETE**（fail-safe，两种失败模式都挡住）
3. 循环内跳过 + `nOrphaned` 计数 + `console.warn` 留痕
4. 更正注释两处：缺陷是「循环缺存在性检查」而非 `entMap` fallback；措辞改为「没有任何行持有该 uuid」而非「实体被删除」

**改动规模**：单文件 `src/m2/SQLiteAdapter.ts`，约 +60/-10，无 import 变更、无 schema 变更、无数据删除。
