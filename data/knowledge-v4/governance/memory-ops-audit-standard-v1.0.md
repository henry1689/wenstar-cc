## 第一章 · 总则

### 第一条　目的

记忆系统的每一次写入、回填、删除都可能**不可逆**（哈希固化、原文删除、钙分覆盖）。
本规范确立这些操作的留痕义务、审批边界与冲突处理流程，使任何一次历史状态都可被追溯和解释。

### 第二条　审计卷宗与体验记忆的分界

| | **审计卷宗** | **体验记忆** |
|---|---|---|
| 内容 | 谁在什么时候对什么做了什么 | 实体之间的对话与记忆内容 |
| 生命周期 | **永久只增不删**，不入遗忘流程 | 受 ADR-MEM-003 生命周期约束 |
| 压力处理 | 走冷归档迁移，不做逻辑删除 | 按 θ_forget / 墓碑期处置 |
| 载体 | `append_log` · Harness 审计日志 · `docs/LEDGER.md` · `docs/agent-collab/` | `memories` · `conversations` · `dialog_groups` |

> 依据：ADR-MEM-003 裁决②「审计变更账本 + 删除追溯日志永久只增不删」。
> 理由：带 TTL 的台账会让删除/钙化/权限变更全部失去可追溯性，回滚与串扰溯源直接废掉。

## 第二章 · 留痕义务

### 第三条　必须留痕的四类操作

| # | 操作 | 留痕位置 | 必填内容 |
|---|---|---|---|
| 1 | **卷宗化回填**（快照/哈希/日志） | `dialog_groups.append_log` | `type` + `actor` + `detail`（含跳过原因） |
| 2 | **摘要生成/重生成** | 同上 | `summary_generated` / `summary_regenerated` + 字符数 + 哈希前缀 |
| 3 | **生命周期流转** | 同上 | `lifecycle_changed` + 前后状态 + 触发原因 |
| 4 | **物理删除** | `docs/LEDGER.md` + 删除追溯日志 | 删除对象（精确主键）、依据条款、执行人、时间、备份位置 |

### 第四条　禁止的「留痕」

- ❌ 为凑齐覆盖率而写入假数据（无 40D 的组必须写 `agg:'none'` 占位或留 NULL，**不得填零向量**）；
- ❌ 自动「修复」哈希不匹配（自动重算 = 把篡改洗白，只能告警）；
- ❌ 裁剪 `append_log`（超水位只告警；增长控制交给上游节流）。

### 第五条　变更记录 ≠ 行为规范

**Bug 修复记录、变更说明、会话存档只作历史备查，不构成规范。**
规范只存在于：法典 → ADR → 本规范及其同级文件。
引用历史修复来说明「当前应该怎么做」是**无效论证** —— 历史修复可能早已被后续决策推翻。

## 第三章 · 操作前置

### 第六条　数据库改动的停服铁律

**任何直接改库的操作必须在停服窗口内执行，执行前备份。**

理由（实测事故）：sql.js 把整库载入 WASM 内存，运行中进程每 150ms 批量 flush 一次。
离线改库会被内存库**覆盖**，表现为「改完重启又变回去了」，且 `integrity_check` 仍为 ok，极难察觉。

### 第七条　备份与校验

| 项 | 要求 |
|---|---|
| 备份时机 | 结构性改动（DROP/ALTER/批量 UPDATE/DELETE）之前 |
| 备份完整性 | 压缩备份必须 `gzip -t` 通过后才可删除源文件 |
| 删除前核验 | 按**精确主键**核对，禁止按时间窗或模糊条件批量删 |
| 测试数据 | 测试产生的数据在任务完成后必清（本仓 `memories` 不隔离 test，尤须小心） |

### 第八条　迁移的幂等要求

每一批数据改制必须满足：**任何时刻中断，重跑结果一致**。
断点续传靠数据库扫描条件（`WHERE col IS NULL`）驱动，不依赖内存队列 —— 进程重启自动接着跑。

## 第四章 · 法典修订流程

### 第九条　五步流程

```
提案 → 关联 ADR → 业主评审 → 版本升级 → 代码对齐 → 合规巡检
```

| 步 | 要求 |
|---|---|
| 提案 | 写明改哪一条、为什么改、不改的后果 |
| 关联 ADR | 法律级改动必须有对应 ADR；无 ADR 的法条改动不予受理 |
| 业主评审 | **法律修改权归业主**。Agent 可起草，不得自行颁行 |
| 版本升级 | 同主题只保留最新版，旧版入 `_archive/`，不并存 |
| 代码对齐 | 法典生效后，代码必须在同期对齐或登记为缺陷 |
| 合规巡检 | 定期抽查「条文—代码—测试」三者是否仍对应 |

### 第十条　法典与代码冲突的处理

| 情况 | 处置 |
|---|---|
| **代码不符合法典** | 视为**缺陷**，按缺陷流程修复 |
| **法典落后于代码** | 启动修订；**修订期间不得以「法典还没改」为由继续跑偏** |
| **两者都在演进** | 先冻结该条款的执法（不据此判违规），在 ADR 中记录冻结原因与解除条件 |

### 第十一条　草稿的效力

标注为「草案 / 待业主裁决」的条文**不具现行效力**，不得据以判违规，也不得登记进
`GOVERNANCE.md` 效力层级总表。草案生效的唯一标志：业主明确裁决 + 写入正文 + 登记索引。

## 第五章 · 观测与告警

### 第十二条　必须持续观测的四项

| 指标 | 含义 | 异常信号 |
|---|---|---|
| 回填完成率 | 有 `content_hash` / 快照的组占比 | 长期停滞不前 ⇒ 某批组反复被扫到（占位没写成功） |
| 哈希不匹配数 | 完整性校验失败次数 | 出现非零 ⇒ 疑似篡改，立即人工介入 |
| 跳过原因分布 | `no_conversations` / `no_40d_data` 等 | 某一原因突然占多数 ⇒ 上游写入链路断裂 |
| 消费计数分布 | `consume_count` 直方图 | 大量组集中在 10（封顶）⇒ 阈值需复核或计数口径有误 |

### 第十三条　告警分级

| 级 | 判据 | 响应 |
|---|---|---|
| **P0** | 数据丢失 / 跨户籍可见 / 哈希不匹配 | 立即停写、人工介入、追溯 |
| **P1** | 回填连续失败 / 原文缺失 | 当日处理 |
| **P2** | 覆盖率偏低 / 日志水位告警 | 排期处理，登记 LEDGER |
