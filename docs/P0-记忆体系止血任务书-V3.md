## 一、P0-1 召回止血（先解决"记不住最近的事"）

### 1.1 问题

会晤路径的近期槽/历史槽**纯按钙化分排序、无时间近因因子**。历史槽被 29~40 天前的钙化=10 地标永久占满。

### 1.2 🔴 关键前提：那套槽位有**两份实现**（V3 新增发现）

| 实现 | 位置 | 谁在用 | 量级 |
|---|---|---|---|
| A | `src/m4/retrieval/meeting-recall.ts:141 recentCalciumRows` / `:157 historyCalciumRows` | `MeetingWallAdapter`（SearchOrchestrator 路径） | ≤10 条 |
| B | `src/webui/chat/retrieval-stage.ts:268-279`（**内联 SQL**） | **会晤主力路径** | 15 条 |

`retrieval-stage.ts` 从 `meeting-recall.js` **只导入了 5 个符号**（`RECALL_TRIGGER_RE / extractTopicKeywords / keywordRecallMemories / recallSandboxConversations / shouldEscalateToLlmPicker`）—— **两个槽位函数不在其中**。

而 `MeetingWallAdapter` 的注释写着「近期槽+历史槽——共享工具（meeting-recall.ts），**与隔离墙同源**」。

> 🔴 **注释与实现相悖。只改 A，你实际感受到"记不住"的 B 一行没动。**

### 1.3 修改方案（两步，顺序不可颠倒）

**第一步 · 收编（消除第二份实现）**

把 `retrieval-stage.ts:268-279` 的内联槽位查询替换为对 `recentCalciumRows() / historyCalciumRows()` 的调用。**这一步不改变行为**（SQL 等价），先跑全量测试确认零回归。收编后：

- 真源唯一 → 后续任何调整只改一处
- 行为回归由测试锁住 → 证明"收编不改语义"

**第二步 · 改真源（`meeting-recall.ts`）**

历史槽 —— 时间分层配额（替换 `historyCalciumRows`）：

```ts
/**
 * 历史槽：时间分层配额（V3）
 * 原实现：≥1天 全部按 calcium DESC 取 TOP6 → 被 29~40 天前的钙化=10 地标永久占满
 *        实测：最近 5 天的 176 条记忆在该排序里最好排名第 43
 * 新实现：按时间片分配名额，片内按钙化排序 —— 保证"近期"一定有代表
 */
const BUCKETS = [
  { fromDays: 1, toDays: 3,    quota: 2 },   // 1~3 天
  { fromDays: 3, toDays: 7,    quota: 1 },   // 3~7 天
  { fromDays: 7, toDays: 30,   quota: 2 },   // 7~30 天
  { fromDays: 30, toDays: 1e9, quota: 1 },   // 30 天+（古老地标）
];
// 每片：WHERE julianday('now')-julianday(created_at) >= ? AND < ?
//       ORDER BY calcium_score DESC, created_at DESC LIMIT quota
// 片内不足额时，用后续片补足（**避免名额浪费** —— V2 未处理）
```

近期槽 —— 候选池扩容 + 近因重排（修改 `recentCalciumRows`）：

```ts
// 候选池 20 → 按 (钙化归一 × 0.6 + 近因 × 0.4) 重排 → 取 limit
const calciumNorm = Math.min(1, r.calcium_score);          // 🔴 不是 /10，见下
const recency     = Math.max(0, 1 - ageHours / 24);
```

> 🔴 **归一化用 `min(1, calcium)` 而不是 `calcium/10`**：实测钙化 **95.8% < 1**、绝大多数落在 0.2~1。若除以 10，钙化项缩到 0.007~0.036，近因项（上限 0.4）**压倒性主导** ⇒ 近期槽实际退化成"纯最新 8 条"，把"当天重要的事"这个信号整个丢掉。用 `min(1,·)` 让钙化在 <1 的区间里保持区分度。
> 必须有一条测试锁住：**当天高钙（1.5）能压过当天低钙（0.3）但更新的内容**。

### 2.3 修改方案

**2.3.1 会晤路由指令过滤 —— 用结构信号，不扫正文**

判据来自 chat.ts 的会晤路由逻辑（**它本来就知道这条消息触发了会晤进入/退出**），不是在 persistence-stage 里猜：

```ts
function shouldSkipMemoryWrite(p: { isMeetingEntry: boolean; isMeetingExit: boolean }): boolean {
  return p.isMeetingEntry || p.isMeetingExit;   // 只写 conversations，不写 memories
}
```

> ⚠️ `chat.ts` 当前**未暴露**该信号，需先添加状态传递 —— 这将 `src/webui/chat.ts`（**HIGH**）拉进文件集，执行时须走豁免。

**2.3.2 UUID 处理 —— 兜底归属，而不是丢弃**（V3 修正）

V2 写的 `enforceMemoryUuid` 是 **deny-by-default 拒绝写入**。**这在原则上是错的**：

- 它与本任务书通篇的「只增不删」自相矛盾 —— 一边禁止删除记录，一边把新记忆直接丢掉
- 户主场景（玉瑶 / 无实体）本来就可能没有实体归属
- 结果是：一个**数据质量问题**被转成了**永久记忆丢失**

正确做法是**兜底链**：

```
会话活跃实体 UUID  →  户主/我（SELF-00001）  →  仍取不到：告警 + 照写（NULL）
```

只有"确实无法归属"才留 NULL，并把**拦截/兜底清单输出到报告**，作为下一轮数据卫生的依据。

### 2.4 附：查清 166 条的写入者（根因，不是清洗）

P0-3 只能清存量；**166 条仍在产生**说明写入路径还在漏。必须在 P0-2 里查出：
- 是哪条代码路径写的（`persistence-stage`? `dialog-group-stage`? 还是某条降级路径）
- 为什么它的 `global_uid` 与任何 conversation 都对不上（见 P0-3 实测）

### 3.0 前置：先核验关联可行性（V3 新增 —— 实测已完成）

| 关联路径 | 可救回 | 结论 |
|---|---|---|
| B3：`memories.global_uid` ↔ `conversations.global_uid` | **0 / 166** | ❌ **不可行**（166 条 global_uid 全部非空，但**一条都对不上**） |

### 3.1 B3：166 条无 UUID memories

- **只走结构性关联**；关联不上**保持 NULL**（NULL 是安全态：会晤路径看不到、户主路径 `allow-unowned` 能看到）
- **禁止**按正文角色名推断（实测：166 条里 **142 条（86%）根本不提任何人名**；全表对照 **2387/8184 = 29.2%** 的已归属记忆正文提到的是**别人** ⇒ 名字推断会整体串档）
- **禁止** `'PENDING_MANUAL'` 等非 UUID 哨兵（破坏列不变量，且与 NULL 在 deny-by-default 下行为等价，不换来任何信息）
- **先做**：查这 166 条的 `global_uid` 是什么形态、由谁生成（这才是根因；见 2.4）

### 3.2 B4：vault_log UUID 补全

```sql
-- landmark / promote / merge_promote：source_id 关联 memories（实测可行）
UPDATE vault_log
SET belong_entity_uuid = (SELECT m.belong_entity_uuid FROM memories m WHERE m.id = vault_log.source_id)
WHERE operation IN ('landmark','promote','merge_promote')
  AND (belong_entity_uuid IS NULL OR belong_entity_uuid = '')
  AND EXISTS (SELECT 1 FROM memories m WHERE m.id = vault_log.source_id
              AND m.belong_entity_uuid IS NOT NULL AND m.belong_entity_uuid NOT IN ('','null'));
```

> V3 改用**关联子查询**而非 `UPDATE ... FROM`：SQLite 3.45.2 虽支持 `UPDATE FROM`，但子查询形式能天然避免多对多放大，语义更可控。

**promote_sand(139) / auto_promote(5) 全部为 null**：**先查根因**（是谁写的、是否也绕过了 UUID 校验），再决定回填还是保持 NULL。**不强行赋值。**

## 五、P0-5 钙化升级机制调查（V3 恢复 —— V2 误删）

### 5.1 为什么必须有这一项

```
08-27 / 09-08 的 14 条  = 钙化 10（天花板）
其后整整一个月，最高    = 1.5
全表 95.8% < 1（9186/9593）
```

钙化是**全局排序键**（会晤槽位、MemoryInjector 优先级、V13 emotion 路都用它）。**升级链断掉 = 整个排序信号失真** —— 这不是"存量脏数据"，是**机制故障**。P0-1 只是绕开它（给老地标留 1 个名额），没有回答"为什么之后一个月的记忆爬不上来"。

关联既有文档：`docs/adr/ADR-008-calcium-unification.md`。

### 5.2 调查内容（只读）

- 钙化升级的触发条件是什么？写在哪？（`MemoryAssessor` / `SleepTimeConsolidator` / `AQCEngine`？）
- 08-27/09-08 那 14 条为什么能到 10？之后的记忆为什么停在 1.5？
- 是否存在"只有特定来源能拿高钙"的隐性偏好？
