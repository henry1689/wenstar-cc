## 四、#18 调试方案（非锚点 namespace 全灭）

### 4.1 问题与已排除项

**现象**：1616 条非锚点记忆 `namespace` 全为 `default`，其中今日新增 254 条本应是 `test`。
同一次请求里 `:317`（锚点路径）正确落 `test`，`:399`（非锚点路径）却落 `default`，
**同 `seq_pos`、相差 1ms、内容对应 `cleanReply`**。

**已静态穷尽排除**（6 项）：
`writeMemory` 探针 pass · 列/占位符/参数对齐 · 无 UPDATE 覆盖点 · `getSQLite()` 无代理 ·
服务确跑新代码 · 纯函数无副作用。

**⇒ 静态分析已到头，必须运行时观测。**（业主 2026-11-03 已授权重启）

### 4.2 打点设计（关键：不只打 namespace，要打 testMode 本身）

在 `src/webui/chat/persistence-stage.ts` 的 **4 处** namespace 赋值前各加一行：

```
[NS-DEBUG] line=<317|330|399|469> testMode=<值> seq=<seq_pos> uuid=<前8位> head=<内容前20字>
           stack=<Error().stack 第3层调用者>
```

**为什么必须打 `testMode`**：`namespace` 是三元表达式 `testMode ? 'test' : 'default'`，
输出 `default` **只有两种可能** —— ① `testMode` 本身是 `false`（**根因在上游传参**，
`persistence-stage` 无辜）② 打点位不是实际执行路径（有第 4 个写入点）。
不打 `testMode` 就无法区分这两种，会白跑一轮重启。

**开关**：`if (process.env.WS_NS_DEBUG === '1')` 包裹，默认关闭，诊断完即回滚或保持关。

### 4.3 执行步骤

1. `harness_run_flow` 拿令牌 → 改 4 处打点（**一文件一令牌一次写入**）
2. `tsc --noEmit` = 0 + `npx vitest run` 主仓 0 failed
3. commit（打点独立成单，便于回滚）
4. **重启前检查**：确认无并行会话正在写库；记录重启前 3000 端口持有者 PID
5. `pm2 restart wenstar-webui` → 验证 **3000 端口换了新 PID 且唯一持有者**（防僵尸实例）
6. 发一条 `testMode=true` 请求
7. `grep NS-DEBUG` 拿 4 行输出 → **对比 `:317` 与 `:399` 的 `testMode` 值**
8. 按结果分流：
   - `:399` 的 `testMode=false` → **根因在上游**（调用方没传 testMode），去修调用链
   - `:399` 压根不打印 → **存在第 4 个写入点**，顺着 stack 找
   - 两处都 `true` 但 namespace 仍 `default` → 打点位错，需重定位
9. 修复 → 回归 → **回滚打点**（或保留 env 开关默认关）
10. 关闭 LEDGER #18

### 4.4 重启风险控制（依据历史教训）

- 🔴 **多实例**：重启后必须确认 3000 端口**唯一**持有者（历史：`harness-mcp` 保活拉起 webui 致僵尸实例，stdout 不消费致管道阻塞）
- 🔴 **单实例锁**：node 闪窗 = 多份看守进程互杀；重启前后核对 pm2 计数
- 🔴 **改库前停整条进程链**：sql.js 内存库会覆盖离线改库（本次只改代码不改库，风险低）
- 重启会**短暂中断服务**（业主已授权）

### 4.5 打点实测结论（2026-11-03 执行后）

重启后按 `WS_NS_DEBUG=1` 采集，四条结论：

1. **同请求内 L317（conversations）与 L399（memories）的 `testMode` 完全一致**

2. **测试行 memories 正确落 `namespace='test'`** ⇒ 重启后问题**不复现**
3. **时间对比**：09:29（重启前）同 `seq_pos` 出现 `conversations=test` / `memories=default` 矛盾；
   15:14（重启后）两者均 `test`
