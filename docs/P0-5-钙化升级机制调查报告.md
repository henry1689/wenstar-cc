> 方法：S1 只读诊断（生产库副本 + 代码静态追踪 + git 历史考古），**全程未改动任何生产数据**
> 结论一句话：**钙化的"升级链"没断，断的是"回落链"——`lifecycle_state='promoted'`（黑钻）完全逃逸衰减，钙化被永久冻结在历史最高点，而它是全局排序键。**

⇒ `calcium_level` 事实上是个**没有单一真源的字段**。

## 二、🔴 核心结构性缺陷：`'promoted'` 状态完全逃逸衰减

`MemoryAssessor.runDecay()` 的 6 个衰减分支，其 `WHERE` 覆盖的 `lifecycle_state` 只有四种：

```
suppressed ／ candidate ／ active ／ healed
```

而黑钻晋升（`VaultManager:214`）把状态设成 **`'promoted'`** —— **六个分支一个都不覆盖它**。

```
promoted   2953 条  🔴 不参与衰减（钙化只增不减，永久封顶 10）
active     1738 条  ✅ 参与衰减
candidate  1325 条  ✅ 参与衰减
```

⇒ **一旦晋升黑钻，钙化就被冻结在其历史最高点，永不回落。**
而钙化是**全局排序键**（会晤槽位、`MemoryInjector` 优先级、V13 emotion 路都用它）
—— 这就是 P0-1 里「历史槽被 29~40 天前的高钙地标永久占满」的**机制本体**。
P0-1 只是给它留了一个名额绕开，**没有治它**。

### 正反馈闭环（相关性坐实，机制待定）

```
高钙行（≥5，35 条）：34/35 被召回 >20 次
对照（钙化 <1，9189 条）：7269 条（79%）从未被召回
```

被召回的钙化高 → 钙化高又优先被召回，**闭环成立**。
但**抬起钙化的那一步代码未查实**，见第四节。

## 三、修正三条错误认知（其中一条是**上次会话自己写下的**）

### ① 🔴 提交 `6b407d4`（2026-09-23）的归因是错的

该提交信息写着：

> `5~10` 34 条（**max 10**，因 `applyRecallIncrement` 每次 +0.2、上限 10）

但 `git show 801ad16:src/app/vault/VaultManager.ts`（v1.0 首版）显示：`applyRecallIncrement`
**从第一版起只有定义、没有任何调用点**。**它不是那 34 条的成因。**
该次修复只在**晋升门槛处做了量纲归一**（`raw > 1 ? raw : raw × 5`），**未动存储层**
—— 所以刻度混杂今天原样还在。

### ② `computeCalcium` 的值域与存储刻度不是一回事

`computeCalcium` 的返回被 `Math.min(1.0, ...)` 封在 **[0, 1]**；而存储刻度是
`calciumMin: 0 / calciumMax: 10`，累加路径直奔 10。
**全表 372 条（3.88%）的 `calcium_score > 1` —— 这些必然来自累加路径，不可能是 `computeCalcium` 产的。**

### ③ V3「之后停在 1.5」的表述比实际乐观

见 Q2 的实测表：是 **10 月上限塌到 1.9**，而非温和地停在 1.5。

## 四、P0-5b：上游来源追溯（已完成，**结论是「此路不通」**）

### 4.1 假说与证据

**假说**：高位记忆走 `MemoryAssessor.runSandToGold`，把 `conversations.calcium_score`
直接继承进 `memories.calcium_score`（`clamp` 到 0~10）。

**支持证据**（生产库副本，35 条高位记忆逐条回溯到源会话）：

```
高位记忆（35 条）钙化均值 8.75   vs  其源会话「今天」钙化均值 0.63   →  落差 8.12
对照组（钙化 1~2，28 条）1.69    vs  源会话 0.97                    →  落差 0.72
conversations 今天仍有 ≥5 的 17 条（最高 9.4）                       →  上游确实能产出高值
```

落差**随记忆钙化升高而放大**（0.72 → 8.12），与「晋升时继承、源之后回落」方向一致。

### 4.2 🔴 但假说在关键处站不住

```
① 35 条里 locus_path = chat.promoted 的只有 2 条
   其余 33 条是 user.misc.default(16) / user.emotion.positive(15) / …
   而全表常态就是 user.misc.default（7130 条）
   ⇒ locus_path 描述的是「内容域」，**不描述来源**，无法用来定位写入口
```

### 4.3 🔴 决定性障碍：来源字段的值域已被污染，**事后取证不可能得出结论**

```
② promotion_reason 有 7 种值，且混着不该在其中的：
   "梦境沉淀"×17 ／ NULL×11 ／ "user.emotion.romantic"×2 ／ "user.emotion.positive"×2
   ／ "user.daily.general"×1 ／ "multi-factor:landmark+recall>=3+strong-trace+narrative-tag"×1
   ／ "landmark+high-calcium"×1
   ← 其中三种是 **locus_path 风格的值漏进了 promotion_reason**
③ 35 条里只有 7 条的 id 尾部形如 `_<数字>`（可反查会话），其余 28 条不行
```

**三条硬限制**：

1. **没有任何钙化变更的历史** —— `memories` 只存当前值，没有变更日志/审计表记录
   「哪一步改的、从多少改到多少」
2. **两个来源字段的值域已互相污染**（`promotion_reason` 里混着 locus 值）
3. **id 反查只对 7/35 有效**

⇒ **数据本身回答不了「钙化在哪一步被抬起来」。** 继续取证只能得到推测。

### 4.4 结论与建议

**P0-5b 的交付不是答案，而是「此路不通」的证明。** 正确做法是**写入侧埋点**：

| 方案 | 内容 | 量 |
|---|---|---|
| **P0-5b′ 变更溯源埋点**（建议） | 在**全部加钙点**各写一条 `calcium_change_log`（id / 旧值 / 新值 / 来源标记 / 时间） | 小：一张只增表 + 5 处埋点 |
| 事后取证 | ❌ 已证明不可行 | — |

埋点是 P0-5 修法 A/B/C/D 的**共同前提** —— 不知道谁在抬，就无法判断该掐哪条。

## 五、修法选项与**业主已定的结论**

> 2026-10-07 业主决定，记录如下（本节其余部分保留为分析依据）。

### ✅ 已决定的第 1 条：**黑钻应当终身免疫衰减** —— 方案 A 作废

业主拍板：「黑钻应当终身免疫衰减」。

⇒ 第二节所述 `'promoted'` 逃逸 `runDecay` 的六个分支，**不是缺陷，是有意设计**。
黑钻是终身珍藏，冻结其钙化在语义上是正确的。

🔴 **但这把问题的性质换了位**：既然冻结是对的，那么真正的毛病就**不在衰减层，而在排序层** ——
一个永久停在 10 的钙化值，作为**全局排序键**会永久占据首位，且**永不让位**。
⇒ 修法方向由 A 转向 **D（钙化从"排序键"降级为"候选入场券"）**，
即 ADR-011 决策 D1 已立的方向：让"谁排前面"由多轴融合决定，钙化只决定"够不够格进候选"。
**D 属 ADR-011 后续 Phase，超出 P0-5 范围。**

### ✅ 已决定的第 2 条：**先埋点观察，C 推迟**

业主拍板：「先埋点观察，C 推迟」。

⇒ **不在口径未明前重写 9597 条 level**（5.1 显示现存值不服从任何已知口径，此时重算等于把一个可能错的阈值固化到全表，而 `calcium_level` 已被 6+ 处决策依赖）。
⇒ 本批收敛为**只做 P0-5b′ 埋点**；C 待埋点暴露真实失真来源后再做。

### 5.1 🔴 C 的难度比预估高：**存量 level 值不服从任何已知口径**

对 9597 条实测四种候选口径（统一换算到存储刻度 [0,10] 比较）：

| 口径 | level≥2 的行数 | 与**现存** level 不一致 |
|---|---|---|
| ① `computeCalcium`（3/6/8） | 35（0.4%） | 8822（**91.9%**） |
| ② `MemoryAssessor`/`SleepTime`（2.5/4.5/6.5） | 3622（37.7%） | 7290（76.0%） |
| ③ 锚点重建（0.5/1/2） | 408（4.3%） | 7376（76.9%） |
| ④ 线性十分位（1/3/6） | 41（0.4%） | 8769（91.4%） |

**分档看几乎随机** —— 例如钙化 `[0, 0.25)` 的 3686 条里众数是 **L1**（3316 条）；
而钙化 ≥5 的 35 条里众数是 **L2**（25 条），**钙化 10 的行 level 竟然是 2 而非 3**。

⇒ **存档的 `calcium_level` 已不可信。** 已排除一个 bulk-repair 嫌疑
（`VectorAlignmentGuard.fixZeroCalciumLevel()` 的 `UPDATE … SET calcium_level = 1` ——
运行日志显示它只跑过一次、只改了 6 条）。
**真实失真来源未查明**，是 P0-5b′ 埋点要顺带回答的问题之一。

⇒ **C 因此不只是「四处推导合一处」，还必须先决定存量 9597 条的 level 怎么办**
（全量重算 / 只对新写入生效 / 两者结合）。这是一次**数据迁移**，不是纯代码收敛。

## 六、可推广的教训

这一批里，**四处 level 推导、五处升级入口、一处被注释点名却从未被调用的函数**，全部活在同一张表上，
**没有任何一条测试验证过它们的相互关系**。可推广的判据：

> **当一个字段既是"结果"又是"排序键"时（钙化既是召回的结果、又是召回的排序依据），必须为"闭环的每一段"分别写测试** —— 否则断掉的往往是没人注意的那一段（这里是"回落链"）。

本批交付的是**调查**，不改代码；若据此立修法批次，建议同时补上「衰减覆盖度」的守卫测试：
**任意新增的 `lifecycle_state` 取值，必须显式声明它是否参与衰减**，否则新增状态会静默逃逸衰减——这正是本缺陷的成因。
