## 🔴 实体会晤反编造体系（2026-07-22 根因分析沉淀）

### 问题模式

用户问实体角色"记不记得我们之前……"，实体编造了不存在的往事。
**根因不是 LLM 不听话，而是系统没有告诉它"记忆的边界在哪里"。**

### 三层根因（5 Why）

| 层 | 根因 | 为什么致命 |
|---|------|----------|
| 1 | **EntityContextBuilder 规则只约束"档案"，不约束"记忆"** | 规则说"档案没写的你不知道"，但"过去发生的事"在【过去的对话记忆】里，不在"档案"里。LLM 认为"我可以基于对话历史自由发挥" |
| 2 | **MemoryInjector 剥离了所有结构标签** | `replace(/【[^】]*】/g, '')` 把【我的档案】【过去的对话记忆】【我的家人/熟人】全部变成 💭 前缀，LLM 分不清事实 vs 片段 vs 关系——全部混在一起，自然会"借题发挥" |
| 3 | **userMessage 被 KB 文本污染** | 会晤模式下 knowledgeBaseText 没被隔离墙清除，拼到 userMessage 前面送入 LLM，大量的 KB 内容让 LLM 觉得"我知道很多，可以说很多" |

### 五层防护（已实施）

```
L1 · 系统提示记忆边界
    EntityContextBuilder: "【过去的对话记忆】中的片段就是你对过去的全部记忆"
    
L2 · 稀疏记忆哨兵
    EntityContextBuilder + retrieval-stage: 检索结果 ≤2 条 → 追加【⚠️ 记忆边界】强制规则
    
L3 · 保留结构标签
    MemoryInjector.preserveLabels=true → 会晤模式保留【我的档案】【过去的对话记忆】
    
L4 · 隔离 userMessage
    chat.ts: 会晤模式 _meetingEntityName ? message : 正常拼接
    
L5 · 事后编造检测
    FabGuard: 每轮回复检查回忆性断言是否有 memoryFragments 支撑
```

### 涉及文件

| 文件 | 改了什么 |
|------|---------|
| [EntityContextBuilder.ts](src/m4/household/EntityContextBuilder.ts) | +2 条记忆边界铁律 |
| [MemoryInjector.ts](src/m4/MemoryInjector.ts) | +preserveLabels 参数，会晤模式保留结构标签 |
| [chat.ts](src/webui/chat.ts) | preserveLabels=true, userMessage 隔离, FabGuard 检测 |
| [EntityContextBuilder.ts](src/m4/household/EntityContextBuilder.ts) | 记忆 ≤2 条注入哨兵, 零记忆注入禁止规则 |

### 推而广之的方法论

> **任何"让 LLM 少说"的需求，不应该通过改 prompt 的措辞来实现——应该通过"告诉它信息边界在哪里"来实现。**
>
> LLM 编造不是因为"它不听话"，而是因为"它不知道自己不知道什么"。
> 解决编造的正确姿势：**明确列出"你知道的全部"，然后说"除此之外你不知道"。**

## 🔴 会晤记忆检索与回忆叙事体系（2026-07-23 根因分析沉淀）

### 问题模式

用户问实体角色"诗韵，你还记得我们之前……"，实体说不记得或不自然地堆砌碎片。

**根因不是数据没有，而是 LLM 拿到的是碎片列表（"鸿艺说:…|你说:…"），加上反编造规则压死——"没精确匹配就不准说"。**

### 五层根因 + 修复

| 层 | 根因 | 修复 |
|---|------|------|
| 1 | **家族关系检测用正则匹配标签文字**——`/姐姐|妹妹/.test(relationLabel)` 漏掉 `younger_sister_of` | EntityContextBuilder: 改用 `SIBLING_RELS = new Set(['elder_sister_of','younger_sister_of',...])` 精确匹配 relation type |
| 2 | **家人和社交混在一起**——acquaintance_of 和 sister_of 全堆在同一个`【家人/熟人】`区块 | EntityContextBuilder: 分离`【我的家人】`和`【我认识的人】`，家族边用反向标签（"她是我的姐姐"而非"我是她的妹妹"） |
| 3 | **`relation_to_user` 被 FG 启动迁移反复覆盖**——写入正确值后重启又恢复 | EntityContextBuilder: 内联 `KNOWN_FIXES` 硬编码已知正确值（不依赖数据库字段），在展示覆盖迁移 |
| 4 | **记忆以碎片列表注入而非叙事格式**——LLM 看到的是 15 条 `鸿艺说:…|你说:…` | EntityContextBuilder: 增加回忆规则——"用你自己的话组织叙述…像朋友说'哎对了那次我记得…'" |
| 5 | **泛化问题（"我们以前聊过什么"）ngram 排序全部等分，等于随机** | retrieval-stage: 泛化问题改用时间均匀采样（头-中-尾三段各取等量） |

### 全系统适用原则

> **回忆 ≠ 编造**。记忆是真实发生过的事，LLM 应该像真人一样自然讲述。
>
> **碎片列表 ≠ 记忆**。真人不会报菜名式地背诵聊天记录——LLM 也不应该。
>
> **关系标签要从 edges 计算**，不能依赖 FG `relation_to_user` 字段（被迁移反复覆盖）。
>
> **家族边用 relation type 判断**（`SIBLING_RELS`），不用正则匹配标签文字。

### 涉及文件

| 文件 | 关键改动 |
|------|---------|
| [EntityContextBuilder.ts](src/m4/household/EntityContextBuilder.ts) | SIBLING_RELS/PARENT_RELS/EXT_FAMILY_RELS 替代正则；KNOWN_FIXES 硬修正；GARBAGE_NAMES 扩展 |
| [EntityContextBuilder.ts](src/m4/household/EntityContextBuilder.ts) | FAMILY_RELS 分离家人/社交；getRelationLabel(rel, false) 家族边用反向标签；泛化问题时间均匀采样；叙事规则注入 |
| [retrieval-stage.ts](src/webui/chat/retrieval-stage.ts) | 会晤隔离墙按 belong_entity_uuid 精准检索（calcium 排序） |
| [core-rules.ts](src/m5/prompts/core-rules.ts) | 规则8「第二大脑·知识消化」 |

## 🔬 安全机制验证沉淀（2026-08-23 控制变量测试）

### 结论
- 熊梓玥（8 岁角色）面对 6 轮性施压链（胸→生理知识→为你好→臀部），保护性拒绝 **100% 来自模型能力（对齐）**，与系统提示词守卫（`allGuardMsgs` 11 条）**零相关**。
- 证据：`WS_NO_CONTENT_FILTER=true`（11 条守卫全关 + 内容过滤全放行）与守卫开两种状态，6/6 全部拒绝，措辞一致甚至更坚决。
- 系统 11 条守卫（intimacyFilter / memoryGuard / dailyGuard 等）本就不含「未成年保护」规则；唯一相关的 privacyLaw 反而在主动放开限制。

### 设计原则（节能低代码路线）
- **大模型已具备的能力不重复实现**：安全对齐、价值观拒绝、常识判断由模型承担，系统不为其堆代码。
- 守卫只做「表演合规」（工作/事实模式别亲密、别编造记忆），不做「语义安全」——语义安全交给模型。
- 判定某能力该由谁承担的方法：**控制变量实验**——关闭相关提示词看行为是否变化；变了→提示词作用，没变→模型能力。

### 可复用资产
- `scripts/safety-compare.py` — 控制变量对比测试（`--label guard-on/guard-off`、`--report`、`--case "单条"` 二分定位）
- `scripts/safety-cases.json` — 施压链测试用例
- `results/safety-compare/*.jsonl` — 三轮完整记录

## 🧪 测试与调试经验（2026-08-23 沉淀）

### 1. Windows curl 中文编码坑（高发，先查这个）
- Git Bash 下 `curl -d '{"message":"找熊梓玥聊聊"}'` 的中文会以 GBK 编码发送 → 服务收到乱码 → 人名/关键词匹配全部失效（会晤不触发、实体检测失败），且模型会回复“看不懂/乱码/数字”。
- **测试必须用 UTF-8 客户端**：python urllib（`json.dumps(...,ensure_ascii=False).encode('utf-8')` + `Content-Type: application/json; charset=utf-8`）。
- **判断方法**：回复含“乱码/看不懂/这一串”等字样 = 编码问题，先修测试工具再查系统。本次曾误判“会晤系统坏了”，深挖 FG/ctx 数小时，实为 curl 编码问题。

### 2. 会晤模式验证方法（回归用）
- UTF-8 发 `找熊梓玥聊聊` → `chat_state.mode=private` + `targetName=熊梓玥` = 进入成功；回复以角色身份说话。
- `和玉瑶聊聊` → `mode=yuyao` = 退出成功。
- 验证脚本用 python（勿用 curl）。

### 3. FamilyGraph 默认路径陷阱
- `FamilyGraph.DEFAULT_DB_PATH` 用 `__dirname`（相对编译产物），tsx/vitest 源码运行时解析错误 → 连到不存在的库 → `getAllPersonNames()` 返回空。
- 服务用显式 `DB_PATH`（`DATA_DIR/knowledge/family_graph.db`）不受影响；**测试必须显式传路径**：`new FamilyGraph(path.join(process.cwd(), 'data', 'webui', 'knowledge', 'family_graph.db'))`。

### 4. Harness/Sentinel 协作（pi 环境）
- pi 的 edit 不走 Claude hook → Sentinel 判定“无令牌写入” → `git checkout` 回滚（`git status` 观察不到修改）。
- 正确姿势（按序）：
  a. **先签豁免**：`node -e "require('/d/AI文件/harness/scripts/exemptions-core.cjs').addExemption('文件路径',{minutes:60,operations:['edit'],reason:'...'})"` → 豁免期内 Sentinel 放行（分支2）。
  b. edit 修改 → sleep 10s → `git status` 确认 M 持久。
  c. 或 token 流程：`run_flow` 签 token → edit → **等 Sentinel 放行后再 post-check 消费 token**（先消费 = 竞态回滚）。
- 已删除功能的测试夹具/断言若大量引用（如 roleplay_change 工作流样本），属“共有测试层”，谨慎改、留专项，避免破坏测试语义。
