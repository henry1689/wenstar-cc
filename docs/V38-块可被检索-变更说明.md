## 一、P1-B 留下的悬空

P1-A 建好了 `dialog_groups` 表，P1-B 补上了写入侧（闭组时落块）—— **但块至今搜不到**：它不在任何检索域里，检索链路上完全看不见。P1-C1 把块接进检索。

## 二、两处方案细化（勘察后对原方案的修正，实施前已报业主确认）

### 细化 4 · 撤销「新建 dialog_group 索引」

原 ADR 第 8 条要求 `SearchIndexBuilder` 加 `source_type='dialog_group'` 并做块内 800 字切块索引。**撤销**：

| 事实 | 依据 |
|---|---|
| `search_index` 已占全库约 **80% 体积** | V34 专门治理过（319.9MB → 216.5MB，删 3 个冗余索引） |
| `conversations` 已**全量索引** | V34 撤除了 `is_compacted = 0` 过滤，覆盖全量 |
| 块 = 它那些 conversations 的聚合 | **同一份索引换个 GROUP BY 即可** |

⇒ 零新增索引体积、零新增写入路径。检索单元从「单条消息」变为「块」是**聚合粒度**的变化，不是新建一层索引。本批用测试钉死该不变量（`不得出现 source_type='dialog_group' 的索引行`）。

### 接入点 · 用现成扩展点，不做外科手术

仓库已有 **Foundation 适配器注册表**（`createDefaultRegistry`，含 knowledge/black_diamond/work/vault/note 样板域），由 `runFoundationRoutes` 统一调度，该入口**已在跑**（`retrieval-stage` 的 `WS_FOUNDATION_ROUTES = true`），其设计约束明确写着「不触碰 V13/V11 主链」「每个适配器异常独立隔离」。

⇒ 本批只需**新增一个适配器并注册**，不动七层仿生检索管线。

## 三、本次改动

### 3.1 `DialogGroupAdapter`（新） —— 块检索域

- 从既有 `search_index` 按 n-gram 取 conversation 候选 → 内层子查询按 `dialog_group_id` 聚合 → 外层 JOIN `dialog_groups` 取块级元数据（钙分 / 场景指纹 / 衰减类别 / 轮数 / 闭合原因）。
- **户籍过滤走 `buildSqlClause(ctx.policy)`**（收编 UUIDPoliceFilter，禁手写 UUID SQL —— 户籍管理法铁律 0.4 第 4 条）。
- 🔴 **police 子句必须放在仅 `conversations` 可见的内层子查询里**：`buildSqlClause` 产出的是**裸列名** `belong_entity_uuid`，而本查询涉及 `conversations`/`search_index`/`dialog_groups` **三张都有该列的表** ⇒ 直接拼进 JOIN 会 ambiguous column 报错。
- **deny-by-default**：无白名单 → `AND 1=0`；`strict` 模式不走 `OR IS NULL` 逃生口。无归属的块检索不到（宁缺勿泄）。
- 异常隔离：`search()` 全程 try/catch 返回空数组（与既有 5 个适配器同策略）。

### 3.2 枚举扩张的三处连带面（勘察时漏掉、由 tsc 与回归暴露）

`SearchDomain` / `RetrievalRoute` 是**联合类型**，加值会打破两类东西：

| 类别 | 位置 | 不补的后果 |
|---|---|---|
| 穷举 `Record<SearchDomain, …>` 映射 | `retrieval/backref.ts`（全仓仅此一处） | **编译失败 TS2741** —— 该映射决定命中后回源到哪张表 |
| 路由 → RRF 权重映射 | `retrieval/fusion.ts` | 🔴 **编译能过但静默失效**：`RRFFusion` 是 `weights[route] ?? 0.05`，缺映射不报错，块路权重掉到 0.05（比 conversation 还低），几乎永远排不上来 |
| 注册表清单式断言 | `__tests__/adapters-s6.test.ts` | 断言精确计数，域集合扩大后必然失败 |

更新 `adapters-s6.test.ts` 时**保留了精确计数强度**（不改成 `toBeGreaterThan` 之类宽松形式），并补 `toContain('dialog_group')` 让新域显式登记。该断言是**清单记录**而非**行为规格** —— 规格由新增的 12 条测试承担，未做任何放松（本仓 CLAUDE.md 危险信号 #9 的适用边界）。

### 3.3 配置

- `retrieval-fusion.config.yaml`：新增 `foundation_rrf_domain_weight.dialog_group: 0.28` 与顶层 `enable_dialog_group_memory: true`
- 权重 0.28 的定位：高于单条对话(0.05)/记事(0.08) —— 块是中期记忆的主要承载者；低于黑钻 —— 块是原始素材，黑钻是已提炼的结论
- **开关是「注册级」而非「查询级」**：注册表在编排层构造，关掉即整条路不存在，不会出现「开关关了但某处仍在查」的半失效状态

## 四、📘 白皮书更新摘要

**《太虚境检索体系》章节（标题：对话块检索域 · 聚合粒度）**

1. **新增 `dialog_group` 检索域** —— 与 `conversation`（单条消息）的区别是**聚合粒度**：块是「一段自闭合的连贯场景」。
2. **块不另建索引** —— 复用既有 conversation 倒排索引，按 `dialog_group_id` 聚合；`search_index` 体积零增长（该索引已占全库约 80%）。
3. **块域走 Foundation 适配器注册表** —— 与既有 5 个域同机制（并行执行、异常隔离、police 统一兜底），不触碰 V13/V11 七层主链。
4. **户籍过滤位置规范** —— police 子句必须置于单表作用域子查询内（裸列名在三表 JOIN 中会歧义），块级 deny-by-default。
5. **枚举扩张的连带面** —— `SearchDomain` 加值必须同步：穷举映射（`backref.ts`）、RRF 权重映射（`fusion.ts`，缺失会**静默压权重**）、注册表清单断言。

## 七、🔴 验证中发现的一处真实缺陷（**不在本批修复范围**）

**现象**：`dialog_groups.belong_entity_uuid` 与其名下 `conversations.belong_entity_uuid` **会不一致**。

**实测（生产库）**：11 个块中 **1 个不一致**（9%）——

```
块 00059320261006133223M01EMEU_DG_9408
  dialog_groups.belong_entity_uuid       = TXS-000000740
  conversations.belong_entity_uuid       = TXS-000000327   ← 权威
```

**根因**：两条写入路径的归属解析器不同 ——
- `conversations` 的归属来自 `persistence-stage` 的 `EntityOwnershipResolver`（**权威字段**，`meeting-recall.ts` 注释明写「过滤依据是 conversations.belong_entity_uuid」）
- `dialog_groups` / `*_ANCHOR` 的归属来自 `flushDialogGroup` 的 `resolveAnchorOwnership`（有 `dg.entities → FG 名 → 会晤 UUID → 玉瑶 UUID` 四级降级）

**性质**：锚点侧的问题**先于本批存在**（锚点一直用 `resolveAnchorOwnership`）；P1-B 把该口径**传播**到了块表。

**本批为何不受影响**：`DialogGroupAdapter` 的过滤依据是**子查询里的 `conversations.belong_entity_uuid`**（权威），不读块表的归属 ⇒ 不会因此泄漏或误藏。

**影响与建议**：该不一致目前是**潜伏态**（无消费者）。但 `dialog_groups.belong_entity_uuid` 是 NOT NULL 且被 v16 建表注释声明为「归属唯一真源」，一旦 P1-C2 或未来任何查询直接按块表归属过滤，就会踩到。**建议单开小批次**：让块/锚点的归属与 `conversations` 同源（这正是 V35-A 在上下文窗口做过的「归属唯一真源」收敛）。
