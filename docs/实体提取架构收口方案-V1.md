## 一、结论摘要

做两件事，缺一不可：

| | 改造 | 效果 |
|---|---|---|
| **A** | 把实体取证并入**每轮已有的主回复 LLM 调用**，删除独立的实体提取调用 | 不增加 token/延时，反而**少一次 LLM 调用** |
| **B** | 物理拆除滑窗生成器、观察区、离线终审及全部旁路 | 垃圾失去来源，无法死灰复燃 |

判据从「**像不像人名**」（字面，必然军备竞赛）改为「**有没有被原文引入**」（语义 + 可校验证据）。

## 二、现状调用链

```
用户消息
  │
  ├─ ChatEntry（回复前）
  │    ├─ M1 滑窗 detectPersonNames        ← 2~3 字切片，垃圾发生器
  │    ├─ extractEntitiesLLM（独立 LLM 调用） ← 每轮一次额外请求
  │    └─ regexFallback（LLM 超时兜底）      ← 又一套字面词表
  │    → entity_genes（混合滑窗 + LLM + 正则）
  │
  ├─ 检索 / 知识上下文（使用 entity_genes）
  │
  ├─ 主回复 LLM 调用（m5.orchestrate）      ← 每轮本来就有的一次
  │
  └─ 持久化（回复后）
       ├─ post-process → updatePersonProfile
       ├─ RelationshipExtractor → integrateSocialRelation
       ├─ dialog-group 闭组 → acquaintance_of
       ├─ InductionScheduler → entities / entity_relations
       └─ FamilyGraph → candidate 观察区 → 离线 LLM 终审（EntityTriageService）
```

**问题**：一次用户消息最多触发 **3 次 LLM 调用**（实体提取、知识路由、主回复），其中实体提取这条链路输出的是**无证据的切片**。

## 三、改造后调用链

```
用户消息
  │
  ├─ 已登记人名精确匹配（确定性、只读，零 LLM）   ← 保留
  │
  ├─ 主回复 LLM 调用（唯一一次）
  │    └─ 输出 = 取证头 + 分隔行 + 正文
  │         ├─ 取证头 → 代码校验 → admitted 实体
  │         └─ 正文  → 实时流式转发 / TTS
  │
  └─ 持久化（回复后）
       ├─ admitted 实体 → entity_genes（只含准入结果）
       ├─ FG 节点/档案/关系（只接受 admitted）
       ├─ entities / entity_relations（只接受 admitted 或 FG 同步）
       └─ 审计日志：每条准入记录含 evidence + 原文命中结果
```

## 四、方案 A：主调用内联取证

### 4.1 协议定义

在系统提示末尾追加固定段：

```text
【实体取证】
在正文之前，先输出本消息中被显式引入的实体，每条一行，格式：
entity: 名称|类型|证据原文

规则：
1. 证据原文必须逐字复制用户消息中的连续片段，不得改写、不得拼接、不得概括；
2. 只记录被明确介绍或指名的实体（"她叫X""这是我同事X""X老师"）；
3. 未指明具体名称的称谓（"我朋友""一个医生"）不输出；
4. 类型仅限 person / emotion / event / place / org；
5. 无实体则整块省略；
6. 最后输出分隔行 ---，然后开始正常回复。
```

示例：

```text
entity: 安琪|person|她叫安琪
entity: 罗珍思|person|这是我同事罗珍思
---
好啊，安琪这个名字挺温柔的……
```

**落点**：`src/webui/chat.ts:2752` 已实例化 `PromptAssembler`，在 `:2904` 渲染前提交一个块：

```ts
assembler.add({
  id: 'entity-evidence',
  type: 'task',
  priority: 900,
  source: 'm1/entity-admission',
  modeScope: ['normal', 'entity_meeting', 'roleplay', 'secretary', 'task'],
  content: ENTITY_EVIDENCE_INSTRUCTION,   // 上面的固定文本，单一真源
  conflictPolicy: 'override',
});
```

不追加到 `finalKnowledgeText`（那是知识内容），也不改 provider 层 —— 组装器是既有扩展点。

> 注：`outputGuard` 的 `speaker` 头协议在主链路**无生产调用方**（仅单测），不会与 `entity:` 头冲突；分隔行集合仍复用同一常量，保持对称。

### 4.2 解析规则（字段边界，不用正则枚举）

复用 `outputGuard` 已验证的三条原则：

| 原则 | 原因 |
|---|---|
| 逐行处理、认 `entity:` 前缀 | 不在正文里全文枚举引号/键名风格 |
| 只扫描正文开始前的连续行（上限 12 行） | 正文中出现 `entity:` 不会被误判 |
| `looksLikeRawJson()` 为真时整体跳过 | V45 事故：剥离器把纯 JSON 削成 `[{` |
| 分隔行集合复用 `HEADER_SEPARATORS`（`---` 等） | 与既有协议对称 |

解析失败 → **零实体**，不阻断回复。

### 4.3 代码侧校验（不可由 LLM 决定）

```ts
export interface EntityAdmission {
  name: string;
  type: 'person' | 'emotion' | 'event' | 'place' | 'org';
  evidence: string;
  relation?: string;
  admitted: boolean;
  rejectReason?: 'empty' | 'length' | 'evidence_not_in_message' | 'name_not_in_evidence';
}

export function verifyAdmission(raw: RawEntity, message: string): EntityAdmission {
  if (!raw.name) return reject('empty');
  if (raw.name.length < 2 || raw.name.length > 12) return reject('length');
  if (!raw.evidence || !message.includes(raw.evidence)) return reject('evidence_not_in_message');
  if (!raw.evidence.includes(raw.name)) return reject('name_not_in_evidence');
  return { ...raw, admitted: true };
}
```

**要点**：`message.includes(evidence)` 是反幻觉的唯一硬闸门。LLM 可以编名字，但编不出原文里不存在的连续片段。

### 4.4 流式处理

当前流式路径（`server-chat-routes.ts:614`）把每个 token 原样推给 SSE 并喂给增量 TTS。取证头不能出现在屏幕上或语音里，因此增加 **HeaderGate**：

```
LLM token 流
  → 按行缓冲
  → 判定：
     ① 前 12 行内命中 `entity:` → 进入头模式，丢弃头块直到分隔行
     ② 前 12 行内未命中 `entity:` → 判定无头，把缓冲原样放出
  → 正文 token 转发 SSE / 增量 TTS
```

- 首字延迟增加 = 头块生成时间（通常 < 300 ms，且头块很短）。
- 若模型不遵守协议 → 判定无头 → 原样转发，用户无感；FG 侧零写入。
- 非流式路径在 `processChat` 返回前统一剥离。

### 4.5 删除独立提取调用

| 删除对象 | 位置 |
|---|---|
| LLM 提取整段 | `src/webui/chat/ChatEntry.ts:127-183` |
| `extractEntitiesLLM` | `src/m1/LLMEntityExtractor.ts` |
| `regexFallback` / `hasEntitySignal` | 同上 |
| `EXTRACT_PROMPT` / 三层过滤 / 会话缓存 | 同上 |
| 条件化开关 `entity_conditional` | `getRetrievalFusionConfig` 中对应项 |

**净效果**：每轮少一次 LLM 请求（约 150~400 tokens），首字延迟下降；实体提取的质量由主模型的完整上下文决定，优于独立浅层提取。

### 4.6 时序影响与抵消

| 用途 | 改造前 | 改造后 | 处置 |
|---|---|---|---|
| 回复前检索/知识上下文 | 可用本轮新实体 | 不可用 | 保留「已登记人名精确匹配」；未知人物在 KB/FG 中本无内容，损失可忽略 |
| 记忆 `entity_genes` | 可用 | 回复后可写 | 无影响（持久化在回复后） |
| 归属解析 `belong_entity_uuid` | 可用 | 回复后可算 | 需核实调用时机（S1 验证项） |
| FG 写入 | 可用 | 回复后 | 无影响（原本也是异步后处理） |

**必须在 S1 验证**：`EntityOwnershipResolver`、`MemoryAssessor`、`persistence-stage` 的调用时机确实在回复之后。若存在回复前依赖，需单独列出并给出方案（预期不存在）。

### 4.7 失败矩阵

| 情况 | 用户可见影响 | FG 影响 | 处置 |
|---|---|---|---|
| 模型未输出取证头 | 无 | 零写入 | 计入「协议缺失率」监控 |
| 头格式错误 | 无（原样显示？→ 由 HeaderGate 剥离失败时原样转发） | 零写入 | 告警 + 采样 |
| 证据不在原文 | 无 | 丢弃该条 | 审计记 `evidence_not_in_message` |
| 名字不在证据中 | 无 | 丢弃该条 | 审计记 `name_not_in_evidence` |
| LLM 超时/不可用 | 主回复失败（既有降级逻辑） | 零写入 | fail-closed |
| 流式被截断 | 用户看到部分回复 | 零写入 | 既有重试/兜底 |

## 九、备选方案与不选理由

| 备选 | 不选理由 |
|---|---|
| 保留独立提取调用，只把提示词写严 | 仍多一次 LLM 调用；且独立调用看不到主回复上下文 |
| 用 function calling / tool 协议 | 当前 `DeepSeekLLMProvider` 未实现 tools 参数，需改 provider，超出本任务范围 |
| 取证块放尾部 | 流式会把协议行推到前端与 TTS，需尾部缓冲，实现复杂且易泄漏 |
| 主回复改非流式 | 首字延迟回归，用户体验倒退 |
| 继续加固字面黑名单 | 已证伪：生成器不变，下游只会继续军备竞赛 |

## 十、开放项（业主 2026-11-07 已确认）

| # | 问题 | 结论 |
|---|---|---|
| 1 | 取证块位置：正文前 vs 正文后 | ✅ **正文前**（流式可确定性剥离，失败可原样转发） |
| 2 | 是否保留 emotion / event 提取 | ✅ **保留，但不作为 FG 准入对象** —— 只作后期检索与感知用的标注信息，附着于已合法存在 FG 实体；不建 FG 节点、不进入准入清单 |
| 3 | 关系词（「是我同事」）是否同块输出 | ✅ **是**，`relation` 字段同样受 evidence 校验 |
| 4 | 已登记人名是否需要 evidence | ✅ **不需要**（只读匹配，不建档） |
| 5 | 协议缺失率的告警阈值 | ✅ **首周人工观察，第二周定阈值**（建议 < 5%），并纳入长期跟踪维护 |

### 10.1 由 #2 衍生的硬约束

- emotion / event **不是**准入实体，**永不**触发 `addNode` / `entities` 新建；
- 它们只写 `entity_genes` 与记忆标注，供检索、感知、情感轨迹使用；
- 仍然要求 `evidence`（防止凭空产出），但校验失败只丢弃标注，不影响主回复。
