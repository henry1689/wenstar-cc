## 本轮完成：bridge 接线 + tsc 归零

### 问题

接线后 `npx tsc --noEmit` 报 108 个错误，全部源自一处：

```
src/webui/server-memarch-bridge-routes.ts(38,35): error TS6059: File 'memarch-bridge/src/core/BridgeRegistry.ts'
is not under 'rootDir' 'src'.
```

根因：主 tsconfig 的 `rootDir: "src"`，而 **类型位置**的
`typeof import('../../memarch-bridge/...')` 同样会把整个子工程拉进主编译单元
（bridge → memarch-v2 → governance，连锁 107 个）。另有 1 个真实契约错误：
`retrieve(q, ns)` 传裸字符串，实际签名要求 `RetrieveContext`。

### 采用的方案（原「方案 A：改 rootDir」已作废）

不改 tsconfig，改为在**唯一的跨界引用点**断开静态依赖：

| # | 位置 | 改动 |
|---|---|---|
| 1 | `server-memarch-bridge-routes.ts` 类型声明 | `type BridgeModule = typeof import(...)` → 手写 `BridgeModule` interface（只声明实际消费的 4 个导出 + 窄接口） |
| 2 | 同文件运行时 import | 字符串字面量 → 变量说明符 `BRIDGE_SPEC` + `/* @vite-ignore */`，使 TS 不做静态解析 |
| 3 | 同文件 `/retrieve` 端点 | `retrieve(q, ns)` → `retrieve(q, { namespace: ns as RetrievalNamespace })` |

**为什么不用改 rootDir**：`plan_review` 的自动授权白名单只覆盖 `src/` 前缀，
`tsconfig.json` 在仓库根拿不到写令牌（除非业主密码门签 owner-closure）。
而方案 C 在工程上反而更对——运维端点本就设计成「不访问就不加载」，
在类型层面也解耦是一致的。

**契约漂移的守护没有丢**：`bridge/memarch-v2/governance` 的类型正确性由
`tsconfig.memarch.json` 独立守护（实测 0 错误），运维端点自身由 4 条契约测试守护。
