### 1. 主编译单元解耦（`f2ac1a1`）

接线后 `npx tsc --noEmit` 报 108 个错误，全部源自
`server-memarch-bridge-routes.ts` 的**类型位置** `typeof import('../../memarch-bridge/...')`
——它把整个 bridge 子工程（→ memarch-v2 → governance）拉进主编译单元，
而主 tsconfig 的 `rootDir` 限定在 `src/`。另有 1 个真实契约错误：
`retrieve(q, ns)` 传裸字符串，实际签名要求 `RetrieveContext`。

**处置**（不改 tsconfig、不改子工程）：
- 手写 `BridgeModule` 契约，只声明本文件实际消费的 4 个导出 + 三个窄接口
- 运行时 import 改变量说明符 + `@vite-ignore`，令 TS 不做静态解析
- `/retrieve` 改传 `{ namespace }` 符合 `RetrieveContext`
- 新增 `src/__tests__/memarch-bridge-routes.test.ts`（4 条契约测试）

> 原定的「方案 A：改 tsconfig rootDir」不可行 —— `plan_review` 自动授权白名单
> 只覆盖 `src/` 前缀，`tsconfig.json` 在仓库根拿不到写令牌（除非业主密码门）。
> 方案 C 在工程上反而更贴合「运维端点不访问就不加载」的隔离设计。

## 🔴 未完成：`/retrieve` 在灰度 0% 下不可用

**现象**：`[retrieve] 路由到 legacy 但 legacyRetriever 未注入`

**根因**：`memarch-bridge/src/adapters/OldRetrievalAdapter.ts:56` 的路由完全由
`flag.route()` 决定，**忽略了 `RetrieveContext.forcePathway`** ——
这个字段在 `MemoryPort.ts` 契约里定义了却没有任何实现使用它。

**影响**：灰度 0%（当前生产状态）时，运维端点无法自检 v2 检索；
更关键的是**无法在不改生产路由的前提下验证 v2 检索是否可用**。

**修法**：让 `OldRetrievalAdapter.retrieve` 尊重 `forcePathway`
（`'B'` 强制走 v2，`'A'` 强制走 legacy），运维端点传 `forcePathway: 'B'`。

**阻碍**：`memarch-bridge/` 不在 `plan_review` 自动授权白名单内（只允许 `src/` 前缀），
需业主密码门签发 owner-closure：
```
node scripts/harness-cli.cjs owner-closure issue <manifest.json> --project <根> --minutes 30
```
