# 会话断点（2026-11-05 12:30）

## 本轮主线：MemArch v2 向量能力从「不存在」到「已上线」

### 起点（实测，不是推测）

v2 库 35 张表里**一张 vec_ 表都没有**。直接调 Retriever 的实测输出：

```
[memarch-recall] semantic KNN failed, fallback to FTS5: no such table: vec_mem_semantic
[memarch-recall] emotion  KNN failed, fallback to FTS5: no such table: vec_mem_perception
「最近在忙什么」    → 命中 2 条（都是这个问题本身）
「还记得我们上次聊的事吗」→ 命中 0 条
```

8 条召回腿里只有 `bm25` 真正在工作。「语义检索」从未存在过。

### 已完成（commits `14405fb` / `fd9577b`）

| 层 | 改动 |
|---|---|
| 扩展 | 装 `sqlite-vec@0.1.9`，`vector_index.ts` 加载 vec0 + 幂等建三张向量表 |
| Embedding | `EmbeddingProvider.ts` — 本地 **bge-small-zh-v1.5 / 512 维 / ONNX**，懒加载 + 单例 |
| 语义腿 | `semantic_vector.ts` 用真 512 维向量替换 40D 哈希投影（旧的拿 40 维 MATCH 512 维表，必然抛错） |
| 情感腿 | `emotion_40d.ts` 用 `q.vec40` 修复 10 vs 40 维度错配 |
| 超时 | `timeout_breaker.ts` 超时判定由「elapsed >= ms」改为「fallback 是否真的被采用」 |
| 预算 | `recall_ms` 120 → 300（实测冷启动同时撞线的必然值） |
| 预热 | `createBridge` 后台预热 embedding（不 await，失败不影响初始化） |
| 运维 | `/health` 暴露 `vector` 字段（vec0 状态 + 三表行数） |

## 🔴 未完成 / 新发现的缺口

### 1. `entity_edges` 只迁进 14 条（PPR 腿实质空转）

主库 `entity_relations` 13,636 行，但 `entities` 3,999 个里**只有 1,047 个有 uuid**：

| type | 有 uuid / 总数 |
|---|---|
| person | 1,047 / 3,152 |
| object | 0 / 809 |
| emotion / event / place / self | 0 / 38 |

两端都能映射到 uuid 的关系只有 14 条。**根因是 UUID 全域统一（户籍三元组项目）没做完**，
不是迁移脚本的问题。

### 2. 情感腿的 query 向量空间未对齐

`q.vec40` 是 `query_understanding` 的**哈希投影**，与库内 `perception_40d`
（M2 感知编码器产出的真实感知向量）不在同一空间。腿能跑通、不报错，
但 distance 只能当弱信号用。真正的对齐需要接 M2 感知编码器。

### 3. `/retrieve` 运维端点仍不可用（灰度 0%）

`OldRetrievalAdapter.retrieve` 忽略 `RetrieveContext.forcePathway` —— 这个字段在
`MemoryPort.ts` 契约里定义了却**零实现**。修它需要改 `memarch-bridge/`，
当前无密码门授权。

### 4. `04_vector_index.sql` 无法修改

该文件被 Sentinel 置为只读（`attrib +R`），Edit 报 EPERM。实际维度（512）
由 `vector_index.ts` 内联建表决定，DDL 文件里的 `float[1024]` 已与实现不一致 ——
**技术债，需业主通道处理**。
