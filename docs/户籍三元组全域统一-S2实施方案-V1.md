## 一、结构设计

### 1.1 先解决一个模型缺陷（业主 P5 引出）

业主裁定「微信只对玉瑶(TXS-000000001) + 徐诗雨(TXS-000000007) 开放」，但现行模型**表达不了**：

```
belong_entity_uuid = 'X'   → 仅 X 可见
belong_entity_uuid = NULL  → 全体可见
                              ↑ 没有第三态
```

### 1.2 根因：一列承担了两个职责

| 问题 | 属于哪一维 | 现由谁回答 |
|---|---|---|
| 这是**谁**的数据？ | **DNA**（溯源） | `belong_entity_uuid` |
| **谁**能看见它？ | **UUID**（隔离） | `belong_entity_uuid`（**同一个值**） |

NULL 又重载两种含义：「共享」与「未登记」。⇒ **这是任务书 D1/D5「同一问题两种答案」的结构性根源。**

### 1.3 结构性解：把「可见性」从「归属」里拆出来

```sql
ALTER TABLE knowledge_base ADD COLUMN visible_entity_uuids TEXT;  -- JSON 数组
```

**三态模型（互斥完备，无例外分支）**

| # | `visible_entity_uuids` | `belong_entity_uuid` | 语义 | 例 |
|:--:|---|---|---|---|
| 1 | 非空 | 任意 | **受限共享** —— 名单内可见 | 工作微信 → `["TXS-…001","TXS-…007"]` |
| 2 | 空 | 非空 | **私有** —— 仅归属者 | 【FG档案范式】熊梓铭 |
| 3 | 空 | 空 | **共享** —— 全体 | 系统文档、一般资料 |

- **优先级**：态 1 > 态 2 > 态 3
- **归属不再承担可见性判定** —— 回归 DNA 溯源职责，将来才可能被 DNA 主链替换

**为什么不是给微信打补丁**
1. 没有 `if (是微信)` 分支 —— 三态各一条规则
2. 被混同的两个概念**永久分开**，私有域将来沿用同一模型即可扩展
3. 判定点**只有一处**（`UUIDPoliceFilter`），符合法条第四条
4. `PolicePolicy.visibleUuids` 本就是 `Set`，户籍法「不在白名单=拒绝」**天然支持多名单** —— 本次只是让**数据行也能声明名单**

### 1.4 判定实现（唯一处）

```ts
export interface PolicePolicy {
  // …既有字段…
  /** true = 该表支持「受限共享」三态（含 visible_entity_uuids 列）。默认 false。 */
  restrictedSharing?: boolean;
}
```

```sql
AND (
  ( COALESCE(visible_entity_uuids,'') <> ''
    AND EXISTS (SELECT 1 FROM json_each(visible_entity_uuids) WHERE json_each.value IN (?,…)) )
  OR
  ( COALESCE(visible_entity_uuids,'') = ''
    AND ( belong_entity_uuid IN (?,…) OR <无归属是否可见由域决定> ) )
)
```

- `json_each` 可用性**已实测确认**（`sql.js` 带 JSON1，2026-10-07 验证）
- `restrictedSharing` 默认 `false` ⇒ memories / conversations / black_diamond / vault_log 的 SQL **一字不变**

## 二、两类记录，两种 NULL 语义（评审 P2-2 采纳 —— 本版核心澄清）

评审提的「知识库实体三元组 vs 记忆条目三元组」，**精确表达了我方案"按域分治"的实质**。正式命名并写入法条：

| | **实体档案件** | **经历记忆件** |
|---|---|---|
| 表 | `knowledge_base` | `memories` / `conversations` / `black_diamond` / `vault_log` |
| 描述 | 客观资料（文档/档案/资料） | 某主体在某情境下的经历 |
| **`belong = NULL` 语义** | **共享** —— 全体可见 | **未登记** —— 仅户主钥匙可见 |
| 依据 | 业主 2026-10-07 裁定 | 《UUID 户籍管理法》铁律 4 |
| 交互 | 两类**不得互相援引** NULL 语义 | |

> 这就是任务书法条第三条「按域分治」的精确形式。评审的这条建议**让方案更清楚了**。
