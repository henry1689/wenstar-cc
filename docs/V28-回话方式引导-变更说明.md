> 变更类型：表现层提示词追加（单点插入，不改结构 / 不改感知 / 不改既有内容）
> 变更日期：2026-09-23
> 影响文件：`src/webui/chat.ts`、`src/__tests__/prompt-assembly-spec.test.ts`、本文件
> 依据规范：`docs/prompt-assembly-spec-v1.md`（PAS v1）

## 一、根因（为什么必须做，而不是事后贴词）

角色回复的「不像在说话」问题，此前被反复当成**输出侧**问题去解：

- 早期思路是后处理贴词（`ThinkingPauseInjector` 一类：在 LLM 返回的文本里插停顿词、语气词）；
- 该思路已被明确否决——它把「说话的样子」退回成**词表匹配**，既僵化又与内容脱节，
  容易出现「该快的时候在拖、该慢的时候在冲」。

真正的根因在**输入侧**：提示词只告诉模型「说什么」（人格、关系、场景、长度），
从未告诉它「怎么说话」。模型因此默认走「写文章」的语域——完整、工整、无起伏。

用贴词去修补一个输入侧缺失，是在下游治上游的病。

## 二、修复方案

### 2.1 单点插入

在 `src/webui/chat.ts` 的 PromptAssembler 注册段（`assembler.render()` 之前）追加一个
persona 块：

```ts
assembler.add(personaBlock('speech_style', SPEECH_STYLE_GUIDE,
  ['normal', 'entity_meeting', 'secretary']));
```

- 文案共 **714 字**，只描述「真人说话是什么样」，分三节：
  - **【回话方式】** —— 停顿、边想边说、情绪起伏、话里有话
  - **【看情况变】** —— 按对方状态（想聊 / 难受 / 纠结 / 说事 / 松散 / 亲近）切换说话方式
  - **【尺度】** —— 明确「这些是『可以这样』，不是『必须这样』」
- **不列词表**：全文不含任何语气词/叹词枚举（由测试断言锁定）。
- **不做后处理**：不碰 LLM 输出，不插词、不改写。
- 异常包裹在 `try/catch` 中，引导缺失不阻塞主链路。

### 2.2 为什么用 personaBlock 而不是新模块

PAS v1 已确立「文案仅一处定义」（P-01）与分层承载。本变更落在**既有承载**上
（`PromptAssembler` 的 persona 类块），不新建模块、不新建词表、不新增配置项。

### 2.3 modeScope 的事实说明

`PromptAssembler.render()` 按 `b.modeScope.includes(mode)` 过滤（`PromptAssembler.ts:109`）。
`chat.ts:2300` 是**全仓唯一的 render 调用点**：

```ts
const _mode = _isMeeting ? 'entity_meeting' as const : 'normal' as const;
```

即渲染侧 `mode` **只可能是 `normal` 或 `entity_meeting`**。全仓没有任何一处把 `mode`
设为 `'roleplay'`（0 命中）。

因此：

| modeScope 取值 | 是否生效 | 说明 |
|---|---|---|
| `normal` | ✅ | 日常对话（渲染侧实际取值之一） |
| `entity_meeting` | ✅ | 会晤模式（渲染侧实际取值之一）。**personaBlock 默认只有 `['normal']`，不显式加则静默失效** |
| `secretary` | ⬜ 惰性 | 渲染侧从不产生该取值。保留是为与兄弟块（`m6_self` / `master_profile` / `identityBlock` 默认值）风格一致，**不产生行为差异** |
| `roleplay` | ⬜ 未加入 | 同上为惰性取值。加入不产生行为变化，只会制造「已覆盖角色扮演」的假象，故**不加** |

> 注：`_currentRole = 'secretary'`（`chat.ts:149`）是**角色**（RoleType），
> 与 `ChatModeKind` 是两套概念，不可混同。

## 三、白皮书更新摘要（架构层）

**标题：表现层说话方式引导的承载定位**

1. 「回话方式」属**表现层**职责，与 L0「像真人说话」同属一类，落点在既有
   PromptAssembler 的分层承载上，不新设管线阶段。
2. 确认**输入侧引导优先于输出侧后处理**这一取向：不采用在 LLM 输出上贴词的做法，
   具体用词由模型自行决定。
3. 本变更不触碰四平面定义、不影响 M1–M9 分层与依赖方向、不改变 PAS 的优先级/
   预算/截断机制，仅新增一个 persona 类块。
4. **接口契约（22 段 `finalKnowledgeText` 注入顺序）未变**：顺序仍为
   亲密过滤 → 家族约束 → PFC 上下文 → 角色指令 → M6 自模型。
   `speech_style` **不进入该 22 段链路**，而是走 PromptAssembler 的 `assembler.add()`
   通道，最终随 `_assembled.text` 整体并入——即它是 22 段之外的**平行承载**，
   不插队、不调换任何既有段序（本变更 diff 中 `finalKnowledgeText` 命中数 = 0）。
5. **数据流图（`finalKnowledgeText` 装配流程）不变**：

   ```
   各 personaBlock/hardRule/... → assembler.add()
                                  → assembler.render({mode, maxChars:8000})   ← speech_style 在此被
                                  → _assembled.text / .blocks / .dropped        modeScope 过滤
                                        ↓
   22 段链路（亲密过滤→家族约束→PFC→角色指令→M6 自模型）
                                        ↓
                              finalKnowledgeText（未变）
                                        ↓
                    chat.ts:2317 ctx.m5.orchestrate(...) → LLM
   ```

   即 `speech_style` 从**上游汇入**，22 段链路与 `orchestrate` 调用点均未被触碰。

## 九、审计卷宗（提案留存，永久）

> 本节按流水线 `PROPOSAL_AUDIT_TRAIL` 要求留存：原始方案、优化方案、

### 9.1 原始局部方案（全文）

**方案 A —— 输出侧后处理贴词**

在 LLM 返回文本之后做后处理，向回复里插入停顿词、语气词、口吃片段，
使输出在**表面形态**上「像说话」。典型实现为 `ThinkingPauseInjector` 一类：
以规则/词表匹配句子边界，再按上下文选择插入何种填充。

设计要点：

- 不改变提示词，只改输出；
- 用词表决定插入什么（例如在长句中段插「嗯…」）；
- 插入发生在 orchestrate 之后、返回给用户之前。

**该方案在 S2 阶段被明确否决。**

### 9.2 AI 提出的全局优化方案（全文）

**方案 B —— 输入侧 persona 块引导（采用）**

在 PromptAssembler 注册阶段追加一个 `personaBlock('speech_style', …)`，
把「怎么说话」作为**提示词内容**交给模型，让模型自行决定具体用词与节奏。

设计要点：

- 只描述行为特征（可停顿、边想边说、情绪起伏、看情况变、尺度），**不列词表**；
- 具体用词由 LLM 决定，不做输出侧干预；
- 落在既有承载（persona 类块）上，不新建模块、不新增配置开关；
- modeScope 显式含 `entity_meeting`（personaBlock 默认仅 `['normal']`）；
- priority 300（默认值，低优先级，超预算时可被安全丢弃）；
- 异常 `try/catch` 隔离，不阻塞主链路。

**全局性体现**：该方案解决的是「输入侧从未告知模型语域」这一**根因**，
而非在输出侧逐句打补丁；同时把边界固化为 5 条可执行断言（§六），
防止后续任何改动把实现退回词表贴词。
