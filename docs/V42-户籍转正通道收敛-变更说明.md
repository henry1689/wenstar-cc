### 7.1 白皮书更新摘要

**标题：户籍实体的转正判据 —— 「进门查一次」不等于「一直有效」**

1. **观察区晋升补挂同源闸门**（`FamilyGraph:2800`）。
   原 `promoted = evidenceScore >= CANDIDATE_PROMOTE_SCORE` 是**纯计数**判据 ——

2. **闸门异常按 fail-closed 不晋升**（与修复 3 的 `_addNodeInner` 处置一致）。

3. **正名：转正通道全仓共 3 条，且各有明确处置**（见 §一·2 表格）。
   `SET status='active'` 的业务写入点全仓仅 `2803`(证据晋升) / `2932`(LLM终审) 两处；
   `SET entity_source='real'` 三处中仅 `1235`(占位升级) 是运行时通道。
   **通道 2 有意不改**（LLM 能读 `contexts` 做语义判断，加字面闸门是能力倒退）；
   **通道 3 有意不改**（`placeholder` 实测为 0，且 `entity_source` 全仓无业务读取方）。

## 八、方法论记录

1. **实测推翻了方案的默认假设（如实记录）**：我原本拟「三条通道全部补闸门」，
   实测后 `placeholder` 总数 = 0、`entity_source` 无业务读取方 ⇒ 通道 3 改动**零收益**，
   通道 2 的 LLM 语义能力**强于字面闸门**。最终收敛为 1 处。
   ⇒ 教训：**同类路径要逐条实测「它现在跑不跑、跑起来影响谁」，不能因为模式相同就一律改。**

2. **通道盘点必须穷举写入点，不能靠猜**：最初我只找到 2 条转正通道，
   全仓 grep `SET status = 'active'` 才发现第 3 条（`applyJudgments:2932`）。
   ⇒ 教训：**盘点用「写入语句」做检索词，不用「业务概念」做检索词** —— 后者会漏掉想不到的路径。

3. **闸门放行 ≠ 安全**：`明凤凰` 的 `ctx` 明确是「以前是公明，现在叫光明…光明凤凰街道」，
   字面判据却判它「有姓氏」放行。修复 3 的能力边界在本轮实测中被**同时验证了两面** ——
   拦住了含虚词的（`东坑这`），放走了整词的（`明凤凰`）。**这是预告过的边界，不是回归。**

4. **豁免已过期但 pre_check 通过，两者是不同系统**：
   `harness_pre_check` 查的是 Harness **基础设施保护区**（本次 `blocked:false`），
   而 `exempt list` 查的是 **Sentinel 写入豁免**（本次全部 `剩0min`）。
   ⇒ 二者不可互相推断，必须分别确认。
