# ADR-021 拆除 FG 观察区（candidate）与离线终审

- 日期：2026-11-08
- 状态：已采纳
- 前置：ADR-020（实体准入内联取证）§6 修订
- 依据：业主 2026-11-07 裁决「完全取消 RAG 提取实体名存放观察区这个流程，前后只用一次 LLM 筛选和提供录入最后依据」「彻底清除……物理清除，避免死灰复燃」；任务书 `docs/实体提取架构收口任务书-V1.md` §8 批3

## 1. 背景

原链路：**滑窗生成人名 → 写入 FG 观察区(status='candidate') → 累积提及/上下文证据晋升 active → 离线 LLM 批量终审**。

这条链是「先写入、后判定」的补偿装置：判定所需的信息（这个人是怎么被介绍的、原句长什么样）在写入端就已经丢失，
只能靠事后计数与 LLM 猜测补回来。实测后果：近 30 天 1820 个 category='G' 的候选淹没观察区；
离线终审也无法可靠区分真实姓名与滑窗片段。

批1 已物理删除产生端（滑窗生成器等 5 类）；批2b 已把准入前移到写入前（确定性取证 + 原文证据硬闸门）。
此时观察区与离线终审已无用武之地。

## 2. 决策

**物理删除观察区机制本身**，而不是「保留但停用」——保留会留下可被重新接线的残骸，
违背业主「物理清除、避免死灰复燃」的明确裁决。

删除内容：

| 装置 | 位置 |
|---|---|
| 证据累积与晋升 | `FamilyGraph._accumulateCandidateEvidence` + `integrateFromEntity` 调用点 |
| 终审数据层 | `FamilyGraph.collectCandidateItems` / `applyJudgments` |
| 上下文词表与阈值 | `CANDIDATE_PROMOTE_SCORE` / `NOISE_RECLAIM_MIN_CONFIDENCE` / `NAME_*` 四个词表 / `_hasNameTitleContext` / `_hasNameStrongContext` |
| candidate 初始化 | `addNode` 的 `grade===3 → initialStatus='candidate'`；启动归一 `UPDATE … status='candidate'` |
| 超期回收 | `StatusRules` 的 `CANDIDATE_EXPIRE_DAYS` 与 `candidate → void` 分支 |
| 离线终审模块 | `src/app/entity/EntityTriageService.ts`、`EntityQualityJudge.ts`（物理删除） |
| 调度装配 | `maintenance.setEntityTriage` / `runEntityTriage` / 定时器 / 首轮触发 / stop 清理；`server.ts` 装配块 |

保留：

- `status` 枚举中的 `'candidate'` 与读取侧 `NOT IN ('void','candidate')` 过滤 ——
  **历史库/他库防御**，不再有任何产生点。
- `StatusRules.isExemptFromExpiry` —— 保留为历史候选行的防御性豁免判定（当前无候选行，恒 false）。
- `FamilyGraph._isPrefixSlice` —— 写入端计数冻结判据仍被 `updatePersonProfile` 使用。

## 3. 行为变化

1. 新写入的 person 不再进入观察区，**直接 active**（准入已在写入前完成取证）。
2. 启动时不再把 status 为空的行打上 candidate 标记（生产实测此类行 = 0，无行为变化）。
3. 不再有每日实体离线终审调度与 LLM 调用（省 token；此前每轮扫描 candidate 队列）。
4. 存量：生产库 `status='candidate'` 行 = 0，本批不改任何数据；历史/他库残留由批5 按业主确认处置。

## 4. 验证

- `npx tsc --noEmit` = 0
- `grep -rn "candidate" src/m4/household/FamilyGraph.ts` 仅剩注释与历史防御过滤，无写入/晋升
- `candidate-zone.test.ts` 改为退役断言（方法不存在、无 candidate 写入、状态机无超期规则）
- 重启后日志不再出现「实体离线终审 (EntityTriage) 已装配」
- FG 人物数不变（19 active / 12 dormant），无新 candidate

## 5. 回滚

单提交 revert + 恢复两个被删模块；无 DDL、无数据迁移。
