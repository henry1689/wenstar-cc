## 一、为什么要有两条链路

同一个问题在系统里有两种性质截然不同的答案需求：

| 用户问法 | 需要什么 | 只有一条链路的后果 |
|---|---|---|
| 「你还记得我喜欢的那个吗」 | **结论、感受、偏好** —— 压缩后的特征子集 | 若只有 A 链路：钙化记忆天生残缺，答得出但没细节 |
| 「那天我们到底说了什么，一字一句讲给我听」 | **原文、场景、语气** —— 完整回放 | 若只有 B 链路：每轮都要全表扫，成本爆炸且必然串音 |

⇒ **A 链路负责「记得什么」，B 链路负责「当时是怎么说的」**。两者不是备份关系，是**不同粒度的同一事实**：A 是可复述的语义沉淀，B 是不可再造的原始档案。

这条分界决定了访问模式也必须分开：

- A 链路是**检索型**：海量候选 → 相关性/钙分排序 → 取前 N 条注入。允许扫、必须扫。
- B 链路是**寻址型**：先有确定的组 id，才有资格取内容。**没有 id 就不许读**。

## 二、决策

### D1 · 链路定义与驱动方式

| | **A 链路 · 钙化心智** | **B 链路 · 沉睡卷宗** |
|---|---|---|
| 物理载体 | `memories`（砂金）/ `vault_log`（金库）/ `black_diamond`（黑钻） | `conversations` 原文 + `dialog_groups` 卷宗元数据 |
| 基本单位 | 单条记忆（行）/ 对话组（块级通道） | **对话组 = 卷宗**（`dialog_group_id`） |
| 驱动方式 | **钙分驱动**：不需要字面命中，高钙组可独立进候选 | **字面命中驱动**：关键词/摘要命中才有候选 |
| 访问模式 | 全库检索 + 排序 + 截断 | **单点寻址**（`BArchiveReader.getByGroupId`） |
| 允许的操作 | 扫描、排序、向量相似、多路融合 | 按 id 读、按 id 追加日志、按 id 计数 |
| **禁止的操作** | — | **无锚点全表扫描 / 向量检索 / 按组遍历** |

### D2 · 「禁止全局检索」是结构性约束，不是纪律要求

约束落在**代码结构**而非文档：

1. `BArchiveReader` 是 `dialog_groups` 的**唯一读取入口**，对外只暴露 `getByGroupId(groupId)`。
   没有 `list()` / `scan()` / `search()` 之类的返回多组 API —— 想违规也没有接口。
2. `assertAnchoredRead(sqlText)` 在每次下发 SQL 前做运行期断言：凡 `FROM dialog_groups` 而缺
   `dialog_group_id = ?` 的语句直接抛错。**守卫在代码里，不在 review 清单里。**
3. 守卫测试（`b-archive-guard.test.ts`）用 `RecordingSql` 记录全部下发 SQL 逐条断言，
   并反射检查 `BArchiveReader.prototype` 只含 4 个方法。

> **允许的例外**：带字面命中的倒排召回（必须过 UUID 过滤），这是「先由检索层给出候选 id，再单点读」的合法形态。

### D3 · 卷宗化四项数据的口径（一经落地不可改）

| 数据 | 列 | 口径 | 为什么 |
|---|---|---|---|
| 内容哈希 | `content_hash` | `sha256(seq_pos ␁ role ␁ content ␂ …)` 前 **32 hex**，**只覆盖 conversations 原文** | 原文不会变；摘要会重生成 |
| 摘要哈希 | `summary_hash` | `sha256(block_summary)` 前 32 hex，空摘要写 `NULL` | 摘要是 LLM 产物，与原文不同源，必须独立校验 |
| 40D 快照 | `perception_40d_snapshot` | JSON：`{dims, agg, dim_version, generated_at, vector}` | 40D 量纲会演进，快照必须能自解释 |
| 追加日志 | `append_log` | JSON 数组，`{ts, type, actor, detail}`，**只追加，永不修改既有条目** | 可追溯、可审计 |

**内容哈希为什么把摘要排除在外**：混算的唯一后果是——每次重生成摘要都要全量重算哈希，且无法区分「原文被改了」还是「摘要被重写了」。分开后，两者各自回答各自的问题。

**`SEP_FIELD` / `SEP_ROW` 为什么用控制字符**：正文里出现任何可打印分隔符（`|`、`\n`、`\t`）都会造成拼接歧义 —— `["a|b", "c"]` 与 `["a", "b|c"]` 拼出来一样，哈希就失去了防篡改意义。控制字符 0x01/0x02 是不进入对话正文的天然边界。

### D4 · 生命周期三态，且与钙分阈值对齐

`active → consolidating → archived`

- 三态是实现真值（`DialogGroupLifecycle`），T002 原文的 `active→decaying→suppressed→archived` 四态**作废**；
- `archived` 在块路检索中降权 0.5（不是删除，原文永存）；
- **与 ADR-MEM-003 的关系**：本 ADR 只管「状态怎么流转」，ADR-MEM-003 管「什么条件下可以物理删除」。三态机不产生删除动作。

### D5 · 两套钙分量纲永不互转

| 量纲 | 载体 | 值域 | 门槛 |
|---|---|---|---|
| 记忆钙分 | `memories.calcium_score` | **0 ~ 1** | 永生 `θ_permanent = 0.85` |
| 块钙分 | `dialog_groups.block_calcium_score` | **0 ~ 10** | 高钙通道 `floor(5)`；召回归一 `/5` |

**禁止**把 `block_calcium_score` 直接与 `calcium_score` 比较、相加、换算。这是 P087「钙分双算」教训的延伸 —— 两套量纲混用会让排序结果不可解释，且没有任何一处代码能说清某个分数到底是什么。

块钙分是**确定性规则**产物（`BlockValueScorer`，零 LLM）：
`scene(0~2) + emotion(0~2) + commitment(0~3) + turningPoint(0~2) + degradedPenalty(-3~0)`，截断到 `[0,10]`。

### D6 · 组级 40D 快照的聚合口径如实标注

- 数据源：`memories.perception_40d`（组内逐轮）；
- 聚合：**逐维等权平均**，`agg='mean'`；
- 无 40D 的组写 `agg:'none'` 的**显式占位**，不写 `NULL`。

> **与 P145 微调 1 的偏差（如实记录）**：微调 1 原写「按钙分加权平均」。
> 但对话组结构内**未保留逐轮钙分**（`dialog_groups` 只有 `emotions` 曲线与 `maxCalcium` 峰值），
> 按钙分加权需要的信息根本不存在。**为实现可解释且不伪造，本批采用等权平均并在 `agg` 字段如实标注 `'mean'`。**
> 将来若补齐逐轮钙分落库，可升 `dim_version` 后重算，旧快照因带 `agg` 字段仍可自解释。

**无 40D 写占位而不写 NULL 的原因**：扫描条件是 `perception_40d_snapshot IS NULL` —— 写 NULL 会让该组每批都被重新扫到，形成永不收敛的回填循环。

### D7 · 消费计数区分真实消费与运维回填

| 类型 | 触发 | 计数 | 钙分 |
|---|---|---|---|
| `USER_CONSUME` | 深度回忆真正回放了原文 | +1（同组 30 分钟节流，最多计 10 次） | 每次 +0.3，封顶 10 |
| `OPS_BACKFILL` | 运维/回填触达 | 只记账 | **不改** |

理由：如果回填也算「用户消费」，那存量治理跑一遍，所有老组一起涨钙分 —— 钙分就变成了「被脚本碰过几次」的计数器，失去语义。

**只在渲染成功后才计数**（`render` 返回非空才调 `recordConsume`）：读失败/空卷宗不算用户消费过。

### D8 · 深度回忆的触发边界（fail-closed）

只有 `detectDetailLevel(message)` 判定为 **`detail` / `full`** 时才尝试深度回忆；普通提问连库都不查（守卫测试锁死）。

会晤态下必须解析出**当前发言人 UUID** 才能展开，解析不出就**不展开**：
- 不展开 = 用户拿到的是普通摘要片段，体验略降；
- 错误展开 = 用户拿到的是**别的角色**说过的原话，属隐私串台。

⇒ 宁可少展开，不可展开错。这与空间路由器「宁可多看，不可全盲」是**相反方向的同一原则**：路由要宽，隐私要窄。

## 三、备选方案与为何放弃

| 方案 | 内容 | 放弃理由 |
|---|---|---|
| **A · 只保留 A 链路** | 深度回忆时把钙化碎片拼长，凑出「完整感」 | 直接撞 ADR-014/MemSym 反编造铁律 —— 拼出来的细节是编造，不是回忆 |
| **B · 只保留 B 链路** | 每轮都从原文检索，不要钙化层 | 每轮全表扫 `conversations`；且原文没有「重要性」概念，会把无关寒暄与关键承诺同等对待 |
| **C · B 链路也做向量检索** | 给卷宗建向量索引，按语义召回 | 与「禁止全局检索」直接冲突；且卷宗是**可寻址档案**不是**候选池**，给它建索引等于承认它可以被随机命中 —— 那就不是卷宗了 |
| **D · 闭组时同步算哈希** | 闭组热路径顺带算 content_hash | 闭组瞬间 `conversations` 可能还没写完最后一轮，此时算出的哈希会漏内容，而**哈希一旦写入不可逆** |
| **E · 新建独立 UUID 体系（T002 的 EventUUID）** | A/B 各持 EventUUID 双向锚点 | 仓内 `EventUUID` 零实现、零生产者。现成的 `dialog_group_id`（组）+ `belong_entity_uuid`（户籍）已经构成完整锚点；再加一套主键 = 第三套口径，正是本 ADR 要消灭的东西 |
| **F · 独立 MemoryHealthDaemon** | T002 设想的记忆健康守护进程 | 已有等效能力分散在三处：Harness Sentinel（文件层）、`system-health-guard.md`（治理层）、`BlockArchiveService` 的完整性校验（数据层）。再立一个常驻进程不增加任何保护，只增加一个需要保活的进程 |

> **E / F 特别说明**：这两项是 T002 原文明确要求、但在仓内从未落地的设想。
> 本 ADR 明确**不采纳**，理由如上，并在《V3.0 真值规范》§4.3 / §4.5 同步记为「未落地」。

## 五、待业主裁决事项

### 5.1 《太虚境户籍法》增补条款（草案，未生效）

T002 Phase 5 要求「户籍法增补 §12」。**现状不匹配**：户籍法用「第X条」编号，第十二条已被
《法定本名与关系称谓的严格分界》占用。故改为**追加第四十二条**，草案全文如下：

> **第四十二条　记忆系统的户籍隔离强制约束**
>
> 记忆系统的一切条目（A 链路砂金/金库/黑钻，B 链路对话原文与卷宗元数据）必须绑定主体 UUID。
> 主体 UUID 一经写入**不可变更**，不得因会话切换、重启、数据迁移而改写。
>
> A/B 双链路的所有条目，其 `belong_entity_uuid` 为**户籍归属的唯一真源**，禁止按正文内容推断归属。
>
> 检索与读取的第一道工序必须是主体 UUID 过滤，**先过滤、后排序**；不得先取候选再在出口过滤
> （出口过滤会让本不该被读取的内容先进入内存，构成越权读取）。
>
> 不同户籍主体的 B 链路卷宗**逻辑隔离，物理同一**：同一张表、同一套代码，以行级 UUID 严格隔离；
> 任何跨主体的批量操作视为越权。无归属记录仅户主本人可见（deny-by-default）。
>
> 违反本条的任何代码路径视为缺陷，不视为「配置问题」。

**状态**：📝 草案 —— 法律修改权归业主，**须业主裁决后方可写入户籍法正文并登记 GOVERNANCE 效力层级表**。

## 六、后续出问题先看这里

| 症状 | 先查 |
|---|---|
| 深度回忆不触发 | `detectDetailLevel` 返回是否 detail/full；`extractDialogGroupId(hit)` 是否取到 id |
| 深度回忆串到别的角色 | `audienceUuid` 是否解析成功（会晤态 `GroupSession.speakerUuid`）——失败时应 fail-closed 而非展开 |
| 完整性校验恒报「被篡改」 | 校验侧是否用**原始行**（`seq_pos`）而非映射后的驼峰对象（`seqPos`）——这正是批 B 首版踩过的 bug |
| 回填任务跑不完 | 是否有一批组反复被扫到 —— 检查 `agg:'none'` 占位是否写入成功 |
| 卷宗摘要与原文对不上 | `summary_hash` 是否为 `NULL`（空摘要不写哈希）；`summary_state` 是否为 `failed` |
| 配额里 B 链路被挤掉 | 组片段标签是否含「记忆」二字 —— `MemoryInjector` 的记忆档判定依赖它（见 ADR-010 §14.2） |
