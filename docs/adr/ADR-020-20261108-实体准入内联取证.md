# ADR-020 · 实体准入内联取证（批2 第1波：契约模块）

- **日期**：2026-11-08
- **状态**：已采纳（第1波：协议/解析/校验/流式闸门；第2波接线与删旧代码另批）
- **相关**：`docs/实体提取架构收口方案-V1.md` §4、`docs/实体提取架构收口任务书-V1.md` 批2、ADR-018/019

---

## 1. 决策

把「实体准入」收敛为独立契约模块 `src/m1/entity-admission.ts`（四件套）：

| 组成 | 内容 |
|---|---|
| 协议 | `ENTITY_EVIDENCE_INSTRUCTION`：正文前输出 `entity: 名称\|类型\|证据原文`，末尾 `---` 再开始回复 |
| 解析 | `parseEntityEvidence()`：**字段边界**逐行识别，只扫正文开始前 ≤12 行；纯 JSON 整体跳过 |
| 校验 | `verifyAdmission()`：证据必须是用户消息的**连续子串**，且名字必须在证据里 —— 唯一反幻觉硬闸门 |
| 流式 | `EvidenceHeaderGate`：头块不进 SSE/TTS；失败安全（超限/异常一律原样放行，不吞正文） |

`outputGuard.HEADER_SEPARATORS` 导出为单一真源，取证头与 speaker 头共用同一分隔行集合。

## 2. 为什么这样设计（追溯依据）

- **旧路径的问题**：滑窗生成器（批1 已删）与独立 LLM 提取各有一套判据，且判据是"看起来像人名"——
  中文人名与滑窗片段字面不可分，实测 30 天新增 1820 个垃圾候选。
- **不可由 LLM 决定的判据**：`message.includes(evidence)` 让模型"编不出原文里不存在的连续片段"；
  这是与 LLM 能力无关的硬闸门，优于任何二次分类器。
- **零额外调用**：取证并入主回复调用，不再单开一次 LLM（省 token、省延迟），
  且能用主模型的完整上下文判断"是否被显式引入"。
- **失败安全的取舍**：解析失败/协议缺失 → 零实体、不阻断回复；流式闸门异常 → 原样放行。
  不对称取舍：宁可漏准入（垃圾不进库），不可吞正文（用户看不见回复）。

## 3. 备选方案与为何放弃

| 方案 | 放弃原因 |
|---|---|
| 继续用独立 LLM 提取 + 事后过滤 | 多一次调用且判据仍是"像不像人名"，无法证伪 |
| 正则直接抽名字 | 批1 已证明中文人名与片段不可分 |
| 流式不剥头、前端再处理 | 头块会进语音（TTS）与日志，且前端无统一协议 |
| **内联取证 + 原文硬闸门（采纳）** | 可证伪、零额外调用、失败安全 |

## 4. 影响范围与回滚

**本波**：新增模块与测试（16 例）、`outputGuard` 仅加 `export`、本 ADR。**未接线**，生产行为零变化。

**后续波次**（另批）：`chat.ts` 注入指令块与回复后解析、`server-chat-routes.ts` 接流式闸门、
`ChatEntry.ts` / `L3EntityAnnotator.ts` 删除旧 LLM 提取、物理删除 `LLMEntityExtractor.ts`。

**回滚**：删除模块 + 还原 `outputGuard` 的 export；无数据变更。

## 5. 后续出问题先看这里

1. **回复开头露出 `entity:`** → 检查流式闸门是否接线（第2波）；非流式检查 `parseEntityEvidence` 是否被调用。
2. **合法新实体进不来** → 看 `admissionStats`：`protocolMiss` 高说明模型没遵守协议（检查指令块是否注入）；
   `rejected` 多说明证据不复述原文（协议措辞需收紧，不要放宽校验）。
3. **不要把校验放宽成"相似"**：`includes` 是唯一硬闸门，任何模糊匹配都会重新打开幻觉入口。

## 6. 修订（2026-11-08，批2b）：从「模型遵守协议」改为「确定性取证」

### 6.1 实测结论

主回复取证头协议在生产模型上的合规率是 **0/4**。四种注入方式全部无效：
① `PromptAssembler` task 块；② 独立 system 消息（`responseContract`）；
③ 用户轮前缀「输出格式要求·必须遵守」；④ 回忆类非闲聊消息 + 完整推理。

已排除接线问题：指令确实进入最终 prompt（实测 `inKB=true`、`[ResponseContract] applied`），
剥离器也不吞头。**结论是模型不会为了格式协议牺牲人设台词** —— 这不是接线故障，是服从性边界。

同时发现：`entity_genes` 的人名来源只有 FMM 词典与 FG 已知名单，显式介绍出来的新人名
从未进入 `entity_genes`，因此 M4/FG/记忆检索在本轮根本看不见他。这才是「合法新实体进不来」的真因。

### 6.2 修订后的结构

**一个判据、一个闸门、全部写入点共用**：

| 环节 | 实现 | 说明 |
|---|---|---|
| 判据 | `findIntroEvidence(text, name)` | 名字 ±10 字窗口内出现介绍线索（介绍动词/社会角色/亲属称谓）→ 返回窗口原文作为证据 |
| 发现 | `extractIntroducedPersons(text)` | 规则命中处即证据，证据恒为原文连续子串（`叫X` / `X是我的Y` / `这是我同事X` / `X老师`） |
| 校验 | `verifyAdmission` / `verifyAdmissions` | **未变**：证据必须是用户消息连续子串且包含名字 |
| 写入点① L3 | `L3EntityAnnotator.annotate` | 确定性取证进入 `entity_genes`（带 `evidence` + `admission:'deterministic'`），本轮即可参与 M4/FG/记忆检索 |
| 写入点② FG 家族 | `integrateFromEntity` → `hasExplicitPersonIntro` | `hasExplicitPersonIntro` 改为委托 `findIntroEvidence`（删除其重复的窗口关键词实现） |
| 写入点③ FG 社交 | `integrateSocialRelation` | 新建节点前过同一道闸门（已存在人物行为不变） |
| 写入点④ 知识库 | `storeRelations` | 新建 `entities` 行前过同一道闸门 |
| 可选增强 | `admitModelFromReply` | 主回复头块仍解析、仍校验，但不作为准入前提 |

### 6.3 行为变化（明确声明）

「只是提到某人」（如「和张中山开会」）**不再建档**，必须有介绍线索。这是批1 已定原则，
当时未覆盖 FG 社交通道与知识库通道，本次补齐。已入库人物不受影响（只闸新建）。

### 6.4 证据字段的落库边界

`EntityGene.evidence` / `admission` 是**可选**字段，随 `entity_genes` JSON 整存落库
（`persistence-stage` 的 `entityGenes` 原样存）。`Transcoder` 的固定二进制格式不纳入这两个字段
（该路径仅做可调通校验）；旧数据反序列化不受影响。
