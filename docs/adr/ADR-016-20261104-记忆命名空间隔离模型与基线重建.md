# ADR-016: 记忆命名空间隔离模型正式化 与 MemArch v2 基线重建

- **状态**: ✅ 已签字生效（业主 2026-11-06 三决定，见下「修订单 R1」）
- **修订单 R1（业主 2026-11-06）**: 本单 §2.3 原规定「L3 痕迹归属**由 namespace 承载，不设 UUID 列**」——业主裁决**改为补 `belong_entity_uuid` 列**（选 B）。理由（业主原话）：「统一管理大方向，后续进一步完善也要用到 UUID 的信息数据归属和人格隔离原则，互不干扰精准定位」。故 §三 变更清单第 7 项由「明示不设 UUID 列」改为「**补 `belong_entity_uuid` 列**，与 namespace 双承载：namespace 做检索硬隔离，UUID 做精准定位与人格隔离，二者冗余但语义不同、互不干扰」。本次为**法条修订**，依《记忆系统运维审计规范》第九条走「提案→关联 ADR→业主评审→版本升级→代码对齐」，业主已评审通过。
- **决策**: 记忆隔离采用**「一角色一命名空间」的物理隔离**模型，namespace 语义冻结为四类（个人域 / 系统域 / 测试域 / 扮演域）；检索硬过滤改为 `namespace IN (当前实体域, 'default')`；同时**重建 MemArch v2 基线**（v2.0.0 → v2.1.0）以消除设计与实现的不一致。

## 一 · 为什么必须做这个变更

### 1.1 设计文档内部自相矛盾

| 位置 | 规定 |
|---|---|
| §1.2 / §16.1（L107 / L1253） | `namespace: 'default' \| 'test' \| 'roleplay'` —— **只有三个值** |
| §3.4 晋升（L774） | `if (m.namespace !== 'default') return { to: null }` —— **非 default 不得晋升** |
| §8.1 步骤②（L831） | 检索**硬过滤** `namespace='default'` |
| §10.1（L1008-1014） | 视图 `WHERE COALESCE(namespace,'default')='default'` |

**但设计方案通篇没有回答：多个角色（玉瑶 / 徐诗雨 / 罗珍思 …）的记忆如何隔离。**

- 检索链路 §8.1 全流程**没有任何 UUID / 实体过滤**
- `belong_entity_uuid` 在全文**零出现**
- 唯一的角色相关过滤是 `v_conv_real` 的 `roleplay_char IS NULL OR roleplay_char=''`，
  而真实对话的 `roleplay_char` 本就为空 —— **该条件恒真，等于不过滤**

**结论：按设计原样实现，所有角色的记忆会全部混在 `default` 中并被互相召回。** 这正是业主实测到的串台。

### 1.2 实现已经事实上采用了另一套模型，但没有回写设计

`memarch-bridge/scripts/step3-migrate.js` 把数据按角色写入 8 个 namespace：

```
ns_shiyu(7194)  ns_a-zhen(3799)  ns_yuyao(3259)  ns_legacy_unknown(2986)
ns_xiongziming(1975)  ns_wangquanfen(843)  ns_shiyun(295)  ns_shihan(247)
```

**按 §8.1 与 §10.1 的硬过滤，这 8 个域的数据一条都不应被召回、一条都不应晋升。**
实现与设计在核心模型上直接冲突，且冲突未被记录。

### 1.3 基线完整性已经破损

| 项 | 值 |
|---|---|
| 文档自称基线 | `MemArch-v2.0.0-Baseline`，MD5 `C3DCBFC83B96EBE88D06D230F26CF503` |
| 当前文件实际 MD5 | `852C188E507B7DBF37FD1B4154C14F94` |
| 文档规定 | 「任何需求变更必须走【变更单】，禁止口头修改；变更后重新计算哈希并升版本号」 |
| 6 份任务书 | 全部绑定 `C3DCBFC8...`，**已失效** |

**该文件在 git 中为未跟踪状态，无历史可追溯，无备份副本可比对** ⇒ 无法审计"发布后被改了什么"。

**这是必须修复的质量缺陷：规则写了但没被执行。**

## 二 · 决策

### 2.1 namespace 语义冻结（四类，无第五类）

| namespace | 语义 | 检索 | 晋升 | 写入者 |
|---|---|---|---|---|
| `ns_<entity>` | **个人记忆域** —— 该角色视角下的一切记忆 | ✅ **仅该实体** | ✅ | 该角色的对话轮次 |
| `default` | **系统占位域** —— 不含真实个人记忆；仅系统运维/历史遗留占位 | ❌ **不参与个人检索** | ❌ | 无（只读占位） |
| `test` | 测试隔离 | ❌ 永不召回 | ❌ | 测试流量 |
| `roleplay` | 角色扮演 | ❌ 永不召回 | ❌ | 扮演模式 |

**命名规范**：`ns_` + 小写实体标识（ASCII 或拼音），全局唯一，在 `namespace_registry` 注册后方可使用。

**🔴 为什么 `default` 不参与个人检索**（本单相对设计 v2.0.0 的关键收紧）：

设计原文的检索白名单是 `namespace IN (:ns, 'default')`。这保留了**一条串台通道** ——
任何落进 `default` 的记忆，所有角色都能读到。历史上"玉瑶的记忆被诗雨说出来"正是这类混流。

而 `memories` 是 L3 **个人痕迹**（"某人视角的语义片段"），语义上**每条都必须属于某一个实体**。
真正的公共知识（规范、常识、家谱事实）存放在 **L4 `semantic_facts`**，不在痕迹层，走另一条读取路径。

⇒ **个人检索白名单只有 `ns_<当前实体>`，不并集 `default`。**
`default` 保留为系统占位与历史遗留容身之处，但不成为召回来源。

### 2.2 读写规则

**读**：
```sql
namespace = :currentEntityNamespace
```
- **只读自己的域**；`default` / `test` / `roleplay` 均不进入个人检索。
- `namespace` 是**必填查询参数**，无默认值；空值或未注册的域直接抛错。
- 公共知识走 L4 `semantic_facts` 的独立通道，与痕迹层召回互不混流。

**写**：
- 必须显式给出 namespace；无默认值。
- **写入一致性断言**：写入 `ns_<X>` 时，若调用上下文声明的当前实体不是 X ⇒ 拒绝写入。
  这是防串台的最后一道闸（历史事故：`ContextMemory` 模块级单例导致玉瑶的记忆写进诗雨域）。

**跨角色查询**（如「全家最近怎么样」）：
- 必须是**显式 API**，不是默认行为；
- 必须写审计账本（`audit_ledger`）；
- 结果**按角色分组返回**，不混合排序 —— 避免模型把 A 的记忆当作 B 的说出来。

### 2.3 共同经历的处理：各存各的主观版本

**不设 `shared` / `family` 共享域。** 理由：

1. **符合痕迹层语义** —— `memories` 是 L3「某人视角的语义片段」，不是客观事件表；
2. **符合人脑模型** —— 同一件事，两人的记忆本就不同（这正是 CLS 理论中情节记忆的性质）；
3. **避免归属歧义** —— 共享域必然要回答"这条记忆属于谁、谁有权改"，会引入新的串台通道；
4. **避免第二套隔离机制** —— 一旦有 shared 域，检索规则就必须变成多域并集判断，复杂度与出错面同时上升。

客观事件事实（"昨晚三人一起吃饭"）如需共享，应写入 **L4 语义层（`semantic_facts`）**，而不是痕迹层。

### 2.4 归属不明的历史数据

`ns_legacy_unknown`（2,986 条，占 conversations 29.5%）**保持隔离，不迁不删、不并入 `default`**。

并入 `default` 的后果是所有角色都能看到它 —— 重蹈串台覆辙。
保留隔离 + 提供人工复核通道：逐条判定归属后改写 namespace，复核一条迁移一条。

1. **任何对基线设计文档的修改，必须先有 ADR 变更单，且状态为 ✅ 已批准**；
2. 修改后**必须**重算 MD5，写入文档头，并升版本号（次版本号 +1）；
3. **必须**同步更新所有绑定该基线的任务书；
4. 基线文档**必须**纳入 git 跟踪 —— 未跟踪的基线等同于无基线（本次破损的直接原因）。
