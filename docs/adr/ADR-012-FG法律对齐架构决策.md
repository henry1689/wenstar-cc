# ADR-012: FG 法律对齐 —— 单一字典 + 单一采集引擎 + 单一读取入口

- **状态**: 提议中 — 待豆包验收（T010 Phase 0）
- **决策**: 把 FG 的 **6 套关系词表收敛为 `RELATION_TYPE_DEFS` 一个真源**；把 4 条写入路径收敛为 **PAE 一个采集引擎**（加定时 + 文档来源，不新建第二个引擎）；把 3 套档案读取语义收敛为 **`PersonProfileView` 一个入口**、关系读取收敛为 **`getUserRelation` 一个入口**；**读取改为零副作用**；**密级、分户基因码、legacy_ids 按法律保留并接线**（不删）；节点与卷宗**不做物理删除**，清理范围限于孤儿边/重复边。
- **日期**: 2026-10-21
- **依据**: [太虚境户籍管理法 V2.1](../../data/knowledge-v4/governance/taixu-household-registration-law.md)（第三/五/八/十一/十二/十四/十五/十九/二十二/二十四/二十五/二十七/三十/三十三/三十四/四十一条）、[FG 红线 V3.5](../../data/knowledge-v4/governance/redlines/fg-kinship-redlines.md) §二/§三/§四/§十一、T008 审计（P031×2）、T009 盘点（P032×2）、[FG 结构规范 V1.0](../FG-结构规范-V1.0.md)
- **相关**: T009 / T010、ADR-010、ADR-011
- **编号说明**: GOVERNANCE「治理纪律 5」要求新 ADR = 当前最大序号 + 1；`docs/adr/` 现存最大为 **011**，故取 **012**（T010 草案中的「ADR-013」顺延为 012）。ADR 正文不引用自身序号，如业主另有 013 规划，改号成本为零。

## 一、问题

T008/T009 两侧审计得到同一个结论：**FG 不是"缺设计"，是"设计太多、彼此不相识"**。

| 症状 | 实测 |
|---|---|
| 6 套关系词表 | DEFS 44 种；其余 5 套词表 + DB 实际值引用 **66 种**类型，**32 种不在 DEFS** |
| 4 条写入路径 | 3 条失效（FGRelationExtractor 产出恒 0 / HWG 零调用 / 社团关系零调用），只有 PAE 存活 |
| 3 套读取语义 | 会晤读 `dossier.selfProfile`（2.1% 填充）/ 普通读顶层 flat（33.6%）/ 关系两套优先级 |
| 读取有副作用 | `getPersonProfile` 会改状态并**删除该节点全部边** |
| 词表漂移 | `RELATION_TYPE_DEFS` 自 2026-07-16 定稿后零变化，新入口各自新建词表 |
| 密级失效 | 法律要求三级密级；实现把密级接到**记忆**上，节点列零读取 |
| 观察区蓄水 | 992 个 candidate / 23 个 active；近 10 天新增 1003 个节点 |

## 二、决策

### D1 关系类型：`RELATION_TYPE_DEFS` 为唯一真源

- 补齐 32 个缺失类型（规范附录 A），含 `lover_of`（业主定音的正式身份）。
- 其余 5 套词表改为**从 DEFS 派生**，不是"同步维护"。
- 启动断言：写入白名单 ⊆ DEFS；每个 `reverse` 目标 ∈ DEFS。

> **为什么不是"删掉多余的"**：`RelationLabels` 的定向标签、`FamilyGraph.REVERSE_RELATION` 是
> 红线 §二/§三 明确引用的映射表。删表会违反上位红线；正确做法是**把表的内容收进 DEFS，
> 让这些名字变成 DEFS 的视图**。

### D2 采集：PAE 扩展，不新建引擎

法律第十四条(2)已规定「信息采集唯一合法引擎：PAE」。新增第二个提取器会同时违反：
- 第十四条：唯一合法引擎
- 本仓不变量 #7：禁止重复实现

因此**扩展 PAE**：新增「定时扫描已闭组对话组」与「文档上传触发」两个输入通道 +
统一 JSON schema + 三级去重，其余（`acquisitionIntegrityGuard` 6 项）复用。

### D3 读取：`PersonProfileView` + `getUserRelation` 双入口

- 会晤/普通模式共用一个档案视图，消除 flat 与 dossier 的分裂。
- 关系只认 edges，带方向返回，解析「实体↔用户」边而非全边。
- **读取零副作用**：`_checkStatusDowngrade` 从所有 `get*` 移除。

### D4 法律强制字段：**保留并接线**，不是删除

| 字段 | 法律依据 | 决策 |
|---|---|---|
| `security_level` | 第九条(一)、第二十七条 | 保留列 + 接入读取过滤（当前零读取，属实现缺陷） |
| `family_gene` / `social_group_genes` | 第五条、第三十五条⑩ | 保留并按分户治理重算（当前仅 15/18 人有码） |
| `legacy_ids` | 第八条(4) | 保留（T007 刚用它完成合并溯源） |
| `tags` / `circle_level` | 无法律依据、零读写 | 删除 |

### D5 生命周期：用法律已有语义替换 candidate/void

- candidate → `entity_source = 'placeholder'`（第十五条、第三十二条(五)）
- void → `archived`（第三十三条：合并后旧节点 status=archived，编号永久归档）
- 不新增状态、不删除状态；四档保持不变。

### D6 清理边界：节点与卷宗不物理删除

第十一条(1)(3)：卷宗只增不删、PendingItem 超期只标记不物理删除；第三十三条：合并后旧节点置 `archived`。
⇒ 删除清单**限于**孤儿边、重复边、未定义类型的边（迁移后）。
⇒ 任何边删除必须写入 `_changeHistory`。

### D7 证据字段：只存溯源主键，不存原文

`edges.properties` 以 `created_from = dialog_group_id / document_id` 为主键；
`evidence` 只放 ≤120 字摘要。理由：隐私（第二十七条私密级）+ 日志/边数据的爆炸半径。

## 三、被否的方案

| 方案 | 否决理由 |
|---|---|
| **A. 直接删 candidate/void**（T010 初稿） | 992 个观察区节点会立刻变成在册实体；法律第十三条「未分配 TXS-ID 的实体不参与逻辑」，而它们都有 TXS-ID ⇒ 会晤/检索会串档。改用 §D5 映射 |
| **B. 新建 FGEntityExtractorService**（T009/T010 初稿） | 违反第十四条(2)「唯一合法引擎」+ 不变量 #7 |
| **C. 删除密级/基因码/legacy_ids**（T010 初稿） | 与第九条/第五条/第八条直接抵触 |
| **D. 物理删除 void 节点 + 空 dossier 节点**（T009 初稿） | 与第十一条「只增不删」抵触；改为标记 + 边清理 |
| **E. 保留旧词表"只补 DEFS"** | 补齐后仍有 6 处实现，漂移会复发（2026-08-25 已复现一次）；必须派生化 |
| **F. 一次性大改** | 现有 1003 个新节点在持续写入；必须先停服定基线，再分 Phase 落地 |

## 四、后果

**正面**
- 关系类型新增只改一处；会晤与普通模式档案一致；读取不再破坏数据。
- 法律要求的密级/分户/编号溯源真正生效（从"纸面条文"变成"可校验"）。
- 观察区不再蓄水：不达标的名字根本不写 nodes。

**代价 / 风险**
1. **Phase 4 是高风险停服窗口**：candidate→placeholder、void→archived、flat→dossier 三类迁移同时做，
   必须双库备份 + 72h 回滚（第三十九条）。
2. **删除 `integrateFromEntity` 的逐句写档案分支**会影响会晤身份实时更新 ⇒ Phase 2 必须先上 PAE 定时，
   观察一段时间（新旧并行）再切。
3. **密级接入会改变现有可见性**：当前所有档案都是密级 1，默认全可见；接入后需要为已有节点补密级，
   否则可能误拦。迁移规则：`X/A` 类与亲密字段 → 3，职场类 → 2，其余 → 1。〔需业主确认〕
4. **法律内部不一致**（第二十五条要求 `relationMap`，第十九条把它归档）⇒ 本规范暂保留 `relationMap`，
   建议业主按第三十七条行使解释权后统一修订法律。

## 五、验收判据

见《FG 结构规范 V1.0》附录 D（6 条），核心是：**写入被断言拦住、读取不改数据、
会晤与普通模式字段一致、密级越权不可见、迁移后 integrity ok 且 `social_group_genes` 非空率 100%**。
