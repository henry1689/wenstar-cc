# T002 实现视角评估

> 所有结论均来自**代码实读**。凡未能实测者已标注「待实测」。

## 零、对 R002 的回应：基线核对「各自只覆盖一半」

豆包 R002 的结论是「当前召回确实以单条 memory 为单位，对话组未成为召回基本单位」，证据取自 `meeting-recall.ts` 与 `retrieval-stage.ts:512/1157`。

**我核对到的情况**：`src/m4/retrieval/adapters/DialogGroupAdapter.ts` **已实现块级召回**，并注册进 `createDefaultRegistry`：

```ts
// src/m4/retrieval/index.ts:67-70
let _dgOn = true;
try { _dgOn = getRetrievalFusionConfig().enable_dialog_group_memory !== false; } catch {}
if (_dgOn) reg.register(new DialogGroupAdapter(deps.sqlite));

// src/config/retrieval-fusion-config.ts:128-129
enable_dialog_group_memory: true,   // 默认开
```

`DialogGroupAdapter` 做的事与 T002 Phase 2 任务 1 几乎逐条对应：

| Phase 2 要求 | 适配器实现 |
|---|---|
| 按 dialog_group 聚合召回 | 内层 `GROUP BY dialog_group_id` |
| 组级综合得分 | `density * 0.6 + calcium * 0.4` |
| 取 TOP N 组 | `ORDER BY matched_rows DESC, block_calcium_score DESC LIMIT ?` |
| 每组取代表性片段注入 | `TEXT_ROUNDS = 6` 轮正文拼 `hit.text` |
| 块级钙化参与排序 | `block_calcium_score` 已进 ORDER BY |

**决定性的一步**：`createDefaultRegistry` **确有主链路调用**，但位置是：

```ts
// src/webui/chat/retrieval-stage.ts:346-359
// 🔴 统一检索中枢接入：会晤场景也走 SearchOrchestrator 多路并行 + RRF 融合
const _reg = createDefaultRegistry({ sqlite: _sqlite as any });
_reg.register(new MeetingWallAdapter(_sqlite as any));
const _orRes = await _orchestrator.runSearch(_reg, {...});
```

全仓 `createDefaultRegistry` 的调用点**只有这一处，且位于会晤模式分支内**。

### ⇒ 修正后的准确基线

| 模式 | 召回单位 | 块级召回 |
|---|---|---|
| **会晤模式** | SearchOrchestrator 多路 + RRF（含 DialogGroupAdapter） | ✅ **已接线**（`runSearch` → `runAllAdapters` 遍历全部注册适配器，已实读确认） |
| **普通模式** | 三槽位 memories 单条排序（`:512`/`:1157`） | ❌ 未接入 |

**所以 Phase 2 不是「从零改造」，而是「把已建好的块级能力接入普通模式，并补齐组级生命周期」。**

**待实测**：会晤模式召回结果里是否真的出现过 `domain='dialog_group'` 的 hit（取决于 `buildSqlClause(ctx.policy)` 的户籍过滤与数据存在性；会晤调用传 `policy: { enforce: false }`）。

## 二、Phase 1 是真缺口，但四项必须先定

`block_summary` 全空属实。**另有一条**：`DialogGroupAdapter` **没读 `block_summary`**（它用 `narrative_tag` 与 `block_calcium_score`）。摘要生成后必须同步改适配器让它参与检索/注入，否则写进去没人用。

1. **生成时机**：闭组时同步会阻塞流程，建议**异步队列**，允许「摘要未生成」的组正常检索。
2. **成本与容错**：679 组 × 1 次 LLM，需**限流 + 断点续传**。
3. **质量验收**：抽样 10 偏少，建议 ≥30 且覆盖三种闭组原因（topic_switch 626 / meeting_exit 30 / idle_timeout 15）。
4. **与 `narrative_tag` 的关系**：补充还是替代？并存会导致检索口径分叉。

## 三、Phase 3 的数据库风险被低估

- **sql.js 内存库会覆盖离线改库**——必须**杀掉整条进程链**后迁移，只停一个进程不够。
- 迁移脚本必须幂等，迁移前备份。
- **`event_state_40d` 组级聚合规则未定义**：40D 是消息级向量，组级取首条/末条/均值/质心？直接影响回放保真度，建列前必须定死。
- **`content_hash` 覆盖范围未定义**：组内原文后续补充或勘误会导致哈希失配，需明确「对哪一版快照」。

建议拆成「加列（低风险）」+「回填（高风险）」，回填必须停服窗口。

### C：PAE 缓存区止血（业主选定方案 a）

1. **`source` 不再存对话原文**（`ProfileAcquisitionEngine.ts:724`）：

```ts
// 现状（泄漏源，实测 57% 的 pendingItems.source 含对话原文）
const source = `${options.source || 'conversation'} | ${field.evidence.substring(0, 80)}`;

// 改为：来源标识 | 时间 | 证据哈希
const source = `${options.source || 'conversation'} | ${new Date().toISOString()} | ev:${sha256Hex(field.evidence).slice(0,8)}`;
```

- `field.evidence` **保留用于评分**（`:540-544` 的 `evidenceScore` 依赖它），仅改存库方式
- 不需要给 `acquire()` 加参数；追溯用哈希回查 `conversations`（低频操作）

2. **`_isValidPendingValue` 补 source 通道 + 语义判据**：当前只收 `value` 且判据是格式特征（换行/括号/特定词开头），导致 source 57%、value 16% 泄漏。

3. **缓存区生命周期：未确认超 30 天淘汰**（业主 2026-10-18 定 N=30 天）。

4. **存量清理**：1789 条 pendingItems，已确认 0 条；按新判据重审后精确清理（对话原文类直接清，需业主确认清单后执行）。
