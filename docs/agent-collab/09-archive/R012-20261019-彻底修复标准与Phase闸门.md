# 业主裁决：彻底修复标准 + Phase 闸门机制

## 一、业主态度

表哥明确：**铁了心要彻底修好，不接受半成品，不接受留隐患。**
理由：隐患留到后面，Phase 2/3 一动代码又翻出来，改来改去把程序改乱。

本文件将"彻底"量化为可执行标准，所有 Agent 必须遵守。

## 二、彻底修复的五条铁律

### 铁律1：根因必须挖到代码层，不接受"现象级修复"

- 每个 issue 必须回答：**哪段代码、哪一行、什么逻辑导致了这个问题？**
- 不接受"可能是""应该是""大概率"——必须读到源码确认
- 反例：I003 最初归因"件1未落盘"就是现象级，I004 挖到 _rebuildMemoryAnchors() 的主键覆盖才是根因
- 正例：Claude 用 aw_input 前缀指纹定位重建器特征，一击命中

### 铁律2：修复必须加防复发机制，不接受"修了这次就行"

每个修复必须同时包含：
1. **修复代码**（解决当前问题）
2. **回归测试**（覆盖触发场景，防止以后改坏）
3. **运行时自检/告警**（问题再发生时能被发现，而不是静默失败）
4. **文档记录**（根因+修复方案写进 ADR 或 issue，后人能查到）

缺任何一项 = 不彻底，验收不通过。

### 铁律3：验证必须全量+独立，不接受抽样+自证

- **执行者不能自己验证自己的改动**——必须由另一方独立验证
- 关键数据校验必须**全量扫描**，不是抽样（如：锚点归属要查全部1975条，不是抽30条）
- 验证结论必须标注**判据来自哪段代码/哪个SQL**，不允许用未经验证的假设当排除证据（I003教训）

### 铁律4：已知问题必须当场解决，不允许"留到后面"

- 发现问题 → 当场修 → 当场验证 → 当场关闭
- 除非：问题影响面评估后确认不阻塞当前Phase，且记录在案并有明确处理计划（写进03-issues/）
- "以后再说""先这样吧""不影响使用" = 不允许

### 铁律5：Phase 闸门——当前Phase不彻底关闭，不进下一Phase

每个Phase结束前必须通过**闸门检查**：
- [ ] 该Phase所有03-issues/已关闭
- [ ] 所有修复都有回归测试
- [ ] 全量验证通过（不是抽样）
- [ ] 防复发机制已上线
- [ ] 文档/ADR已更新
- [ ] 豆包按D002五维验收通过

**闸门不过 = 不进下一Phase。** 宁可在当前Phase多花一轮，也不带病前进。
