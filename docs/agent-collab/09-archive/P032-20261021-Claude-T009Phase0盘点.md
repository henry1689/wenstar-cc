### 1.3 另外两套「状态词表」

- `PERSON_STATUS` 枚举只有 **active / dormant / archived**（RelationshipTypes.ts，3 态），
  且全仓只有 **HWG（死路径）** 在用（HumanWorldGraph.ts:142,148,234）。
- FG 实际使用 **6 态**：active / candidate / dormant / archived / void / deceased，
  全部是裸字符串。状态机（§三）不在枚举内 —— **类型系统完全看不见真实状态**。

### 1.4 结论

- 业主要的「统一格式和规范」在关系层不是补 7 种，而是**要确立单一真源**：
  `RELATION_TYPE_DEFS` 为唯一字典，其余词表**派生或启动断言 ⊆ DEFS**。
- 现存代码中未定义类型合计 **20+ 个**（含 6 个反向目标、`sister_of/brother_of`、`lover_of`、
  `lives_in/residence_of/has_appearance`），比 T008 初判的「7 种」更大。
- `lover_of` 是**正式身份**口径（RelationLabels.ts:40 注释，业主 2026-10-06 定音），
  必须在 Phase 1 补进 DEFS，不能当垃圾类型删除。

### 2.3 为什么会「空壳化」——三个结构性原因

1. **写入源萎缩**：四条写入路径只剩 PAE 存活（PI P032 §一），而 PAE 一次只写 1–3 个字段。
2. **V6 替代无迁移**：旧数据在 `imageTraits/personalityPrefs`；会晤读取只认 `selfProfile` ⇒
   32% 的人有形象数据但会晤看不到（P031 P0-1）。
3. **`buildDossierFromFlat` 本身有缺陷**（FamilyGraph.ts:4829-4878）：
   - `basicInfo.education = profile.occupation`（职业写进学历，:4833）
   - `gender/birthYear` 恒 undefined（:4832）⇒ 落库 `JSON.stringify` 后为 `{}`
   - 结果：1009 个 person 有 `dossier` 键，但**有效 basicInfo 只有 28 个**。

### 2.4 结论

dossier 不是「设计太复杂」，而是**写得更少、读得更少**的双萎缩：
- Phase 1 统一结构时应**以实际读路径为准**保留字段，而不是照抄 10 模块；
- `imageTraits/personalityPrefs` 与 `selfProfile` 必须二选一（或定优先级合并），并写一次性迁移；
- `boundDocuments/memoryAnchors` 属于「有消费方、无产出」——保留结构，Phase 2 补写入触发。

## 三、状态生命周期状态机

### 3.1 设计（唯一真源：`shared/StatusRules.ts`）

```
                  ┌──────────── 90 天无活动 ────────────┐
   active ────────┘                                    ▼
       ▲                                          dormant
       │  <90 天有活动                                   │ 365 天
       └────────────────────────────────────────────────┤
                                                        ▼
                                                    archived（终态）
   candidate ──── 30 天无活动 ────▶ void（终态，回收）
   任意 ────（读路径/每日扫描）────▶ 同规则
   deceased / archived / void ──── 不自动变更
```
阈值：`DORMANT_AFTER_DAYS=90`、`ARCHIVE_AFTER_DAYS=365`、`CANDIDATE_EXPIRE_DAYS=30`
（StatusRules.ts:16-26）；`_judge.verdict==='noise'` 的 candidate 豁免自动回收（:58-62）。

### 3.2 触发点（全量）

| 触发 | 位置 | 语义 | 现状 |
|---|---|---|---|
| **读路径降级** | FamilyGraph.ts:4526 → `_checkStatusDowngrade` :4531-4557 | 任一 `getPersonProfile*` 都可能改状态；**void 时删边** | ⚠️ 破坏性读（P031 P0-4） |
| 每日批量 | LifecycleManager.ts:42-111 | 全量扫描 + 流转 | ✅ 已接线（DailyMaintenanceScheduler.ts:158-161） |
| 每日 household | FamilyGraph.ts:1228-1266 | dirtyNames + placeholder + lifecycle + pending 过期 | ✅ 已接线 |
| 候选晋升 | FamilyGraph.ts:2990-3075 | 证据分 ≥3 + 强上下文/称谓 + 准入闸门 | ✅ 在写路径内 |
| 候选终审 | EntityTriageService → `applyJudgments` | 梦境 LLM 判 noise；**保守策略=只提升，噪声仅标注** | ✅ 已接线（server.ts:725-744） |
| 占位升级 | `promotePlaceholders` :1320-1385 | `entity_source: placeholder→real`（不改 status） | ✅ |
| 手动 | `setEntityStatus` :1875 / LifecycleManager:120 | 人工流转 | ✅ |
| 存量迁移 | migrateToV4 :1149 | 空 status → candidate | ✅ 每次启动 |

### 3.3 实测：状态机在跑，但观察区在「蓄水」

- 日志：`DailyMaintenance` 811 行、`FGMaintenance` 68 行、**`[Lifecycle]` 转换 0 行**、
  `观察区超期回收` 0 行。
- 原因不是没跑，而是**没有可回收的**：992 个 candidate 的最后活动时间**全部在 2026-10**；
  >30 天且未豁免的仅 **16 个**（>90 天 10 个，无时间戳 4 个）。
- 观察区入口是 M4 的 RAG 提取：`M4Orchestrator.ts:286 → integrateFromEntity`，
  L3 弱名字直接 `candidate`（FamilyGraph.ts:2190-2205）。日志累计 **1600 次**
  `[FG Candidate] L3 进观察区`。近 10 天新增 **1003 个 person**，几乎全是 candidate。
- 代码里已有实证记录（:3059-3063）：**498 个 candidate 中 497 个是纯裸提及**，
  active 97 个里 72 个（74%）是同一路径产出的高频词垃圾。
  ⇒ 「观察区」实际退化为**高频词计数器**，晋升通道极窄（需强上下文/称谓），
  只能等 30 天到期转 void。

### 3.4 三个结构性风险

1. **读路径与回收路径共用 `_checkStatusDowngrade`**：一次普通档案读取就可能删边（P0-4）。
2. **到期集中爆发**：当前 992 个 candidate 集中在 10-11～10-21 创建，
   30 天后（11 月中旬）会**在同一天附近批量 void 并删边**；若期间有待确认的真人，
   会被无差别回收（豁免只认 `_judge=noise`，而多数 candidate 没有终审标记）。
3. **维护对象错位**：`FGMaintenance` 每日维护的是 `hwg_persons/hwg_relations`
   （FGMaintenance.ts:55-78），而 HWG 四表 **0 行** ⇒ 「自生长维护」对主库 FG 零作用。
   真正对 FG 生效的只有 `LifecycleManager` 与 `runDailyHouseholdMaintenance`。

## 四、基因码 / 圈层 / 安全密级：三者的设计意图与死因

三者都在 `6ac709b`（2026-07-19，V4.0 户籍管理体系）一次性引入。

### 4.1 基因码（family_gene / social_group_genes）

- **设计意图**：V3.3/V4「双轮 BFS 全量分配」——家族连通分量 → `FAxx`，社交组 → `CO/SC/BUxx`
  （FamilyGraph.ts:1537-1653）；建边时增量继承/追加（:2414-2459）。
- **实现状态**：每次启动 `migrateToV4 → _rebuildGroupGenes` 全量重算（:1155）。
- **实测**：`family_gene` 15 人 / 3 族；`social_group_genes` 非 `WW` 18 人 / 2 个值。
  与图结构**一致**：家族边端点去重 14、CO 边端点去重 18。
- **未接线原因**：不是 BFS 坏了，而是 **`acquaintance_of`（1024 条，77%）不分配任何组码**，
  1008 人只靠 acquaintance 相连 ⇒ 基因码对 99% 的人为空。读取方只有
  `householdOf/socialGroupsOf`（server-household-routes.ts:182-183）。
- **附带**：`migrateToV4` 每次启动全量重算并写库，是启动耗时与写放大来源之一。

### 4.2 圈层（circle_level）

- **设计意图**：V2.0 圈层等级 1–5（`autoAssignCircle` 按 `DEFAULT_BASE_INTIMACY` 推算，
  FamilyGraph.ts:7096-7121）+ 批量分配（:7124-7140）。
- **实测**：`circle_level` **1076/1076 全 0**；`autoAssignCircle` /
  `batchAutoAssignCircles` **全仓 0 调用**；唯一读取是调试路由（server-family-routes.ts:139）。
- **死因**：V2.0 迁移只建了列与算法，**从未接入任何启动/维护/写路径**。
- 设计文档中圈层只在架构规划里出现（docs/architecture-optimization-plan.md:86-171），
  没有落到实现。

### 4.3 安全密级（security_level）

- **提交声称**：`6ac709b`「UUIDGatekeeper V4.0 …… **security_level 密级接入**」。
- **实际实现**：当时的读取是 `UUIDGatekeeper._checkSecurityLevel(memory)`，
  读的是**记忆记录的 `memory.security_level`**，不是 `nodes.security_level`
  （`git show 6ac709b -- src/m4/household/UUIDGatekeeper.ts` 第 280 行）。
- **现状**：该方法在 `d0ab7d5`（V10.0-V10.5）被移除；当前 `UUIDGatekeeper` 只按
  三层 UUID 白名单过滤，**不读任何密级**。
- **FG 节点列**：`security_level` 只在建表/建节点/“我”节点写入（FamilyGraph.ts:755,974,984,1044），
  **全仓 0 处读取**。
- **结论**：这是「错位接入」——密级概念在 **记忆域** 成立，被误当成 **节点域** 字段；
  Phase 4 应删除 `nodes.security_level`，若需要密级，应在记忆/检索域单独定义。

### 4.4 三者对照

| 字段 | 设计意图 | 实际接线 | 建议 |
|---|---|---|---|
| family_gene / social_group_genes | 家族/社团分群 | BFS 有，读取仅 2 个 dashboard 方法；77% 的边不覆盖 | 要么把 acquaintance 纳入分群，要么废弃 |
| circle_level | 圈层优先级/隐私 | 列 + 算法，零调用，全 0 | 废弃（除非 Phase 1 明确用途） |
| security_level | 数据密级 | 错位到记忆域，节点列零读取 | **删除节点列**；密级归记忆域 |
