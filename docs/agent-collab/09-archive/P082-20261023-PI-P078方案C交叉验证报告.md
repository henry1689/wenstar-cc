## 三、🔴 发现的真缺口：R1 恢复路径漏开门卫（P080 未列）

**现象**：`chat.ts:483` 恢复路径只调 `markRestoreFromSnapshot()`（采素材），**未调 `beginMeetingSideEffects` 或等价的 `gatekeeper.startMeeting(uuids)`**。EntityMeeting.ts:465 的 startMeeting 是正常 WAKE 路径开的，恢复路径绕过它。

**影响定性**（经 UUIDGatekeeper 逐层核实）：
- base 白名单仅「我+玉瑶」（server.ts:829-834）；恢复后 sessionEntities 为空；
- M4Orchestrator.filterMemories（:138）→ `_isUuidVisible`：会晤实体的带 UUID 记忆 → 不在 base → **被拦（fail-closed）**；
- **方向是「少召回」不是「泄漏」**（与 I007 串档方向相反），但会晤中重启恢复后，实体自有记忆在 M4 记忆通道召不回——P078 修纪要时同路径的第二个「恢复绕过采集」缺口（P080 §三自述这是第二次同路径遗漏，此为**第三处**）。

**修复建议（给 Claude，一处改动）**：`chat.ts:483` 处恢复活跃会晤时补开：
```ts
if (ctx._groupSession.active) {
  ctx._entityMeeting?.markRestoreFromSnapshot();
  // 补：恢复路径的门卫（与 beginMeetingSideEffects 的门卫半边对称；素材半边已由上行采集）
  const _st = ctx._groupSession.getState();
  ctx._entityMeeting?.beginMeetingSideEffects(
    _st.participants.map(p => p.name).join('、'), _st.participants.map(p => p.uuid));
}
```
（beginMeetingSideEffects 本身会重采素材——与 markRestoreFromSnapshot 重叠无害；或单开一个只开门卫的入口更干净。）

**不阻塞 commit**：该缺口在路径B（会晤中重启）才触发，路径A 已实测通过；可修完再提，或先提后补（任务2 复测路径B 时一并验证）。
