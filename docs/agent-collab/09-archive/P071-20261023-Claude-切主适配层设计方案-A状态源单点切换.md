## 一、S1 摸底结论

### 1.1 `_meetingEntityName` 的唯一汇聚点

```ts
// chat.ts:612 —— V15 编目 L1 点
const _activeMeetingName = ctx._entityMeeting?.isActive() ? ctx._entityMeeting.getEntityName() : null;
```

**这一行是切主的咽喉**：改它，下游 14 点传播（V15 probe 编目 L0–L13）全部跟着变，
而 20 个文件消费的是 `_meetingEntityName` / `meetingEntityUuid` 这些**派生值**，
**它们不关心来源** → 切主对下游透明，这 20 个文件**不用改**。

### 1.2 chat.ts 中 EntityMeeting 的调用点（14 处，已按类型分组）

| 类型 | 行号 | 调用 |
|---|---|---|
| **状态判定** | 830 / 831 / 832 | `detectIntent(msg, names, _em.isActive(), alias)`、`_em.isActive()`、`_em.isMultiParty()` |
| **状态写入** | 844 / 853 / 890 / 926 / 930 / 950 | `enterMulti` · `enter` · `exit`(async, **含纪要**) · `addParticipant` · `switchTo`×2 |
| **状态派生** | 612 / 866 / 889 / 934 / 949 | `_activeMeetingName` · `getEntityName`×3 · `getEntityUUID` |
| **非状态（保留）** | 820 / 2819 | `recordTurn('user'/'assistant')` —— 纪要数据源 |
| **推断** | 948 | `inferSpeaker(message, aliasMap, llm)` |

### 1.3 EntityMeeting 的三类职责

- **状态**（GroupSession 已覆盖）：enter/exit/switchTo/addParticipant/isActive/isMultiParty/getParticipants/getEntityName/getEntityUUID/getState
- **门卫**（`gatekeeper`，6 处调用）：`startMeeting(name, uuids)` / `addSessionEntity(uuid)` / `clearSessionEntities()`
  —— **只吃 uuid/name，不依赖内部状态对象** ✅
- **纪要**（`minutesStore`，1 处 `generateAndStore`）+ `_multiTurns` 轮次累积

### 1.4 门卫与纪要**不依赖内部状态** ⇒ 切主可行性确认

门卫 6 处调用的入参全部是 uuid/name（可从 GroupSession 的 participants 派生），
纪要由 chat.ts 的 `recordTurn` 直接喂内容。**这一条是方案 A 成立的前提。**

## 二、方案 A 设计

### 核心

> **换状态源，不搬全部职责**：状态判定与写入全部改走 GroupSession；
> EntityMeeting 降级为「门卫/纪要的副作用执行器 + 轮次采集器」。

### 四组改动

**① 汇聚点（1 处）— `chat.ts:612`**

`_activeMeetingName` 改由 GroupSession 派生：`speakerUuid` → `participants` 查 `name`，
并保留 `isActive(gsState)` 作前置判定。

**② 状态写入（6 处）→ `gs.dispatch`**

| 现调用 | 改为 |
|---|---|
| `_em.enter(name)` | `gs.dispatch({type:'WAKE', targets:[...], slot})` + 触发门卫 `startMeeting` |
| `_em.enterMulti(names)` | 同上，targets 多个 |
| `_em.exit()` | `gs.dispatch({type:'LEAVE'})` + 触发纪要生成 + 门卫清理 |
| `_em.addParticipant(n)` | `gs.dispatch({type:'JOIN', target})` + 门卫 `addSessionEntity` |
| `_em.switchTo(n)`（×2） | `gs.dispatch({type:'SPEAK', target})` |

**③ 状态判定/派生（7 处）→ 从 `gs.getState()` 派生**

`isActive`/`isMultiParty`/`getEntityName`/`getEntityUUID`/`detectIntent` 的 `inMeeting` 参数。

**④ 保留不动（3 处）**

`recordTurn`×2（纪要数据源）、`inferSpeaker`（发言人推断；GroupSession 侧的 `speakerResolver`
是替代品但语义不同 —— 粘性/LLM兜底，`inferSpeaker` 含待办归属逻辑，**本次不换**）。

### 门卫/纪要接线：用已有的 `onEffect`

chat.ts 已订阅 `participantJoined/participantLeft/speakerChanged`（PI 的 R1）。
追加两个：
- `meetingStarted` → `gatekeeper.startMeeting(...)`（名字与 uuid 列表从 effect 的 `uuids` + participants 派生）
- `meetingEnded` → 纪要生成 + `gatekeeper.clearSessionEntities()`

> 这样做的好处：**副作用跟随状态变更的单一入口**，而不是散在调用点 ——
> 与 P057「埋点放 dispatch 唯一调用点」是同一条原则。

### 回滚

关 `WS_GROUP_V2` → 分支一行不执行 → 走原 EntityMeeting 路径（该路径**一行未删**）。
代码回退 = `git revert`（已推送，可远程 revert）。

## 三、🔴 阻塞点：`recordTurn` 依赖 `_meeting`（需裁决）

```ts
// EntityMeeting.ts:347
recordTurn(role, content, speakerName?): void {
  if (!this._meeting?.isMulti) return;              // ← 依赖状态字段
  const speaker = speakerName || (role === 'user' ? '鸿艺' : this._meeting.entityName);  // ← 依赖状态字段
  this._multiTurns.push({...});
}
```

`isActive()` 同样是 `this._meeting?.active === true` —— **EntityMeeting 的所有状态判定都挂在这个字段上**。

切主后若 `_meeting` 不再被维护，`recordTurn` **直接 return** → `_multiTurns` 断流 → **多人会议纪要丢失**。

**影响面已缩窄**：`if (!this._meeting?.isMulti)` 意味着**单人会晤本来就 no-op** —— 只有**多人会议**的纪要受影响。

### 三个解法

| | 做法 | 评价 |
|---|---|---|
| **A1（推荐）** | 改 `recordTurn` 签名，把 `isMulti`/`speakerName` 由调用方从 GroupSession 派生后传入 | ✅ 判定源与状态源一致，**真正单一真源**；需改 EntityMeeting 的方法签名 + chat.ts 两处调用 |
| A2 | GroupSession 的 effect **反向同步** `_meeting` 字段（仅供纪要用） | ⚠ 改动最小，但字面上是「状态双写」，与硬约束② 撞字面；需明确声明 `_meeting` 降级为「纪要缓冲区」而非状态源 |
| A3 | 把 `_multiTurns` 迁出 EntityMeeting，建独立纪要采集器 | 彻底，但改动扩大，**已偏向方案 B** |

**推荐 A1**：它让 `recordTurn` 的判定来源与状态来源一致（都来自 GroupSession），
比 A2 少一个隐式镜像，比 A3 少搬一个模块。

### ✅ 裁决结果（2026-10-23，业主）：**采用 A1**

> 「A1 改 recordTurn 签名（推荐）」

**授权改动面**：可修改 `src/m4/household/EntityMeeting.ts` 的 `recordTurn` 方法签名
（旧架构文件的方法签名，非状态逻辑），以及 chat.ts 的两处调用（`:820` / `:2819`）。

设计要点（落码时实现）：
- `recordTurn(role, content, speakerName?)` → 由调用方把 `isMulti` 与 `speaker`
  从 **GroupSession 派生后传入**，方法内不再读 `this._meeting`
- `_multiTurns` 累积逻辑、200 轮截断告警**一字不改**
- `this._meeting.entityName` 的取值改由调用方从 GroupSession 的 `speakerUuid` →
  `participants` 查得后作为 `speakerName` 传入
- **不改** `enter/exit/switchTo` 等状态方法的签名（它们在切主后不再被状态路径调用）
