## 二、🔴 真库探针抓到的缺陷（本次最值得记的一条）

单测**全部通过**的前提下，真实生产库只读探针实测：

```
[RetrievalV11] 围栏 SQL 失败（fail-closed 返回空）domain=conversation: near "COALESCE": syntax error
逐条核过=12 命中=0 命中率=0.0%
```

**根因**：`DOMAIN_SPECS` 中 `memory` 与 `conversation` 两域的 `extraWhere` 少了开头的 `AND`，
拼出 `... IN (?,?) COALESCE(...)` 直接语法错误 ⇒ 围栏全量 fail-closed 返回空。

**为什么单测发现不了**：围栏单测用的是假 db，只做子串断言（`expect(sql).toContain('belong_entity_uuid IN')`），
SQL 结构错了照样过。

**教训（已固化为回归断言）**：任何拼 SQL 的模块，必须有**结构性断言**（断言拼装结果的 WHERE 段形态），
不能只断言子串；且**必须在真实库上探针实测**。

修后真库复测：**退化窗口 12 条样本 12/12 = 100% 命中**。

## 六、两个 harness 缺陷（已定位根因，建议 harness 自检）

1. **DS-23 恒判「共性底层通用修复」**：`DelegateReviewer.extractS2Classification()` 扫的是**整份
   `global_memo`**，而 harness 自己注入的全局架构铁律里就含「共性底层」四个字
   （`data/memos/*_memo.md:61,65`）⇒ **任何提交都会被判成 common**。随后要求 memo 里出现
   「横向关联模块清单」或 ≥2 个 `src/...ts` 路径，而铁律模板写的是裸 `chat.ts`（无 `src/` 前缀），
   `hasFileList` 恒 false。**本次绕法：把横向清单与 ≥2 个 `src/...ts` 路径写进
   `s2_evidence.approved_plan`**（该字段会渲染进 memo）。
2. **DS-21 CK-10 要求显式意图标记**：S2 方案中必须出现 `bug_fix / feature / refactor` 字样，
   否则「无法识别修改意图类型」。本次在 `approved_plan` 首行加
   `【本次修改意图类型：refactor】` 后通过。

**已知操作失误（如实记录）**：签 S6-B 时用 `head -1` 抓待确认单，误签了**其他会话**的旧单
`ck_12cd048dd10d84d4`（属 `run_mvpmryvj_mq6u`，2026-10-26）。该动作是只增审计、撤不回。
本次正确单为 `ck_2f2c8ea642440726`（同一 `change_key`）。
**教训：签任务单前必须先按 `run_id` 定位，不得用 `head -1` 取第一个。**
