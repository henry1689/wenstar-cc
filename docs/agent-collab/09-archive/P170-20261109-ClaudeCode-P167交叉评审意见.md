## 一、逐条回答 Q1–Q6

### Q1 · 99.7% 认不认？八项按二分法怎么归？

**结论：数字量级可保留，定义必须改写；“10 条 suppressed 合法排除”不成立。**

#### 1.1 为什么“99.7% 召回守恒”不成立

P167 §一 的表格：

| PI 列 | 数值 |
|---|---|
| 总数 | 7,140 |
| ① 硬过滤后 | 7,112 |
| 差额 | **28** |
| 文中列出的排除项 | 23 test + 8 过期 + **10 suppressed** |

- 10 条 suppressed 在**当前数据**中全部为 `namespace='default'`、`valid_until_ms=NULL`（逐行核对，见附录 A），不可能被 `namespace<>'test'` 或过期条件排除；
- 7,140 − 28 = 7,112 只能由「23 test ∪ 8 过期」凑出（28 = 23 + 8 − 3 重叠），**没有给 suppressed 留位置**；
- 代码侧（独立复核）：
  - `grep lifecycle_state|suppressed src/webui/chat/retrieval-stage.ts` → **0 命中**；
  - `grep lifecycle_state src/m4 --include=*.ts | grep -v __tests__` → 仅 `DialogGroupAdapter.ts`（作用于 `dialog_groups.archived` 降权，不是 `memories`）；
  - `MemoryRetriever` / `meeting-recall` 各槽 / `sweepAllStores` / `recall-bus` 均无 `lifecycle_state` 条件。
- 因此：**P167 的数字是对的，文字错了**——它把“我有 10 条 suppressed”写成了“它们被合法排除”，而数据与代码都表明它们仍在候选池里，只是钙化 0、强度 0.096，排序时靠后。

> P169 §二 说“P167 §一.① 称 10 条 suppressed 均为合法排除”——**我确认这一冲突，判 P168 正确、P167 文字需修订。**
> 另：P167 的“23 test”在当前库中已无法复现（`007` 名下 `namespace='test'` = **0**，见附录 A），请 PI 提供当时的守恒 SQL；这不影响 suppressed 结论，但影响“99.7%”的精确分母。

#### 1.2 八项按“是否属于存储链路”二分

| 归类 | P168 项 |
|---|---|
| **属于存储链路**（写入/落盘/归属/存活/溯源/完整性） | #1 未来时间戳（未复现，若有则属存储）· #2 归属（存储）· #3 重复（存储卫生）· #4 黑钻无源（存储溯源）· #5 FK 孤儿（存储完整性）· #7 memory_entities 索引（存储辅助索引）· #8 ADR-020/021 写入治理 · 测试残留 199（写入卫生） |
| **不属于存储链路**（可达性 / 召回规则 / 实现账实） | **B 素材包层级与包内预算（可达性）** · #6 suppressed 不过滤（召回规则缺失，不是“存储不守恒”）· 21 条 knowledge 新 FK（存储完整性，但由知识关联产生） |

**一句话**：99.7% 就算成立，也只是“存储层基本健康”；**它不能推出“召回守恒”**，更不能用来关闭可达性缺陷。

### Q2 · A（199 条测试残留）与 B（素材包假绿）实质是不是 ⑤⑥⑦ 可达性？

#### A. 测试残留 199 条 —— **不是 15 条名额问题；是数据卫生 + 一处分类错误**

事实链：

1. **15 条上限的位置与作用域**：`retrieval-stage.ts:886` 的 `if (_injectedMems >= 15) break;` 位于会晤实体记忆循环 `for (const _em of _rankedMems)` 内，只数 `_rankedMems`（`memories` 的实体分层召回），**notes 不经过该循环**。
2. **notes 的实际入口**：
   - `NoteAdapter`（`memory_type='note' AND is_valid=1`，用**整句 message** 做 `LIKE`）注册在 `createDefaultRegistry`，会晤分支经 `SearchOrchestrator` 进入候选；
   - `formatHit` 对 `note` 输出 **`💭 content`**，而 `recall-bus` 的 `TIER_MATCHERS` 把 **`💭` 归为 `group`**（见 `recall-bus.ts:99`）；
   - 深度证据层（`collectDeepEvidenceFragments`）的 notes 用 `memFragWithTime('记事', …)` → **`【记事·MM-DD】`**，而批7新增的 `^【(?:档案|记事)】` 是**锚定匹配**，时间后缀使其**匹配失败** → 回落默认 `sand`。
3. **所以**：199 条测试 note 不会被算进 15 条实体记忆名额；它们**只在与消息原文子串命中时**（如 `roundtrip-test-123`、`XXXX`）进入候选，并因 `💭` 被误归类为 `group`，与真实对话组争 group 层名额。

**我的判定**：A **不是** ⑤⑥⑦ 断层的“另一种表现”，而是：
- 数据卫生问题（199 条本不该入库）；
- 以及**分类器依赖格式化文本的脆弱性**（`💭` 同时代表 note / conversation / 低钙 memory / dialog group，天然不可区分）——这一条与 B 同根，属实现缺陷。

它**可能**挤占 group 层（低概率），但不挤占 15 条 top15；实际触发概率取决于用户消息恰好包含测试串，接近 0。**分级 P2（数据卫生）/ P1（分类器结构改造的一部分）**。

#### B. 素材包整包归 `other` —— **是可达性，但不是 top15 名额**

事实链：

1. `runRecallBus` → `applyGate`：非向量候选按 G1 下限放行（`recall-bus.ts:217-245`）；
2. `applyTierFloors`：`other` 是 **passthrough**，`selected = [...passthrough, ...selected]`，**不占 `budget.total`**（`recall-bus.ts:168-210`）；
3. 因此深度素材包（`DEEP_PACKAGE_HEADER + lines + CRYSTAL_DIRECTIVE`，一个字符串、以 `【深度回忆素材包】` 开头 → `DIRECTIVE_FRAGMENT_RE` → `other`）**必定被注入**，不会被 15/16 条记忆名额挤掉；
4. 真正的问题在**包内**：
   - `organizeForQuestion` 按“关键词命中数 → 时间”排序，**不看层级、不看钙化、不看价值**；
   - `buildSweepBudget()` 的字符预算（`maxChars=6000`）会把包内靠后的黑钻/高价值内容**整条跳过**（`organizeForQuestion` 的预算逻辑是 `continue`，不是截断）；
   - `applyTierFloors` 看不到包内条目，**diamond 保底对包内黑钻完全无效**，`diamond=0` + `层保底缺口=2` 是必然结果。

**我的判定**：B **是可达性问题，但层面是“包内排序/预算”，不是“top15 名额”**。它会导致：
- 高价值黑钻在包内被后置或被预算跳过 → 进不了 LLM 上下文；
- 指标假绿（`diamond` 永远 0，保底缺口永远报）；
- 与 P167 的 ⑤⑥⑦ 同属“从候选到注入的损失链”，但**不是同一个环**。

**修正后的统一表述**：
- A ≈ 数据卫生 + 分类器脆弱性（P2/P1）；
- B ≈ 包内可达性 + 指标失真（P1）；
- P167 ⑤⑥⑦ ≈ 候选生成/slot 排序/注入上限（P0，PI 车道）。

### Q5 · 终审验收：双靶子还是账实核对？

**结论：分层，最终终点是“体验/双靶子 + 守恒监控”，账实核对是准入门禁，不是终点。**

| 层 | 门 | 频率 | 作用 |
|---|---|---|---|
| G1 存储/实现账实 | P168 式核对（归属/编码/存活/实现=设计） | 每次改动/每日 | **准入门禁**：不过不允许谈召回 |
| G2 真实话题可达 | P167 双靶子（固定题目集、固定实体、旧/近/关系三类覆盖） | 每次发布 | **终审验收**：用户问得出来才算 |
| G3 守恒监控 | P167-D（每日抽 N 条写入记忆造查询 + 实召率/零召回趋势） | 持续 | 早预警，防复发 |

理由：
- **只用账实**：会出现批7 那种“测试全绿、用户仍召不回”（假绿）；
- **只用双靶子**：样本小、可被挑题，且看不出存储/归属的慢性损失；
- **分层**才能让“能不能召回”与“数据是否还在”各自有判据，且不互相掩盖。

建议把术语固定下来，后续报告只允许写四种数：
1. **存储守恒**（写入成功且完整）；
2. **候选资格**（通过硬过滤）；
3. **注入可达**（进入 prompt 的片段）；
4. **实召**（`recall_count>0` / 用户答复命中）。
P167 的 99.7% 属于第 2 类，7.7% 属于第 4 类，不能混写。

### Q6 · 批7 假绿，根因是不是验收方法本身？

**是，而且是同一类问题的第三次出现。** 具体：

- 批7 单测 `recall-bus.test.ts` 验证的是 `classifyFragmentTier('【金库黑钻·11-09】…') = diamond`（**单独片段**）；
- 生产实际形态是 `DEEP_PACKAGE_HEADER + 多行 + CRYSTAL_DIRECTIVE`（**整包一个字符串**），`classifyFragmentTier(整包) = other`；
- 测试测的是“设计意图中的输入形态”，生产喂的是“真实组合后的形态” → 测试绿、指标不变。

**验收方法改造（建议列为项目硬约束）**：

1. **生产形态夹具**：所有涉及“容器/多行块”的改动，单测必须至少有一个**整包形态**输入（如 `DEEP_PACKAGE_HEADER + 一行金库黑钻 + 一行砂金 + CRYSTAL`），断言最终 tier 与 selected 文本；
2. **阶段契约测试**：断言上一阶段的真实输出（`retrieval-stage` 返回的 fragments → 分类 → 注入），而不是只测纯函数；
3. **线上探针 + 指标前后**：每次声称修复，必须附一条真实查询的生产日志（如 `diamond 0→N`、`shortfalls` 清空），否则不算完成；
4. **结构化优先**：`RecallCandidate` 在源头携带 `tier`（adapter domain 决定），文本正则只作兼容兜底——从结构上消灭 `💭`/时间标签/整包三重歧义；
5. **容器守卫**：若一个片段以指令头开头且内部含分层标签，测试应直接失败，逼开发者显式声明“整包属于哪一层、内部如何排序”；
6. **文档同理**：修订必须同步正文结论（P167 顶部已改、正文未改，就是文档层的假绿）。

## 五、建议的统一纲领（硬约束）

1. **四层定义**：存储守恒 / 候选资格 / 注入可达 / 实召，四个指标分开报，任何报告必须标注属于哪一层。
2. **生产形态验收**：验收必须跑生产用的组合路径与真实形态数据；单测只作前置，不单独构成验收。
3. **结构化优先**：层级不能再从格式化文本（`💭`/时间标签/整包）用正则唯一推断；源头携带 `tier`，正则为兜底。
4. **容器显式化**：任何多行/整包片段必须声明内部条目的层级与预算规则；禁止“整包 other + 内含分层内容”的隐式形态。
5. **文件单写者**：同一文件同一时间一个 Agent；交接 commit；共享工作树禁止 stash/add -A。
6. **数据红线**：删除/召回规则变更必须停服窗口 + 整库/行级备份 + 业主授权；能过滤就不删。
7. **指标前后**：每项修复必须附生产日志/指标的前后值；没有指标变化的“修复”不算完成。
8. **文档一致**：顶部修订必须同步正文关键结论，否则文档本身即为账实不符。
