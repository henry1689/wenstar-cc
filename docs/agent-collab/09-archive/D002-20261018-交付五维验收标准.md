# 交付五维验收标准

> 用户（表哥）2026-10-18 裁决：所有 Agent（Claude Code / PI / 豆包 等）交付任何任务，必须通过以下五维验收，缺一不可。未通过 = 未完成。

## 五维标准

### 1. 落实：是否真正按商讨方案执行？
- [ ] 代码/数据改动与任务书、评审、决策文件一致
- [ ] 没有静默降级、打折扣、偷换概念
- [ ] 关键设计决策（如双通道召回、只增不删）没有被绕过
- [ ] 如有偏离，必须事先写进 03-issues/ 并经用户裁决

### 2. 达标：是否达到验收标准？
- [ ] 任务书里的验收清单逐项打勾
- [ ] 实测数据达标（如摘要生成率≥95%、召回率提升等）
- [ ] 编译通过、测试通过
- [ ] 抽样人工验收通过（如 Phase 1 要求≥30组、五类闭组原因全覆盖）

### 3. 可靠：是否防复发？
- [ ] 有对应的回归测试（红用例锁住已修复缺陷）
- [ ] 有代码守卫/断言，防止同类问题重新引入
- [ ] 不是"打补丁"，是架构性修复
- [ ] 同类问题全仓库扫描，没有遗漏

### 4. 兜底：失败时怎么办？
- [ ] 有回滚方案（数据库备份、代码 revert 路径）
- [ ] 失败时有明确的错误处理（不是静默失败）
- [ ] 关键路径有降级策略（如摘要生成失败→原文-only召回，不崩）
- [ ] 数据库改动在停服窗口内执行，执行前备份

### 5. 维护：后续怎么管？
- [ ] 有巡检/监控（如定时检查摘要生成失败率、UUID覆盖率）
- [ ] 有告警阈值（如CRITICAL告警触发条件）
- [ ] 有文档（ADR/法典/代码注释同步更新）
- [ ] 有日志（关键操作可追溯）

## 豆包的把关职责

豆包（MainAgent）代表用户执行五维验收：
1. 每个 Agent 交付后，豆包按五维逐项核查
2. 不通过的，写进 03-issues/ 要求整改
3. 通过的，写进 05-decisions/ 标记完成
4. 定期巡检（用户要求时），检查已交付项是否持续达标

## 不通过的处理

- 任一维度不通过 → 任务状态保持 in-progress，不算完成
- 连续两次不通过 → 升级到用户裁决
- 严禁"先交付后补"——兜底和维护必须和功能同时交付

## 适用范围

本标准适用于 WenStarOS 所有开发任务，包括但不限于：
- T002 A/B双链路建设（Phase 1-5）
- P0止血遗留项
- 法典/ADR修订
- 任何代码/数据/文档变更
