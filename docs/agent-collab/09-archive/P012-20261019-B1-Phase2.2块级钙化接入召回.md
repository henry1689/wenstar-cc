## 三、方案（待确认）

**① `DialogGroupAdapter` 让钙分真正参与排序**
- 内层 SQL 改为取候选池 `limit × 5`，完整打分 `0.40/0.30/0.15/0.15` **只在 JS 一处算**（现公式在 `:188-192`）→ 消灭 SQL/JS 两套判据（P0-1 教训）
- 钙分归一 `/10` → **`/5`**（高钙阈值即满分）
- **兜底**：分数非数/NaN → 按 `last_ts DESC` 时间序 + WARN（D002 兜底4）

**② 真源函数 `highCalciumGroups()` 放 `m4/retrieval/meeting-recall.ts`**（与既有五路同文件，不另起第二实现）
- 条件：`entity_uuid` + `block_calcium_score>=5` + `summary_state='done'` + `block_summary NOT NULL` + `last_ts <= now-30min`（沉淀窗，已裁决）
- 排序：时间近因优先 + 钙分 tie-break（R016 原文「按时间近因注入」）

**③ 新适配器 `HighCalciumGroupAdapter`（独立 route `high_calcium_group`）**
- 独立 route ⇒ 独立配额，**不占 memories 槽位**
- **每轮话题相关性门**：候选用本轮 n-gram 对摘要+原文做命中校验，命中者全注入；**无命中按近因保底 1 条**（否则高钙组永远召不回，与「不遗忘」目标冲突）
- 注入形态 `【对话组·高钙·MM-DD】<三层摘要>`

**④ 接线**：`retrieval-stage.ts` 会晤分支独立计数注入 + `index.ts` 注册 + `retrieval-fusion-config.ts` 加 `budget.high_calcium_group_limit`（默认 3）

**防复发四件套**：回归测试（排序区分度 / 独立配额不挤 memories / 沉淀窗 / 降级时间序 / 保底1条）+ 启动自检（可召高钙数 vs 257）+ 本进度文件 + ADR-010 补节

### 落码过程中查出并当场修掉的 4 个问题

1. **注册表按 domain 作 key（一域一适配器）** —— 按 `dialog_group` 注册高钙路会**静默覆盖 B 链路的
   DialogGroupAdapter**（回归测试红）。解法：高钙路**不进注册表**，由会晤链路直接调用适配器；
   新增 domain 还得补 `backref.BACKREF_TABLE` 穷举映射（该文件不在豁免内，编辑被回滚），收益不成比例。
2. **无关键词判据时被压成「保底 1 条」** —— 那条规则本该只在「有判据但无人命中」时生效。
   改为三种情形：无判据→取满 limit；有判据有命中→只注入命中者；有判据无命中→保底 1 条。
3. **候选池只按近因取 `limit×5`** ⇒「重要但更早」的组进不了池子，相关性门形同虚设
   （实测 recall@3 41.4%）。加**相关性驱动补选**：在全部高钙组上按摘要 LIKE 补到 limit 条。
4. **相关者之间只按近因排** —— 加 **命中强度（Σ 词长）优先**，再近因、再钙分。
