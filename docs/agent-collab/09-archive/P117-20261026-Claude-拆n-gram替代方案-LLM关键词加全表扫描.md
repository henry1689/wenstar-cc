# P117 · 拆掉 n-gram 的替代方案设计

> 业主决策：**想办法拆掉 n-gram，用其他办法代替，比如 LLM。**
> 本方案按此设计，并回归 `docs/blueprint/变更台账_2026-07-27_search-engine.md` 记载的**原始架构意图**。

---

## 一、先确认原设计说了什么（不是我编的）

`变更台账_2026-07-27_search-engine.md:25-26` 原文：

> 锁定：**n-gram 本地初筛 + 自有 32D 语义向量精排** 混合方案。
> **n-gram 仅做前置围栏过滤，不参与最终排序**

⇒ **n-gram 的角色从一开始就只是"围栏"（缩小候选集），从来不负责相关性。**
⇒ 而现实代码 `meeting-recall.ts:640` 用 `ORDER BY COUNT(DISTINCT s.term) DESC` 排序，
**已偏离原设计**（让围栏承担了排序职责）。

**所以「拆掉 n-gram」在架构上不是倒退，是回归。**

---

## 二、决定性实测数据

| 方式 | 耗时 | 额外空间 | 每次落盘成本 |
|---|---|---|---|
| **全表 LIKE 扫描**（13,640 条 / 14.9MB） | **31–38 ms** | **0** | 0 |
| n-gram 索引查询 | 1 ms | **436 MB** | **+2.4 s**（3.72s vs 1.32s） |

**核心洞察**：
- 全系统真正需要检索的数据只有 **≈18 MB**（memories 14.9MB + 对话原文 3.0MB）；
- 却为此维护了 **436 MB 索引 —— 索引是数据的 24 倍**；
- 查询快 35 倍（1ms vs 35ms），但代价是**每次落盘多 2.4 秒**。
  在 LLM 生成需 8–13 秒的聊天场景里，**35 ms 完全可以忽略**。

⇒ **这不是"性能换功能"，是"用可忽略的查询延迟，换回 2.4 秒的落盘 + 83% 的空间"。**

---

## 三、替代方案（三层，逐层可选）

### 第 1 层：围栏替代 —— LLM 提取关键词 + SQL 扫描（替代 n-gram 初筛）

**n-gram 的职责是**：把 13,640 条缩小到几十条候选。

**替代做法**：
1. **LLM 一次性提取检索线索**（可合并在既有意图判定调用里，不额外增加一次 LLM 往返）：
   ```
   从用户消息中提取：关键词(3-5个) / 涉及实体 / 时间范围 / 主题
   例：「你还记得上次我们聊的模具交期吗」→ 关键词=[模具, 交期]，实体=徐诗雨
   ```
2. **SQL 围栏**（复用既有 `UUIDPoliceFilter` 归属闸门）：
   ```sql
   SELECT id FROM memories
   WHERE belong_entity_uuid IN (?)                  -- UUID 闸门（既有）
     AND (raw_input LIKE '%模具%' OR raw_input LIKE '%交期%')
   ORDER BY calcium_score DESC LIMIT 50
   ```
   实测单个关键词 **35 ms**，3–5 个关键词 **< 200 ms**。

**为什么可行**：数据只有 14.9 MB。**当全表扫描只要 35ms 时，为它建 436MB 索引是不经济的。**

### 第 2 层：精排替代 —— 回归原设计的"语义精排"，但不建 HNSW 也能做

原设计是「32D 向量精排」。当前 `perception_40d` 字段**有数据但从未建 HNSW、读写方全死**
（`DualHelixWriter.ts:7`）。两条路：

| 路线 | 做法 | 代价 |
|---|---|---|
| **2a. LLM 精排**（推荐先走） | 围栏后的几十条候选（每条几百字）一次性喂给 LLM，让它选最相关的 N 条并给理由 | 一次 LLM 调用，token 约 5–10k；可用便宜模型 |
| 2b. 向量精排 | 为候选几十条现算 40D 相似度（**不需要 HNSW**，几十条线性算即可） | 纯计算，无 I/O；需确认嵌入器可用 |

**2a 的优点**：与业主「用 LLM 代替」的指示一致，且**顺带获得可解释性**（LLM 能说出为什么相关）。
**2b 的优点**：零 LLM 成本，且 `perception_40d` 已有数据。

> 建议 **2a 先落地，2b 作为降本备选**——两者可并存，按开关切换。

### 第 3 层：完全不用索引后的召回质量保障

拆掉 n-gram 后必须守住的三件事：

| 保障 | 手段 |
|---|---|
| **不漏召回**（关键词没覆盖到的表达） | 围栏放宽：UUID + 时间窗 + 高钙化度作为**兜底候选池**，保证每轮都有候选 |
| **不串档** | 继续走 `UUIDPoliceFilter` 归属闸门（现状 99.2% 覆盖，天然可靠） |
| **不退化排序** | LLM 精排取代 `COUNT(DISTINCT term)`，且**原本那个排序就违反原设计** |

## 四、拆除范围与顺序（建议）

| 步骤 | 内容 | 风险 |
|---|---|---|
| **S1** | 停止**写入** `source_type='conversation'` 的索引（203 万行 / 66%）——先止血，不减功能 | 低（读侧仍能用旧数据；新数据无索引，但召回走新围栏） |
| **S2** | 新召回链路并行上线（LLM 关键词围栏 + 精排），**双跑对比**：同一批查询，旧路径 vs 新路径，对比召回结果 | 低（双跑不影响生产） |
| **S3** | 双跑达标后，切换默认链路到新路径，n-gram 降级为「异常兜底」 | 中（需切换开关 + 回滚预案） |
| **S4** | 观察期后，删除 `search_index` 表 + `indexDocument` 写入链路 | 中（不可逆，需备份） |
| **S5** | 库从 535MB 回落至 ~88MB；落盘 3.72s → 1.32s | — |

**关键**：S1 就能立刻止住膨胀（不再新增 2.4 秒/次的落盘成本），**不影响任何现有召回**。

## 五、与「补藤」的关系（你的 P1）

**两者互补，不冲突**：
- **补藤**（`entity_belong_id` 59% 空）⇒ 让**围栏的 UUID 闸门更准** ⇒ **新围栏方案效果更好**；
- 所以建议顺序：**先补藤 → 再做 S1/S2**，这样新围栏一上线就是高质量的。

## 六、需要你/豆包确认的 3 件事

1. **LLM 提取关键词的位置**：合并在既有意图判定里（省一次调用），还是独立调用（更清晰但多一次成本）？
2. **精排走 2a（LLM）还是 2b（40D 现算）**？我建议 2a 先行、2b 并行验证。
3. **S4 的删除时机**：`search_index` 表删除是否需要保留一份冷备文件？
