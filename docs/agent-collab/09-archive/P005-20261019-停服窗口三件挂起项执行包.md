## 🔴 执行环境铁律（我今天踩过两次的坑，务必读）

1. **本库是 sql.js**：必须用 node runner 读文件→exec→export 写回（参考
   `scripts/migration/p0-v3/run-p0-v3-cleanup.cjs` 模式），**不能用 sqlite3 CLI 直接改文件**
   （服务启动时 sql.js 全量载入会覆盖）。窗口内服务已停，仍须用 runner 保证 export 落盘。
2. **反斜杠转义坑**：`'\_ANCHOR' ESCAPE '\'` 在 **.sql 文件里**是正确形态（单反斜杠）；
   若把 SQL 内联进 **JS 模板字符串**，反斜杠会被 JS 吞掉 → 报 `ESCAPE expression must be
   a single character`。要么放 .sql 文件由 runner 读取执行，要么 JS 里写成 `'\\_ANCHOR' ESCAPE '\\'`。
   我今天两种形态各踩一次——dry-run 必须先跑通再 apply。
3. 每步执行前后打印受影响行数（`db.getRowsModified()`），与下方"预期数"核对。

## 件1：混合组锚点归属重写（预期 ~56 行，dry-run 实数为准）

**背景**：9b83428 已把锚点归属判据改为 conversations 多数决（结构性修复），但**存量**错配锚点
仍需重写。冒烟案例 = 天气窜记忆的 `DG_11824_ANCHOR`（错归阿珍，多数=玉瑶）。
预期从凌晨的 32 涨到 56：旧代码服务未重启期间又产生了混合组。**停服后不再增长，dry-run 实数即终值。**

```sql
-- dry-run（只 SELECT 核数，不改数据）：
WITH mixed AS (
  SELECT c1.dialog_group_id,
    (SELECT c2.belong_entity_uuid FROM conversations c2
     WHERE c2.dialog_group_id = c1.dialog_group_id
       AND c2.belong_entity_uuid IS NOT NULL AND c2.belong_entity_uuid != 'null'
     GROUP BY c2.belong_entity_uuid ORDER BY COUNT(*) DESC, MIN(c2.seq_pos) ASC LIMIT 1) AS majority
  FROM conversations c1
  WHERE c1.dialog_group_id IS NOT NULL AND c1.dialog_group_id != ''
    AND c1.belong_entity_uuid IS NOT NULL AND c1.belong_entity_uuid != 'null'
  GROUP BY c1.dialog_group_id HAVING COUNT(DISTINCT c1.belong_entity_uuid) > 1)
SELECT COUNT(*) FROM mixed m
JOIN memories a ON a.id = m.dialog_group_id || '_ANCHOR'
WHERE m.majority IS NOT NULL AND a.belong_entity_uuid != m.majority;

-- apply：
UPDATE memories SET belong_entity_uuid = (
  SELECT c2.belong_entity_uuid FROM conversations c2
  WHERE c2.dialog_group_id = substr(memories.id, 1, length(memories.id) - 7)
    AND c2.belong_entity_uuid IS NOT NULL AND c2.belong_entity_uuid != 'null'
  GROUP BY c2.belong_entity_uuid ORDER BY COUNT(*) DESC, MIN(c2.seq_pos) ASC LIMIT 1)
WHERE memories.id LIKE '%\_ANCHOR' ESCAPE '\'
  AND memories.belong_entity_uuid IS NOT NULL
  AND memories.belong_entity_uuid != (
    SELECT c2.belong_entity_uuid FROM conversations c2
    WHERE c2.dialog_group_id = substr(memories.id, 1, length(memories.id) - 7)
      AND c2.belong_entity_uuid IS NOT NULL AND c2.belong_entity_uuid != 'null'
    GROUP BY c2.belong_entity_uuid ORDER BY COUNT(*) DESC, MIN(c2.seq_pos) ASC LIMIT 1)
  AND EXISTS (
    SELECT 1 FROM conversations c3
    WHERE c3.dialog_group_id = substr(memories.id, 1, length(memories.id) - 7)
      AND c3.belong_entity_uuid IS NOT NULL AND c3.belong_entity_uuid != 'null');
```

判据与 `resolveAnchorOwnership` 完全同源（多数决 + 同数取 MIN(seq_pos) 最早轮）。
`substr(id, 1, length(id)-7)` 剥 `_ANCHOR` 后缀（不用 `replace`——防 id 内意外含同名串）。

**验证**：
- dry-run 数 == apply 的 getRowsModified（预期 56±，以实数为准）
- 复跑 dry-run == 0
- 抽查：`SELECT belong_entity_uuid FROM memories WHERE id='00005520261018003513M01MISC_DG_11824_ANCHOR'` → 应为 **TXS-000000001（玉瑶）**

## 件2：非锚点地标降级（预期降5683 / 留3491）

**判据**（= `isLandmarkWorthy` 逆命题，单一真源 `src/m2/MemoryLifecycleProtocol.ts`）：
保留 `calcium>=0.65 OR reinforcement>=1.5 OR (recall>=3 AND strength>0.5)`，其余降级。
**锚点行豁免**（`id LIKE '%\_ANCHOR'`）：锚点=闭组情感峰值浓缩，地标语义成立且与
重启重建行为一致（重建路径硬编码锚点 is_landmark=1，豁免使二者不冲突，无需解锁 SQLiteAdapter）。

```sql
-- dry-run：
SELECT 'current_total' k, COUNT(*) v FROM memories WHERE is_landmark = 1
UNION ALL SELECT 'keep_anchors', COUNT(*) FROM memories WHERE is_landmark = 1 AND id LIKE '%\_ANCHOR' ESCAPE '\'
UNION ALL SELECT 'keep_worthy_non_anchor', COUNT(*) FROM memories WHERE is_landmark = 1
  AND id NOT LIKE '%\_ANCHOR' ESCAPE '\'
  AND (COALESCE(calcium_score,0) >= 0.65 OR COALESCE(reinforcement_accumulator,0) >= 1.5
       OR (COALESCE(recall_count,0) >= 3 AND COALESCE(effective_strength,0) > 0.5))
UNION ALL SELECT 'downgrade', COUNT(*) FROM memories WHERE is_landmark = 1
  AND id NOT LIKE '%\_ANCHOR' ESCAPE '\'
  AND NOT (COALESCE(calcium_score,0) >= 0.65 OR COALESCE(reinforcement_accumulator,0) >= 1.5
       OR (COALESCE(recall_count,0) >= 3 AND COALESCE(effective_strength,0) > 0.5));

-- apply（只降级，不动锚点，不动数据内容）：
UPDATE memories SET is_landmark = 0
WHERE is_landmark = 1
  AND id NOT LIKE '%\_ANCHOR' ESCAPE '\'
  AND NOT (COALESCE(calcium_score,0) >= 0.65 OR COALESCE(reinforcement_accumulator,0) >= 1.5
       OR (COALESCE(recall_count,0) >= 3 AND COALESCE(effective_strength,0) > 0.5));
```

**预期数**（01:0x 实测）：当前地标 9174 → 保留 锚点1963 + 优质非锚点1528 = **3491**；降级 **5683**。
**验证**：apply 后 `SELECT COUNT(*) FROM memories WHERE is_landmark=1` == dry-run 的 keep_anchors+keep_worthy；抽样 `SELECT id, calcium_score, recall_count FROM memories WHERE is_landmark=1 AND id NOT LIKE '%ANCHOR' LIMIT 5` 全部满足 worthy 三路之一。

## 件3：修订——从"窗口内"改为"窗口外代码任务"（需确认）

原计划把「SQLiteAdapter 锁定文件两处」列入窗口。实测后**修订如下**：

- **3a 重建路径 is_landmark=1 硬编码 → 不需要改了**。件2 的锚点豁免使"锚点=地标"成为显式政策，
  重建硬编码与政策一致。修它反而制造运行期/重启期不一致。
- **3b ANCHOR 覆盖降级（重启重建用全零向量+截断文本覆盖运行期优质锚点，10-16实测108条被覆盖）
  → 仍需修，但它是代码改动**（重建时保留原行 perception_40d 若非零），在 SQLiteAdapter 锁定文件内，
  需 Sentinel 解锁 + Harness 全流程——**不适合塞进停服窗口**（窗口内改代码+验证风险高）。
  ⇒ 建议：窗口照常执行常执行①②③④⑤；3b 作为独立代码任务排期（PI 或 Claude 认领，需解锁协调）。
  已知代价：本次窗口重启时，运行期锚点的 40D 向量会再次被重建覆盖为全零（既有行为，非本窗口引入），
  3b 修完后的下次重启才固化。

**此项修订需豆包/表哥确认**（R008 原把"SQLiteAdapter解锁"列入窗口顺序）。
