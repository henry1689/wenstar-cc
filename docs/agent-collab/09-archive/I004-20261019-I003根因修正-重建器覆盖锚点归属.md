# I003 根因修正：重建器覆盖，不是 SQL 未落盘

## 一、结论先行

**件1 的 SQL 确实落盘了，是重启时 `_rebuildMemoryAnchors()` 把结果覆盖掉了。**

R010 采用的「件2成功、件1失败 ⇒ 差异在件1语句本身」这一推理不成立：
两条 UPDATE 在同一事务、同一次 `export()` 落盘中执行，件2 能落盘，件1 没有理由单独失败。

## 二、硬证据（生产库只读实测）

| 观测 | 结果 | 含义 |
|---|---|---|
| 锚点总数 | 1975 | — |
| `raw_input LIKE '【核心·%'` 的锚点数 | **1973 / 1975** | 重建器写入的锚点带 `【核心·实体名】` 前缀；运行期写入是 `【核心】`。⇒ **几乎全部锚点都是启动时重建的** |
| 56 个错配锚点中，`raw_input LIKE '【核心·%'` | **56 / 56** | 所有错配锚点都出自重建器，不是运行期写入 |
| 重建后 created_at | 取自 conversations.first_ts | PI 用「created_at 全是原始时间」排除重建覆盖——但重建器正是用 `firstTs` 写 created_at，**该证据无法排除重建** |

## 三、重建器为什么必然写错

`src/m2/SQLiteAdapter.ts::_rebuildMemoryAnchors()`：

1. 先 `DELETE FROM memories WHERE id LIKE '%_ANCHOR'`（每次启动全删）；
2. 查询按 **`GROUP BY dialog_group_id, belong_entity_uuid`** 分组 —— 一个混合组会产生 **多行**（每个归属实体一行）；
3. 循环里 `const id = dg + '_ANCHOR'` —— **所有行用同一个主键**；
4. `INSERT OR REPLACE` ⇒ 后写的覆盖先写的；
5. 行的顺序是 `ORDER BY dg.belong_entity_uuid` ⇒ **最后一个 UUID 字典序最大的实体获胜**，与多数决无关。

⇒ 每次重启，混合组的锚点归属都会被「字典序最大的 UUID」重写一次。
⇒ **migration v21 在 `migrateSchema()`（initialize 第 456 行）执行，重建器在第 749 行执行 —— v21 无论怎么写都会被覆盖。**

## 四、影响面（比 I003 报告的更大）

| 项 | 数量 |
|---|---|
| `dialog_groups.belong_entity_uuid` 与多数决不一致 | **179** 组（不是 56） |
| 其中已有摘要 | 88 组 |
| 这些组的 `search_index(source_type='dialog_group')` 行 | **27,613 行** |

注意：56 是「锚点最终归属 ≠ 多数决」的组数；179 是「对话组归属本身 ≠ 多数决」的组数。
两者不同源于重建器的 UUID 字典序巧合——有的组字典序最后恰好等于多数决。

## 五、修正后的方案（两步，缺一不可）

### 第一步：migration v21（Claude 执行，MigrationManager）

只修**不由重建器覆盖**的数据：

1. `dialog_groups.belong_entity_uuid` → 多数决（179 组）
2. `search_index` 中 `source_type='dialog_group'` 的归属列 → 同步为新归属（27,613 行）

不重置 `summary_state`：摘要正文来自 conversations 内容，与归属无关；只需同步索引归属，
无需重新消耗 LLM。

### 第二步：修重建器（必须，否则每次重启回退）

`_rebuildMemoryAnchors()` 的分组查询改为**每组只取多数决归属**：

```sql
WHERE dg.belong_entity_uuid = (
  SELECT c2.belong_entity_uuid FROM conversations c2
  WHERE c2.dialog_group_id = dg.dialog_group_id
    AND c2.belong_entity_uuid IS NOT NULL AND c2.belong_entity_uuid != 'null'
    AND (c2.is_test IS NULL OR c2.is_test = 0)
  GROUP BY c2.belong_entity_uuid
  ORDER BY COUNT(*) DESC, MIN(c2.seq_pos) ASC LIMIT 1
)
```

这与已修复的 `resolveAnchorOwnership`（conversations 多数决 + 同数取最早轮）是同一判据。

**该文件是 `src/m2/SQLiteAdapter.ts`（高风险、Sentinel 锁定），且与 PI 认领的 3b（ANCHOR 覆盖降级：重建时保留原行 perception_40d）在同一函数。**
建议：**并入 3b 一次 flow 完成**，避免同文件双人编辑。
