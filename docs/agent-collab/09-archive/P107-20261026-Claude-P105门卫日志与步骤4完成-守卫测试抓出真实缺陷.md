## 二、🔴 步骤4 守卫测试：26 用例，**实测抓出步骤3-c 的真实缺陷**

这正是步骤4 的价值 —— 缺陷不是推断出来的，是**跑测试跑出来的**。

### 缺陷：同一个人的回复会出现两遍

| 环节 | 发生了什么 |
|---|---|
| 1 | `ASK_ALL` 把**当前发言人**也入队（P094 裁决①：含当前发言人，一律全答） |
| 2 | 而 `WAKE` 首位**就是**当前 speaker |
| 3 | ⇒ 首轮对队头 `dispatch SPEAK` **必然命中** reducer 的「同人切换 = 无变化」守卫 ⇒ **返回原引用、队列不减** |
| 4 | ⇒ 首轮返回的 `askAll.queue` 仍含已答者 |
| 5 | ⇒ 调用层再让他答一次 ⇒ **A 的回复出现两遍** |

测试用例直接实测到第 3 步：
```ts
const s0 = inAskAll();
const s1 = reduce(s0, speak(A.uuid));   // A 就是当前 speaker
expect(s1).toBe(s0);                     // 🔴 返回原引用 = 纯 no-op，队列压根没动
```

### 修法（`03d1f75`）

在 chat.ts 拼装 `askAll.queue` 时按 `speakerUuid` **过滤掉本轮已答者**；过滤后为空则不发 `askAll` 字段（调用层循环 0 次，与非 askAll 场景同路径）。

**没有动 reducer、没有动 SPEAK 语义** —— 「同人切换 no-op」是**正确的既有设计**（它保护重复切换不产生假 `speakerChanged` effect），且设计稿 §1.1 明确反对给 `SPEAK` 塞队列标记。`ChatResponse.askAll` 的注释本就写着「剩余未答者」，本次是**让实现与已声明契约一致**。

## 三、守卫测试覆盖清单（26 用例，纯状态机，零 LLM/网络/DB/时钟依赖）

| 组 | 断言 |
|---|---|
| ASK_ALL | 全量入队含当前发言人（裁决①）/ 顺序 = 参与者顺序 / 空参与者 no-op / 单人也可入队 |
| SPEAK | **同人 = no-op**（原引用）/ 异人只出队不清空 / 逐人推进每步只减一格 / 非参与者不动队列 |
| JOIN | 队列空时加人**不入队**（防幻觉全员提问）/ 队列非空时追加队尾 |
| LEAVE | 移除离开者 / 非队列成员不动 / **散会清空** |
| WAKE | 清空队列（防上一场会晤残留被带进新会晤） |
| 纯函数性① | 不修改入参（JSON 快照逐字节比对） |
| 纯函数性② | 同输入必得同输出（可重放） |
| 纯函数性③ | 返回新对象而非原引用 |
| diffEffects | 空→非空派生一次 / 非空→非空不派生 / 非空→空不派生 |
| 向后兼容 | `schemaVersion` 与常量一致（**不 bump**）/ 旧快照补 `[]` / 含非参与者**整份拒绝** / 序列化往返 |
| 开关回滚 | 不派发 ASK_ALL ⇒ 队列恒空 ⇒ 循环 0 次 |
| 派生不冗余 | 入队出队不改变 `mode`/`isMulti`/`isActive`（队列不参与派生） |

> 其中 **SPEAK 同人 no-op** 这条用例就是抓出上面缺陷的那条。
