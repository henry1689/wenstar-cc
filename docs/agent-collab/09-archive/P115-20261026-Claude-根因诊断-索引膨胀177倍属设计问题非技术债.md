# P115 · 「为什么这么大、为什么持续膨胀」根因诊断

回答四个问题：**① 为什么这么大 ② 为什么持续膨胀 ③ 是设计还是技术债 ④ 有必要这样设计吗、怎么化解**

---

## 一、一句话根因

> **索引方案选了「字符级滑动窗口 n-gram」，导致 3 MB 原文被放大成 535 MB 索引（177 倍）；
> 且 conversation/memory 两类索引**没有任何删除路径**，索引生命周期与主数据完全脱钩** ——
> 前者是**设计问题**，后者是**技术债**。二者叠加 = 既大又持续膨胀。

---

## 二、数字证据（全部实测，非估算）

### ① 原文 vs 索引

| 项 | 实测值 |
|---|---|
| conversations 全部文本合计 | **3.0 MB** |
| 对话平均长度 / 最大 | 222 字 / 17,315 字 |
| **search_index 占用** | **535.4 MB** |
| **放大倍数** | **≈ 177×** |

### ② 机制：`buildNgrams`（SearchIndexBuilder.ts:30）

```ts
// 2-gram
for (let i = 0; i < cleaned.length - 1; i++) ngrams.add(cleaned.substring(i, i + 2));
// 3-gram
for (let i = 0; i < cleaned.length - 2; i++) ngrams.add(cleaned.substring(i, i + 3));
```

长度 N 的文本 ⇒ 约 **2N 个 n-gram**（N-1 个 2-gram + N-2 个 3-gram）。
一条 222 字对话 ≈ 444 项；实测去重后 **142 项/条**（`Set` 去掉了重复 gram，符合）。

### ③ 索引构成

| source_type | 索引行数 | 占比 | 对应主表 | 每条索引项 |
|---|---|---|---|---|
| **conversation** | **2,026,776** | **65.9%** | 14,295 行 | **142** |
| dialog_group | 693,923 | 22.5% | — | — |
| memory | 302,242 | 9.8% | 13,591 行 | 22 |
| knowledge_base | 49,953 | 1.6% | — | — |
| black_diamond | 4,297 | 0.1% | — | — |

总 3,077,117 行；DISTINCT source_id 16,722；DISTINCT term **688,036**。

### ④ 顺带排除的两个误判

- **不是碎片**：freelist 仅 19 页（0.07 MB / 0.0%）⇒ **VACUUM 无效**；
- **不是 memories 条数多**：memories 全部 70 列合计仅 **14.9 MB**（1.1 KB/行）
  ⇒ P112 P0-1「删到 500 条」**既触红线、也无效**（见 P114）。

## 三、回答「是设计问题还是技术债」

**两者都有，但主次分明：**

### 🔴 设计问题（主因）—— 空间模型选错了

字符级滑动窗口 n-gram 的代价是 **O(N) 空间 + 每 gram 一行 SQLite**。
`indexDocument` 里是 **每 gram 单独一条 `INSERT OR REPLACE`**，无事务批处理：

```ts
for (let pos = 0; pos < ngrams.length; pos++) db.run(`INSERT OR REPLACE INTO search_index ...`);
```

⇒ 一条 222 字对话 = **140+ 次独立 SQL 写入**。
这正是「**单次落盘 14s 阻塞事件循环**」的直接成因（P112 §一 归因到「SQLite 膨胀」，
实际是「**索引写入次数**」而非「记忆条数」）。

### 🟡 技术债（次因）—— 索引生命周期与主数据脱钩

全仓 `DELETE FROM search_index` 只有两处，且只覆盖：
- `knowledge_base`（KnowledgeEngine.ts:568/590）
- `dialog_group`（MigrationManager.ts:911/974 —— 且是**迁移脚本**，非常规清理）

**`conversation`（66%）与 `memory`（9.8%）没有任何删除路径** ⇒
主记录删除/归档后索引永久残留 ⇒ 孤儿索引持续累积 ⇒ **持续膨胀**。

### 🟢 还有一项：写入重复

日志可见 `[SQLiteAdapter] ♻️ writeMemory 去重拦下重复记忆` 与
`[Persist] ⚠️ 写后验证：助手轮未落库`，说明存在重复写入尝试
（主数据侧有去重防护，但索引侧仍在追加）。

## 四、灵魂拷问：「有必要这样设计吗」

**没有。有更省的等价方案，且本仓已经具备其中之一。**

字符级 n-gram 的唯一价值是**中文任意子串匹配**（中文无空格，不能靠空格分词）。
但为此付出 177 倍空间 + 每条 140 次写入，**性价比极低**，而且：

1. **SQLite 原生就有 FTS5 + `trigram` tokenizer** —— 专门解决「CJK 任意子串匹配」，
   索引由 C 引擎构建（一次批量、紧凑存储），空间与写入成本都远低于手工 n-gram。
   手工实现等于**重造了一个更差的 FTS5**。
2. **本仓已有 40D 向量语义检索通道**（`perception_40d`、`findByEmotionalSimilarity40D`），
   大部分「找相关记忆」需求本就该由语义检索承担，字面子串匹配只是补充。

> 即：**当前设计用 177 倍成本，实现了 SQLite 免费自带、且性能更好的能力。**

---

## 五、怎么化解（分层，按「不删有用信息」原则）

### 第 0 层：立刻可做、零风险（纯性能，不改语义）

| 动作 | 收益 |
|---|---|
| **索引写入改事务批量**（BEGIN/COMMIT 包住一条文档的全部 gram） | 140 次提交 → 1 次；**直接消除落盘阻塞**，与索引体积无关 |
| **孤儿索引清理**（先出数字再决定） | 安全，主数据一行不动 |

> 仅做第 0 层就可能让「14s 阻塞」消失 —— **因为阻塞来自写入次数，不是体积**。

### 第 1 层：结构性化解（需豆包选型，改变检索行为）

| 方案 | 说明 | 代价 |
|---|---|---|
| **A. 迁移到 FTS5 + trigram** | SQLite 原生，CJK 任意子串，批量建索引 | 需迁移与回填；检索 API 适配 |
| **B. 降级索引粒度** | 只索引摘要/话题标签，不索引全文 | 子串召回变弱，但 40D 向量检索可补 |
| **C. 索引冷热分离** | 近 N 天在线，历史归档独立库按需挂载 | 复杂度中等，历史召回变慢 |

**我倾向 A**：语义等价、收益最大、且是「用平台能力替掉自造轮子」。

### 第 2 层：根治（无论选哪条都必须做）

- **索引与主数据同生命周期**：删除/归档 conversation、memory 时**同步删其索引**；
- 写入侧去重与主数据侧对齐（避免重复索引追加）。

### 明确不做

- ❌ **删除 memories 到 500 条**（P112 P0-1 原案）—— 既触业主红线，又只占 9.8% 索引、无效（详见 P114）；
- ❌ **VACUUM** —— 碎片仅 0.07 MB，无效。

## 六、请裁决

1. **第 0 层我可否立即做**（事务批量 + 孤儿清理）？零语义风险，且可能直接解决阻塞。
2. **第 1 层选 A/B/C**？我建议 A（FTS5 trigram），但需豆包确认检索行为变更可接受。
3. P112 P0-1（GC 删记忆）**建议撤回或改为上述疏导**——它无法解决 66% 的 conversation 索引。
