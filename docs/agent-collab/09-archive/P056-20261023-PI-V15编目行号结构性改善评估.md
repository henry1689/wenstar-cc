# P056 - V15 编目行号结构性改善评估（P055 任务2）

## 一、现状机制（已核实）
- `chat.ts:392` 的 `MEETING_PROP_POINTS` 数组用**硬编码行号**（`line: 753` 等）标注 14 个 `_meetingEntityName` 传播点。
- `meeting-prop-points.test.ts` **已有 14 个 PROBES 特征串**（如 `'dna.entity_genes.push'`），判据是"声明行号那行的源码必须含该 probe"。
- 漂移根因：任何在某点之前的编辑把行号推偏，编目自身不报错 → 只能在 S5 闸门发现（已第五次漂移）。

## 三、三方案评估

### 方案A：特征串定位（catalog 存 probe，运行时解析行号）
- **改动**：catalog 字段 `line: number` → `probe: string`（+可选 `occurrence` 消歧序号）；测试用 `src.findIndex(l => l.includes(probe))` 定位，替代硬编码行号。
- **收益**：**根治漂移**——行号不再是断言对象，编辑推偏后自动重定位，永不漂移。测试侧 PROBES 已就绪，成本低。
- **L1/L10 消歧**：加 `nth`（第 N 次出现）或更长 probe。L10 本质是"主点 vs 旧路径"两点，可拆为两个 probe 或用 `occurrence`。
- **风险**：低。probe 失效（代码重构改了特征串）时会明确报"找不到 probe"，比行号漂移信号更精准。
- **推荐**：**✅ 首选**。12 点直接换，L1/L10 加消歧参数。

### 方案B：保持行号 + 自动校准脚本
- **改动**：写脚本重新 grep 校准行号，CI 或 pre-commit 触发。
- **收益**：改动小。
- **缺点**：**治标**——行号仍是脆弱真源，每次编辑都要跑校准；校准脚本本身依赖特征串（等于绕一圈还是回到方案A的特征串，却多维护一个脚本）。**不推荐**。

### 方案C：废弃编目，运行时动态检测
- **改动**：删除 catalog，运行时反射/AST 扫描传播点。
- **收益**：无静态清单可漂移。
- **缺点**：chat.ts 是重量级模块，运行时扫描成本高；且编目本身是 S4/DS-06 **人工评审基准**（承载 desc/via 语义），纯动态检测丢失这层文档价值。**不推荐**。

## 四、结论与建议
- **推荐方案A（特征串定位）**：12/14 点可零消歧直接换 probe；L1 用 `occurrence` 或加长 probe；L10 拆主点/旧路径两 probe。根治第五次漂移的结构性问题，测试判据（PROBES）已存在，实施成本低、风险低。
- **不急于实施**（遵 P055 §三 任务2 "给出评估结论和建议，不急于实施"）：本报告仅评估。若业主批准，PI 可实施（改 catalog 字段 + 测试定位逻辑 + 14 点校准，预计单文件改动，tsc=0 + 现有测试全绿）。
- **影响面**：仅 `chat.ts`（catalog 定义）+ `meeting-prop-points.test.ts`（定位逻辑）两文件；不影响运行时行为（编目纯文档/测试用，运行时零消费）。

## 五、遗留说明
- 本评估在**当前工作区**（含 Claude 批A/B/C 未提交改动）基础上做，14 点行号取当前值。若后续 chat.ts 继续变动，方案A 天然免疫（probe 自动重定位），这正是其价值。
