## 二、🔴 本批的结构性发现：旧实现不是「没选择」，是「没有这个能力」

`src/m5/SceneAnchor.ts` 此前**只有 `resetAnchor()`（归零），没有任何 setter**。

```ts
export function getAnchor(): SceneAnchor { return { ..._anchor }; }   // 只有读
export function resetAnchor(): void { ... }                            // 只有归零
```

⇒ **结构上就无法「恢复现场」**。这解释了为什么旧实现只能归零：不是设计者想丢基线，
而是模块压根没有写回入口。批C 新增 `setAnchor()`（与 `getAnchor()` 对称）才使恢复成为可能。

## 三、时序正确性（本批最核心的论证，错了就是「压了但立刻被覆盖」的假货）

chat.ts 每轮的真实顺序：

```
:831   enter()                 ← 状态机
:947   影子投影（批B 位置）      ← 【采样点】此刻模块单例仍是玉瑶现场
:2502  orchestrate()           ← M5Orchestrator:63 每轮 extractAnchor 用会晤内容覆盖单例
下一轮 :947                      ← 单例已是实体现场
退出轮 :868 exit() → :947 LEAVE  ← 【恢复点】恢复后本轮 M5 才跑
```

- **压栈时机安全**：`:947` 处单例仍是玉瑶现场（本轮 M5 还没跑），采样不会采到会晤污染；
- **弹栈时机正确**：退出轮恢复后，`:2502 orchestrate` 才用恢复后的玉瑶现场生成回复。
  旧代码做不到——它在 `:855` 归零，且位置在 `exit()` **之前**；
- 同理 `:947` 恢复 `_currentRole` 正好赶在 `orchestrate` 之前，因此能修缺陷③。

> 若时序判断错了，批C 会变成「压了栈但下一轮就被覆盖」的假货 —— 表面绿灯、实际无效。
> 这是本次摸底最花时间也最值钱的一处。

**为什么桥接要单独一层**：`SceneAnchor`/`ContextMemory` 都是**模块级单例**，读写是副作用操作，
而批A 建立的不变量是 `sessionReducer`/`project` **零 IO 纯函数**。把副作用混进纯函数层
等于亲手拆掉那个不变量，故隔离在 `contextBridge.ts`，chat.ts 只在开关分支调用。

**`applySlot` 对空槽拒绝写回**：写回空锚点等于把现场抹成白板 —— **比不恢复更糟**，
会直接复现缺陷②的症状。已单测锁定。

### ② `typeof NaN === 'number'` 让 NaN 溜进情感槽

`normEmotion` 原用 `typeof s.pleasure === 'number'`，**NaN 能通过**（`typeof NaN === 'number'`）。
一个 NaN 进槽会污染后续所有算术（夹逼、加权、40D 计算）且极难定位。已改为 `Number.isFinite` 判据。
