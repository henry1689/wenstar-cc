## 一、P0-2 `_meeting` 状态管理审计

### 🔴 缺陷① 多人会晤不持久化 → 重启永不恢复

`saveLastMeeting()` 全文件**唯一调用点是 `EntityMeeting.ts:200`（`enter()` 内）**。

| 入口 | 是否写持久化 | 后果 |
|---|---|---|
| `enter()`（单人） | ✅ `:200` | 正常恢复 |
| `enter()` 自动升级单→多人分支（`:168-186`） | ❌ 不写 | 升级后的多人会晤重启丢失 |
| **`enterMulti()`（`:220-252`）** | ❌ **不写** | **多人会晤重启后 `restoreLastMeeting()` 读空 → 永不恢复** |
| `switchTo()` 多人叠加分支（`:320-340`） | ❌ 不写（且改了 `entityName`） | 重启恢复到**旧主名实体**，当前发言人错位 |
| `switchTo()` 单人分支 | ✅ 经 `exit()`→`enter()` | 正常 |

### 🔴 缺陷② `restoreLastMeeting()` 的持久化清除失败会永久劫持

`exit()` 的 `DELETE FROM engine_store` 包在 `try/catch` 内（异常仅 `console.warn`）。
一旦清除失败，记录**永久残留**且**无时效校验**（`saveLastMeeting` 写入了 `savedAt`，
但 `getLastMeeting()` 只读 `entityName`/`entityUUID`，`savedAt` 从不参与判断）
→ 下次启动 `restoreLastMeeting()` 无条件拉回旧会晤实体。

### 🔴 缺陷③ 恢复路径首轮同样命中 P0-1

`restoreLastMeeting()` 调用点 `chat.ts:843`，仍在角色路由 `chat.ts:494` **之后 349 行**。
重启首轮：角色路由按「非会晤」定格 `secretary` → `:843` 恢复会晤 → 以
`isEntityMeeting=true` + secretary 双参调 M5 → **重启首轮必泄漏**，且比普通唤醒轮更稳定复现。

### 🟡 缺陷④ 纪要人数门槛与 `isMulti` 判定不一致

`isMulti = entities.length >= 2`（P2-2 修正），但 `exit()` 纪要条件
`_multiParticipants.length >= 3`。→ **2 人会晤退出不生成纪要**。
注释写「3人+」属原设计，但 P2-2 已把 2 人纳入多人语义，两处口径未同步（待业主确认是否为预期）。

### 🟡 缺陷⑤ `exit()` 不重置 `_isFirstTurn`

`enter()`/`enterMulti()`/`switchTo()` 均置 `_isFirstTurn = true`，`exit()` 清理段未置 false。
字段语义是「本轮是否会晤首回合」，跨会话残留会影响首回合特判。

## 二、P0-3 场景锚点 / 情感基线一致性

### 🔴 缺陷⑥ 三重置只在「退出」时执行，「进入」无对称动作

`resetSession()` / `resetContext()` / `resetAnchor()` 的调用点**全部集中在
`chat.ts:855-864`（退出分支内部）**；进入会晤分支（`chat.ts:812-845`）**零调用**。

两个方向的后果：
- **泄漏进**：玉瑶态积累的 `SceneAnchor` / `ContextMemory` 跨轮状态**原样带入实体会晤前几轮**
  （实体开场发言继承玉瑶的场景锚点）
- **丢失掉**：退出时执行的是 `reset`（**归零**）而非「保存玉瑶基线 → 下次进入再恢复」
  → 玉瑶的场景基线**被永久销毁**，而日志措辞是
  `'[MeetExit] 转场回玉瑶: 场景锚点/情感基线已重置'` —— **"已重置"掩盖了"基线丢失"**

### 🔴 缺陷⑦ 情感快照只按实体 UUID 存取，玉瑶基线无人维护

全仓 `saveEmotionSnapshot`/`loadEmotionSnapshot` 各仅 **1 处调用**：
- `chat.ts:880` 退出时 → `saveEmotionSnapshot(_exitUuid, ...)`（**实体**的）
- `chat.ts:1096` 进入时 → `loadEmotionSnapshot(_muuid)`（**实体**的）

玉瑶（TXS-000000001）的快照**永远不被 save 也不被 load** →
玉瑶态情感基线不参与身份切换的对称保存/恢复。
另：`:880` 保存时取的 `p` 是**退出轮（实体会晤最后一轮）的感知**，若曾想用它做玉瑶基线，
语义也是错的（存的是实体的收尾情绪）。

### 🟡 缺陷⑧ 会晤中感知维度被整体丢弃

`DeepSeekLLMProvider.ts:1724-1732`：`_isEntityMeeting` 时 `contextBlock` 只保留
`[当前会晤: entities]`，`dimContext`（pleasure/intimacy/… 六维）与风格参考**整块不注入**。
→ 会晤中**场景维度信息缺失**，而身份维度（档案）与记忆维度（KB）照常注入
= prompt 三要素中「场景」这一维实际为空，三者天然不一致。

## 三、P0-4 LLM prompt 身份 / 场景 / 记忆三者一致性

### 🔴 缺陷⑨ 出口清洗窗口与生产内容顺序冲突 → 条件性完全失效

三处事实叠加：

1. **生产顺序**（`chat.ts:2296`，S2-R2 顺序修复）：会晤模式
   `finalKnowledgeText = 实体档案 + '\n\n' + _assembled.text(记忆)` —— **档案在前，记忆在后**
2. **清洗窗口**：`sanitizeMeetingPrompt` 默认 `headLimit = 2000`，**只在头部 2000 字符内检测**
3. **档案本身**：`EntityContextBuilder` 产出含 `## 你的身份` / 环境数据 / 家人 / 基本信息 /
   社会身份 / 性格 / 你认识的人 + 追加的**户口本**（`chat.ts:1081`，列全部 TXS 成员）+
   知识库档案（`:1111`）+ 情感延续（`:1098`）+ 对话延续（`:1111`）—— 远超 2000 字符

**纯函数探针实测**（`sanitizeMeetingPrompt`）：

| 场景 | total | 前 2000 含人设 | `stripped` |
|---|---|---|---|
| ① 档案 1900 字 + 记忆含人设 | 1925 | true | **true**（能洗） |
| ② 档案 4000 字 + 记忆含人设 | 4109 | false | **🔴 false（完全失效）** |
| ③ 人设在最前（现有 V27 单测的形态） | 4109 | true | true（能洗） |

**关键**：现有 `meeting-prompt-isolation.test.ts` 的夹具是**情形 ③（人设在最前）**，
与生产实际顺序**正好相反** → 单测全绿，生产却在情形 ② 下静默漏网。

**诚实标注**：情形 ② 成立的前提是「记忆段确实携带玉瑶人设」。
本轮尝试统计生产库（`data/fusion_memory.db`、`vault.db`、`family_graph.db`）均 **0 行**，
未定位到真实生产库，**该前提未获数据验证**。
但**以下两点不依赖该前提，独立成立**：
- 身份泄漏的主通道（`buildRoleSystemPrompt` role 通道）**根本不经过清洗器** ——
  全仓唯一调用点 `chat.ts:2469` 只洗 `finalKnowledgeText`，而 system prompt 由
  `DeepSeekLLMProvider.ts:1709` 独立构造
- 单测夹具形态与生产顺序相反，**防线的测试证据不可信**

## 四、P1-1 退出会晤与重启恢复逻辑审计

### 🔴 缺陷⑩ 进入会晤前的角色现场只在「天界实体」分支保存

`chat.ts:828` `_savedHumanRole = _currentRole;` 被 **`if (isCelestialEntity(_enterTargets[0]))`**
包住 —— 只有警幻仙姑这类天界实体会晤才保存人间现场。

| 场景 | 进入前角色 | 退出后角色 |
|---|---|---|
| 天界会晤（警幻仙姑） | lover | ✅ lover（`:896` 复原） |
| **普通人间会晤（徐诗雨/阿珍）** | **lover / counselor / strategist** | 🔴 **`secretary`**（`:900` 无条件硬置） |
| `enterMulti` 多人分支 | — | 🔴 连天界保存都不走（`:821` 无 `isCelestialEntity` 判断） |

**业主症状的第二种形态**：与玉瑶处于亲密模式（lover）时喊「徐诗雨过来聊聊」，
退会晤后**直接变成秘书口吻** —— 与 P0-1 同族（角色状态机与会晤状态机不联动），
但根因不同：P0-1 是**进入时**没改角色，本条是**退出时**把角色砸回 secretary。

### 🟡 退出清理本身对称性 OK（已核）

`chat.ts:852-905` 的退出链路：`resetSession` → `resetContext` → `resetAnchor` →
`_em.exit()` → `setSessionEntityUuid(null)` → 存情感快照 → 记 `_exitEntityUuid` → 重置角色，
`EntityMeeting.exit()` 内部亦对称清除 `engine_store`（有结构修复注释，`:303-311`）。
**主链路无缺失**，问题集中在缺陷⑥⑦（reset ≠ 恢复基线）与缺陷⑩（角色不复原）。
