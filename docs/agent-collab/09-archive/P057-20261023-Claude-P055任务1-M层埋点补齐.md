## 一、改了什么

**`src/m5/group/GroupSession.ts` — `dispatch()` 内新增 M 层埋点**

```
[Hook] module_entry module=m5.GroupSession.dispatch action=<WAKE|JOIN|SPEAK|LEAVE|RESUME|IDLE> participants=<N>
[Hook] module_exit  module=m5.GroupSession.dispatch 耗时=<ms> status=<applied|unchanged> effects=<N> participants=<N>
```

- 格式：**m5 文本范式**，与 `DeepSeekLLMProvider` 同款（`reasoning-leak-length-cap.test.ts` 断言的就是这个范式）
- 出口用 **try/finally** 而非在末尾直打 —— 监听者抛异常时 `module_exit` 仍要打出来；
  否则最需要可观测的失败路径反而无日志（DeepSeekLLMProvider 只用 `_status` 变量，此处补上兜底）
- 两处 `console.log` 各自包 try/catch —— **埋点失败绝不影响主链路**（照 `m2.SQLiteAdapter` 的 `_hook` 范式）

## 二、为什么埋点放 `dispatch` 而不是调用方（与「唯一调用点」原则的关系）

P054 §五.1 记录的问题是：S4.5 审议时我以「埋点放唯一调用点」为理由通过审查，
但实际交付的 `GroupSession.dispatch` 内**根本没有埋点**。所以这次不只是「补上」，还要讲清放哪。

| 选项 | 判定 |
|---|---|
| 放 `reduce` / `diffEffects` | ❌ **纯函数**。零副作用是它们能被 87 例单测覆盖的前提 —— 与 `chat/retrieval-stage.ts:143` 对 `recall-quota.ts` 的处理同一原则 |
| 放 `chat.ts` 投影块（调用方） | ❌ `GroupSession.reset()` 内部调的 dispatch 会漏埋；未来新增调用点仍会漏 |
| **放 `dispatch`（采用）** | ✅ 它是 GroupSession 状态变更的**唯一入口**（ADR-013 硬约束②「状态只有一处写」），且本身是**有状态方法**（改 `_state`、push `_trail`、触发监听者），不是纯函数 |

## 四、写代码过程中的两个坑（记录备查）

### 1. 🔴 令牌 content_hash 绑定修改前内容 —— 连续编辑必被静默回滚

`run_mvjr7cnx_k2xv` 令牌下：第一次 Edit（加埋点声明 + try 骨架）**成功**，
后续两笔修复编辑（补 `for` 闭合、调缩进）**全部被 Sentinel 静默回滚** ——
Edit 报成功、Write 报成功，磁盘纹丝不动，而仓库因此**处于 tsc 报 TS1005 的不可编译态**。

连 `Write` 整文件重写都被回滚（`mtime` 显示确实写入了 33 秒前，但内容是旧的）。

**实测有效的配方**：`run_flow` 取新令牌 → **只做一次写入** → **立刻 grep 验活**。
第三次（`run_mvkbvtm1_5kni`）按此配方一次写对，tsc 立即归零。

> 这与 memory 里既有的「令牌 TTL 半落地」是同一族问题，但表现更极端：
> **不是中途过期，是首次编辑后 hash 失配即回滚**。

### 2. 埋点包裹 try/finally 时把 `return next;` 写进了 `for` 内部

第一次尝试加 `finally` 时，`return next;` 被放进了 `for (const eff of effects)` 内部，
导致 `} finally {` 试图直接闭合 `for` —— `TS1005: ';' expected`。
教训：**改控制流结构时，括号配对要在一次编辑内写完整**，不要指望分笔补。
