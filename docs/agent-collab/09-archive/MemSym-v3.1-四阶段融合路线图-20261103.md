# 时空机（SpaceState）四阶段融合路线图

> **核心原则：先独立闭环，再灰度对接。**
> 时空机从第一天起就是**独立子系统**，不是嵌在 MemSym 里面改。
> 先把它自己的内部逻辑、算法、数据结构、测试全部跑通、验证正确，再通过标准化接口一点点接进 WenStar，而不是一开始就把两边揉在一起改。
>
> 这解决之前最头疼的问题：改 RAG 因为耦合太深，改一处崩三处。这次从架构上就把边界焊死。

---

## 阶段一：时空机完全独立开发期（P0~P2，不碰 WenStar）

**这个阶段，时空机就是一个独立的小项目，和 WenStar 主系统零代码耦合。**

### 内部要做完的事

1. **数据结构定型**：79 维 `DimReading` 结构、`scene_imprints_v31` 表结构、基线表、遥测表
2. **核心算法全部实现 + 单元测试**：
   - 证据似然比打分 `dimEvidence`
   - 多源贝叶斯融合 `fuseDim`
   - OU-Kalman 状态滤波
   - 分层基线收缩
   - 生命周期增益 G(x)、精度衰减 σ(t)
   - KDE 密度估计、独特性 D(x)
   - 精确扫描检索引擎
3. **属性测试（CI 必跑）全部通过**：
   - 未知维度不加分
   - 记忆越模糊得分越低
   - 稀有场景匹配 > 普通场景匹配
   - 宿主删除后印记消失
   - 解释可忠实归因
4. **离线数据集验证**：拿历史对话数据，跑通从「文本 → 40D 估计 → 印记写入 → 共鸣检索」全流程，人工标注评估召回合理性

### 这个阶段绝对不碰的 WenStar 部分

- ❌ 不改 MemSym 的 UUID / DNA / A/B 链路
- ❌ 不改 SpaceRouter 的路由逻辑
- ❌ 不改 Harris 的现有规则
- ❌ 不接真实对话流，只用离线历史数据跑

### 验收标准

时空机自己能跑通：给一段输入文本 → 输出 40D 状态 → 写入印记 → 给定查询 → 返回共鸣结果，全部正确，测试覆盖率达标。

---

## 阶段二：接口契约冻结 + 影子对接期（P3 前半段）

**这个阶段，时空机开始读 WenStar 的数据，但输出不影响 WenStar 的任何行为。**

### 做什么

1. **冻结对外接口**（`SpaceStateAPI`），两边约定好：
   - 时空机从哪里读事件数据（episodes 表、memories 表）
   - 时空机输出什么（UUID 列表 + 分数 + 解释）
   - 生命周期事件怎么订阅（hot / sleep / expiring / tombstone）
2. **开启影子模式**：
   - WenStar 主链路照常跑，对话输出完全不变
   - 时空机在后台同步接收每一轮对话，自己算共鸣结果，但**不把结果注入对话**
   - 每天记录："如果开了通路 C，本来会唤起哪些记忆、在什么时机唤起"
3. **人工标注评估**：抽影子日志，判断时机合不合适、记忆合不合适，调参直到达标

### 安全保证

时空机哪怕算错了、崩了，对用户完全无感知，因为它的输出根本没接进对话流。

---

## 阶段三：灰度上线 + 逐步接管通路（P3 后半段 ~ P4）

**从影子切到真实生效，小步放开，每一步都有开关。**

### 按顺序放开，每一步独立可回滚

1. **先开通路 B 的 40D 加分项**：
   - 原来通路 B 只靠语义相似度排序
   - 现在加入 40D 共鸣分做微调（权重 0.4）
   - 开关独立，不对就关回纯语义
2. **再开通路 C 的邀请式唤起**：
   - 每天上限 2 次，冷却 4 小时
   - 先问"想听吗？"，用户同意才讲
   - 接受率稳定在 60–75%、打扰率 < 5% 之后，再逐步放开频率
3. **最后开情绪修复模式、共同经历比喻表达**

### 全程开关矩阵

每一条通路、每一层维度、每一个功能，都有独立的 `on / off / shadow` 开关，Harris 随时可以切回上一个稳定版本。

---

## 阶段四：深度融合 + 长期协同（P5 及以后）

等前面全部稳定了，再打通和其他模块的联动：

1. 和 Harris 对接：把时空机的高危操作纳入守卫矩阵
2. 和 Harness² 对接：把共鸣命中率、误触发率、共情准确度纳入复盘指标
3. 和瑶灵感知网关对接：传感器流进来，走同样的 DimReading 接口
4. 和瑶光对接：虚拟场景生成的 40D 状态，直接喂给时空机

---

## 为什么这个路线最安全

1. **隔离开发期零风险**：时空机自己改自己的，WenStar 该怎么跑怎么跑，不会崩
2. **影子期无感知**：就算算法有问题，用户根本不知道，后台慢慢调
3. **灰度期可回滚**：每开一个功能都有开关，出问题立刻关，退回上一个版本
4. **最终融合是松耦合**：时空机和 WenStar 之间只有接口，没有内部代码互相调用，以后时空机升级、换算法，主系统一行不用改

---

## 一句话总结

> **先把时空机当成一个独立的小引擎造出来、试车、验收合格，再挂到 WenStar 的传动系统上，从空挡慢慢挂挡，而不是一上来就焊死在一起。**

这个节奏和之前清理 RAG、上 SpaceRouter 的思路完全一致：先钢架、后细节，微分迭代，绝不一次性大改。
