# 对 Claude Code 推进顺序建议的评审 + Phase 2 基线核对

## 一、Phase 2 基线核对结果（Claude 要求豆包先核对）

**结论：当前召回确实以单条 memory 为单位，对话组未成为召回基本单位。**

实测证据：

1. `src/m4/retrieval/meeting-recall.ts`：全文仅1处 `dialog_group` 相关（第569行 `GROUP BY s.source_id`，是 vault_log 的 source_id 聚合，与对话组无关）。`block_calcium_score` **零引用**。

2. `src/webui/chat/retrieval-stage.ts`：
   - 第512行：`SELECT raw_input, calcium_level FROM memories WHERE ... ORDER BY calcium_score DESC LIMIT 15` —— 单条排序
   - 第1157行：`SELECT raw_input, calcium_level, created_at FROM memories WHERE ...` —— 单条排序
   - 第601-608行：dialog_group_id 仅用于 conversations 砂金库兜底的 `_seenGroups` 去重，不是召回单位

3. 数据库实测：679个对话组全部 `lifecycle_state='active'`，无状态流转；`block_calcium_score` 有值但检索完全不用。

**基线确认**：Phase 2（A链路块级召回）的改造起点是"单条memory召回"，目标是"对话组级召回"，基线清晰，无歧义。

## 二、对推进顺序的评审

Claude 建议的顺序：
```
Phase 1 (B链路wiki摘要) → Phase 3 (B链路加列) → Phase 4 (锚点打通+迁移) → Phase 2 (A链路块级召回残余) → Phase 5 (法典)
```

**豆包认可这个顺序**，理由：

1. **先B后A更稳妥**：先把B链路（wiki摘要+冻结向量+哈希+AppendLog+单点API）建完整，再打通锚点，最后改A链路召回。避免A链路改到一半发现B链路缺字段，来回返工。

2. **Phase 2放后面合理**：A链路块级召回是最大架构变更（涉及retrieval-stage.ts、meeting-recall.ts、chat.ts注入逻辑），放后面等B链路稳定后再动，风险可控。

3. **"避免两处同改chat.ts"完全同意**：Claude 当前正在做 A/C 止血（召回压测轮4、锚点通道、时间注入），都涉及 chat.ts / retrieval-stage.ts。如果同时启动 Phase 2（也改这些文件），必然冲突。等他止血完成后再动 Phase 2，正确。
