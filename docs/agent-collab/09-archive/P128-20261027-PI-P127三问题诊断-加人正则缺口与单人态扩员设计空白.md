## 问题 1 · 加人不工作 —— 双层根因

### 根因 A：正则不覆盖实测句式（识别层从未触发）

`EntityMeeting.ts:824` add 正则：

```ts
/(?:叫|让|喊|把)\s*([一-龥]{2,4})\s*(?:也)?\s*(?:来|过来|参加|加入|进来)/
```

| 实测句 | 判定 | 原因 |
|---|---|---|
| 「这样**找**阿珍过来一起聊聊」 | → **normal**（AI 口头答应去叫，人没加） | 动词表**缺「找」**——只有 叫/让/喊/把 |
| 「**阿珍你也过来**一起聊聊」 | → **wake**（被门卫拒，1159173） | 无动词前缀、称呼后无逗号，不命中任何加人句式 |

### 根因 B：单人会晤态没有扩员路径（即便识别了也加不成）

`chat.ts:1153` add 实际执行分支的前提是 `_isMulti`（群聊中加人）；
单人态下 add 落入 `chat.ts:1175` 兜底 → **门卫拒绝**（"先说结束/再见回到玉瑶"）。
即：**单人会晤 → 多人，唯一现行路径 = 退出后重新叫人**，"直接把人叫进来"在会晤态被设计性禁止。

> 注：任务书问「GroupSession.addParticipant 是否调用」——是，但仅限多人群聊中（JOIN，chat.ts:1156）；单人态分支根本到不了它。

## 问题 2 · 「找两人一起聊」不生效 —— 识别正确，缺的是「扩员」分支

- 意图识别**工作正常**：日志 `wake targets=徐诗雨,罗珍思`——两目标都取到了；
- 单人会晤态下 wake/switch/add **一律走 1175 deny**（这是 2026-10-06 P2-2 严格模式的既定行为：防单人对话中被唤醒打断）；
- **非会晤态**同样句子能正确开多人（1129737 铁证）；
- 缺口 = `inMeeting && !isMulti && 多目标` 这一格**没有设计**：既不扩员、也不给出「加人」引导，只回"先退出"。

**附带文案缺陷**：deny 文案 `targetName=intent.targets[0]`=徐诗雨（**当前对话者本人**）→"想找徐诗雨聊得先说结束"自我指涉；多目标时应报**待加入者**（罗珍思）。

## 问题 3 · 退出后状态没重置 —— 证伪：记录轮次错位

1. **退出链完整**：1159266 `MeetExit 转场回玉瑶` + `LEAVE participants=1→0` + 1159272 `会晤结束（徐诗雨）`——GroupSession 清空、场景锚点/情感基线重置，全到位；
2. **退出后无 deny**：紧接着的 1159351 是干净的 WAKE（单人罗珍思，对应 seq=17024「找阿珍聊聊」）；
3. 业主看到的"第二次 deny"（1158844，seq=17020）**日志位置在「再见」之前**——即系统里「找…过来一起聊聊」发生在退出**之前**，手记顺序与系统实际错位。
4. **保留复验项**：修复上线后的回归测试中重放此序列（叫人→再见→再叫）确认。

**旁观察（转 Claude，非本任务）**：同段 err 日志出现 `[RetrievalV11] 围栏 SQL 失败 fail-closed domain=dialog_group: no such column: id / domain=memory: datatype mismatch`——若发生在 `91bba6d`（id 列名修复）之前属已知已修；若之后则 S3 两段式仍有残留，建议 Claude 用 P128 时间线核对时点。
