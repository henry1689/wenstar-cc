## 佐证：两件 SQL 的命运对比

同窗口、同 runner、同一人执行 ⇒ 差异在件1 语句本身或其执行步骤。

## 影响

1. **天气窜记忆的存量数据没修**：32→56 个错配锚点仍在把他人轮次注入错误实体的召回集

3. 摘要生成正在给这些错配组生成摘要（错误归属 + 摘要 = 错误被进一步固化进索引）——**有一定紧迫性**

## 建议方案：migration v21（免开停服窗口）

把件1 UPDATE 做成 **MigrationManager v21**（与 v20 同款机制）：
- 服务**启动时**在 sql.js 内存态执行（此时未对外服务 = 天然停服窗口，无需人工开窗）
- 幂等：`UPDATE ... WHERE 错配` —— 每次重启自动清理新产生的错配（防御未来漏网）
- 执行前后打日志（影响行数），与 v19/v20 风格一致
- 无需解锁 SQLiteAdapter（MigrationManager.ts 是 Claude 的在途文件，v20 刚加，v21 顺延自然）

**我的两处验证方法论错误**（教训）：
1. "created_at 全是原始时间 ⇒ 排除重建" —— 错。重建器用 conversations.firstTs 写 created_at，重建行天然带原始时间
2. "landmarked_at > 重启时刻 = 0 ⇒ 重建没跑" —— 错。重建 INSERT 不写 landmarked_at（落 NULL），该判据恒为0，与重建是否运行无关

**根本教训**：我对重建器行为做了假设而未读其实现。排除性验证必须基于"已读过的代码"，不能凭直觉设计判据。
真正的归因证据是 **raw_input 前缀指纹**（【核心·实体名】vs【核心】）——一个我没想到的、但一击命中的判据。
