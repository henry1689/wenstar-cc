## 二、但我必须指出两处会改变优先级的发现

### 🔴 发现 1：P0「激活 M2 GC 控制膨胀」**实测无效**

P112 P0-1 与你的 P0 都指向「GC 控膨胀」。我做过实测（P114/P115）：

| 项 | 实测 |
|---|---|
| 库文件 | 535.4 MB |
| **memories 表（70 列全部字段合计）** | **仅 14.9 MB**（1.1 KB/行） |
| **search_index** | **约 436 MB（83%）** |
| 空闲页 freelist | 19 页（0.07 MB）—— **无碎片，VACUUM 无效** |

**对照实验**（原生 SQLite `VACUUM INTO`，读全库+重写全库，与 `db.export()` 成本同构）：

| 库 | 体积 | 耗时 |
|---|---|---|
| 全库（含索引） | 523.9 MB | **3.72 s** |
| 剔除 `search_index` | **88.0 MB** | **1.32 s** |
| 差值 | **−83.2%** | **−64.6%** |

⇒ **删 memories 到 500 条，库仍在 500 MB 量级、落盘仍慢**。
⇒ **膨胀的真凶是索引，不是记忆条数**；「控制膨胀」必须动索引，否则 P0 白做。

> 而且 memories 这 13,640 条是你几个月积累的真实记忆（10-20 单日 1,122 条），
> 触「亲密数据必须保留」红线。

### 🔴 发现 2：**n-gram 不是"原生体系不完整时补的外挂"**

你说「n-gram 是外挂，UUID 可靠了就可以拆」。我查了读侧，**不成立**：

| 读点 | 用途 | 是否 V13 主链 |
|---|---|---|
| `meeting-recall.ts:640` | **会晤召回**：`FROM search_index s JOIN conversations c ... ORDER BY COUNT(DISTINCT s.term) DESC` | ✅ 主链 |
| `DialogGroupAdapter.ts:152/164` | **对话组召回**（conversation + dialog_group 两类） | ✅ 主链 |
| `MemoryRetriever.ts:144` | 记忆关键词召回（仅 `source_type='memory'`） | ✅ 主链补充 |
| `UnifiedSearchEngine.ts:115` | V11 旧路径 | ❌ 仅 V13 降级时 |

**关键**：会晤召回里，n-gram 承担的是 **`COUNT(DISTINCT term)` 的文本相关性排序**。
UUID 解决的是「**这是谁的**」，**不解决「这几十条里哪条最相关」**。

⇒ **拆掉 n-gram，UUID 补不上它会失去的东西** —— 会晤/对话组召回会退化为
「UUID 过滤 + 时间排序」，文本相关性维度消失。

## 三、对「掀桌子顺序」的建议（在你的基础上修正）

### 你的原方案 vs 我的建议

| 你的顺序 | 我的评估 | 建议 |
|---|---|---|
| **P0 激活 M2 GC 止血** | 🔴 **实测无效**（见发现 1） | **改为 P0'：索引降本**（见下） |
| **P1 补藤**（`vine_group_id`+`entity_belong_id`） | ✅ **完全同意，且应最优先** | 保留为 **P1**，并强调它是最高价值的「治本」 |
| **P2 拆 n-gram** | ⚠️ **不能"拆"，只能"降本"**（见发现 2） | 改为 **P2'：n-gram 降本** |
| **P3 补 `atom_repair_index`** | ✅ 同意 | 保留 |
| **P4 40D 扇区索引** | ✅ 锦上添花 | 保留 |

### 建议的落地顺序

#### P1（最高价值，纯增量、零召回风险）—— 补藤
- 回填 `entity_belong_id`（59% 空 ⇒ **最大的社会学缺口**）+ `vine_group_id`（28% 空）；
- 这是**纯补数据**，不删不拆，召回只会变好；
- **与你的「UUID 是社会根基」完全一致**，而且补齐后 n-gram 降本的底气才足。

#### P0'（真止血，需选型）—— 索引降本，而非删记忆
三条路径，成本/风险递增：

| 路径 | 做法 | 效果 | 召回影响 |
|---|---|---|---|
| **a. 停写无用索引** | 确认 `conversation` 索引是否**每次对话都写**；若写入侧可收敛（如只索引摘要而非全文），立竿见影 | 减写入与体积 | 会晤召回粒度变粗 |
| **b. 迁 FTS5 + trigram** | SQLite 原生 CJK 子串，C 引擎批量建索引 | 体积与写入成本双降 | **基本无损** |
| **c. 索引外置** | `search_index` 移出主库，`export()` 只序列化 ~88MB | **落盘 3.72s → 1.32s（实测）** | **零影响** |

**我倾向 c + b 组合**：c 立刻见效且零召回影响；b 是长期正解（用平台能力替掉自造轮子）。
具体选型请你/豆包定，我不擅自改检索行为。

#### P2' — n-gram 降本（不是拆）
- 在 P1 补藤 + P0' 降本完成后，再把 n-gram **降级为「补充召回」**（保留文本相关性但缩小规模）；
- **明确不做**：直接删 `search_index` — 会丢 `meeting-recall` 的排序维度。

## 四、一句话总结

> **你判断对的部分**：UUID 账簿可靠（99.2%），藤和修复索引只建了一半，这个顺序感是对的。
> **需要修正的部分**：
> ① P0「GC 删记忆」**实测无效**（记忆只占 14.9MB，索引占 83%），且触红线；
> ② n-gram **不是纯外挂**，它在 V13 主链的会晤/对话组召回里提供**文本相关性排序**，UUID 补不上；
> ③ 所以正确姿势是 **「先补藤（P1）→ 索引降本（P0'/P2'）→ 而不是先删记忆、也不是直接拆索引」**。
