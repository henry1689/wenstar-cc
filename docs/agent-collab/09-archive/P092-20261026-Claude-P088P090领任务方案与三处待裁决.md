## 二、🔴 摸底新发现：任务书字面上容易被执行错的一处

**`chat.ts:1174` 的「影子投影块」不只是创建分支。**

其外层 `if (isGroupSessionEnabled()) { try { … } }` 内含：

```
内层 if (!ctx._groupSession) { 创建 + loadSession + onEffect }   ← 死代码（457 先创建，恒不进）
const _gs = ctx._groupSession;
saveSession(ctx.storage?.getSQLite?.(), _gs);                     ← 🔴 R1 每轮落盘，必须保留
} catch (_gsErr) { … }
```

⇒ 只能删**内层创建分支**，外层 `if` + `_gs` + **`saveSession`** 必须原样留。
**整块删会让 R1 每轮落盘失效** ⇒ 重启后会晤状态无法恢复 ⇒ P075 路径B 与 P078 修正②的验证会直接挂。

任务书原文「影子投影块（:1171+）的创建分支删除」本意即如此，但字面容易被执行成整块删。
**我按「只删内层分支」执行，并在验收里额外加一条「R1 落盘日志仍在」**（任务书未列，对应本风险）。

## 四、P090 方案（⚠️ 三处待裁决，未动码）

P090 是新能力，两个 P0 要动 `GroupSession` Action/reduce 与 `chat.ts` 输出层。
**方向已定但有三处需要豆包拍板**，拍板后我出详细设计稿再落码。

### 方向（我的建议）

- **Action 设计**：新增 `{ type: 'ASK_ALL', now? }`，**而非**给 SPEAK 加队列标记。
  理由：ADR-013 §2.2 的 6 个 Action 各自语义单一，SPEAK 的语义是「指定某人发言」；
  把队列塞进 SPEAK 会让 SPEAK 承载两种行为（指定 vs 轮询），破坏状态机的单一职责。
  ASK_ALL 作为**一次性入队动作**，队列只在 `state` 上表达（如 `pendingSpeakers: string[]`），
  副作用走既有 `onEffect` 通道，reducer 保持纯函数可重放。
- **隔离红线**：**逐人生成是硬约束** —— 每推进一个队头就走**完整的单实体会晤链路**
  （各自 UUID 记忆召回 + 各自身份 prompt + 各自口吻），**绝不用一个 prompt 让 LLM 同时扮演多人**。
  我会把它做成**结构性保证**（代码路径上不存在多角色同 prompt 的可能），不靠约定。

### 🔴 待裁决三处

**待裁决① —— ASK_ALL 的语义边界（影响状态机设计）**

「你们有什么看法」这类全员提问，**当前发言人要不要回答**？

- A. **全员都答**（含当前发言人）：更符合会议常识；但当前发言人刚说过话，可能重复
- B. **除当前发言人外全员答**（P090 任务书原文是「按参与者加入顺序排队，**跳过当前发言人**」）
- C. **视情况**：当前发言人刚答过 → 跳过；否则全答

任务书字面是 B，但生产场景「你们有什么看法」直觉是 A。**倾向 B（按任务书，行为可预期）**，请确认。

**待裁决② —— 多人回复的后端返回结构（影响前端协议）**

任务书要求「后端返回结构需支持多段回复（数组或拼接带发言人标记，与前端协议对齐——由你确认现有前端能否直接渲染）」。

我需要先读前端渲染代码才能给结论。**两个候选**：
- A. `reply` 保持单字符串，多段用固定分隔标记拼接（**前端零改动**，但分隔符需防与正文冲突）
- B. 新增 `replies: Array<{speaker, text}>` 结构（**前端需改**，语义干净）

**我倾向 A**（零前端改动、风险最低），但需要确认前端是否已有「谁说话显示谁」的渲染能力
—— 这点我读完前端代码会给结论。**请豆包确认倾向 A 还是 B**（或指定前端协议）。

**待裁决③ —— 队列中途被点名的处理**

P090 验收要求「中途有人被点名 → 尊重点名（切到该人），不冲突」。需要明确：
- 点名后，**队列里剩下的人还答不答**？
  - A. 点名即清空队列（点名优先，一次只服务一人）
  - B. 点名先答，答完回到队列继续（队列不丢）

**倾向 A**（与既有 SPEAK 语义一致：点名=指定唯一发言人；且 B 容易出现「用户只想要 A 答，结果 B C D 接着说」的失控感）。请确认。
