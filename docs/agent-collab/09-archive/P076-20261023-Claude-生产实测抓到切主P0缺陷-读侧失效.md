# P076 · 生产实测抓到切主 P0 缺陷（读侧失效）

**状态：已实测确认，等豆包/业主裁决修复方案与是否应急关开关。**

---

## 一、缺陷一句话

切主只切了**写侧**（`_em` 不再被写、状态唯一写入 `GroupSession`），
**读侧仍有 10 处直接读 `_em`** ⇒ 这些点在新架构下**恒读到空状态** ⇒
会晤「进去了但系统以为没进」。

## 三、根因（含我的归因，不推卸）

### 直接根因

`chat.ts:1149` 的实体上下文注入块：

```ts
if (ctx._entityMeeting?.isActive()) {     // ❌ 该 if 在开关分支之外，无双分支
  ...
  _meetingEntityName = ctx._entityMeeting.getEntityName();   // :1158
  setSessionEntityUuid(_meetUuid);                            // KB 按会晤实体过滤
  ...
}
```

切主后 `_em` 不再被写 → `isActive()` 恒 false → **整块不执行** →
`_meetingEntityName = null` → `CognitivePipeline.isEntityMeeting = false` → 身份回落玉瑶/秘书。

### 🔴 我的归因：P071 的 S1 摸底范围错了

P071 §1.1 写的假设（31–33 行）：

> 「20 个文件消费的是 `_meetingEntityName` / `meetingEntityUuid` 这些**派生值**，
> 不关心来源 → 切主对下游透明，这 20 个文件**不用改**」

**这个假设被实测证伪**：大量文件**不走派生值，直接读 `_em`**。
且 P071 §1.2 的 S1 摸底**只摸了 `chat.ts` 单文件的 14 处调用点**，没做全仓 grep。

**教训（需写进 ADR-013 的执行要求）**：切状态源时，
**「写侧唯一」必须配「读侧全量盘点」**，两者缺一即分叉。
我做前者时把后者当成「下游消费派生值所以不用改」，跳过了全量盘点。

## 五、修复方案（推荐 C，请裁决）

| | 方案 | 评价 |
|---|---|---|
| A | **10 处逐个补双分支** | 每处都要手写 GroupSession 等价读法，7 文件散布，**漏一处就是一个新缺陷**（本次就是这么漏的）；后续每次加读点都要记得加分支 |
| B | 写 gs 时回写 `_em` | 双写，**直接违反 ADR-013 硬约束②**，不可选 |
| **C** | **`_em` 状态读方法转发到 GroupSession（读视图）** | ✅ 见下 |

### 方案 C：把 EntityMeeting 的状态读方法改成「GroupSession 只读视图」

给 `EntityMeeting` 注入状态源（chat.ts 创建处接线），内部改为：

```ts
isActive()      → 开关开 ? gs.getState().active      : this._meeting?.active
isMultiParty()  → 开关开 ? gs.getState().multi        : ...
getEntityName() → 开关开 ? 由 gs speakerUuid 派生 name : ...
getEntityUUID() → 开关开 ? gs speakerUuid             : ...
getParticipants()→开关开 ? gs.getState().participants : ...
```

**为什么这是最优解**：

1. **严格符合硬约束②** —— 状态**写**仍然只有 `GroupSession.reduce` 一处；
   `_em` 这些方法退化为**纯读视图**，不再是第二状态源（这点与 B 有本质区别）。
2. **下游 18 个读点一行不用改** —— 正好兑现 P071 想要的「20 文件零改动」，
   只是手段从「下游只消费派生值」（错的前提）换成「上游提供读视图」（对的手段）。
3. **改动面 1 个文件 + 1 处接线**，风险远低于 A 的 10 处散改。
4. **回滚完整**：关 `WS_GROUP_V2` 即读回 `this._meeting`，与旧路径逐字一致。
5. **Phase 4 清旧代码时**，这些读方法直接删转发分支即可，债务不累积。

**需要单独处理的边界**：`isFirstTurn` / `incrementTurn` 属**会晤轮次上下文**，
不是群聊状态（GroupSession 无此概念）→ 应**留在 `_em`**（不违反②），
否则又会造出「状态归 gs 但轮次归 _em」的半切。
