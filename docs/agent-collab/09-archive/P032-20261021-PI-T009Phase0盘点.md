## 二、PI 6 项盘点明细

### 1. 实体提取器：FGRelationExtractor 为何产出 0
- **已接线**：`server.ts:793` 构造 + `:794` setLLM(llmProvider) + `:805` extractAndApplyRecent，在 `initPipeline`(:471) 启动路径，**24h 节流**（engine_store key `fg_llm_extract_ts`）。
- **数据实证**：FG 库 `properties LIKE '%"_llm":true%'` 边 = **0**（总边1346）→ 从未成功产出。
- **根因**：
  ① **设计为"启动时一次性+24h节流"批量**，非真正定时任务——只在 initPipeline 启动瞬间跑，服务长期运行不再触发；
  ② 启动上下文脆弱（与全部初始化竞争，任一前置抛错即中断）；
  ③ 白名单仅8类 + conf≥0.7 + 血缘0.9，真实 LLM 输出需同时满足才落库。
- **附带缺陷（降级路径也是坏的）**：`MockLLMProvider.rawCall`(:745) 返回 `{"persons":[],...}`（**无 `relations` 字段**），而 `parseExtractionResponse`(:172) 取 `data.relations||[]` → 恒空。注释称"依靠正则管道 fallback"，但该 fallback 不存在。

### 2. 关系提取器：HWG enhanceFromConversation 为何零调用
- **零调用方**（全仓 grep 无 `enhanceFromConversation(` 调用，排除定义/测试）。
- HWG 四表（hwg_persons/relations/events/snapshots）**全 0 行**（Claude P031 实测）。
- 设计意图：会话中抽取「我↔人物」关系写影子表，供网络查询 `getNetwork`。**从设计到实现从未接线到任何调用者**——典型的"设计了但没接线"。

### 3. PAE 自动触发链路
- 构造：`server.ts:750`（rawCall 闭包注入 llmProvider）+ `:760` acquisitionIntegrityGuard 自检。
- **触发**：`chat.ts:1293` / `:3149` 的 `_profileAcquisitionEngine.acquire(...)` —— **对话消息驱动**，非定时/启动。
- 结论：PAE 是唯一存活的写入路径，但触发依赖对话热路径（与"定时 LLM 提取"的业主方向不同，Phase 2 需改造为定时）。

## 三、失效链路根因小结（Phase 1 输入）

1. **FGRelationExtractor**：启动一次性+24h节流 ≠ 定时任务；Mock 降级返回 persons 非 relations（双缺陷）。→ Phase 2 应替换为真正的定时 LLM 提取器（FGEntityExtractorService），Mock 兜底须返回 `{"relations":[]}` 同构。

3. **PAE**：存活但对话驱动 → Phase 2 改为手动接口（T009 Phase 2「PAE 改为手动接口」）。
