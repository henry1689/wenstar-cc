# Phase 1（B链路wiki摘要）最终方案评审

## 总体结论：✅ 认可，可以开工

Claude Code 这版方案比 T002 任务书里的原始设计更扎实，特别是"双通道召回"的澄清直接点出了原始设计的盲点。

## 关键改进点（比原设计好的地方）

### 1. 双通道召回（最关键）

**原设计盲点**：T002 只写了"生成摘要写入 block_summary"，没明确说摘要要参与召回排序。

**Claude 指出的问题**：如果摘要只在组被选中后才拼进 hit.text，就会出现"摘要能注入，但不参与选组"——"上次我们聊过想去哪玩"这种问法，原文里没有"玩"字，永远召不回那一组。

**定案**：候选 = 原文命中 ∪ 摘要命中（source_type='dialog_group'）。摘要同时作为召回入口，不是二选一。

**豆包认可**：这是对的。B链路的核心价值就是"通过摘要/关键词召回原文组"，如果摘要不参与选组，B链路就只剩"展示"功能，失去了召回意义。

### 2. summary_state 列设计

用独立的 `summary_state` 列（NULL=待生成/done/failed），不用 block_summary 占位。避免检索读到占位符。细节到位。

### 3. 后台异步生成，不阻塞热路径

- 闭组时只写 NULL，零阻塞
- 每5分钟一批50组，后台异步生成
- 无待处理组时零 LLM 调用（符合"零 LLM 监控"铁律）

**豆包认可**：这个设计对。摘要生成是 LLM 调用，放闭组热路径会拖慢对话响应。

### 4. 批量补全在运行中服务里跑

明确写了"sql.js 内存库 flush 会覆盖离线改库"——这是本仓踩过的坑，写进硬约束是对的。

### 5. 抽样验收标准严格

≥30组，五类闭组原因全覆盖，不按比例分配（后三类只有3~30个，必须全抽或抽满）。这个验收标准比我原来想的严格，好。

## 需要补充确认的4个点

### Q1：三层摘要的具体格式？

T002 里定义的三层是：
- 标签摘要：narrative_tag + 关键词列表（5-10个）
- 叙事摘要：2-3句话概括
- 情感摘要：primary_emotion + emotion_curve总结 + 情感强度峰值

BlockSummaryService 生成的"三层摘要"是否按这个格式？还是 Claude 有更优的格式设计？需要在实现注释或 ADR-010 更新里写清楚。

### Q2：双通道召回的排序权重？

候选 = 原文命中 ∪ 摘要命中后，排序怎么算？
- 原文命中和摘要命中同等权重？
- 还是摘要命中权重低一些（比如 ×0.7）？
- 还是合并计算（同一组既有原文命中又有摘要命中时加分）？

这个直接影响召回质量，需要定清楚。建议：同一组双通道都命中时加权（说明相关性更强），纯摘要命中的基础分略低于纯原文命中。

### Q3：summary_state=failed 的组怎么处理？

- 自动重试（比如重试3次后标记永久failed）？
- 还是人工介入？
- failed 的组在检索时怎么处理（排除还是按原文-only处理）？

建议：自动重试3次，仍失败则标记 failed 并排除出摘要召回通道（但仍可通过原文命中召回）。

### Q4：1轮组（377个，55%）要不要生成摘要？

实测数据说"1轮组377个（55%）"——只有1轮对话的组。这些组内容可能很少（平均1006字符/组，但1轮组可能更少），生成摘要的意义不大，还会消耗 LLM token。

建议：设置最小阈值（比如组内 conversations ≥3条 或 总字符 ≥500）才生成摘要，低于阈值的组标记 summary_state='skipped'，不消耗 LLM。

## 索引体积代价评估

+1016万行（现有191.6万行的58%）→ 约293万行。

**豆包评估**：可接受。理由：
1. search_index 是 n-gram 倒排索引，摘要增加关键词是必然代价
2. 之前刚删了 idx_si_term 冗余索引（48MB），空间有富余
3. 查询性能：n-gram 索引查询是 O(命中数)，不是 O(总行数)，总行数增加不直接拖慢查询
4. 如果后续性能有问题，可以再考虑摘要索引单独存储或分层
