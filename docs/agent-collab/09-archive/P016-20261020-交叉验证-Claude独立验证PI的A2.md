## 二、四项验收

### ① 生命周期规则正确 —— ✅ 全量 0 错配

| 时点 | 组数 | 存储分布 | 独立判据分布 | **规则错配** |
|---|---|---|---|---|
| 重启前 02:20 | 866 | active 588 / consolidating 278 / archived 0 | active 584 + 沉淀窗 4 / consolidating 278 / archived 0 | **0** |
| 重启后 02:35 | 871 | active 592 / consolidating 279 / archived 0 | active 586 + 沉淀窗 6 / consolidating 279 / archived 0 | **0** |

> 两次快照的存储分布与独立判据**逐项吻合**（沉淀窗内的 4/6 组现值为 active，判据要求"不动"，一致）。
> 另：**PI 启动日志的分布 `active=592 consolidating=279 archived=0` 与我的独立快照完全相同** ——
> 执行者与验证者两条独立路径得出同一结果。

**附带证明了 PI 自述的生产缺陷修复有效**：其一，`sql.js` 数组绑参数若未修好，UPDATE 会静默匹配 0 行，
279 个 consolidating 组不可能落库（实测已落库且 0 错配）；其二，落盘条件缺 `dialogGroups` 若未补，
重启后状态会回退（实测重启前后一致）。

### ② 只 UPDATE 不 DELETE（只增不减）—— ✅

- **代码层**：全仓 `src/` 检索 `DELETE FROM dialog_groups` —— **0 处**；`DialogGroupLifecycle.ts` 内只有
  `UPDATE dialog_groups SET lifecycle_state…`，无任何 DELETE。
- **数据层**：跨一次真实重启，组数 867 → **871**，`removed = 0`（只增不减 ✅），
  `lifecycle_state` 无 NULL、无非法值（`other = 0`）。

### ③ 重启幂等 —— ✅（唯一变化是规则本身的边界跨越）

真实 `pm2 restart` 一次：

| 指标 | 结果 |
|---|---|
| 服务日志 | `[Repair] 批次6 组级生命周期流转: 1 组（分布 active=592 consolidating=279 archived=0）` |
| 逐 id 比对（867 组交集） | **state_changed = 1**，新增 4 组，删除 0 |
| 那 1 组 | `00017520261020095709M01DAIG_DG_12870`：active → consolidating |
| 判定 | 该组创建于 09:57（本地），快照时约 39 分钟 —— **刚跨出 30 分钟沉淀窗** ⇒ 这是规则要求的
  边界跨越，**不是无谓流转**；且独立判据显示其新状态与规格一致（`rule_mismatch = 0`） |

⇒ 重启不产生任何"本不该变"的流转，幂等成立。与 P013 报告的 boot2「仅流转 1 组」现象同源。

### ④ archived 组仍可被关键词命中 —— ✅（代码 + 实测双证）

- **代码层**：`src/m4/`（检索层）与 `src/webui/chat/` 中检索路径**没有任何 `lifecycle_state` 过滤**
  （仅出现在建表 INSERT 与测试夹具）⇒ 归档不等于不可召回。
- **实测**（在**副本**上把一个真实组改成 `archived`）：用其原文里的 2 字关键词跑
  `DialogGroupAdapter` → 返回 5 组，**目标 archived 组在其中**（`target_hit_by_dialog_group = true`）。

## 四、方法论

1. **判据必须照抄规格、不照抄代码**：我按 R016 文本重写 `specState`，才能真正回答"实现是否符合设计"
   而不是"实现是否等于实现"。
2. **幂等要看"变化的那一条是不是规则要求的"**：单看 `transitions=1` 会误判为不幂等；
   逐 id 比对 + 复算规格才区分出「边界跨越」与「无谓流转」。
3. **两条独立路径互证**：PI 启动日志的分布与我的独立快照逐项相同，比任何单方自证都强。
