# P039 · T013 Phase1 · PI 设计建议 + 风险清单

> Phase 1 = 设计+骨架（不改核心逻辑）。本文为 PI 侧（数据层+意图识别）设计建议 + **任务书未预见的风险**。
> 结论带代码/数据依据。业主红线「数据保护」贯穿所有建议。

## 一、PI 侧设计建议

### 1.1 加人/减人正则白名单（意图识别）
**复用并收紧现有 detectIntent 状态机**，不另起炉灶。白名单句式：
- 加人：`(叫|让|喊|把)\s*(?:上)?\s*<NAME>\s*(?:也)?(?:来|过来|参加|加入|进来)` + `<NAME>也来/把<NAME>拉进来`
- 减人：`<NAME>(?:先走|先回去|不用来了)` + `让<NAME>离开` + `散会|结束|就到这吧`
- **NAME 必须经 `getUUIDByName` 解析为 FG active 实体**（复用 P0-6 已排除 candidate），解析失败=不操作（模糊情况不操作，符合业主红线）
- **状态机消歧**：无会晤→wake（进入）；会晤中→add/remove。避免「让诗雨和阿芬过来开会」被误判加人（实为唤醒，P0-5 已验证此句式）。

### 1.2 动态参与者管理（单一真源）
- 参与者列表 = `EntityMeeting._multiParticipants` 现有结构（EntityInfo{name,uuid,category}）**提升为新状态机的唯一真源**，所有层（记忆/档案/情感/场景）按它取。
- 加人/减人只改这个列表 + 记日志（业主红线：所有操作写日志）。

### 1.3 记忆检索隔离（UUID 过滤，收口到咽喉）
- **现状风险**：UUID 过滤分散在 retrieval-stage 多处 `policy.enforce`，I007 就是某处 `enforce:false` 致空子句→全库召回串档。
- **建议**：新架构把 UUID 过滤收口到**一个强制函数**（如 `applyMeetingUuidFilter(ctx, uuid)`），所有检索路径必须过它，且默认 deny-by-default（无 uuid=返回空）。与我 3b 在 `_addEdgeInner` 加写入闸门同一思路（咽喉收口）。

### 1.4 FG 档案隔离
- 只注入**当前发言者** dossier（复用 `EntityContextBuilder.buildEntityContext(uuid)`）。
- 其他参与者只注入**摘要**（name+relation+一行简介），不注入完整档案（防跨人格信息泄漏 + 控 prompt 长度）。
- relationMap 只注入「当前发言者 ↔ 用户」那条边（现有 EntityContextBuilder 已按此读，复用）。

### 1.5 时间分隔（微信记录式）——⚠️ 与闭组是两件事
- **显示分隔线**（用户要的"1分钟"）：前端/注入层，距上次消息 >1min 且新一轮开始 → 写一行「今天 HH:mm」分隔。**纯显示，不闭组**。
- **闭组**（现有30min，chat.ts:2603 `_dgIdleCloseMs=30*60*1000`）：不动，保持30min。
- **两者解耦**：1min 只影响显示分隔，30min 才闭组。避免"1分钟就闭组"破坏连续对话。

### 1.6 旧数据兼容（红线）
- 新架构**只读**旧 dialog_groups/conversations/memories/nodes/edges，不改格式。
- 检索接口 `runSearch/runRetrieval` 签名不变（现有23个测试套依赖）。
- 新对话新格式 = 新增列/新表（additive），旧数据原地。

## 二、🔴 任务书未预见的风险（按严重度）

### R1【P0】双 sql.js 内存库互相覆盖（新旧架构共存期）
- 依据：sql.js `export()` 序列化**整个内存库(~96MB)** 防抖落盘（SQLiteAdapter:305）。经验#19/I005 实证：两个持有内存库的进程/路径，后落盘者**整库覆盖**前者。
- 风险：新旧架构过渡期若各自持内存库写入 → 互相覆盖，正是"日志成功、库里NULL"。**Phase 4 灰度期极易触发**。
- 建议：过渡期**严格单写者**（新架构接管写入后，旧路径只读）；或双写同一内存库实例（不新建第二实例）。

### R2【P0】七层隔离 = 每轮 +2 次 LLM 调用（语音实时性风险）
- 依据：Layer1 发言者判断（LLM）+ Layer7 输出校验（重生成）。语音聊天要求低延迟。
- 风险：每轮多2次 LLM = 延迟翻倍 + token 成本翻倍，语音场景卡顿。
- 建议：Layer1 用 **rule-first**（点名/提及命中就定，不调 LLM；仅歧义时 LLM——我 P012 的 inferSpeaker 已是此结构）；Layer7 校验用**轻量自称一致性检查**（正则抽 speaker 自称 vs 期望），非整段重生成。

### R3【P0】"不确定默认玉瑶"在多人会晤中破坏沉浸
- 依据：Layer1 说"不确定默认玉瑶"。但玉瑶通常**不是会晤参会者**。
- 风险：多人会晤中发言者判不出 → 默认玉瑶 → 玉瑶突然插话，打断会晤（正是业主要避免的）。
- 建议：默认应为**当前主发言**（会晤中）/玉瑶（非会晤）。仅非会晤态才默认玉瑶。

### R4【P1】旧 EntityMeeting 废弃会重引入历史边缘 bug
- 依据：EntityMeeting 累积大量边缘修复（P0-5 多人唤醒别名/语序、P1-3 点名切换、exit 语法位置、天界会晤现场保存…），我有 18 例回归测试锁着。
- 风险：Phase 4 "废弃旧状态机"若重写，这些 bug 会回归。
- 建议：新状态机**移植**我的 18 例回归测试用例（行为不变式），而非从零重写。

### R5【P1】加人减人正则白名单的唤醒/加人歧义
- 依据：P0-5 实测「让诗雨和阿芬过来开会」是**多人唤醒**，但含"让+名+过来"=加人白名单句式。
- 风险：白名单不消歧会把唤醒误判加人。
- 建议：白名单判据必须**先看状态**（无会晤→唤醒；会晤中→加人），且多人目标（≥2人）一律走唤醒不走加人。

### R6【P1】UUID 过滤收口不彻底会重演 I007
- 依据：I007 根因 = 某检索路径 `enforce:false` 致 UUID 子句空串→全库召回串档（retrieval-stage:458）。
- 风险：新架构若有任何检索路径绕过 UUID 过滤 → 串档复发。
- 建议：UUID 过滤做成**编译期强制**（类型上 ctx 必带 uuid）+ 运行期 deny-by-default + 单元测试覆盖所有检索入口。

### R7【P2】情感/场景隔离的状态持久化
- 依据：Layer5/6 要每人独立情感/场景状态。现情感快照在 DB（emotion_snapshots 存量）。
- 风险：若新状态存内存，重启丢失；若存 DB，红线禁改表（只能新增列/表）。
- 建议：存 `properties.dossier`（JSON，additive）或新表 emotion_scene_state（additive），不改旧表。

### R8【P2】压测 1000 轮的成本/可行性
- 风险：1000轮真 LLM 压测 = 高成本 + 慢。
- 建议：**结构压测用 Mock LLM**（固定 speaker/content 输出，验状态机/隔离逻辑）+ **小样本真 LLM**（如50轮验 prompt 效果）。分开统计。

### R9【P2】回滚方案的"新数据可读性"
- 风险：若新架构写新格式且旧架构读不了，回滚后新数据成黑洞。
- 建议：新数据放**新表/新列（additive）**，旧读路径忽略它们；回滚=切回旧读路径，新数据留着但旧不读（可接受），或双写过渡。

### R10【P3】会议总结（会议模式独有）与群聊的代码分叉
- 依据：用户说"会议模式仅多一个会议总结"。
- 风险：若为这点差异分叉两套状态机，回到多路径分裂老路（正是 T011 刚统一的词表分裂教训）。
- 建议：单一状态机，会议总结作为**可选 hook**（会晤结束时触发），不另起分支。

## 三、建议的实施顺序调整
1. **先做 R1 单写者 + R6 UUID 收口**（数据保护红线相关，最高优先），再做七层隔离。
2. 七层隔离中 **Layer1/Layer7 的 LLM 成本**（R2）先用 rule-first 落地，LLM 兜底后接。
3. Phase 4 废弃旧代码前，**先移植18例回归测试**到新状态机（R4），再删。
