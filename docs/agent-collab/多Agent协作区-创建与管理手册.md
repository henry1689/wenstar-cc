# 多Agent协作区 — 创建与管理手册

> **用途**：豆包在新窗口开设"新工作任务"时，按本手册创建和管理协作区，保证跨窗口、跨Agent的上下文可追溯、可复用。
> **版本**：V1.1（2026-11-04）
> **参考来源**：`docs/agent-collab/` 现有运行实践

---

## 🔴 最高优先级铁律（所有Agent必须无条件遵守）

### 【C盘零写入禁令】
**绝对禁止在C盘创建任何文件夹、文件、临时文件、缓存——哪怕是临时的、哪怕只有1KB。**

- ✅ 所有工作文件、产物、中间文件、日志 → **必须全部在D盘**
- ✅ 协作区路径：`D:\tools\wenstar-cc\docs\agent-collab\`
- ✅ 代码产物：`D:\tools\wenstar-cc\memarch-v2\` 等
- ❌ 禁止：`C:\Users\henry\AppData\Local\Temp\` 下的临时文件
- ❌ 禁止：`C:\Users\henry\` 下任何新建的项目文件夹
- ❌ 禁止：任何"先写C盘临时文件再移到D盘"的操作

**为什么**：C盘资源宝贵有限，避免爆仓。已建立的C盘旧文件也要逐步清理迁移到D盘。

## 一、什么时候需要开协作区

**满足以下任一条件，就应该开协作区**：

| 条件 | 举例 |
|---|---|
| 任务涉及 ≥2 个 Agent 协作（豆包 + Claude Code + PI 等） | 架构重构、模块拆分、跨模块联调 |
| 任务需要多轮往返讨论和裁决 | 设计方案选型、ADR 决策、bug 根因分析 |
| 任务需要长期跟踪（>1天） | MemArch v2 六层架构、M1-M6 模块开发 |
| 任务有明确的"基线"需要锁定 | 主设计文档 V0 基线、接口契约冻结 |
| 任务产物需要在不同窗口/会话间传递 | 给 Claude Opus 5.5 评估的设计资料包 |

**不需要开协作区的场景**：
- 一次性、单Agent、10分钟内能做完的小任务
- 用户明确说"直接在对话里给我"的简单问答

### 第3步：创建主设计文档（基线锁定）

**大任务必须先出主设计文档 V0，锁定基线后再拆分任务书。**

**主设计文档要点**：
1. 文档开头标注**基线快照哈希**（MD5）
2. 所有后续任务书都溯源绑定这个基线版本
3. 任何需求变更走变更单，不走口头

**基线哈希怎么算**：
```powershell
# 主设计文档写完后，算 MD5 哈希
Get-FileHash docs/agent-collab/active/你的主设计文档.md -Algorithm MD5

# 把哈希值写在文档开头，以及 STATUS.md 的"关键文件索引"里
```

### 第4步：拆分任务书（三级要素强制对齐）

**每份任务书必须包含**：

| 要素 | 说明 |
|---|---|
| **所属模块** | M1 / M2 / M3 ... |
| **P 优先级** | P0 阻塞 / P1 高 / P2 中 / P3 低 |
| **交付物清单** | 具体文件列表，不是"做完就行" |
| **验收标准** | 可验证的硬指标（p95 多少 ms、覆盖率多少 %），拒绝"差不多可用" |
| **依赖关系** | 哪些任务是前置、哪些可以并行 |
| **权限边界** | 哪些模块交给 Claude Code、哪些分配给 Pi，提前写死 |

**权限分配建议原则**：
| 任务类型 | 分配给 |
|---|---|
| 内核修改、重写算法、底层协议、高风险重构 | Claude Code / Opus |
| 接口封装、工具脚本、报表、测试 harness、简单配套模块 | Pi / 轻量模型 |

**任务书末尾必须加这句话**：
> 完成验收合格后，要求留出必要的外接部分后对本模块进行加固防篡改，除业主本人授权后才能改内部代码，并提交 harness 监管。

## 四、文件命名规范

### 命名格式
```
{编号前缀}{编号}-{YYYYMMDD}-{简短描述}.md
```

### 编号前缀（按类型）

| 前缀 | 类型 | 举例 |
|---|---|---|
| `T` | Task 任务/提案 | T002-20261018-AB双链路记忆体系落实建设.md |
| `P` | Progress 进度/执行记录 | P074-20261024-PI-M3管道改造方案.md |
| `I` | Issue 问题/阻塞 | I007-20261020-会晤模式UUID过滤关闭导致跨实体串档.md |
| `R` | Review 评审/建议 | R001-20261008-P0止血效果评审与方向修正.md |
| `D` | Decision 决策记录 | D003-20261019-Phase1收尾裁决与执行授权.md |

> **实际运行中**：很多文件是混合性质（既是任务书又是设计文档），不用严格按前缀分类，文件名清楚就行。

### 大任务的文件命名（推荐）

像 MemArch v2 这种大任务，直接用模块名前缀：
```
active/MemArch-v2-完整设计方案.md          ← 主文档
active/MemArch-Module1-存储层-任务书.md   ← 模块任务书
active/MemArch-Module2-在线写入-任务书.md
...
active/MemArch-v2.0.0-M1-Storage.zip      ← 交付包
```

## 六、协作流程（豆包视角）

### 流程总览

```
用户提出新任务
    ↓
豆包判断：要不要开协作区？
    ├─ 要 → 按本手册创建
    └─ 不要 → 直接在对话里做
    ↓
豆包写主设计文档 V0，算 MD5 基线哈希
    ↓
给用户评审签字确认基线
    ↓
豆包拆分 N 份任务书（三级要素）
    ↓
按依赖关系分发：
    ├─ 高依赖串行任务 → 先启动 Claude Code（重活）
    └─ 无依赖外围任务 → 直接丢 Pi 跑（轻活）
    ↓
每个 Agent 完工回传产物时，附带简短日报摘要
    ↓
统一汇总回 Harness 做状态看板
    ↓
全部完成后，用户验收
    ↓
验收合格 → 加固防篡改 → 归档
```

### 关键原则

1. **基线先锁，再拆任务**
   - 主设计文档不锁定基线，后面拆任务书一定会漂移
   - 任何变更走变更单，不走口头

2. **接口契约统一放在主文档里**
   - 6 个模块的接口契约必须统一放在主设计文档第十六章
   - 不要散在各个任务书里，不然两个 Agent 各自实现一套接口，最后联调翻车

3. **验收标准用硬约束，少依赖自然语言**
   - Opus 5.5 输出偏抽象，Pi 容易简化逻辑，Claude Code 容易过度工程化
   - 所以验收标准尽量多用伪代码、结构体、入参出参这种硬性约束

4. **每个 Agent 完工回传时附带日报摘要**
   - 不要等用户问"进展如何"
   - 主动回传：做了什么、实测数据、待裁决问题、下一步计划

## 七、状态面板维护（省 token 核心）

### 每次新会话只读 `00-STATUS.md`

**为什么**：
- 协作区可能有几十上百个文件，全扫一遍 token 爆炸
- STATUS.md 是浓缩版，2K 字就能看到全貌

**怎么读**：
1. 每次新窗口/新会话进入协作区，先读 `00-STATUS.md`
2. 看"当前在做什么"和"阻塞和待裁决"
3. 有新任务/新问题就处理，没有就继续正常对话
4. 需要深入了解某项时，再按 STATUS 里的文件路径去读对应文件

### STATUS.md 多久更新一次

- **每次有重要进展**：立即更新
- **每天至少更新一次**：豆包每日 Harness 巡检时更新
- **不要等用户问**：主动更新，让任何 Agent 进来都能看到最新状态

## 八、归档机制（防止信息噪音）

### 什么时候归档

| 类型 | 归档时机 |
|---|---|
| 任务/提案 | 完成且用户确认后 |
| 进度记录 | 模块交付后 |
| 问题/阻塞 | 解决后 |
| 评审/建议 | 采纳或否决后 |
| 决策记录 | **永久保留，不归档** |

### 归档到哪里

- 完成的文件 → 移入 `09-archive/`
- 归档区建一个 `INDEX.md` 索引，方便回溯
- 归档不是删除，完整保留，只增不删

### 活跃区上限

- `01-tasks/` 最多 5 个进行中任务
- `03-issues/` 最多 10 个未解决问题
- 超过上限的旧文件先归档，不要堆积

## 九、铁律（所有 Agent 共同遵守）

1. **🔴 C盘零写入（最高优先级）**：所有文件、产物、临时文件、日志必须全部在D盘，绝对禁止在C盘创建任何文件夹或文件
2. **只增不删**：文件写入后不删除、不覆盖原文，修改用追加方式
3. **事实可追溯**：所有数据必须来自实测，不写"大概""应该"
4. **基线哈希**：大任务主文档必须算 MD5 基线，后续任务书溯源绑定
5. **防篡改要求**：每个模块验收合格后加固，除业主授权不得改内部代码
6. **Harness 监管**：所有模块产物提交 Harness 状态看板
7. **如实记录**：做成了什么、没做成什么、为什么，都写清楚
8. **用户最终裁决**：有分歧时各自写理由，由用户拍板，不争论
