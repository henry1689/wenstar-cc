## 一、双来源提取器设计（FGEntityExtractorService）

### 1.1 触发〔建议①：事件驱动 + 定时补漏〕
| 触发 | 时机 | 说明 |
|---|---|---|
| **主：闭组事件** | 对话组闭组（`block_close_reason` 落库）后异步触发 | 上下文最完整；不耗对话热路径 token；即时性好 |
| **次：文档事件** | 知识库个人档案文档上传/更新后触发 | 来源二 |
| **兜底：定时补漏** | 每日 03:00 扫描「已闭组但未提取」的增量 | 修补漏触发 |

- **幂等游标**：`engine_store.fg_extract_cursor`（上次处理的 dialog_group seq / 文档 version），只处理新增。
- **禁用**旧的「启动一次性+24h节流」（P032 实证该设计致 FGRelationExtractor 产出恒0）。

### 1.2 处理单元
- **对话组**：整组（非逐句/RAG）。取 `conversations WHERE dialog_group_id=?` 全轮 + 组级 `block_summary` 作上下文喂 LLM。
- **文档**：整篇 .md/.txt/.pdf 文本 + 文档元信息。

### 1.3 准入门槛（户籍法第二十二条，提 3.1 的2/3条件）
实体需满足 ≥2 条才录入：①有明确交互 ②有特征描述 ③有持续提及。不满足 → 不建节点（宁缺勿滥，防幻觉垃圾）。

## 二、统一 prompt 模板 + JSON schema

### 2.1 JSON schema（唯一契约，Mock/降级/异常同构〔建议④〕）
```json
{
  "entities": [{
    "name": "法定本名", "type": "person|org|place|object|event",
    "aliases": ["昵称/称谓"], "category": "S|U|A|B|X|G",
    "entity_source": "real|ai|fictional|historical|placeholder",
    "confidence": 0.0,
    "dossier": { "basicInfo": {}, "selfProfile": {}, "socialIdentity": {}, "lifeMilestones": [], "misc": {} },
    "evidence": "对话原文片段/文档摘录"
  }],
  "relations": [{
    "from": "本名", "to": "本名", "relation": "∈RELATION_TYPE_DEFS",
    "confidence": 0.0, "evidence": "…", "sourceRef": "dialog_group_id|doc_id"
  }],
  "reasoningTrace": "…"
}
```
- **canonical 空结构**：`{"entities":[],"relations":[],"reasoningTrace":"<why>"}` —— DeepSeek/Mock/异常/超时**一律返回该同构**，靠 TS 类型约束（非注释）。修复 P032 的 Mock 返回 `persons` 非 `relations` 缺陷。

### 2.2 prompt 要点
- system：`你是人物档案与关系提取专家，只输出符合 schema 的 JSON，不解释不编造未出现的信息。`
- user：注入〔完整对话组/文档〕+ 当前时间 + 关系类型字典（RELATION_TYPE_DEFS 的 relation+label 列表，强制 LLM 只从中选）。
- temperature 0.1；输出超时/非 JSON → 返回 canonical 空结构（不重试污染，交补漏任务）。

## 三、三级去重规则〔建议⑤⑥〕

### 3.1 实体去重
- 主键：**TXS-UUID**；辅助：规范化 name + aliases。
- 合并判据：新实体 name/alias 命中已有节点（精确 name → aliases → 唯一子串）→ 合并进已有节点（**绝不新建重复人**，同 P029 都灵/陈都灵合并教训）。
- **UUID-at-creation**〔建议②〕：确认新建时**同事务分配 TXS-UUID** + 过 EntityWriteGate 姓氏/白名单校验；**禁止 uuid=NULL**（P0-2/P1-3）。

### 3.2 关系去重（幂等键带溯源〔建议⑤〕）
- 幂等键 = `(source_id, target_id, relation, created_from)`，其中 `created_from = dialog_group_id | doc_id`。
- 同边同来源重处理 → 更新置信/证据（取更高）；同边不同来源 → **并存**，按来源优先级合并展示。
- `relation` 必须 ∈ RELATION_TYPE_DEFS（单一真源）+ **启动断言**：写入白名单 ⊆ DEFS，违反 fail-fast〔建议③〕。
- 低置信（<0.7）→ PendingItem（见 3.4）。

### 3.3 字段去重（dossier）
- 幂等键 = `dossier.<fieldPath>`。
- **来源优先级：文档 > 对话推断**〔建议⑥〕：文档来源字段**强制覆盖**；对话来源只填文档缺失字段，不覆盖已有值。
- `_systemReadOnly` 字段永不覆盖（现有保护保留）。

### 3.4 PendingItem 去向〔建议⑦〕
- 0.4-0.7 置信 → PendingItem，**必须有去向**（否则重蹈 security_level/circle_level 死字段覆辙）：
  - 每日汇总「今日待确认档案 N 条」，用户一句话确认/否决；
  - TTL 30 天未确认自动过期清除（防累积）。
- 确认后升级为正式字段（写 _changeHistory + source=用户确认）。

### 3.5 变更流水
- 所有写入记 `_changeHistory`（户籍法第十九条六，上限10000）：`{time, operation, field, before, after, reason, source}`。
