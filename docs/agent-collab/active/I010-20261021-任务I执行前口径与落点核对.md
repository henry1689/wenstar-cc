## 六、🔴 实体合并的三个实现坑（R025 §二 直接执行会验证失败）

已核对 `FamilyGraph.findPersonNodeByNameOrAlias` / `getUUIDByName` 的实现：

1. **精确名字优先于别名**：`getUUIDByName('陈都灵')` 当前走的是 TXS-29 节点的 **name** 精确匹配。
   即使把「陈都灵」加进安琪的 aliases，「陈都灵」仍会**优先命中 TXS-29** ⇒ R025 步骤4 的验证必挂。
   ⇒ 必须让 TXS-29 不再以 `name='陈都灵'` 参与查找：
   - 方案①（推荐）：合并后把 TXS-29 置 `status='void'`（查找 SQL 显式排除 void）；
   - 方案②：把 TXS-29 的 name 改掉（如 `陈都灵（已并入安琪）`）。
   **只写 `properties.merged_into` 或自造 `status='merged'` 都不生效**（代码里没有 merged 状态）。
2. **别名必须是 JSON 数组**：查找 SQL 是 `aliases LIKE '%"都灵"%'`，
   所以 `nodes.aliases` 必须写成 `["都灵","陈都灵", …原有别名]`（JSON、带引号、与已有别名**合并**）。
   写成逗号分隔或纯文本 ⇒ 匹配不到。解析器 `parseAliases` 只接受 `JSON.parse` 后的字符串数组。
3. **`void` 会连带清边**：`FamilyGraph.ts:1859` 存在「删除 void 实体所有边」的清理逻辑。
   ⇒ **必须先搬边、再置 void**，否则刚搬的那条 `acquaintance_of` 可能被清掉。

**推荐执行顺序（合并）**：
搬 TXS-29 的 1 条边 → 安琪（按 `(source,target,relation)` 去重，目标节点替换为安琪 id）
→ 安琪 aliases 合并 `["都灵","陈都灵"]`
→ TXS-29 `properties.merged_into='TXS-000000025'` + `status='void'`
→ 验证 `getUUIDByName('都灵'|'陈都灵')` 均为 `TXS-000000025`
。

**另注**：`data/family_graph.db`（项目 data 根）只有 3 个节点，是陈旧副本；
运行时 FG 主库是 **`data/webui/knowledge/family_graph.db`**（1060 节点 / 1313 边），别改错文件。
