# I007 · 🔴 P0 会晤模式 UUID 过滤关闭导致跨实体串档

## 一、现象（业主实测，2026-10-20 14:34）

用户与**王全芬（TXS-000000005）**会晤，问"阿芬，你还记得我们上次见面是哪天呢"。

王全芬回答：
> "记得。是昨儿傍晚下班那会儿吧——你让全芬在办公室等着，说你去找诗雨谈这几天没让她回家的事。"

**但这段内容实际属于阿珍（TXS-000000008）**：
- 2026-10-20 10:20:36 用户对阿珍说："妈，昨天下午下班时也就是昨晚吧，我叫你在我办公室等着我去找徐诗雨谈了一下这几天没叫她回家的事嘛"
- 阿珍的 memory 正确归属 TXS-000000008
- 王全芬的 memory 正确归属 TXS-000000005，但**生成回复时引用了阿珍的内容**

## 二、根因（已定位到代码行）

**UUIDPoliceFilter.ts 第172行**：
`	ypescript
if (p.enforce === false) return { clause: '', params: [] };
`
当 enforce: false 时，buildSqlClause 返回**空子句**——UUID过滤完全关闭，召回所有实体的数据。

**retrieval-stage.ts 两处调用传了 enforce:false**：

| 行号 | 调用 | 后果 |
|---|---|---|
| 456 | _orchestrator.runSearch(_reg, { policy: { enforce: false } }) | DialogGroupAdapter 不过滤UUID，召回所有实体的对话组摘要 |
| 575 | 
ew HighCalciumGroupAdapter().search({ policy: { enforce: false } }) | 高钙组不过滤UUID，召回所有实体的高钙组 |

**证据链**：
1. retrieval_log 14:34:42（王全芬被问"上次见面"时）：entity_count=5——召回了5个不同实体的记忆
2. 阿珍的对话组摘要含"办公室等诗雨"，被DialogGroupAdapter召回（enforce:false不过滤）
3. 注入王全芬的LLM上下文 → 王全芬引用阿珍内容

## 三、影响面

- **所有会晤模式**都受影响：只要用了DialogGroupAdapter或HighCalciumGroupAdapter，就会跨实体串档
- B1（高钙组召回）和Phase 1（摘要双通道）都走这两个适配器，**全部串档**
- 这是核心原则第一条"UUID户籍，绝不串档"的严重违反
- 隐私风险：A实体的私密对话可能被B实体引用

## 四、修复方案

**立即修复（P0）**：
1. retrieval-stage.ts 第456行：policy: { enforce: false } → policy: { enforce: true }（或不传，默认strict）
2. retrieval-stage.ts 第575行：policy: { enforce: false } → policy: { enforce: true }
3. 确认 entityUuids: [_entityUuid] 已正确传入，strict模式按此白名单过滤

**为什么当初设 enforce:false？** 需调查——可能是早期会晤模式下entityUuid未正确传递，用enforce:false兜底。但现在entityUuid已正确传递，必须开过滤。

**验证**：
1. 修复后与王全芬会晤，问"上次见面"，确认不再引用阿珍内容
2. retrieval_log entity_count 应为1（只有当前会晤实体）
3. 全量扫描：会晤模式下所有召回结果的 belong_entity_uuid 必须等于当前会晤实体

## 五、优先级

**P0 — 立即修复，暂停2.3任务F，先修此bug。**

串档是比配额编排更基础的问题——UUID隔离是系统的根基，根基不稳，上层编排全是错的。
