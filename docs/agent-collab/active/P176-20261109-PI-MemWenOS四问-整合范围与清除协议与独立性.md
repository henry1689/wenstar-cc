## 问题一 · MemWen OS 整合了 Wenstar 的哪几大块？

**不是新造一套，是把现有六大块"认领归位"到统一架构**（P174 扫描已实证：五层物理结构已存在）：

| MemWen 层 | 整合的 Wenstar 现有大块 | 关键文件/表 |
|---|---|---|
| **MW-Gateway 写入层** | ① 写入链：persistence-stage → **MemoryWriteGateway**（批4b 收口中）→ SQLiteAdapter 三入口 + DualHelixWriter（DNA 双螺旋）+ memory-identity（genes/编码） | `src/webui/chat/persistence-stage.ts`、`src/m2/*` |
| **MW-Store 存储层** | ② 存储底座：fusion_memory.db 六主表（memories 68列/dialog_groups/conversations/black_diamond/knowledge_base/memsym_elements）+ **zvec C++ HNSW** + FTS5 | `data/webui/fusion_memory.db`、`src/app/knowledge/*` |
| **MW-Read 读取层** | ③ 检索链四路：槽位（retrieval-stage/meeting-recall）、40D 语义联想（MemoryRetriever）、关键词（sweep+FTS5）、摘要（组摘要/高钙组/素材包）+ **五级闸门** + **RecallBus 层保底** + 配额 | `src/webui/chat/retrieval-stage.ts`、`src/m4/*`、`src/m3/FiveStageGate.ts` |
| **MW-Consolidate 巩固层** | ④ 仿生巩固遗忘：钙化 L0-L3、黑钻结晶、**decay 遗忘曲线**（decay_log 9万条）、**dream 梦境整合**（653条）、BlockSummary 组摘要 | `src/app/memory/*`、`src/m3/*` |
| **MW-Archive 归档层** | ⑤ **BlockArchive 哈希封存** + 备份链 + schema_version 迁移 | `src/app/memory/BlockArchiveService.ts` |
| **MW-Govern 治理层** | ⑥ 治理体系：ADR/蓝皮书/法规注释、**Harness S1-S7**、313 测试文件、守卫矩阵 | `docs/adr/*`、Harness |

**明确不纳入（边界）**：
- **FG 户籍图谱**——最高安全资产，MemWen **只引用不动**（belong_entity_uuid/entity_genes 是接口）；
- **40D 唤醒 / SpaceState 新模块**——业主明令 40D 链路不碰，等新模块联调；
- **知识库线**（knowledge_base 独立检索）——与 MW-Read 有交叠，边界在 M1 审计时定；
- **会晤/roleplay/上层应用**——消费方，不属于记忆系统本体。

## 问题二 · 怎样整合进去？

**不是搬代码，是四步"归位"**（每步 Harness 走批）：

1. **逻辑归位**（零代码）：六大块打上 MW 层标签，写进 ADR-024——**已完成**（本文件表一即归位表）；
2. **收口**（M1）：三写入口收口到 **MemoryWriteGateway 单入口**；观测/守卫/迁移挂 MW-Govern；事件流逻辑视图+outbox；
3. **新增件**（M2-M5）：真正的新东西只有——`src/memwen/` 核心库（§问题四）、意图路由 MW-Route、dense 第五路、dormant/forgotten 状态、查询改写、动态预算、双时态版本行；
4. **接线**（贯穿各期）：现有模块**改为调用** memwen 核心的函数（`strengthDecay`/`allocBudget`/`dormantPredicate`…）——**公式唯一实现落核心库，旧模块只做 I/O 适配**。

## 问题三 · 如何彻底清除被替代的旧系统？

**替代清单**（每期明确，现已确定的主要项）：

| 被替代的旧实现 | 替代者 |
|---|---|
| `C = histChars × 1.0` 预算公式（R3 正反馈源） | `allocBudget` 动态解析解 |
| 固定配额 A30/B50/C20 | 指代依赖度自适应 ρ |
| `suppressed` 单态（141 条一刀切） | `dormant`（可唤醒）/`forgotten`（吸收态）双态 |
| TF-IDF hash 256 维顶替 dense | dense 第五路（model@ver 版本绑定） |
| 失效"原地写 invalidated_at" | append-only 版本行（v2 已纠正） |
| 绝对余弦阈值（0.45/0.35） | z 值分位标定（按 model@ver） |
| `recall_count DESC` 排序马太（P167-⑥） | 探索配额/去马太（M4 若裁决做） |
| 单链哈希（与删除冲突） | 分段+墓碑+外部锚定 |

**五步退役协议**（防"新旧并存混乱"，每步 Harness 收口）：

```
① 新实现上线 + 守卫矩阵全绿 + MW-Bench 不降（留出集下界）
② 旧路径挂 config 开关降级（默认仍走旧路）→ 切换到新路
③ 观察期（N 天，指标对比：四层指标 + 生产日志前后值）
④ 物理删除：代码移除 → grep 零引用验证 → 全量测试（差集证据）
⑤ ADR 记录退役 + STATUS 推送
```

- **可回滚**：②的开关在④之前始终可切回；
- **数据永不删**：被替代的只是**代码路径**；数据走 append-only（事件流/墓碑），历史可重建；
- **先例**：ADR-022（删零调用导出/合并双闸门）就是这套协议的执行样本——**有成功先例**。

## 问题四 · 新系统在哪里？能独立加固维护吗？

**诚实说明现状**：MemWen OS 目前**不是物理实体**——它是横跨 `src/m2/m3/m4/webui` 的**逻辑架构层**（文档+宪法已立，代码散在原处）。

**独立性方案（建议，待你拍板）——渐进物理化，三阶段**：

| 阶段 | 形态 | 独立性 |
|---|---|---|
| **现在（M0-M1）** | 逻辑层：ADR-024 + 附录 v2 宪法绑定，代码在原处 | 宪法独立、代码未独立 |
| **建议（M1 起）** | **新建 `src/memwen/` 独立核心库**：附录 v2 的 16 条守卫对应的**纯函数全部落这里**（`strengthDecay`/`dormantPredicate`/`allocBudget`/`rewriteGate`/`rrfFuse`/`chainHash`/`asOfFilter`/`conflictAction`/`wilsonCI`/`blendScores`/`layerWeights`/状态机…） | **核心独立**：纯函数、零业务依赖、可独立跑属性测试/蜕变测试 |
| 远期（M4+） | 各旧模块逐步改为 `import { mwXxx } from '../memwen/'`——**依赖方向单向**：memwen 不 import 业务代码，业务 import memwen | 核心库可独立加固（守卫即规格）、独立维护（公式↔函数↔守卫三联表就在附录） |

**为什么这样能独立**：
1. **公式唯一实现**落 `src/memwen/`——附录 v2 §八 16 条守卫**全部测这个库**，不依赖数据库/LLM/服务（纯函数）；
2. **依赖单向**：业务层怎么改，核心库不受影响；核心库改了，守卫立刻全量把关；
3. **独立测试**：蜕变测试 9 条 + 属性测试在 memwen 内闭环，毫秒级，无需起服务；
4. **不独立的部分**（SQLiteAdapter/服务装配）仍受 Harness + 单写入口收口管辖——**"能独立的独立，不能独立的收口"**。

**为什么不建独立仓库**：MemWen 与主系统耦合在数据 schema（fusion_memory 六表）与服务装配上，拆仓成本远超收益；`src/memwen/` 目录级隔离 + 依赖单向已足够获得"独立加固维护"的全部好处，且**零迁移风险**。
