## 问题一 · 守恒 SQL 提供，及"23 条 test vs 0 条"的时点差异解释

### 1.1 守恒 SQL（当时口径，原样提供）

```sql

SELECT COUNT(*) FROM memories WHERE belong_entity_uuid = 'TXS-000000007';
-- 硬过滤（唯一排除条件, 与 P167 §一.① 一致）
SELECT COUNT(*) FROM memories
 WHERE belong_entity_uuid = 'TXS-000000007'

-- ⇒ 当时: 7135 - 23 = 7112（= 我报的"硬过滤通过"）
```

### 1.2 "23"与 CC 附录 A 的"0"都是真的 —— 时点不同，有备份链为证

| 时点 | `namespace='test'` | 证据 |
|---|---|---|
| 11-09 12:15（批6 启动前备份） | 全库 **0** | `data/backups/batch6-20261109041506` |
| 11-09 12:37–12:53（批6b/6c/6d 三份备份） | 全库 **38** | `batch6b/6c/6d` 三份整库备份 |

| ≈15:00（我跑守恒审计时） | 007 名下 **23** | conservation 输出 `7135-23=7112`（期间探针又写入 3 条） |
| ≈19:xx（CC 附录 A 快照） | 全库 **0** | CC 复核 + 我 20:2x 复跑：**007=0 / 全库=0** |

**结论**：
1. **23 条真实存在**（备份链 12:37 起全库 38 条可证，非幻觉）；
2. 12:15→12:37 的 0→38 是**批6 执行期间 roundtrip 探针写入生产库**（P168 §二.A 已立案的同一现象——"验收探针应只写副本"）；
3. **15:00→19:00 的 23→0 是被清理**——全库 `DELETE ... namespace='test'` 无直接代码命中（已 grep），清理方**待查**（嫌疑：maintenance GC / 批7 验收清理 / 业主授权的数据线动作）。**此为账实问题，移交批8 查清**（P168 §二.A 的"探针为何写进生产库"合并立案）；
4. **方法论教训（认）**：分母必须标注**快照时点**——同一指标 4 小时内 0↔38↔0 波动，任何守恒数字脱离时点即不可比。我 P167 初版未标快照时刻，**修订时已补**（本文即补）。
