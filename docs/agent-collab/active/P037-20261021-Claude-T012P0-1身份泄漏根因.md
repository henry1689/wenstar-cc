# P037 · T012 P0-1 压测身份切换根因定位（Phase A/B，未改代码）

**只读摸底 + 离线探针，零生产代码改动。**

## 一、现象回溯（业主实测）

> 压测时和徐诗雨会晤中，回复者突然变成玉瑶，但内容还是徐诗雨口吻。

## 二、根因（三处缺陷叠加，缺一不发病）

### 🔴 缺陷①（主因）：角色路由早于会晤状态机执行

`src/webui/chat.ts` 同一函数体内两段逻辑的**执行顺序倒置**：

| 步骤 | 位置 | 动作 |
|---|---|---|
| 1 | `chat.ts:494` | `const _inMeeting = ctx._entityMeeting?.isActive?.() ?? false;` —— 此刻**尚未** enter |
| 2 | `chat.ts:496-505` | 非会晤分支 → `classify()` + `evaluateTransition()` → `_currentRole = 'secretary'` |
| 3 | `chat.ts:808-822` | 会晤状态机才执行 `detectIntent()` / `_em.enter()` / `_em.enterMulti()` |
| 4 | `chat.ts:953` | `_meetingEntityName = getEntityName()` |
| 5 | `chat.ts:2489` | `m5.orchestrate(..., _currentRole, !!_meetingEntityName, ...)` |

**相隔 314 行。** 唤醒轮 / 加人轮 / 换人轮：步骤 2 按「非会晤」分类定格角色，步骤 3 才进入会晤，
步骤 5 以 `isEntityMeeting=true` + **玉瑶角色**双参调用 M5。

### 🔴 缺陷②：角色 prompt 的会晤隔离只覆盖 recaller 一支

`src/app/role/RoleProfiles.ts:156-180` 的 `buildRoleSystemPrompt(role, level, knowledge, isEntityMeeting)`
**只有 `if (role === 'recaller')` 分支检查 `isEntityMeeting`**，其余 4 个角色的 `systemPrompt` 是硬编码字符串。

离线探针实测（`buildRoleSystemPrompt(role, 0, undefined, true)`）：

| role | 会晤模式泄漏标记 |
|---|---|
| secretary | 🔴 1（`你的名字叫玉瑶`） |
| lover | 🔴 1（`你的名字叫玉瑶`） |
| counselor | 🔴 1（`你的名字叫玉瑶`） |
| strategist | 🔴 1（`你的名字叫玉瑶`） |
| recaller | ✅ 0 |

### 🔴 缺陷③：出口清洗器根本不洗 system prompt

`src/webui/chat/prompt-sanitizer.ts` 的 `sanitizeMeetingPrompt` 全仓**唯一调用点**是
`chat.ts:2469`，作用对象是 `finalKnowledgeText`（**知识库文本**）。
玉瑶人设走的是 `DeepSeekLLMProvider.ts:1709` 的 `systemPrompt` 通道，**完全不经清洗**，直达 LLM。

> V27 时代的「234/234 100% 泄漏」修复只封住了 KB 通道，role prompt 通道一直是敞开的。

## 三、离线探针实测（三步闭环）

**探针 A — 角色 prompt 隔离面**：见缺陷②表格。

**探针 B — 唤醒轮角色分类结果**（非会晤分支，`classify()` + `evaluateTransition()`）：

| 消息 | rule | `_currentRole` |
|---|---|---|
| 叫徐诗雨过来聊聊 | continuation | **secretary** |
| 把徐诗雨和阿珍叫过来 | continuation | **secretary** |
| 换阿珍 | continuation | **secretary** |
| 徐诗雨 | continuation | **secretary** |

**所有唤醒/加人/换人消息一律输出 `secretary`** → 每一次进会晤都必然触发缺陷①。

**探针 C — 唤醒轮 system prompt 全文矛盾检测**（模拟 `buildRoleSystemPrompt('secretary', 0, kb, true)`
拼进 `buildSystemPrompt(..., isEntityMeeting=true, ...)`）：

```
🔴 身份指令自相矛盾（两条同时出现在同一 system prompt）
  「你的名字叫玉瑶」@45   ← 最前段，权重最高
    ...2026/10/21 12:00:00⏎⏎你的名字叫玉瑶。你是鸿艺的专业私人秘书，18岁。⏎⏎【身份定位】你现在是鸿艺的工作秘书...
  「你不是玉瑶」@701      ← identityRule 铁律
    ...0. 🔴【最高优先级·身份铁律】你不是玉瑶！你不是AI！你就是你档案里那个人...
```

**结论**：system prompt 头部（@45）下令「你是玉瑶」，同 prompt 中段（@701）下令「你不是玉瑶」。
LLM 面对两条最高优先级指令的正面冲突，多轮压测下会随机倒向玉瑶 —— 表现即为
「**突然变成玉瑶，但内容还是徐诗雨口吻**」（口吻来自 KB / 实体档案上下文，自称来自 role prompt）。

## 四、被排除的疑似点

| 疑点 | 结论 | 依据 |
|---|---|---|
| `DeepSeekLLMProvider.ts:1700` `_effectiveRole` 强制 secretary | **当前无触发源** | 触发条件 `0 < max_length <= 15`；实测全部产出方：M5 模板最小 60、`deriveM5Strategy` 最小 80、CandidateSelector 20、chat.ts fallback 20、server.ts hybrid 0。属**潜伏地雷**，非本次主因 |

## 五、修复方案（待确认后进入 Phase C）

### 方案 A（推荐）：角色路由后置到状态机之后
把 `chat.ts:494-512` 的角色路由块**移到 `:808-920` 会晤状态机之后**执行。
- 利：一次移动根治全部三类轮次（唤醒/加人/换人）；顺序与业务语义一致（先定状态，再定角色）
- 弊：需确认 494-512 之间无被下游依赖的中间副作用（`p` 感知值、`WM.currentTag`）

### 方案 B：角色 prompt 会晤隔离补全
`buildRoleSystemPrompt` 对 secretary/lover/counselor/strategist 增加 `isEntityMeeting` 守卫
（同 recaller 的 `{identity_clause}` 机制，或会晤时直接降级为 recaller 模板）。
- 利：纵深防御，即使顺序再被改动也不泄漏
- 弊：4 个角色模板各需一份会晤态文案

### 方案 C：出口清洗扩到 system prompt
把 `sanitizeMeetingPrompt` 也应用到 `DeepSeekLLMProvider` 的 `systemPrompt`。
- 利：兜底
- 弊：治标；清洗器带安全回退，洗掉「你的名字叫玉瑶」会连带洗掉 secretary 的整段人设，回退后又原样返回 = 无效

> **推荐 A + B**（A 治本，B 纵深）。C 不建议单独使用。

### 附带（同批修复，低成本）
`DeepSeekLLMProvider.ts:1700` 的 `_effectiveRole` 强制 secretary 在 `isEntityMeeting=true` 时应跳过，
否则它是埋在地下的第二颗雷（当前虽无触发源，但任何新增短回复策略就会引爆）。
