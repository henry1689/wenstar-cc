# T013 · 统一群聊模式架构重构

## 业主裁决
长痛不如短痛，直接跳到统一群聊模式，不再修修补补旧架构。
**数据保护是红线**：以前的聊天数据必须保护，并能被新架构继续调用。

## 🔴 数据保护红线（最高优先级，违反即失败）

### 绝对禁止
- 禁止删除任何历史对话组、记忆、FG节点/边
- 禁止修改现有数据表结构（只能新增字段，不能删除/改名字段）
- 禁止重置钙化分、高钙组、对话组摘要
- 禁止清空任何数据库表
- 禁止数据迁移时丢失任何一条记录

### 数据兼容性原则
1. 旧数据只读：新架构读取旧数据，不修改旧数据格式
2. 新数据新格式：新产生的对话/记忆用新格式存储
3. 检索接口不变：runSearch/runRetrieval接口保持兼容
4. UUID过滤不变：UUIDGatekeeper机制保持，只是触发时机适配新架构
5. 回滚可用：新架构出问题时，旧数据完整，可立即切回旧架构

### 数据迁移方案
- 不做批量数据迁移，旧数据原地保留
- 新架构启动时自动检测旧数据并加载
- 新对话用新格式写入，旧对话保持原格式
- 召回时统一检索新旧数据，对用户透明

## 🔴 人格隔离七层设计（重中之重）

### 第一层：发言者判断隔离
- LLM第一步输出结构化speaker，再生成内容
- 不确定时默认玉瑶，绝不猜
- 输出格式：speaker=名字, content=内容

### 第二层：身份prompt隔离
- system prompt按speaker动态加载身份
- 禁止发言者是徐诗雨时出现你的名字叫玉瑶
- 身份模板动态加载，不是硬编码

### 第三层：记忆检索隔离
- 发言者确定后用对应UUID过滤记忆检索
- 徐诗雨只能看到徐诗雨的记忆
- UUIDGatekeeper检索前生效

### 第四层：FG档案隔离
- 只注入当前发言者的dossier
- relationMap只注入当前发言者与用户的关系
- 其他参与者只注入摘要，不注入完整档案

### 第五层：情感状态隔离
- 每人独立pleasure/arousal/intimacy
- 切换发言者加载对应情感状态
- 兼容旧情感快照数据

### 第六层：场景锚点隔离
- 每人独立场景状态
- 切换发言者resetAnchor+加载对应场景
- 禁止场景跨人格延续

### 第七层：输出校验隔离（兜底）
- 生成后校验自称是否匹配speaker
- 不匹配则拦截重生成
- 重试2次失败则降级玉瑶+告警

### 人格隔离验收
1. 压测1000轮零人格串档
2. 自称100%匹配
3. 记忆100%UUID过滤
4. 切换后场景/情感100%重置
5. 输出校验拦截率100%

## 🔴 加人减人严格控制（LLM不得自行判断）

### 核心原则
- 加人减人必须用户明确指令，LLM不得自行判断
- 模糊情况不操作，只正常回复
- 发言不等于加人
- 所有操作写日志

### 加人触发（必须同时满足）
1. 明确指令词：叫/让/喊/把 + XX + 来/过来/加入/参加/进来
2. 或明确句式：XX也来/把XX拉进来/让XX加入我们
3. XX必须是FG active实体
4. 不满足则不执行加人

### 减人触发（必须同时满足）
1. 明确指令词：XX先走/XX先回去/让XX离开/XX不用来了
2. 或明确句式：散会/结束/就到这吧
3. 不满足则不执行减人

### 实现方式
- 加人减人用正则白名单，不依赖LLM
- 发言者判断可以用LLM
- 流程：消息到达->正则检测加人减人->有则执行+写日志->无则进入发言者判断

### 验收
1. 压测1000轮零误加人/零误减人
2. 模糊指令100%不触发
3. 明确指令100%正确执行

## 时间分隔（微信记录式）
- 每轮聊天后30分钟无消息->闭组
- 新一轮开始时先写一行时间日期分隔
- 类似微信今天14:30的分隔线
- 方便查找和追溯时间
- 兼容旧对话组的闭组逻辑

## 🔴 PI 提出的 3 个 P0 风险 — 业主裁决（2026-10-21）

### R1：双 sql.js 内存库互相覆盖
- **风险**：新旧架构共存期，各自持内存库写入，后落盘者整库覆盖（96MB）
- **裁决**：✅ **同意过渡期严格单写者**
  - 新架构接管写入后，旧路径只读
  - 或双写同一内存库实例（不新建第二实例）
  - Phase 4 灰度期必须遵守，违反即数据丢失

### R2：七层隔离 = 每轮 +2 次 LLM 调用（语音延迟翻倍）
- **风险**：Layer1 发言者判断（LLM）+ Layer7 输出校验（重生成），语音场景卡顿
- **裁决**：✅ **同意 rule-first + LLM 兜底分层方案（不是纯轻量）**

**Layer1 发言者判断分层**：
| 层 | 方式 | 触发条件 |
|---|---|---|
| rule-first | 用户明确点名（"诗雨说"/"阿珍你觉得呢"）→ 直接判定 | 有明确点名 |
| LLM 兜底 | 无点名/歧义/指代不明 → 调 LLM 判断 | 规则未命中 |

**Layer7 输出校验分层**：
| 层 | 方式 | 触发条件 | 延迟 |
|---|---|---|---|
| 第一层（轻量正则） | 检查输出中是否包含其他参与者名字/别名 | 每轮都做 | ~1ms |
| 第二层（LLM 深度校验） | 判断输出内容是否符合当前发言者身份 | 正则命中可疑，或含身份敏感词 | ~1-2s |
| 第三层（兜底） | 降级玉瑶 + 告警日志 | LLM 校验也不确定 | 0 |

**效果预估**：90% 情况不调 LLM，延迟可控；10% 歧义情况 LLM 兜底，保证准确。

### R3："不确定默认玉瑶"在多人会晤中破坏沉浸
- **风险**：多人会晤中发言者判不出 → 默认玉瑶 → 玉瑶突然插话打断会晤
- **裁决**：✅ **同意会晤中不确定时默认当前主发言（不是玉瑶）**
  - 非会晤态：不确定默认玉瑶
  - 会晤态：不确定默认当前主发言（最近发言的参与者）
  - 两者都写告警日志，便于后续优化
