# P021 · I007 修复报告（Claude）

**结论：✅ 已修复，机制层独立验证通过（修复前命中实体数=2、修复后=1）；待 PI 交叉验证（P022）**

## 一、根因（三层，缺一层都解释不了现象）

1. **调用层**：会晤分支给统一中枢 `SearchOrchestrator.runSearch` 与高钙通道都传了
   `policy: { enforce: false } as any`。
2. **过滤层**：`buildSqlClause(policy)` 遇 `enforce === false` **直接返回空子句**
   （该字段注释明写「false 仅供离线巡检探针用」）。
3. **后果**：注册表里**五个**适配器只靠 `ctx.policy` 做 UUID 过滤 ——
   `DialogGroup` / `Vault` / `BlackDiamond` / `Note` / `Conversation` ⇒ 会晤时**全库召回**；
   而高钙通道与 `MemoryAdapter` 走 `entityUuids` 过滤（本就正确），所以泄漏集中在块路与金库路。

**比单纯泄漏更糟的一点**：注入时标签统一用 `_meetingEntityName` 拼
（`【王全芬的记忆·10-20】`）⇒ 阿珍的对话组被**伪装成王全芬自己的记忆**注入，
模型无从察觉来源不对 —— 这才是「嘴上说自己、内容是别人」的完整机理。

## 二、修复（`src/webui/chat/retrieval-stage.ts`，两处 call site + 一个策略常量）

```ts
const _meetingPolicy: PolicePolicy = {
  visibleUuids: new Set<string>([_entityUuid]),  // 会晤实体 UUID = 检索主体唯一真源
  allowUnowned: false,                            // 无归属记录一律拒（deny-by-default）
  searchScope: 'strict',                          // 仅在该 UUID 范围内搜索
};
```
- 两处 `policy: { enforce: false }` → `policy: _meetingPolicy`。
- **刻意不并入 `_gatekeeper.getEffectiveWhitelist()`**：那份白名单可能被残留的
  `sessionEntities` 污染（本文件下方注释记录过「冻结在上一个会晤实体」的实测泄漏链），
  而检索主体的真源是 `EntityMeeting`，不是会话层。
- 高钙通道的适配器**目前不读 policy**（用 `entityUuids[0]` 过滤，本就没漏），但仍传正确策略 ——
  它一旦开始读 policy 就不该再踩同一个坑。
