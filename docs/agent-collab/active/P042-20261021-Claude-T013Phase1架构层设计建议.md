# P042 · T013 Phase 1 · Claude 侧架构设计建议

> Phase 1 = 设计 + 骨架，**不改核心逻辑**。本文只提交设计，零代码改动。
> 输入：T012 摸底的 10 项实测缺陷（P037/P039）+ PI 的 R1-R10 风险清单（PI P039）+ 业主裁决（P041）。
> 目标：与 PI 设计合并成 **ADR-013**。

## 〇、我在 T012 摸底拿到的 4 条独有输入（PI 侧没有）

这四条是新架构**必须一次性吃掉**的东西，不是可选项：

| # | 实测根因（P037/P039） | 对 T013 的架构含义 |
|---|---|---|
| 1 | 角色路由 `chat.ts:494` 早于会晤状态机 `:808` **314 行**，唤醒/加人/换人轮一律被分类成 `secretary` | **状态必须先于身份解析**。新状态机不允许「先算身份、后进会晤」的顺序 |
| 2 | `_currentRole` 有**三份副本**（chat.ts 模块级 / M5Orchestrator 实例 / DeepSeekLLMProvider 静态），外加 `_savedHumanRole`、`_meeting`、`_multiParticipants` —— 共 6 份会话状态散在 3 个文件 | **会话状态必须单一对象 + 单一写点**。任何"副本"都要消灭 |
| 3 | `DeepSeekLLMProvider.ts:1700` `_effectiveRole = max_length<=15 ? 'secretary' : _role` —— 一个**与身份无关的参数**（回复长度）能覆盖身份 | **身份解析必须是纯函数**，不允许任何副作用覆盖；回复长度/风格参数与身份通道物理隔离 |
| 4 | `sanitizeMeetingPrompt` 洗 KB 文本不洗 system prompt；`headLimit=2000` 与生产「档案在前」顺序冲突 → 单测夹具形态与生产相反，**假绿灯** | **隔离必须在源头结构性保证**，不能靠末端正则清洗兜底。兜底只能是第七层，不能是唯一防线 |

> 第 4 条是方法论教训：**防线放在别人看不见的地方，测试就会骗你**。

## 一、统一群聊状态机设计（替代 EntityMeeting）

### 1.1 核心原则：一份状态对象，六个字段

现在有 6 份会话状态散落 3 个文件，新架构收敛为**一个可序列化对象**：

```ts
/** 参与者（PI 负责数据层，此处只定结构 —— 协作接口 #1） */
export interface Participant {
  uuid: string;          // FG 实体 UUID（唯一键，所有隔离按它取）
  name: string;          // 显示名（主名）
  aliases: string[];     // 别名（PI 的加人减人白名单用）
  category: string;      // 'human' | 'celestial'
  joinedAt: number;      // 加入时间戳
  turnCount: number;     // 该参与者本轮会话发言轮数
}

/** 会话状态 —— 唯一真源（取代 _meeting / _multiParticipants / _savedHumanRole / _currentRole） */
export interface SessionState {
  mode: 'yuyao' | 'meeting';      // 派生量：participants.length > 0 ⇒ meeting
  participants: Participant[];    // 玉瑶默认不入列；空数组 = 玉瑶态
  speakerUuid: string | null;     // 当前发言者（玉瑶态为 null）
  turnIndex: number;
  contextStack: ContextSlot[];    // 第五/六层 + 角色复原（见 §4）
  lastActivityAt: number;
}
```

**三条硬性约束**（对应我的输入 #1/#2）：

1. **禁止冗余布尔**：`isMulti` 不再单独存储，由 `participants.length >= 2` 派生。
   （现在的 bug：`isMulti` 判 `>=2` 但纪要门槛 `>=3`，两处口径不一致 —— P039 缺陷④）
2. **状态只有一处写**：所有变更走 `dispatch(action)` 单入口，禁止任何模块直接改字段。
3. **身份解析在状态之后**：`resolveIdentity(state)` 只接受 `SessionState`，**不接受**任何可被别处覆盖的参数。

### 1.2 状态流转接口（取代 enter/enterMulti/switchTo/exit 四个入口 + 状态机 if-else 丛林）

```ts
type Action =
  | { type: 'WAKE';       targets: string[] }      // 进会晤（1 人或多人，同一入口）
  | { type: 'JOIN';       target: string }         // 加人
  | { type: 'SPEAK';      target: string }         // 换主发言
  | { type: 'LEAVE';      target?: string }        // 减人（缺省=散会）
  | { type: 'RESUME';     state: SessionState }    // 重启恢复
  | { type: 'IDLE';       now: number };           // 时间分隔/闭组

export interface GroupSession {
  getState(): SessionState;
  dispatch(a: Action): SessionState;      // 同步、纯、不变（返回新对象）
  serialize(): string;                    // 持久化（engine_store 单键，见 §5）
  restore(s: string): boolean;            // 重启恢复
  onEnter(fn: (prev, next) => void): void;   // 钩子：PI 的加人减人回调挂这里（协作接口 #3）
}
```

**为什么用 reducer 风格**：
- ① 每次状态变更**自动可审计**（action 序列即日志，满足业主「所有操作写日志」红线，零额外代码）
- ② 第七层输出校验失败需要**回滚一轮**时，只需重放 action，不用手写 undo
- ③ 序列化天然支持 —— 整个 state 是纯数据，`JSON.stringify` 即持久化（直接修掉 P039 缺陷①「多人不持久化」）

### 1.3 与 PI 的分工落点

| 本接口 | PI 负责 |
|---|---|
| `Action.WAKE/JOIN/LEAVE` 的**触发判定** | PI 的加人减人正则白名单 → 命中后调 `dispatch`（协作接口 #3） |
| `Participant.aliases` | PI 的别名归一 |
| `RESUME` 的序列化载体 | PI 的数据兼容层（只读旧数据） |

## 二、chat.ts 接入方案（第二项任务）

**不整体搬迁现有代码**。采用**适配层 + 逐段替换**：

```
chat.ts 现状（:787-920 if-else 丛林）
    ↓ Phase 2-1 只做一层薄适配
    →  groupSession.dispatch(intentToAction(intent))     // 一次调用替代 8 个分支
    ↓ Phase 2-2 起逐段删旧分支
```

- **`_currentRole` 的三份副本一次性消灭**：身份由 `resolveIdentity(state)` 在调用 M5 的**那一个点**算出并传入，
  `M5Orchestrator._currentRole` 与 `DeepSeekLLMProvider._currentRole` 静态字段**删除**（改为每次传参）。
- **第 3 条地雷（`_effectiveRole`）随同清除**：身份参数与长度参数分属不同对象，
  `generate({ identity, expression })` 而非 `generate({ role })`，类型上无法被 `max_length` 覆盖。

> 这条直接消灭我实测的 `@45「你的名字叫玉瑶」` 与 `@701「你不是玉瑶」` 在同一 system prompt 正面冲突（P037 探针 C）。

## 三、LLM 发言者判断 prompt 规范（第一层）

### 3.1 分层（采纳 PI 的 rule-first，但**默认路径不调 LLM**）

```
① rule-first（PI 白名单，零成本）
   点名命中（"诗雨说"/"阿珍你觉得呢"）+ 状态判定（无会晤→WAKE；会晤中→JOIN/SPEAK）
   ↓ 未命中
② 粘性保持（默认路径，零成本）★ 新增，PI 建议里没有这一步
   会晤中 → speakerUuid 保持不变，记 speaker_sticky_hold 告警
   玉瑶态 → speakerUuid = null（= 玉瑶）
   ↓ 仅「会晤首轮且无人点名」才走这一步
③ LLM 兜底（结构化输出，一次调用）
```

**② 是我对 R3 的结构性回应**（详见 §六）：多数情况根本不需要"默认值"，只需要"保持"。

### 3.2 LLM 判断的 prompt 规范

**必须结构化输出，且与回复生成合并**（详见 §五 R2 回应）：

```
输入：参与者列表（name + uuid + 一行摘要）+ 最近 N 轮对话 + 本轮用户消息
输出（严格 JSON，单行）：
  {"speaker_uuid":"TXS-xxx","speaker_name":"徐诗雨","confidence":0.0-1.0,
   "reason":"用户直接点名"|"话题承接|代词指代|默认主发言"}
约束：
  - speaker_uuid 必须来自输入列表，不允许臆造
  - confidence < 0.6 ⇒ 由调用方按 §3.1② 的粘性规则处理，不采信
  - 不确定时**不得输出玉瑶**（除非玉瑶在 participants 中）
```

**校验**：`speaker_uuid ∈ participants` 不成立 → 直接走粘性保持 + 告警，不重试（避免无限重试拖垮延迟）。

## 四、身份 prompt 动态加载 + 情感/场景隔离（第二/五/六层）

### 4.1 身份：`resolveIdentity(state)` 纯函数

```ts
resolveIdentity(state: SessionState): {
  speakerUuid: string | null;
  speakerName: string;
  dossierText: string;        // 只有发言者的完整 dossier（第四层由 PI 的 builder 产出）
  participantsDigest: string; // 其他人只给 name+relation+一行摘要（PI §1.4）
  rulesText: string;          // 自称铁律（会晤态：只能自称 speakerName）
}
```

**结构性保证**（不是清洗）：
- 会晤态（`speakerUuid !== null`）**根本不经过玉瑶 role 通道** —— 不是"经过再洗掉"，
  而是分支上就没有玉瑶模板。这修掉了我输入 #4 的根本问题。
- 玉瑶态才走玉瑶 persona 模板，且**不经过任何 `isEntityMeeting` 条件**（不需要这个标志了 —— `mode` 已经决定）。

### 4.2 情感/场景：`ContextSlot` 压栈弹栈（**不是 reset**）

```ts
interface ContextSlot {
  uuid: string | null;        // null = 玉瑶
  emotion: { pleasure: number; arousal: number; intimacy: number };  // 第五层
  sceneAnchor: SceneAnchor;                                              // 第六层
  contextMemory: ContextMemoryState;
  savedRole?: RoleType;       // 玉瑶态保存（修掉「lover 进会晤、退出变 secretary」）
  savedAt: number;
}
```

**压栈时机**：`WAKE`（第一次从玉瑶态进入会晤）压玉瑶现场
**弹栈时机**：`LEAVE` 至 `participants` 为空时弹回玉瑶现场

**这修掉 P039 的三条缺陷**：
- 缺陷⑥：`resetContext()/resetAnchor()` 现在只在退出时归零 → 改为**弹栈恢复**，玉瑶基线不丢
- 缺陷⑦：情感快照只按实体 UUID 存取、玉瑶快照无人维护 → 玉瑶槽位（`uuid=null`）进入栈
- 缺陷⑩：`_savedHumanRole` 被 `isCelestialEntity` 包住 → 现场保存**对所有实体统一**，不看域

**兼容旧数据**：`emotion_snapshots` 表原样保留，`WAKE` 时从它读初值填入新槽（additive，不改表）。

## 五、输出校验兜底（第七层）—— 我对 R2 的回应

**核心主张：不要为了校验再调一次 LLM，把校验合并进主生成的同一次响应。**

| 方案 | 每轮 LLM 调用增量 | 说明 |
|---|---|---|
| 任务书原案（Layer1 判断 + Layer7 校验各一次） | **+2** | 语音延迟翻倍 |
| PI 建议（rule-first + 轻量校验） | +1（兜底时） | 已改善 |
| **本文建议：结构化合并生成** | **+0（默认）** | 见下 |

**实现**：主回复让 LLM 单次输出结构化头 + 正文：

```
speaker: 徐诗雨
---
（正文，自然语言，不出现结构化标记）
```

**校验在同一个响应体上做**（正则抽头，~1ms）：
- `speaker` 头缺失/不在参与者列表 → 正文仍可用，但按 §3.1② 粘性规则**重新归属**，记告警
- `speaker` 头与正文自称冲突（正则抽到"我是玉瑶"但头是徐诗雨）→ **二次 LLM 校验**（PI 的第二层，~1-2s）
- 二次校验也不确定 → 第三层：**降级 + 告警**（不自动重生成，避免延迟雪崩）

**依据**：系统已有结构化字段边界的先例与教训（reasoning/content 字段边界 V31/V34/V45，
剥离器误伤纯 JSON 的 V45 修复）—— **结构化头必须用字段边界而非正则枚举**，
否则会重演「把纯 JSON 削成 `[{"`」那个坑。这条写进 ADR-013 的实现约束。

**风险声明**（不粉饰）：
- 结构化头占 token（约 15-30 token/轮），可接受
- 结构化头可能污染前端显示 → 必须在出仓前剥离，且剥离逻辑要有单测
- 若 LLM 顽固不写头 → 回退到 §3.1② 粘性（不阻塞回复），并累计计数触发 prompt 迭代

## 六、R1/R2/R3 三个 P0 风险的明确回应

### R1 · 双 sql.js 内存库互相覆盖 —— **同意 PI 的单写者，我再加一条**

- ✅ 过渡期严格单写者；新架构接管写入后旧路径只读
- ➕ **架构约束**：Phase 2/3 **不引入任何新的 DB 写路径**。
  `SessionState` 的持久化走 **`engine_store` 单键 JSON**（复用 `EntityMeeting.LAST_MEETING_KEY` 的同一机制，
  换一个新 key 如 `group_session_state`），**不新增表、不动 sql.js 库**。
- ➕ **灰度期只切读路径**：Phase 4 灰度先切「prompt 组装/身份解析」（纯读），
  写路径（对话组/记忆落盘）**最后才切**。这样 R1 的暴露窗口缩到最小，且回滚 = 关开关，数据零风险。

### R2 · 七层隔离 = 每轮 +2 次 LLM 调用 —— **同意 rule-first，我主张合并生成使默认路径 +0**

见 §五。合并后：
- **默认路径 +0 次**（校验在同一次响应体上做）
- 歧义路径 +1 次（二次校验），且按 PI 的 rule-first，歧义本就只占少数
- 我实测的现状是**每轮本来就有一次生成**，所以相对成本是 0 而不是 2

### R3 · 不确定默认玉瑶破坏沉浸 —— **同意会晤中默认主发言，我改成"粘性保持"**

**我的主张：`speakerUuid` 是粘性的** —— 只有 `WAKE/JOIN/SPEAK/LEAVE` 四个 action 改变它，
普通消息**不改**。所以"不确定"时根本不需要"默认值"，只需要"**保持不动**"。

| 场景 | PI 建议 | 本文建议 |
|---|---|---|
| 非会晤不确定 | 默认玉瑶 | `speakerUuid = null`（= 玉瑶），等价 |
| 会晤中不确定 | 默认当前主发言 | **保持 `speakerUuid` 不变**（同一效果，但语义更强：不需要额外的"当前主发言"字段） |
| 会晤首轮无人点名 | — | **LLM 兜底**（这是唯一真调用 LLM 的时机） |

好处：`speakerUuid` 成为**状态的一部分**而非"每次推断的结果"，与 §1 的单一真源天然一致；
告警日志统一记 `speaker_sticky_hold`，压测时可统计粘性命中率来评估是否需要放宽 LLM 兜底阈值。

## 七、回滚方案设计（第八项任务）

| 层 | 措施 |
|---|---|
| **开关** | `WS_GROUP_V2`（环境变量/config 开关）。**默认关闭**，Phase 4 前不切 |
| **旧代码保留** | Phase 4 之前**不删** `EntityMeeting` 任何一行。回滚 = 关开关，旧代码原样接管 |
| **数据兼容** | 新状态只写 `engine_store` 新 key；**旧代码不读新 key** → 回滚后旧架构从旧 key 恢复，行为等价于"会话中断一次"，**零数据丢失** |
| **读路径** | 新架构只读旧数据（dialog_groups/conversations/memories/nodes/edges），不迁移、不改格式（业主红线） |
| **回滚演练判据** | ① 关开关后服务正常启动 ② 871 对话组 / 11598 记忆 / 1036 节点可读 ③ 旧会晤可继续 ④ 新架构写入的对话在旧架构下可召回 |

**对 PI R9 的补充**：同意"新数据放新表/新列，旧读路径忽略"，但建议**新数据只放 `engine_store`（KV）而非新表** —— KV 的旧读路径天然忽略，比"新表 + 旧表共存"更不容易出双读歧义。

## 八、实施顺序（对 PI 建议的补充）

PI 建议先做 R1（单写者）+ R6（UUID 收口）。**我同意，但插入一项前置**：

| 顺序 | 项 | 理由 |
|---|---|---|
| **0** | **L2 身份隔离纯函数** | 成本最低（一个纯函数 + 删除三份 role 副本）、**业主体感最差的问题当场消失**、且是纯 prompt 层改动 → **回滚零风险**。先给业主看到效果，再做重活 |
| 1 | R6 UUID 收口 + R1 单写者 | 数据安全红线（PI 依据成立） |
| 2 | 状态机替换（含 L5/L6 状态槽 + 序列化持久化） | 主体工程 |
| 3 | L1/L7（延迟敏感，最后调优） | 结构化合并生成需要实测 token/延迟 |

> 第 0 步之所以要前置：T012 的 10 项缺陷里，**只有身份泄漏是业主能直接感知的**。
> 先修它，业主在 Phase 2/3 的漫长重构期里不会一直撞见同一个 bug。

## 十、需要业主/豆包确认的点

1. **结构化生成头**（§五）是否可接受？它改变回复的中间形态（有 `speaker:` 头），前端与语音链路需配套剥离。
   若不可接受，退回 PI 的方案（默认 +1 次兜底 LLM 调用）。
2. **第 0 步前置**（先修身份隔离纯函数）是否同意？这等于在 Phase 2 里先插一个小切片。
3. **`ContextSlot` 栈深**：多人会晤中切主发言（`SPEAK`）**不压栈**（同一会话内换人），只有进/出会晤才压弹。
   是否符合业主对"换人"的预期？
