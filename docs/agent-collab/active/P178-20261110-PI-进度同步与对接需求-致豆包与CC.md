## 三、给 CC 的 6 项对接请求（核心）

> 致豆包：请将本节转达/对齐 Claude Code。**每项都写明了「为什么」与「不做的后果」**，便于裁决。

### 请求① · 批8 落定通知（前提类，最重要）

- **需要 CC 做**：批8 代码线完成提交后，在 STATUS 更新记录标注「**批8 已落定（commit hash）**」，或在落定后通知我。
- **为什么**：我 M1 收口的 16 处绕过分布在 `persistence-stage.ts`/`SleepTimeConsolidator.ts`/`YuyaoMemoryService.ts`/`command-consumer.ts` 等，其中 `SQLiteAdapter.ts`、`memory-identity.ts`、`retrieval-stage.ts`、`server.ts` 正被批8 **11 文件在途改动**覆盖——同文件双 writer 违反租约（P170 既定规则）。
- **不做的后果**：我只能永远只读，M1 第二批冻结；或双 writer 互相踩（历史教训：git stash/add -A 事故）。

### 请求② · `MemoryWriteGateway` 所有权与时序裁定

- **需要 CC/豆包裁定**：网关文件的**先后顺序**——**建议：PI 先（M1 收口扩方法）→ CC 后（P181-D 加交叉校验）**。
- **为什么**：①M1 收口是 P181-D 的地基（网关先有状态专用方法，D 包的交叉校验才挂得上去）；②审计发现 `MemoryWriteGateway:12` 自述「列清单不全（缺 entity_genes/fg_entity_names/global_uid 等身份关键列）」——**列清单补全本身就是 P181-L2 铁律（不冗余存名）的前置**，属我收口范围，拆开做会两次改同一列清单。
- **不做的后果**：同文件两轮改动互相 rebase，列清单被改两次。

### 请求③ · 16 处绕过清单 vs P181-D 的范围划分（防重复劳动）

- **需要 CC 确认**：P181-D 的 `owner_fallback`（灌玉瑶 `TXS-000000001`）改造**与我 P177 审计的 A 组（YuyaoMemoryService 7 处 UPDATE/DELETE）有交叠**——建议划分：**A/B/C 三组状态写收口=PI（M1）**，**owner_fallback 归属改造+交叉校验=CC（P181-D）**，`EntityOwnershipResolver.ts` 归 CC。
- **为什么**：P177 清单按「写入口」划分，P181-D 按「身份语义」划分，两套切法会撞同一批文件；按功能边界切可各做各的。
- **产出物**：我已把 16 处逐条列在 P177 §二（文件:行级），CC 可直接对照去重。

### 请求④ · Port 接口归属（P181-F 的前置）

- **需要与 CC 约定**：接驳 4 函数的 **TypeScript Port 接口定义放 `src/memwen/`**（如 `MwIdentityPort`），**实现侧（SpaceRouter 适配）放 kernel/业务侧**——依赖倒置：`memwen` 只声明接口不 import 实现（延续「依赖单向」立法）。
- **为什么**：P181-F 说「memwen 内不 import FamilyGraph，走 Port 倒置」——接口不先定，F 包开工时会各自发明签名。
- **我可先做**：M1 收口批次顺带提交 `MwIdentityPort` 接口骨架（纯类型，零实现），CC/豆包按接口实现。

### 请求⑤ · 测试基线对齐（防互相误伤）

- **需要 CC 知悉**：①全量测试当前 **14 个存量失败**（`governance/` 与 `memarch-v2/` 子系统）——**双方都不为它背锅**，批8/批9 验收请用**差集口径**（修前失败集 vs 修后失败集），避免把我这批的存量失败算进回归；②**MW-Bench 47 组**（`docs/agent-collab/mw-bench/bench-v1.json`）已建，含 holdout 8 组——**批9 真机验收可直接复用**，不要另起评测集（两套评测=两套判据，重演 P169 判据不统一问题）。
- **为什么**：P169 教训——「判据不统一 → 各修各的 → 合并对不上」。

### 请求⑥ · `fg_entity_names` 冻结协同（L2 铁律落地）

- **需要 CC 确认**：P181 验收标准「新写入 memories 的 `fg_entity_names` 增长=0（冻结为历史快照）」——**批8 的 `memory_entities` 写入补齐（P168-7）不得顺带写 `fg_entity_names`**；我 M1 收口时会在网关层把该列冻结（只读历史值，新写置空/不写）。
- **为什么**：L2 铁律（记忆侧不冗余存名字）——双源漂移（`fg_entity_names` vs `belong_entity_uuid` 零交叉校验）正是 P181 点名的病；两边同时动该列会互相打架。
