# P031 · FG 写入侧审计（PI，只审计不改码）

> 范围：PAE / FGRelationExtractor / HumanWorldGraph(+社团关系) 三条录入路径 + nodes/edges schema。

## 一、nodes / edges schema（FamilyGraph.ts:747-775）

**nodes**：id(PK) · type(NOT NULL) · name(NOT NULL) · aliases(JSON'[]') · properties(JSON'{}') · uuid · category(CHAR1) · security_level(默认1) · entity_source(默认'placeholder') · status(默认'active') · legacy_ids(JSON'[]') · family_gene · social_group_genes(默认'WW') · created_at · updated_at
**edges**：id(PK) · source_id(NOT NULL,FK) · target_id(NOT NULL,FK) · relation(NOT NULL) · properties(JSON'{}') · created_at · updated_at
> 注：**无 CHECK 约束、relation 无外键/字典约束**——关系类型合法性全靠应用层。

## 三、问题清单（按严重度）

### 🔴 P0-1：FGRelationExtractor 写入的关系类型在字典中不存在
`FGRelationExtractor.ts:199` 白名单含 **`elder_sister_of`/`younger_sister_of`**，但 `RelationshipTypes.ts:38` RELATION_TYPE_DEFS **无此二项**（只有 `sibling_of`）。
后果：写出的边 `getRelationCategory()`→undefined、`getRelationLabel()`→降级 `elder/sister/of`、`reverse`→自反（`_reverseRelation`:316 兜底返原值）。
**修法**：DEFS 补 `elder_sister_of`/`younger_sister_of`（reverse→sibling_of 或互reverse），或白名单改用 `sibling_of`。

### 🔴 P0-2：社团关系路径用正则建 **uuid=NULL 的 person 节点** + 无校验建边
`integrateOrgRelation`(:7244)：`rawInput.substring` 正则抽人名(`[一-龥]{2,4}`)+org → `ensureNode`(:7283) 建节点。
`ensureNode` 只写 `id,type,name,properties` → **uuid=NULL（无户籍）、status 默认 active**。
后果：对话原文的 2-4 字片段（如"在**公司**"→"在"被当人名）可建垃圾 person 节点且无 UUID，污染户籍/检索；正是 T008 专项#1「社团关系」的现实实现。
**修法**：建 person 前过 EntityWriteGate/姓氏校验；必须分配 UUID；org 边加置信门槛。

### 🟠 P1-1：setDossierField 无字段白名单/值校验
`FamilyGraph.ts:4707`：任意 `fieldPath.split('.')` 自动建中间对象直写 dossier，**无白名单、无类型/范围校验** → PAE 可写任意嵌套字段（properties 膨胀 + 语义漂移温床）。仅 systemReadOnly(:4736) + changeHistory 上限(:4753) 兜底。

### 🟠 P1-2：顶层字段 vs dossier 双写可漂移（已知）
`:4225-4226` 注释实证：熊梓玥 顶层 `gender='female'` 但 `dossier.basicInfo.gender='未知'`。读侧已做"dossier优先+顶层兜底"，但**写侧无同步机制**。

### 🟠 P1-3：ensureNode 建节点缺 uuid + status 默认 active
`:7283` 最小 INSERT，uuid/category/security_level/entity_source/legacy_ids/family_gene 均落默认。person 经此创建=**户籍缺失的 active 节点**（与 UUID 户籍铁律冲突）。

### 🟡 P2-1：FGRelationExtractor 死代码
`:202` minConf 含 `father_of/mother_of`（0.9）、`:216` 年龄校验含同二者——但白名单(:199)不含它们，永远到不了这两处（血缘分支实际只有 `parent_of`/`child_of` 生效）。无害但误导。

### 🟡 P2-2：关系词表跨系统不一致
FG 白名单 8 类 / HWG KINSHIP_MAP ~18 类 / RELATION_TYPE_DEFS ~40 类，三套词表**各自持有**，新增关系类型需同步三处，易漂移（P0-1 即此后果）。

### 🟡 P2-3：HWG confidence 无证据强度分档
`_ensureRelation`(:288) 固定 `CONFIDENCE.KINSHIP_FROM_CONVERSATION`，命中即同置信、重复只 MENTION_BOOST 递增——不随证据强度/来源分档。

## 四、写入侧规范建议（草案，供交叉合并）

1. **关系类型单一真源**：RELATION_TYPE_DEFS 为唯一字典，FG 白名单/HWG KINSHIPMap 均从其派生（或启动校验断言白名单⊆DEFS），杜绝 P0-1 类漂移。
2. **nodes 必填**：person 建节点必须 `uuid NOT NULL` + 过 EntityWriteGate；ensureNode 拆分为 org-only（允许无uuid）与 person（强制uuid）。
3. **edges 必填**：relation 必须 ∈ RELATION_TYPE_DEFS（DB 层可加触发器或应用层校验）；source/target 已 FK。
4. **setDossierField 加白名单**：限定 dossier 允许写入的 fieldPath 集合 + 值类型/范围校验。
5. **社团关系**：integrateOrgRelation 改走 EntityWriteGate + 置信门槛，不裸正则建 person。
6. **顶层/dossier 单向化**：写侧收敛到单一位置（dossier），顶层作只读派生，消除漂移。
