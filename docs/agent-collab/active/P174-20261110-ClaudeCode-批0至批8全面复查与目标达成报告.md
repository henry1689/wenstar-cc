### A2 · 不该混的，绝不混 —— 未达标（数据层达标，表现层不达标）

**数据层（有利证据）**：
- 会晤隔离单一咽喉 `applyMeetingUuidFilter`（`meetingIsolation.ts:21`）enforce 恒 true；命中校验 `verifyMeetingHits`（`:54`）在 `retrieval-stage.ts:666` 调用。

- `MEMPROBE` 注入头均为 `【罗珍思的记忆·…】`，未见他人 UUID 记忆。

**表现层（不利证据，直接复现）**：
- `attributeReply` 只把**参与者白名单内**的名字识别为分段标记。单人席位 `['罗珍思']` + 正文 `徐诗雨：…` 时，返回 `speakerName='罗珍思'、multi=false、body='徐诗雨：…'`，前端再拼 `【罗珍思】` ⇒ **`【罗珍思】徐诗雨：…`**（与业主截图同形）。

**判定**：**数据隔离未见越权；A2 按“回复正文”判据未达标**。后续必须把“回复中的发言人集合”纳入 A2 验收。

### A4 · 会晤/群聊模式正常 —— 未达标

**能做**：会晤状态机、席位、双人/多人发言、发言者切换均在工作；日志有 `[Gatekeeper] 会话开启: 2人 — 徐诗雨、罗珍思`、`[SpaceView] 席位=2(在场2)`。

1. 一条包含“骚一点”字样的用户消息可把 `骚一点` 唤醒为参会者：`detectIntent` 实测 `wake → ['骚一点']`；生产日志出现 `[Gatekeeper] 会话开启: 2人 — 罗珍思、骚一点`，随后 `[Identity] speaker=骚一点`，开场协议原文“你是 **骚一点**”。

## 三、新发现问题（23 起）

### #23 🔴 ADR-021 后 person 闸门“grade 3 仅长度”直接写 active

- 代码：`FamilyGraph._addNodeInner`（`FamilyGraph.ts:2112`）→ `checkPersonEntity`（`EntityWriteGate.ts:56`）→ `gradeEntity`（`EntityCandidateGrader.ts:179`）。`grade>=3` 即放行；ADR-021（`FamilyGraph.ts:2129`）已物理拆除观察区 ⇒ **放行即 active**。
- 实测（纯函数）：

| 名称 | grade | 闸门 |
|---|---|---|
| 骚一点 | 3「候选姓名(仅长度)」 | **allowed** |
| 声爸爸 | 3「候选姓名(仅长度)」 | **allowed** |
| 爹爹日 | 3「候选姓名(仅长度)」 | **allowed** |
| 屄日还爽 | 3「候选姓名(仅长度)」 | **allowed** |
| 阿珍一 | 3「候选姓名(仅长度)」 | **allowed** |
| 辛苦啦 | 0「句子片段」 | blocked（唯一被拦） |

- 数据：FG `active` person 24 个，其中 4 个是 11-09 新建的上述垃圾；`created_at` 全部晚于 ADR-020/021。**P168 §一.8 的“未见新垃圾”结论错误**——当时只数了节点数量，没有看 names/status，本报告更正。
- 影响：垃圾名进入 `getAllPersonNames`（`FamilyGraph.ts:5985`）→ 成为唤醒候选 → 成为席位。

### #24 🔴 垃圾实体成为会晤参与者并拥有数据

- 日志：`[Gatekeeper] 会话开启: 2人 — 罗珍思、骚一点`；`[Identity] recaller meeting=true speaker=骚一点`；开场协议文本“你是 **骚一点**。你刚刚被叫来……”。
- 数据：`TXS-000001362`（骚一点）名下 **3 条 memories（roleplay）+ 2 条 conversations + 1 条 anchor**，时间 11-09T12:05Z。
- 影响：用户消息被记到一个由句子片段生成的“人”名下；之后的召回/摘要/称谓都会带着这个名字。

### #25 🔴 输出守卫对白名单外的发言人标记不处理

- `attributeReply`（`outputGuard.ts:391`）/ `splitSpeakerSegments`（`:165`）只认 `SessionState.participants` 内的名字。
- 复现（纯函数）：
  - 白名单 `['罗珍思']` + 正文 `徐诗雨：…` → `speakerName='罗珍思'`、`multi=false`、body 保留 `徐诗雨：…` ⇒ 前端拼成 **`【罗珍思】徐诗雨：…`**；
  - 白名单 `['徐诗雨','罗珍思']` + 三行含 `阿珍一：` → `阿珍一：` 被并入徐诗雨段，body 为 `【徐诗雨】… 阿珍一：…`；
  - 白名单含 `骚一点` → `multi=true`，输出 `【罗珍思】…【骚一点】…`。
- 影响：正是业主截图“一个角色回复里三个人说话”的直接机制；即使数据层没有越权，正文身份也会错。

### #26 🔴 双实体注册表主名漂移 / 五个名字

- FG nodes：`TXS-000000008` = **罗珍思**，aliases `["阿珍","珍珍"]`。
- `entities`：同一 UUID `TXS-000000008` 的行 `name=阿珍`（id 6）；`罗珍思` 另占 `TXS-000004689`（id 9273244）；`阿珍一` 占 `TXS-000001096`（id 9259579，0 数据）。`entities` 还有 object 同名行。
- 影响：不同消费方（FG / entities / memory_entities JOIN）看到的“主名”不一致；LLM 输出自然在 罗珍思/阿珍/珍思/珍一/阿珍一 之间漂移。
- 唤醒实测：`罗珍思 ✓ / 阿珍 ✓ / 珍思 ✓ / 珍一 ✗ / 阿珍一 ✗`。

### #27 🔴 会晤入口与昵称解析缺口（“不见人”）

- `detectIntent('进入会晤模式')` / `('我要进入会晤模式')` = **normal**（无目标 → 不唤醒）。
- `detectIntent('珍一')` / `('阿珍一')` = **normal**；`('珍思')` = wake 罗珍思。
- 单人会晤时 `buildChatState` 返回 `mode='private'`、`participants=[]`（`server-chat-routes.ts:585-595`），UI 没有名单。
- 影响：业主说“都进入会晤模式了也不见她”有三种可复现路径：①只说“进入会晤模式”不指名；②用“珍一/阿珍一”称呼；③单人会被 UI 当作 private，不显示名单。

### #28 🔴 test 锚点 namespace 被重建“洗白”（不是删除）

- 批6d 备份：38 条 `namespace='test'`，全部是 `*_ANCHOR`。
- 当前库：**38/38 仍存在，0 缺失；38/38 已变为 `namespace='default'`**。
- 机制：`_rebuildMemoryAnchors` 每次启动 `DELETE FROM memories WHERE id LIKE '%_ANCHOR'`（`SQLiteAdapter.ts:2912`），再从 `conversations` 重建；重建查询排除 `is_test=1`（`ANCHOR_REBUILD_GROUPS_SQL`），但 `anchorNamespace` 取组内**首条 conversation**的 namespace（`:3019-3030`）——首条通常非 test ⇒ 锚点落 default。
- 影响：P172 的“23→0 被清理、清理方待查”**结案为判定错误**；真实问题是 test 标记在每次重启后丢失，测试锚点进入生产检索。这是 A5 的核心。

### #29 🔴 冒烟测试直接写生产库

- `scripts/__tests__/memory-roundtrip-runtime-smoke.test.ts`：`BASE='http://localhost:3000'`，`POST /api/memory`，服务在跑就执行；写入 `roundtrip-test-<epoch>` 与 `WENSTAR_SMOKE_*`。
- 与 199 条 `note_zone` 测试残留一致；该测试“Prefers in-memory store”，但路由实际落生产。
- 影响：每次全量测试都可能新增生产数据；测试隔离失效。

### #30 🔴 knowledge→memory 关联不做存在性校验

- `KnowledgeContextBuilder.ts:380`：`INSERT OR IGNORE INTO knowledge_memories (knowledge_id, memory_id, relevance) VALUES (?, ?, ?)`，`memory_id = dna.branch_id`，未校验该 id 是否在 `memories`。
- 当前 `foreign_key_check=30`（P168 时 21，仍在增长），全部指向未落库的 `evt_20261109_*`。
- 影响：存储完整性；不影响召回，但会污染关联查询，且每次知识导入都会再生。

### #31 🟡 人名垃圾表双份漂移 + 子串意图匹配

- `FamilyGraph.DIRTY_WORDS`（`:5994`）与 `EntityContextBuilder.GARBAGE_NAMES`（`:28`）是两份手工列表，均不含 `骚一点/声爸爸/爹爹日/屄日还爽/阿珍一`。
- `detectUserIntent` 用 `nmsg.includes(name)` 收集被提及者；实测 `叫的骚一点 → wake ['骚一点']`。
