## 一、现象与实据

生产实测（2026-09-24，业主直接提供原文）：角色对话中，回复**整条是模型的思维过程**，
并在末尾拖出**数千个 `】`** 直至长度上限：

```
用户：带回来，你看着办
回复：用户让我带饭回来，"你看着办"。现在是中午12:10，徐诗雨还在上班/中午。
      保持徐诗雨身份，口语化，有温度。简洁点，答应下来，说我看着带。
      】】】】】】】】】】】】…（数千个）
```

### 1.1 日志铁证（`[ChatStream] done` 的 tokens/len 分布）

| 类别 | `tokens` | `len` | 条数 |
|---|---|---|---|
| 正常回复 | 62 ~ 226 | 150 ~ 360 | 多数 |
| **异常回复** | **0 或 1** | **3012 / 3024 / 3032 / 3037 / 3064 / 3084** | **6 条** |

异常簇**全部卡在 ~3000**，是长度上限的特征，不是巧合。

### 1.2 根因链（每一环均有实据）

| # | 环节 | 实据位置 |
|---|---|---|
| ① | 角色扮演档 `maxTokens: 3000` | `src/common/const/llm-config.ts:56` |
| ② | 角色扮演 `reasoning_effort='max'` ⇒ 思维链吃光预算 | `DeepSeekLLMProvider.ts:1585` |
| ③ | 模型退化为复读 `】` 直至撞 `max_tokens`；`content` 从未产出 ⇒ 流式期间 `tokens=0/1` | 实测日志 + 原作样本 |
| ④ | 流结束兜底 `if (!text.trim())` → `extractAnswerFromReasoning(reasoningBuf)` —— **五条策略全不命中时原样返回** | `DeepSeekLLMProvider.ts:1218-1231` |
| ⑤ | `gateOutgoingReply` 拦不住 | `DeepSeekLLMProvider.ts:308-329` |
| ⑥ | 本应触发的 `noUsableAnswer` 抛错**没触发**（兜底正常返回了字符串，没有抛） | `DeepSeekLLMProvider.ts:1040-1052` 对比 |

**⑤ 的判据失手实证**（关键词枚举第三次擦边而过）：

| 判据里写的 | 本次泄漏文本 | 结果 |
|---|---|---|
| `我要以…身份回应` | `我应该以…身份回应` | ❌ 「要」vs「应该」 |
| `保持角色：` | `保持徐诗雨身份` | ❌ 擦边而过 |

### 1.3 这是**同一类病的第三次复发**

| 次 | 时间 | 当时的补法 |
|---|---|---|
| 1 | 2026-09-12 | V22：为修「会晤退化成『抱歉我暂时无法回应』」，把 fail-closed **削弱成 fail-open** |
| 2 | 2026-09-13 | V23：新增 `CN_META_PLAN_RE` **关键词判据**（`reasoning-leak-cn-meta.test.ts` 有完整记录，其结论原文：「判据做**准**而非做**松**」） |
| 3 | **2026-09-24（本次）** | 关键词再次擦边 ⇒ 复发 |

**结论：关键词枚举这条路已经被证伪三次。本变更改用结构判据。**

### 1.4 关键不对称：非流式早就修好了，流式漏了

`DeepSeekLLMProvider.ts:1040-1052`（**非流式**路径）注释原文：

```
原实现: content 空 → 取 reasoning_content 原文 → extractAnswerFromReasoning 剥离失败时
        **返回原文** → 整段思维链被当回复输出（生产实测多条）。
现约定: 剥离失败(≈原文) 或 形态仍是草稿 → 判「无可用答案」，宁可失败重试也绝不洩漏。
```

**流式路径（`streamChatOnce` 末尾兜底）被 V22 改成了「尽力提取」，从未对齐。**
本变更 = **把流式补到与非流式同语义**，不是新造机制。

## 二、修复：甲 + 乙

### 甲-1 流式捕获 `finish_reason`，撞长度上限直接判死

`finish_reason` 当前**在类型里定义、全仓从未被读取**（死字段，实据：全文件仅 `L73` 一处出现）。
本变更在流式循环中捕获它，并在流结束时：

```
finish_reason === 'length' 且 无可用 content
  ⇒ 内容必然是「截断物」
  ⇒ 抛 noUsableAnswer（交 M5 重试），绝不当作回复
```

> 业主提供的样本正是 `】×N` 吃光额度 ⇒ 必然落 `'length'` ⇒ 本闸直接拦下。

### 甲-2 结构判据 fail-closed（**不用关键词**）

新增 `tryExtractAnswerFromReasoning(raw): string | null`：

- 复用既有**四条结构策略**（复盘型 / 规划型 / 写转场 / 草稿评估段）
- **四条全未命中 ⇒ 返回 `null`** ⇒ 调用方抛 `noUsableAnswer`

**判据是「有没有找到结构标记」，不是「这段话像不像思维链」** ⇒ **零关键词、零误杀**。
这正是 `reasoning-leak-cn-meta.test.ts` 自己写下的方向（「做准而非做松」），只是从关键词路线
切换到了结构路线。

流式结束兜底改为：

```
const strict = tryExtractAnswerFromReasoning(reasoningBuf);
if (!strict) throw noUsableAnswer;      // ← 替代原「剥不动就原样返回」
```

### 乙 角色扮演推理档降级

`DeepSeekLLMProvider.ts:1585`：`_isRoleplay ? 'max'` → `'medium'`。

两条依据：

1. **会晤模式早已是 `'medium'`** —— `M-LEAK A` 就是这么修的，注释原文：
   「原合并使会晤沿用角色扮演的 `reasoning_effort='max'`，思维链吃光 max_tokens → content 为空」
2. **`M5Orchestrator` V25 注释原文**：「这是思维链泄漏的**根因治理** —— 判据再多，
   都不如让 content 一开始就有值」

**下游零改动**：`generate` 判空返回 `''` → M5 既有 `if (!draft)` 重试通道自动接管，
且该通道**强制降至 `'low'`**（`retry-effort-downgrade.test.ts` 已覆盖）。
本变更由此形成 **medium（首发）→ low（重试）** 的阶梯。

### 丙 LLM 链路熔断（ROBUST_LLM 三级保护的第三级）

**背景**：S4 评审指出本仓 LLM 调用链路缺第三级保护。**实测核实**：

| 要求 | 现状 | 判定 |
|---|---|---|
| 超时 30s | `DeepSeekLLMProvider.ts:1120` 主路径 30000 | ✅ 已满足 |
| 重试 3 次 | `L993 maxRetries=2` ⇒ `attempt 0..2` = 3 次 | ✅ 已满足 |
| **熔断** | **LLM 链路无熔断** | ❌ **缺** |

**不是本次改动引入的欠账**，但与本次 bug 直接相关：日志里那些
`API call failed after 3 attempts: 429` 正是**没有熔断、盲目重试**的表现。

**修法：复用仓库现成组件，不另造机制。**

```ts
new RetrieverCircuitBreaker('deepseek_llm', { threshold: 3, cooldownMs: 30_000 })
```

与 `bionic-adapter` 的 `bionic_search` 同款配置。组件位于 `src/app/knowledge/`，
`m5` 引用 `../app/*` 属**既有惯例**（`persona` / `role` / `ApiKeyStorage` 均如此），
且反向依赖检查（CK-01）只对 `mN` 编号模块生效（`parseInt('app')` → NaN）⇒ 不触发。

### 丁 M 层埋点（HOOK_M_LAYER）

**背景**：S4 评审指出被改文件缺 M 层埋点。**实测核实**：全仓仅
`m2/SQLiteAdapter` 与 `m4/FamilyGraph` 有 `[Hook] module_entry/module_exit`，
**m5 整层零埋点**。

**这正是本次定位困难的直接原因** —— 原始 LLM 输出无任何日志，
根因只能靠 `tokens/len` 分布反推（见 §九）。

**修法：照 `m2.SQLiteAdapter` 范式补**
```
[Hook] module_entry module=m5.DeepSeekLLMProvider.generate
[Hook] module_exit  module=m5.DeepSeekLLMProvider.generate 耗时=Nms status=ok|fail
```

### 2.1 明确不做（排除项，附理由）

| 排除项 | 理由 |
|---|---|
| ❌ 加宽 `gateOutgoingReply` 关键词判据 | V23 因加宽而误杀，退化成「抱歉我暂时无法回应」；结构判据已覆盖同一场景 |
| ❌ 调大 `maxTokens: 3000` | 治标且贵；不解决「截断当答案」的逻辑洞 |
| ❌ 另造「单字符复读截断」守卫 | `】×N` 必然撞 `finish_reason='length'`，甲-1 已拦；多一条判据多一份误杀面 |
| ❌ 改动 `M5Orchestrator` / `llm-config.ts` / 前端 | 无需改动，缩小改动面 |

## 三、白皮书更新摘要（架构层）

**标题：LLM 出口语义统一 —— 流式与非流式同守 fail-closed**

1. **出口语义对齐**：流式路径（`streamChatOnce`）此前是 fail-open（剥不动即返回原文），
   非流式是 fail-closed。本变更**终结这一不对称**：两条路径同守「宁可失败重试，绝不洩漏思维链」。
2. **判据路线切换**：由**关键词枚举**（三次复发，见 §1.3）改为**结构判据**
   （有没有找到结构标记）—— 前者随模型措辞漂移必然失效，后者与措辞无关。
3. **长度上限成为一等公民**：`finish_reason` 由死字段变为出口判据的一部分；
   「撞上限」被明确认定为**失败**而非**回复**。
4. **推理预算分级**：角色扮演不再独占 `'max'`，与会晤对齐为 `'medium'`，
   配合既有重试降级形成 `medium → low` 阶梯 —— 让 `content` 一开始就有值（根因治理）。
5. **LLM 链路三级保护补齐**：超时(30s) 与重试(3次) 原已具备，本次补上**熔断**（复用
   `RetrieverCircuitBreaker`），使 LLM 调用链路首次具备完整的三级保护 ——
   缓解 429/502 风暴下的盲目重试。
6. **核心链路可观测性补齐**：m5 层首次具备 `module_entry/module_exit + 耗时 + status`
   埋点。本次根因定位被迫靠 `tokens/len` 分布反推，正是缺这一层的直接后果。
7. **不改变架构边界**：不改分层、不改数据模型、不改 schema、不新增依赖（熔断组件为仓库既有）、
   不动前端契约。

## 九、已知风险与遗留项

1. **乙 的推理档降低可能影响角色扮演深度** —— 见 §六.1，回退路径已写明。
2. **甲 会让「撞上限」的轮次重试一次** —— token 消耗增加；但重试用 `'low'` 档，
   且原本那些轮次产出的也是垃圾，净收益为正。
3. **M3 情感显示条「消失」的成因已查明为浏览器旧文档**（`Ctrl+F5` 后恢复），
   与本次变更无关；同日已发生一次同类现象。**若再次出现，先强刷再排查。**
4. **原始 LLM 输出仍无完整日志** —— 本次根因定位只能靠 `tokens/len` 分布反推。
   丁 补的是**入口/出口埋点**（耗时 + status），**不含原始响应形态**。
   若要下次能直接看到 `content` / `reasoning` / `finish_reason` 三元组，
   还需一条「原始响应形态」埋点（**不在本次范围**，避免隐私与体积风险）。
5. **丙 会改变失败时的行为** —— 连续 3 次失败后进入 30 秒熔断期，期间 LLM 调用
   直接失败走降级。极端情况下可能让「重试本可成功」的请求提前放弃。
   选此参数的理由：与 `bionic_search` 同款配置且已长期运行；熔断窗口仅 30 秒。
   **回退方式**：删除包裹即可，甲乙不受影响。
