## 一、现象与实据

业主报告：**语音播报完全无声**，且控制台**没有任何报错**。

### 1.1 服务端全绿（逐项实测，非推断）

| 检查项 | 实测结果 |
|---|---|
| 业主当轮消息的 mp3 | **17:22:38–39 生成 4 段** |
| 文件本身 | `ffprobe`: `duration=11.952s` / mp3 / 24000Hz / 71712 bytes —— **真音频** |
| URL 可达性 | `/audio/tts_*.mp3` → **HTTP 200 / audio/mpeg / 29664 字节** |
| 实例数 | 仅 `0.0.0.0:3000` 一个监听，**无僵尸实例** |
| 下发页面 | 即 `src/webui/index.html`，`Cache-Control: no-cache`，含增量播放代码 |
| 近期改动 | `index.html` 最后一次改动 `0e6b4df` **未触碰语音路径** |

⇒ **音频送到浏览器之前一路通，卡在浏览器播放这一跳。**

### 1.2 浏览器侧探针实测

| 探针 | 结果 |
|---|---|
| `new Audio('/audio/…mp3').play()`（控制台，无用户手势） | **✅ 浏览器能播** ⇒ **自动播放策略不是原因**（我最初怀疑错了） |
| 挂 `HTMLMediaElement.prototype.play` 探针后连发多条消息 | **每次 `▶ play` + `✅ 成功`，4/4 出声** |

**结论：症状在探针挂上之前已自行消失，原始故障未捕获到失败现场。**
本变更**不宣称已定位原始根因**，而是消除「失败不可见」这一使根因无法定位的结构缺陷。

### 1.3 为什么查不下去 —— 失败路径全部静默

| 位置 | 原行为 | 后果 |
|---|---|---|
| `ap.onerror=advance` | 单段加载失败 → **0 条日志** | 404/解码失败 = 无声 + 干净控制台 |
| `ap.onerror=fin` | 同上 | 同上 |
| `.catch(() => {})`（chatService 解锁） | 静默 | 同上 |
| `.catch(() => { onDone(); })`（chatService 播放） | 静默 | 同上 |
| `_incrTTSTryPlay` 三处 `return` | 代际过期 / 播放中 / 段未就绪 —— **全部静默** | 队列卡死 = 无声 + 干净控制台 |
| 轮询退出只 `clearInterval` | **不置 `finalized`** | `urls[0]` 有洞且未定稿 ⇒ 队列**永久等待且零日志** |

> **违反项目 P0 铁律「禁止静默吞错误」**，且正是本次「反复问业主要控制台截图却拿不到东西」的直接原因。

### 1.4 独立发现：SSE 在音频到达前就被关掉

`index.html` 的 `chat-done` 监听器**无条件 `es.close()`**，而服务端：

```
server-chat-routes.ts:625  → 首个 chat-done：audio_url:null, audio_urls:[], tts_job:null   ← 空！
server-chat-routes.ts:632  → 第二个 chat-done：audio_url/audio_urls 真值 + audio_done:true
server-chat-routes.ts:608  → chat-tts 段推送（逐段）
```

⇒ 第一帧一到就关连接 ⇒ **带音频的第二帧与之后所有 `chat-tts` 段推送全部丢失**，
音频只能靠 150ms 轮询兜底；**兜底一断即无声**。

## 二、修复：①②③④ + 同类全仓

### ① 失败可见化（P0 铁律）

```ts
ap.onerror=()=>{console.warn('[Audio] 段加载失败:',_u);advance();};   // 原: ap.onerror=advance
ap.onerror=()=>{console.warn('[Audio] 增量段加载失败:',url);fin();};  // 原: ap.onerror=fin
.play().catch((e)=>{console.warn('[Audio] 解锁播放失败:',e);});        // 原: .catch(()=>{})
.play().catch((e)=>{console.warn('[Audio] 播放失败:',e);onDone();});   // 原: .catch(()=>{onDone()})
```

**`handled` 幂等护栏保留**（onerror 与 `play().catch` 可能双触发，护栏防一段跳两次）。

### ② 每轮一次的收尾快照

新增 `_audioFinish(why)`，一条日志摊开全部终态：

```
[Audio] 收尾 {"why":"audio_done","gen":3,"audioGen":3,"qgen":3,"ready":4,"cur":4,
              "playing":false,"finalized":true,"played":true}
[Audio] 🔴 有段却一段都没播 {...}          ← 该情形升级为 warn
```

- `why` ∈ `audio_done` / `poll_timeout` / `job_gone` / `job_error` / `send_timeout`
- `_ttsIncr` 新增 `played` 标志，区分「根本没段」与「**有段却没播**」
- **下一次无声 ⇒ 一条日志直接点名卡在哪一环**

### ③ 终态置位（解除永久死锁）

轮询三条退出路径 + 60s 超时**都必须走 `_audioFinish`**，其中置 `finalized=true`。
原先只 `clearInterval` ⇒ `finalized` 永不置位 ⇒ `_incrTTSTryPlay` 在
`if(!url){ if(!Q.finalized)return; }` 处**永久 return 且零日志**。

### ④ SSE 关闭时机后移

```ts
// 原:  es.close(); ...          ← 无条件，第一帧 audio_urls 为空
// 现:
if(gen!==_audioGen){es.close();...;return;}   // 只在代际过期时关
...
if(_streamES){_streamES.close();_streamES=null;}  // 关闭统一在 _audioFinish
```

⇒ 带音频的第二帧与后续 `chat-tts` 段推送不再丢失，**不再单靠轮询兜底**。

### 同类全仓（铁律 0.3）

`ui/src/services/chatService.ts` 存在同一类静默吞，一并修复。

## 三、白皮书更新摘要（架构层）

**标题：前端媒体链路「失败必须可见」+ 队列终态契约**

1. **失败可见性成为硬约束**：媒体加载/播放的任何失败路径都必须留痕，
   杜绝「无声 + 干净控制台」这类**不可诊断**状态。
2. **队列有明确终态**：播放队列的每一轮必须收敛到 `_audioFinish`，
   退出即定稿（`finalized`）+ 打快照，**不存在「挂着等」这种状态**。
3. **SSE 关闭由事件驱动改为终态驱动**：关闭时机绑定「音频已定稿/轮询结束」，
   而非绑定某一个中间事件帧 —— 服务端事件帧的**载荷完整性**不再是隐含假设。
4. **诊断入口前移**：原先要业主开 F12 手工挂探针才能定位；现由服务侧收尾日志自证。

## 八、已知风险与遗留项

1. **原始根因未捕获** —— 探针挂上后症状已消失。本次修的是「失败不可见」这一结构缺陷；
   **下次复发时一条 `[Audio] 收尾` 日志即可定位**，届时再定根因。
2. **`es` 关闭时机后移** —— 若 `audio_done` 与轮询均未触发，连接由下次 `sendStream`
   开头的 `es.close()` 兜底关闭，**不会无限悬挂**；已知最坏情况是多持有一个连接到下一条消息。
3. **`finalized` 在 `job_gone` / `poll_timeout` 时置位** —— 语义为「等够了，视为定稿」。
   极端情况下可能跳过仍在生成的空位段；**优于「永久不播」**，且收尾日志会记录 `why` 供复盘。
4. **遗留（不同问题类，未修）**：`MemoryAssessor.ts:256`、`bionic-adapter.ts:192-193`
   的空 catch —— 已按「只修问题不顺手优化」记录，**交业主统一安排**。
5. **豁免为本次专用**：`ex-97888011` / `ex-38b0bfbe`，60 分钟过期，仅放宽 `S4.5_complexity`。
6. **S4 评审接受为已知限制的 4 项** —— 见 §六.6（C-2 后半 SSE 解析空 catch、C-3 `playAudioQueue`
   else 分支无轮级日志、A2 `finalized` 不可逆的窄竞态、B3 `finalized` 双写 owner 不唯一）。
   **均为评审判 🟡 并同意不改**，不是遗漏。
