## 二、修复：换底座，而不是调参

sql.js 是**内存库 + 全量快照导出**：每次落盘把整个库序列化成字节再写文件，
写放大随库体积线性增长，且**同步在主线程**。换成 `better-sqlite3` 后，
**写库直接落到文件（页级增量），「全量导出」这件事不再存在。**

### 2.1 为什么是 better-sqlite3

| | `sql.js`（现状） | `better-sqlite3` | `node:sqlite`（备选，否决） |
|---|---|---|---|
| 依赖状态 | 生产依赖 | ✅ **已是 dependencies，零新增** | 需 `--experimental-sqlite` |
| 稳定性 | — | 成熟原生绑定 | Node 22 实验特性 |
| 打开生产库 | 需灌 273MB 进 WASM | **28ms** | — |
| 取 5000 行 / COUNT 113万 | — | **6ms / 30ms** | — |
| 同步语义 | 同步 | ✅ **一致** | ✅ |
| **FTS5** | ❌ **无**（日志「FTS5 不可用」实锤） | ✅ 有 | ✅ 有 |
| SQLite 版本 | 3.45.2 | **3.53.2** | 3.51.3 |

功能性实测（全部 `:memory:`，未碰生产库）：FTS5 ✅ JSON1 ✅ WAL ✅ RTREE ✅
递归 CTE ✅ 窗口函数 ✅ UPDATE..RETURNING ✅ 事务 ✅。

### 2.2 为什么架构上是「换引擎」而非「并库」

- 同一个 `.db` 文件（标准 SQLite）直接复用，better-sqlite3 可直接打开
  （已只读实测：`memories` 归属标注 **7724 条**读取正确）⇒ **零数据迁移、零回填**
- 对外 API（`writeRaw` / `queryAll` / `save` / `scheduleFlush`）与 `rawDb` 兼容层保持不变
  ⇒ **628 个调用点、6 个 rawDb 消费方（KnowledgeEngine / MemoryAssessor /
  persistence-stage / retrieval-stage / server）零改动**
- 共享工具函数（`indexDocument` / `writeToDualHelix` / `unifiedSearch` /
  `reportUUIDHealth`）签名是 `db: any`，只调 `db.exec` / `db.run`
  ⇒ 只要外壳提供同名方法，它们一行不用改

### 2.3 删除的机制（结构削减，不是补丁）

换底座后「导出→写文件」中间层整体失去意义，一并删除：

- `flushNow()` / `flushNowAsync()`（6 处 `export()`）
- `_FLUSH_BATCH` 批阈值、`_FLUSH_INTERVAL` 防抖窗口、`_dirtyCount` 脏计数
- `_safeWriteDbFile` 原子快照写（其保护对象——整文件覆写——已不存在）
- `ConversationDB` 4 处 `writeFileSync(…export())`
- `FamilyGraph` 4 处 `export()`

> **这正是本变更的实质：删掉一整套不再需要的机制，而不是改写 600 个调用点。**

### 2.4 明确的偏离声明（ROBUST_PERSIST）

`ROBUST_PERSIST` 要求「保留 scheduleFlush 防抖落盘、save() 调用不可删除」。实际情况：

| 要求 | 处置 | 是否满足 |
|---|---|---|
| `save()` 调用不可删除 | **调用点与签名全部保留**（628 个调用点依赖） | ✅ |
| 保留 `scheduleFlush` | **API 保留**，调用点不变 | ✅（接口层） |
| **保留「防抖落盘」语义** | **移除** | ⚠️ **有意偏离** |
| 事务回滚保护 | better-sqlite3 原生事务，**保留并强化** | ✅ |

**偏离理由**：防抖存在的唯一原因是「全量导出太贵，不能每次写都做」。引擎换成页级即时写后，
该前提消失；**保留防抖反而会扩大崩溃丢数据窗口**（60 秒内的写入丢失），
属于有害残留。此项如实声明，不作含糊处理。

## 三、白皮书更新摘要（架构层）

**标题：存储底座由「内存库全量快照」改为「文件级增量写」**

1. **持久化模型变更**：由 sql.js（内存态 + 周期性全量 `export()` 覆写）改为
   better-sqlite3（页级增量写）。原「导出→原子写文件」链路整体移除。
2. **响应性与持久化解耦**：主线程不再因落盘被冻结 20~53 秒，
   「能否及时响应」不再取决于数据库体积——消除一个**随数据量恶化的隐性失效模式**。
3. **持久化可靠性反而提升**：由「整文件快照覆写」改为页级写，
   消除「写中途失败 ⇒ 库截断/损坏」的既有风险（原 `_safeWriteDbFile` 原子写即为此而设，
   其保护对象随全量覆写一并消失）。
4. **不改变架构边界**：SQLiteAdapter 仍是唯一持久写入通道（API 不变）；
   M1–M9 分层、四平面、UUID 四层标注、FG 户籍单一数据源均未变更。
5. **解锁 FTS5**：sql.js 无 FTS5（启动日志「FTS5 不可用」），换库后可用。

## 四、蓝皮书更新摘要（模块功能）

**标题：m2 持久化层与 m4 FG 层的落盘实现更换**

1. `SQLiteAdapter`：底座换 `better-sqlite3`；`writeRaw` / `queryAll` / `save` /
   `scheduleFlush` 对外签名不变；`rawDb` 暴露兼容外壳（`exec` / `run` /
   `prepare`+`step`+`getAsObject`+`free` / `getRowsModified`）。
2. `FamilyGraph`：同上处理（42.4MB 库，实测 27~29 秒阻塞）；
   `markDirty` 语义保留，但不再触发全量导出。
3. `ConversationDB`：删除 4 处 `writeFileSync(…export())` 落盘点。
4. 启动路径：不再 `initSqlJs` 加载 WASM，改为 `new Database()` 直接打开文件。

### 4.1 部署拓扑（无变更）

不新增/拆分/合并任何服务或进程；不新增依赖（better-sqlite3 已是 dependencies）；
数据库拓扑不变（同一 `.db` 文件，零迁移）。

### 4.2 启动流程（无变更）

入口、预置数据、迁移（`MigrationManager` v2→v12，`schema_version` 表）均不变；
`migrateSchema()` 照常在启动时执行。

### 4.3 配置项清单（无新增）

不引入开关（不给「切回 sql.js」留后门，避免第二套真源）；
`TIANQUAN_FLUSH_INTERVAL_MS` 等原防抖环境变量随机制移除而失效。

## 八、已知风险与后续项（不在本次范围）

**4 个脚本仍用 sql.js 且会全文件覆写**，主服务改为持续增量写后其破坏力变大：

| 脚本 | 操作库 |
|---|---|
| `src/m2/BackfillGlobalUID.ts` | `fusion_memory.db` |
| `src/m2/BackfillDualHelix.ts` | `fusion_memory.db`（规约 D3 已标「归档历史脚本」） |
| `src/cli/migrate-entity-relations.ts` | `family_graph.db` + `fusion_memory.db` |
| `src/cli/scan-knowledge-intimate.ts` | `fusion_memory.db`（注释显示 `--report` 只读） |

四者均**不在 `package.json.scripts`**，服务不自动调用；该覆写风险今日已存在
（双 sql.js 实例互覆写），本次不使其恶化，但后果量级会变大。

**后续项（要求）**：这 4 个脚本在运行前必须加 `ServerLock` 守卫，
拒绝在服务持有生产库写锁时执行。因涉及 4 个额外文件，未纳入本次文件集。
