## 一、白皮书更新摘要

**标题：感知向量（40D）存储形态与持久化可观测性 —— 存储层契约修订**

变更条目（4 条）：

1. **存储形态契约统一为 v2 包装** —— 40D 向量的权威存储形态为
   `{"__v":<版本号>,"dims":[...40 元素...]}`，写入口为 `PerceptionVector40DCodec.encodePerceptionV40()`。
   解码端**向后兼容三种形态**（v2 包装 / v1 裸数组 / v0 命名对象），且经全库实测
   **解码失败 = 0**。存储形态统一是**卫生**要求（可读性、版本演进），**不改变任何解码结果**。

2. **「不可解析」不得伪装成「全零」** —— 存储层遇无法解码的向量走 **跳过 + 告警**，
   禁止写零向量。原实现将解析失败写为 `new Array(40).fill(0)`，等价于凭空制造数据：
   下游无法区分「真的全零」与「根本没解析出来」。

3. **持久化可观测性（flush 埋点字段口径）** —— 落盘节点
   `SQLiteAdapter.flushNowAsync()` 的埋点补齐为统一字段：
   `operation_type` / `duration_ms` / `status` + 持久化专属
   `write_latency` / `save_flush`（start→done/failed）/ `transaction_status`（in_progress→committed/rolled_back）。
   说明：本落盘走**整库原子写**（临时文件 + 原子改名），不涉及 SQL 事务，
   故 `transaction_status` 表示原子写成功与否，而非 BEGIN/COMMIT 状态。

4. **内存迁移的往返校验硬约束** —— 任何改变向量存储形态的迁移，必须对每行做
   `decode → encode → decode` **逐维比对**，不一致即**放弃该行**并计数；
   同时对源串做**形态级预检**，避免把垃圾 JSON 当作「合法 v0 命名对象」洗成全零向量。

## 二、蓝皮书更新摘要

**标题：M2 存储层数据治理与回滚方案 —— 40D 形态统一专项**

变更条目（3 条）：

1. **模块功能说明（M2）** —— `MigrationManager` 新增 **v18 版本化迁移**：把
   `knowledge_base.emotion_vector`（1,123 行，全 v1 裸数组）与
   `black_diamond.emotion_vector`（2,464 行中 118 行 v1）统一为 v2 包装。
   迁移幂等（已是 v2 的跳过）、不制造数据（形态不明的不碰）、带往返校验。
   九层管线架构图中 M2 的位置与职责不变；新增的是 M2 内部的**数据形态治理**职责。

2. **数据回滚方案** —— 见下节「三、回滚方案」。

3. **已知缺陷登记（不改，只记录）** —— `PerceptionVector40DCodec` 的 **v0 命名对象分支
   是 fail-open 的**：对任意 JSON 对象都返回全零 40D 向量（`Number(undefined)=NaN`
   被 `isFinite` 跳过），而不是返回 `null`。
   ⇒ **这是本项目「零向量」的真正生产线**（不止显式写零那一处）。
   本批**不修编解码器**（改它影响全部调用方语义，属结构性变更，须业主单独裁定），
   改为在**使用侧**（v18 迁移）做形态级预检自我防护，并加**记录性测试**钉住该行为 ——
   日后若修好 v0 分支，该测试会失败并提示复核迁移预检。

## 三、回滚方案 / 配置变更清单

### 3.1 回滚方案

| 层 | 内容 |
|---|---|
| **代码回滚** | 本批独立 commit。回退该 commit 即回到「兜底写零 + 形态不统一」原状 —— **无数据依赖**，因为 v18 迁移只改包装形态、不改数值，旧代码读 v2 包装同样正确（解码端三形态全认） |
| **数据回滚** | v18 迁移**不需回滚**：它不改变任何向量数值（往返校验保证），且旧代码能正常读 v2 包装。若确需回到 v1 裸数组，可写逆向迁移（`dims` 数组取出即可） |

## 四、本批的方法论更正（如实记录）

任务书初版断言「编解码器只认裸数组、同一列两种形态解码器只认一种」，
并据此把 40D 维定为 🔴 高严重度。**2026-10-08 用真实 `decodePerceptionV40` 扫全库实测：
三种形态解码失败 = 0，该断言为误**（源于初版探针用 `Array.isArray` 判断的局限）。
任务书 §1.2.2 与 S2 方案 §三 批3 均已同步更正。

⇒ 教训：**凡涉及运行时行为的判断，一律用真实模块跑一遍，不能用粗糙探针代替。**

而这次更正也**换来一个更深的发现**：真正的零向量生产线是编解码器 v0 分支的 fail-open
（见「二、3 已知缺陷登记」）—— 比原以为的「显式写零」隐蔽得多，且由本批的守卫测试**当场抓获**
（我自己的迁移第一版就被它洗出了全零向量）。
