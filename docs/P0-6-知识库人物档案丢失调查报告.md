## 一、结论摘要

**共三层原因，彼此独立叠加。文件的物理副本一份没丢，丢的是 `knowledge_base` 表里的行。**

| # | 层 | 内容 | 是否已定案 |
|---|---|---|---|
| **A** | 检索层 | 会晤检索口径是「**自有优先 → `slice(0,3)`**」。熊梓铭名下的自有条目只剩 3 条**对话碎片**，它们占满了 3 个名额 ⇒ 她真正的文档永远挤不进来 | ✅ 已定案 |
| **B** | 归属层 | `scripts/fix-all-entities-final.cjs`（commit `27925c7`，**2026-08-02**）把她名下所有 KB 文档 `belong_entity_uuid` 置 NULL（"去归属"）⇒ 文档从「她的」变成「公共的」，失去自有优先 | ✅ 已定案 |
| **C** | 数据层 | `knowledge_base` 从 **68 条**塌到 **3 条**，丢 **63 条**（含 3 条人物档案 + 13 条人物参考 + 23 条系统文档…）。窗口：**2026-08-26 02:24 → 2026-08-28 19:47** | 🟡 窗口已定，**执行者未定** |

**可恢复性：高。** 08-25/26 的三份备份里 `knowledge_base` 68 条**内容与归属均完整**，磁盘上 `data/knowledge-md/` 与 `data/knowledge-cabinet/docs/` 还留着对应文件可供内容校验。

## 二、现象与判据

业主报告（2026-10-07 实测，与熊梓铭会晤）：

> 「她说她查不到知识库里关于她的文档，但看到了一些零碎的对话」

结构性佐证（服务日志）：

```
[KB·Entity] 会晤实体检索: 熊梓铭 → 3条知识(自有优先)      ← 48 次全部是 3 条
[EntityMem] 会晤实体自有记忆: 14 条(原14)
[PrivacyFilter] 熊梓铭会晤记忆过滤: 38→34 条（剔除他人私密）
```

「3 条」看着像"检索到了 3 条"，实际是 `slice(0,3)` 的**上限**被正好占满 —— 而占满它的正是"零碎的对话"（见 §四）。

## 三、取证方法（可复现）

**逐份备份二分**：对仓库内每一个 `fusion_memory.db` 的历史副本，统计 `knowledge_base` 的行数与关键分类。

复现要点：
- 一律用 **sql.js 只读打开副本**，不碰线上库；
- 判据用**结构化字段**（`classification` / `source_type` / `title LIKE`），不靠正文匹配自证；
- `classification='范式文档'` 与 `title LIKE '%人物档案%'` 是两个独立标记，互为交叉验证。

## 四、层 A · 检索口径（为什么"看不到"）

`src/app/knowledge/KnowledgeContextBuilder.ts`：

```ts
// 实体自有优先 + 过滤低分噪音
const _own   = _entityResults.filter(k => _meetingEntityUuid && k.belong_entity_uuid === _meetingEntityUuid);
const _other = _entityResults.filter(k => !(_meetingEntityUuid && k.belong_entity_uuid === _meetingEntityUuid));
const _kept  = [..._own.sort(降序), ..._other.sort(降序)].filter(k => k.matchScore >= 0.3).slice(0, 3);
```

配合 `KnowledgeEngine` 的过滤口径「**自己的（`belong==该实体`）+ 公共无归属**」（`buildSqlClause({visibleUuids, allowUnowned:true})`）：

- `_own` 先排序 ⇒ 只要自有条目 ≥3 条，**公共条目一条都进不来**；
- 熊梓铭 `_own` 恰好 3 条，且全部是 `巩固记忆:` 开头的**对话碎片**（`source_type='systems_consolidation'`，创建于 2026-10-05）。

⇒ **她的自有名额被对话碎片占满，真正的文档即使还在库里（以"公共"身份）也永远排在第 4 位之后**。
这正是「查不到文档，但看到一些零碎的对话」的精确来源。

## 五、层 B · 熊梓铭被「去归属」（文档还在，但不再是"她的"）

`scripts/fix-all-entities-final.cjs`（commit `27925c7`，**2026-08-02 19:04**）第 P1-1 段：

```js
// P1-1: 熊梓铭 KB 去归属
const docs = SELECT id, title, classification FROM knowledge_base
             WHERE belong_entity_uuid = <熊梓铭> AND classification != '人物参考';
UPDATE knowledge_base SET belong_entity_uuid = NULL, updated_at = ? WHERE id = ?;
```

同脚本 **P1-2** 对徐诗雨则是**真删**：

```js
// P1-2: 徐诗雨 KB 去重 —— 保留最早的一篇，删除其余
SELECT id … WHERE belong_entity_uuid = 'TXS-000000007' AND classification = '人物档案' ORDER BY created_at ASC
DELETE FROM knowledge_base WHERE id = ?
```

**说明**：P1-1 的动机从脚本名看是「系统文档去归属」（即把误挂在她名下的**系统文档**摘掉）。这个动机本身可能是对的；
问题在于它的判据是 `classification != '人物参考'` —— **把「人物档案」一并摘掉了**，而人物档案恰恰是她最需要自有优先的那一类。

## 七、文件层：物理副本**一份没丢**

```
data/knowledge-md/            【FG档案范式】王全芬.md · 熊梓铭.md · 徐诗雨.md · 徐诗韵.md
                              阿芬.md · 梓铭简介：.md · 徐诗雨身高….md（2 份）
data/knowledge-cabinet/docs/  同样 5+ 份（.txt）
```

`data/knowledge-md/` 共 1212 个文件、`data/knowledge-cabinet/docs/` 共 1151 个文件。

🔴 **方向说明**：`KnowledgeEngine` 的 `CABINET_MAP` 是 `source_type → 分类文件夹`，
即这两个目录是知识库的**导出镜像**（KB → 文件），**不是导入源**。
所以"文件在、行没了"是自洽的：文件是当初导出留下的残件。

**这同时是好消息**：恢复时可用文件内容与备份内容**互相校验**。

## 八、附带更正（源码注释误导）

`src/app/knowledge/KnowledgeContextBuilder.ts:167` 的注释写着：

```
实测: 查询"熊梓铭"，… 系统架构文档(公共)挤掉熊梓铭自己的档案("梓铭简介" belong=TXS-000000003)
```

**`梓铭简介`（`belong=TXS-000000003`）在当前库中已不存在**（全库 `title LIKE '%简介%'` 命中 0）。

这条注释会让人以为「实体档案机制在运作、只是排序有问题」，从而**查错方向**。
本次排查即被它误导过一次。建议在恢复批次中一并更正该注释。
