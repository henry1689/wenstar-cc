### 1.1 铁证：响应只有 3 个字符

err.log 中 **66 次**同一告警：

```
[EntityTriage] 判定响应无法解析（可能被截断）→ 本轮全量保持观察。raw 前120字: [{"
                                                                              ↑
                                                              raw 实际内容 = 【[{"】共 3 字符
```

对应 stdout 的 66 条执行日志：

```
[Maintenance] 实体终审: 扫描30 提升0 标注0 观察30
```

（注：该日志**只在 `error` 为空时**打印 —— 即 LLM 调用**成功返回**、但解析全 unknown。）

### 1.2 因果链

```
JUDGE_MAX_TOKENS = 2500
   ↓
模型先输出 reasoning_content（思维链），token 被大量消耗
   ↓
轮到 content 输出时 token 已耗尽 → content 仅剩 "[{"
   ↓
resolveReplyFromFields(content, reasoning) 拿到 "[{" —— **非空** ⇒ 不抛错
   ↓                                    （这正是 Hook 显示 status=success 的原因）
parseJudgeResponse("[{") 解析失败 → 全部判 unknown
   ↓
kept=30 ⇒ "扫描30 提升0 标注0 观察30"，循环 66 次
```

### 1.3 估算错在哪

`EntityTriageService:70` 的注释：

> 评审 F10: 30 条 × 4 键 ≈ 900~1200 tokens，叠加解释文本易截断；截断会让
> parseJudgeResponse 退化为全 unknown（静默零提升）。取 2500 留足余量。

**它准确预见到了「截断 → 全 unknown」这个失效模式，但只估算了输出 JSON 的开销，
没有估算 `reasoning_content` 的开销。** 而 `rawCall` 恰恰无法控制推理强度：

```ts
async rawCall(messages, maxTokens, temperature) {
  return (await this.callDeepSeekApi(messages, maxTokens, temperature, { timeoutMs: 45_000 })).text;
  //                                                                  ↑ 仅 timeout
}
```

而底层 `callDeepSeekApi` **本就支持** `reasoning_effort`（`DeepSeekLLMProvider:1277`
`...(extraParams.reasoning_effort ? { reasoning_effort: ... } : {})`）—— **只是无人传入**。

### 1.4 附带的运维事实（非本批可修）

err.log 另有 **3 次** `实体终审失败(非阻塞): LLM 调用失败: DeepSeek API 402:
{"error":{"message":"Insufficient Balance"}}` —— **账户余额不足**，属运维项，代码层无法修复。
本批不掩盖它：修复后若再遇 402，将以结构化告警暴露。

## 二、方案：4 处改动（3 处可用性 + 1 处参数入口）

### 2.1 改动 1 — 给 reasoning 留出 token 预算

`src/app/entity/EntityTriageService.ts`

```ts
// 现在
const JUDGE_MAX_TOKENS = 2500;
// 改为
const JUDGE_MAX_TOKENS = 8000;
```

**依据**：输出 JSON 本体约 1200 tokens（原估算正确），思维链通常 2000–5000 tokens
⇒ 2500 必然不足、8000 留足余量。**不是拍脑袋调大**——2.2 的批大小下调与之配套。

### 2.2 改动 2 — 降低单批复杂度

```ts
// 现在
export const DEFAULT_TRIAGE_BATCH = 30;
// 改为
export const DEFAULT_TRIAGE_BATCH = 15;
```

**依据**：批越小，单次响应越短、截断概率越低；配合每日可跑多轮（当前每 24h 一次），
总吞吐不降反升。**两个常量同改是一组**，不单独调其一。

### 2.3 改动 3 — 失败可见性（治「66 次无人知」）

`src/app/entity/EntityTriageService.ts`

- `TriageReport` 新增 `parseFailed?: boolean` 与 `rawLength?: number`
- 解析全 unknown 时：**结构化告警**（含 `raw.length`、raw 前 120 字、条数），
  并把 `parseFailed: true` 回传给 `MaintenanceService`
- `maintenance.ts` 的 `runEntityTriage` 相应分支：解析失败时输出**警告级**日志
  （与「正常的全 unknown」区分开 —— 前者是故障，后者是 LLM 判断）

**依据**：本批根因之所以能藏 66 次，正是因为「调用成功但解析失败」与
「调用成功且 LLM 判 unknown」**在日志上无法区分**（都表现为 `提升0 观察30`）。

### 2.4 改动 4 — `rawCall` 增加可选 `reasoning_effort` 入口（业主批准的"可选项"）

**三处同步修改**（缺一不可，否则第 4 参数被静默丢弃）：

| 文件:行 | 改动 |
|---|---|
| `src/m5/types/index.ts:110` | 接口签名追加可选参：`rawCall?(messages, maxTokens, temperature, opts?: { reasoning_effort?: string })` |
| `src/m5/DeepSeekLLMProvider.ts:1180` | 实现追加可选参，透传进既有的 `extraParams.reasoning_effort` 分支 |

不需要深度推理，压低思考既省 token 又缩短响应。

## 六、文档同步摘要（白皮书 / 蓝皮书）

### 6.1 白皮书更新摘要

**标题：实体离线终审的可用性 —— 「跑过了」不等于「跑成了」**

1. **区分「执行成功」与「判定有效」**。原实现下 LLM 正常返回但内容不足时，
   `resolveReplyFromFields` 因结果**非空**而不抛错 ⇒ 外层记为 `status=success`
   ⇒ 维护调度打印「扫描30 提升0 标注0 观察30」⇒ **故障与正常判定在日志上不可区分**。
   本次新增 `parseFailed` 结构化信号，让「截断/解析失败」与「LLM 判 unknown」**可分辨**。

2. **token 预算必须含推理开销**。实体审核是**判定性任务**，但模型仍会先产出
   `reasoning_content`。原 `JUDGE_MAX_TOKENS=2500` 只覆盖了输出 JSON 本体（≈1200），
   未覆盖推理开销 ⇒ content 仅剩 `[{"`。现提至 8000 并配合批大小下调（30→15）。

3. **参数入口要打通才能用**。底层 `callDeepSeekApi` 早已支持 `reasoning_effort`，
   但 `rawCall` 未暴露该入参，导致「能力存在却不可达」。本批打通入口，
   让判定性任务可压低推理强度（省 token + 缩短响应）。

4. **长期方向不变（业主 2026-10-08 指示）**：字面判据已到极限（乙1 覆盖 8.6%），
   根治依赖「梦境 LLM 定期筛选 + 备选区（临时调用，不直接正式归档）」。
   **本批是让该路径第一次真正可用** —— 在此之前它 66 次运行零成功，
   **备选区的设计应在终审真正产出有效判定结果之后再做**，否则取舍规则无真实依据。

### 6.2 蓝皮书更新摘要

**标题：M5 LLM 入口与 M4 实体治理的边界**

1. **`rawCall` 入参扩展**：新增可选 `opts.reasoning_effort`，**向后兼容**
   （5 个既有调用方零适配）。契约变更点仅 `m5/types` 主接口 + `DeepSeekLLMProvider` 实现 +

2. **M4 实体治理的观测性补齐**：`TriageReport` 增加 `parseFailed` / `rawLength`，

## 七、方法论记录

1. **「链路通了」与「功能有效」是两回事，必须实测到最内层**。
   装配 ✓、调度 ✓、执行 66 次 ✓ —— 三层全绿，功能实为零。
   ⇒ 教训：**验证要穿透到业务结果**（`提升X 标注Y` 是否非零），
   停在「没有报错」就会把「跑了 66 次全白跑」当成「正常运行」。

2. **「非阻塞」是双刃剑，必须配可见性**。
   把终审失败标为非阻塞（不拖垮主链路）是**正确的设计**；
   但**没有任何人会发现它一直失败**。⇒ 教训：**非阻塞 ≠ 不告警**，
   凡是「静默降级」都要有对应的可观测信号。

3. **业主说的「没落实到位」要用代码核实其确切含义**。
   S1 核实的结论既不是「没做」也不是「做好了」，而是**「做完了但从未成功过」**——
   这个精确的定位直接决定了本批该改什么（参数与观测性，而非重建机制）。
