## 一、四项改善

### B1 · 守卫升级：堵住注释行这个口子 🔴

**现状**（`sql-schema-consistency.test.ts` `[B5]` 组）：
```ts
if (t.startsWith('//') || t.startsWith('*') || t.startsWith('/*')) return;  // ← 注释直接放行
if (!/\bsearch_index\b/.test(line)) return;
if (!/\b(FROM|INTO|UPDATE|DELETE|JOIN|TABLE|INDEX)\b/i.test(line)) return;  // ← 须含 SQL 动词
```
⇒ 注释里怎么写都不会红。

**问题**：review 实测发现 **6 处过时注释**仍在描述已消失的机制
（「砂金库倒排索引启动补齐」「供 search_index 分块索引」…），
它们是「改善不沉底」的**载体**——下次有人照着注释就把机制接回来。

**方案（计数封顶，只减不增）**：
- 在 `[B5]` 组内新增用例：非白名单文件中 `search_index` **出现次数 ≤ 基线值**
- 基线值 = 批2 清偿 6 处后的实测计数（执行时用 `grep -c` 定，写死为常量）
- **效果**：历史记录（拆除说明注释）允许保留，但**新增一处即红**
- **不选「全禁」**：拆除历史必须留痕，全禁会逼人改用别的措辞绕过守卫

**同时**：新增用例断言**已证实过时的具体表述不得复活**（正则表，比表名更精准）：
```
倒排索引启动补齐 | 供 search_index 分块索引 | 与旧链路并行跑 | 倒排索引查询的最大 n-gram 词数
```
命中即 fail（白名单文件除外）。

### B2 · 围栏耗时埋点 `fence_ms` 🟡

**现状**：`data/retrieval-v11/metrics.json` 只有**整体**耗时
```
v11_retrieval_ms_p50: 97   p95: 179   p99: 179   samples: 14
```
整体 97ms 里围栏占多少、精排占多少 —— **无法归因**。而本轮手测：
围栏 40 分片 **80~91ms**（`conversations` 16,257 行），已是整体耗时的主体。

**为什么必须补**：围栏是纯 `LIKE` 扫描，**随 `conversations` 行数线性劣化**。
今天 1.6 万行跑 80ms，涨到 10 万行就是 500ms —— 没有埋点就只能等用户说「变慢了」。

**方案**（复用既有直方图机制）：
- `ShadowLog.ts` 新增独立采样数组 `fenceLatencies`（与 `latencies` 同构，同用 `LATENCY_RING=2000`、`FLUSH_EVERY=50`）
- 新增输出字段 `fence_ms_p50 / p95 / p99 / samples`
- **唯一埋点位**：`StructuredRecall.recallByStructured` 的围栏段（进/出），
  由调用方计时传入或在函数内自测（不改变返回契约）
- 🔴 红线沿用 ShadowLog：**只记耗时与计数，不记任何原文**

**验收**：跑 20 次真实查询后 `metrics.json` 出现 `fence_ms_samples ≥ 20`，
且 `fence_ms_p50` 与手测（4~48ms）同量级。

### B3 · `_maxTerms=40` 调优（**先实验，后改**）🟡

**现状**：`MemoryConfig.ts:193` `sandboxRecallMaxTerms: 40`，
注释「控制单次 SQL 的 **IN** 规模」—— **已过时**（B3b-5 改成了 `LIKE OR`）。

**实测已知**（`conversations` 16,257 行）：
| 分片数 | 耗时 |
|---|---|
| 3 分片（「研究」） | **4.3 ms** |
| 10 分片 | 41 ms |
| **40 分片** | **80 ~ 91 ms** |

40 分片占了围栏耗时的绝大部分，而**长分片区分度更高、短分片多是虚词碎片**。

**方案（实验驱动，不拍脑袋）**：
1. 从生产真实查询取样 ≥ 30 条（可复用 `shadow/*.jsonl` 的 `trace_id` 关联查询，
   或从 `conversations` 随机抽句作查询）
2. 对每条查询跑梯度 **40 / 24 / 16 / 12 / 8** 分片
3. 记录两个指标：**候选数**（召回）与 **耗时**
4. **判据**：候选数相对 40 分片下降 **< 10%** 且耗时下降 **> 30%** ⇒ 才允许下调
5. 选定值写回 `sandboxRecallMaxTerms`，**注释同步改写**（去掉「IN 规模」）
6. 结果与判据一并写入本任务书「实验记录」节

**若实验显示 40 已是帕累托最优** ⇒ **不改数值，只改正则过时的注释**，同样算达成。

### B4 · 死导出守卫：防「恒空函数」被接回来 🔴

**背景（本次真事故）**：`UnifiedSearchEngine.search` 在 B3a-4 被收口为
```ts
return { items: [], raw: [], hitsBySource: {}, totalCandidates: 0 };
```
但**降级路径仍在调它** ⇒ V13 一抛异常就全链路空检索，日志还显示「降级到 V11」。
全量测试 30 项红里**没有一条能发现它**（没有用例会触发 V13 异常）——
是靠人工读代码发现的。**这不可复制**。

**实测现状**：`grep -rn "UnifiedSearchEngine" src/ --include=*.ts`（非测试）
→ 唯一 import 是 `searchV13`；`search` **零调用点** ✅（B4 已修）

**方案**：在 `[B5]` 同文件新增 `[B6] 死导出守卫` describe 组：
- 维护**收口函数清单**（初值：`['UnifiedSearchEngine.search']`，注释写明收口日期与 commit）
- 断言：这些函数在 `src/**`（除其定义文件与测试）中**零调用点**
- 扫描口径：既查 `import { search }`，也查 `search: unifiedSearch`、
  `await import('...UnifiedSearchEngine')` 后紧跟 `search(`
- **效果**：谁再把降级路径接回恒空函数，测试立刻红

**可扩展**：日后收口其他函数时往清单加一行即可（清单本身有反向断言：
清单项必须**真实存在**且**确为空实现**，防清单腐化）。

### B3 `_maxTerms` 梯度实验（2026-11-02 实测）

**样本**：34 条查询 = 9 条手测 + 25 条生产消息随机抽样（取前 12 字）
**数据源**：`conversations` 16,257 行，单实体 `TXS-000000007`
**方法**：每档 **5 轮取中位数**（首轮单次测量出现「16 分片反而更慢」的反常，是噪声）

| 分片数 | 平均候选数 | 相对 40 分片 | 平均耗时 | 耗时降幅 |
|---|---|---|---|---|
| 40 | 372.29 | 100% | 76.0 ms | — |
| 24 | 372.29 | 100% | 65.1 ms | 14.3% |
| 16 | 372.29 | 100% | 53.4 ms | 29.7% |
| **12** | **372.29** | **100%** | **49.1 ms** | **35.4%** |
| 8 | 354.21 | 95.1% | 43.0 ms | 43.4% |

**判据**（候选降 <10% **且** 耗时降 >30%）：

| 分片 | 候选降 | 耗时降 | 结论 |
|---|---|---|---|
| 24 | 0.0% ✅ | 14.3% ❌ | 不采纳 |
| 16 | 0.0% ✅ | 29.7% ❌（差 0.3 个点） | 不采纳 |
| **12** | **0.0% ✅** | **35.4% ✅** | **采纳** |
| 8 | 4.9% ✅ | 43.4% ✅ | 召回损失超阈值，不取 |

**结论**：**采纳 12** —— 召回**零损失**、耗时 **−35.4%**，严格帕累托改进。
已落 `MemoryConfig.sandboxRecallMaxTerms: 12`，注释写入全表。

**机理**：OR 围栏下分片高度重叠，**前 12 个分片已覆盖全部候选**，后 28 个纯属冗余 ——
这也解释了 40 这个值为什么是浪费。
