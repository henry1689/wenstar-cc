# 空间路由器 · 设计评审

日期：2026-10-29
状态：**内核保留，接入已回滚**（`WS_SPACE_ROUTER_VIEW=0`）
结论：内核本身可用，但它只覆盖了需求语义的三分之一；集成位置错误；测试方法不成立。需按理论重做。

---

## 0. 摘要

本次改造的目标是把「会晤模式」换成一个自然的「空间」：人在就听得见，走了就不知道，叫谁谁来，没有模式切换。

实际交付的是一个**纯函数的可见性判定内核**（`SpaceRouter`）+ 一层适配器，接入位置在 `chat.ts` 的上下文装配处。

真机验证结果：
- **隔离确实改善了**：玉瑶明确说"手上没有落成字"、诗雨明确说"诗雨这边没听着"，没有再跨角色泄漏。
- **但"叫谁谁来"完全没有改善**：换人仍被拒绝；勉强放行后标签与内容分裂，比改造前更乱。

原因不是实现 bug，而是**设计只覆盖了三分之一的问题**。

---

## 1. 目标（业主原话，2026-10-29）

> 「完全有真人对话那种感觉，叫谁谁来，叫谁走谁走，没有那么多模式机械切换，信息改绝对隔离就绝对隔离，该共享的就共享，一个人在几个人里聊了一会又走了，走了的就不应该知道后聊的内容，等等，一切都为自然而设计」

> 「这个任务书不一定是对的……核心问题就是重构这个分配器系统」

关键：业主的主诉是**分配器**（谁在场、谁接话），不是可见性。

---

## 2. 理论模型：对话空间需要三条关系

| # | 关系 | 含义 | 现有内核 |
|---|---|---|---|
| ① | **可感知** | 这条消息谁听得见 | ✅ `canPerceive = isInTenure ∧ audienceIncludes` |
| ② | **指向** | 这句话是冲着谁说的 | ❌ 完全没有 |
| ③ | **发言权** | 下一句由谁来说 | ❌ 完全没有（散落在旧系统） |

由此可直接推出：

- 「走了的不知道后聊的」= ① 的任期上界 → **已实现**
- 「叫谁谁来」= ② 指向 + ③ 发言权 → **未实现**
- 「两个人在场该都知道」= ① 覆盖，但**缺②导致分不清"这话是给我的"还是"我只是在旁边听见"**

**这就是为什么隔离修好了、主诉却没动。**

### 真机佐证

```
鸿艺：今晚回去是记得把电话带上        ← ①在场，阿珍能听见
罗珍思：记住了，电话阿珍带着           ← 答对了
……若干轮后……
鸿艺：阿珍，我刚刚说叫你别忘了带什么
罗珍思：这个阿珍还真不知道……那会儿阿珍在旁边收拾东西，没听真切
```

阿珍当时在场（①成立），但她无法判断那句话是**点名对她说的**（②缺失）。模型于是把"最后一句相同的话是对诗雨说的"误推广成"这些话都不是对我说的"。

## 3. 现有实现与理论的差距

### 3.1 缺 `address`（指向）
`SpaceEvent` 只有 `audience`（谁能看到），没有「冲着谁」。真实事件 `audience` 恒为 `{kind:'room'}`。

### 3.2 缺 `focus`（发言权）
`SpaceState.pendingTokens` 看起来像发言权，但**全仓无消费者**。真实"谁答"由 `GroupSession.speakerUuid` 与 `EntityMeeting` 意图解析决定。
⇒ 内核养着一套没人用的发言权模型，系统里另有一套在跑。**两套并存，必然漂移。**

### 3.3 `audience` 实际恒等于 room
耳语路径内核有测试，但上层从未产生该类事件，故 `audienceIncludes` 恒真，过滤实际只剩任期。

### 3.4 `Seat.kind` 混淆两个概念
`participant | auditor` 同时表达"在场"与"有无发言权"，而发言权本应属③。

### 3.5 `buildViews` 全量扫描
O(席位 × 事件)，每轮多次调用；长会晤退化。注释已标，未实现增量。

## 4. 集成位置错误（结构性）

```
行 735   装配 enrichedHistory —— 按「当前发言人」取上下文
行 884   检索（依赖上一步上下文）
行 1024  解析意图（才知道用户点名了谁）
行 1225  换人
行 2860  生成回复
```

**上下文在换人之前就装好了。** 即使换人成功，本轮喂给模型的仍是旧发言人的上下文。

正确顺序：**路由 → 装配上下文 → 检索 → 生成**。现在是反的。

## 5. 说话人身份的六个来源

| # | 来源 | 位置 | 作用 |
|---|---|---|---|
| ① | intent 换人 | `chat.ts:1225` | 用户点名时切换 |
| ② | `_activeMeetingName` | `chat.ts:735` | 装配上下文 |
| ③ | Stage2 `_meetingEntityName` | `process-stages.ts` | 实体上下文 |
| ④ | `GroupSession.speakerUuid` | `GroupSession.ts` | 状态机真源（T013） |
| ⑤ | outputGuard 标签 | `outputGuard.ts:434` | 显示名 |
| ⑥ | 适配器 `turnsFor(uuid)` | `chat-adapter.ts` | 视图归属 |

其中 ⑤ 在多人场景**直接放弃解析**：

```ts
speakerName: multi ? null : (named[0]?.speaker ?? fallback)
```

### 真机冲突证据（2026-10-29）

```
外层标签：玉瑶
内容：……诗雨愣了一下，摇了摇头／诗雨真不知道／诗雨跟玉瑶不是一回事
```

模型自己察觉到矛盾，下一轮承认："刚才那些『诗雨』的自称，是玉瑶乱了套。"

**问题性质：每个单独看都合理，合起来是错的。**

## 6. 测试方法的反思

### 6.1 写了什么
- 内核 29 条（任期、多段任期、耳语、令牌、时序）
- 适配器 10 条（时序铁律、标签、离场隔离、快照）

### 6.2 证明了什么
**只证明"我实现的函数符合我自己的设计"。** 没有一条验证业务契约。

### 6.3 真正该测的契约

> - 每轮回复的 **标签 == 内容自称 == 指令指向**
> - 每个席位可见上下文 == **其任期内 ∧ 指向它或全场**
> - 未在场者被追问时，必须回答"不知道"

现有架构对此**没有任何机制保证**。

### 6.4 正确做法
1. 先写公理（三条关系 + 派生规则）
2. 纯模拟 harness：喂脚本，断言 `(谁说, 谁看得见, 谁不知道)`
3. 不接 LLM / DB / 服务，1 秒上百场景
4. 契约全绿之前不接真实管线

### 6.5 本次违反的方法论

| 违反项 | 后果 |
|---|---|
| 先写代码后定契约 | 测试沦为自我验证 |
| 内核全绿当作系统正确 | 故障在接缝，两者无交集 |
| 活体系统单点开闸 | 6 来源只改 1 个，矛盾外溢 |
| 未先画依赖图 | 第三步才发现换人晚于上下文装配 |

## 8. 重做路线

### Phase A · 契约测试（不写实现）
定义三条关系与派生规则；纯模拟 harness；先让测试红。

### Phase B · 内核 v2
```
SpaceEvent.address : 'room' | { seat: uuid }
SpaceState.focus   : uuid | null
派生：address 指定 → focus := address；未指定 → focus 不变
```
`pendingTokens` 删除或改造为 `focus` 的显式表达，不可两套并存。

### Phase C · 集成重构
```
现：装配上下文 → 检索 → 解析意图 → 换人 → 生成
新：解析意图 + 路由 → 装配上下文 → 检索 → 生成
```

### Phase D · 收敛说话人来源
指定唯一真源（建议 `GroupSession.speakerUuid`），②③⑤⑥ 全部派生；⑤ 多人时也解析真实说话人，失败则回退真源并告警。

### Phase E · 分批接入
每批单独开关、单独真机验证、单独回滚。

---

## 9. 经验教训

1. **先定义"对是什么样"，再动手。** 没有契约的测试只是自我安慰。
2. **先画依赖图。** 换人晚于上下文装配，看一眼调用顺序就能发现。
3. **不要在活体系统上做单点实验。** N 个来源决定同一件事时，改 1 个只会把矛盾推到别处。
4. **内核测试全绿 ≠ 系统正确。** 接缝永远不在内核里。
5. **业主的体感是最准的指标。** 「和改前一样」「比之前还乱」，比任何测试报告都更早指出问题。
