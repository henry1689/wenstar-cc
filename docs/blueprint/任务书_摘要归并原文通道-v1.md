## 二、核心设计决策

### 2.1 迁移形态（每组 1 行）

| 列 | 取值 | 理由 |
|---|---|---|
| `role` | `'assistant'` | **对齐既有 213 行样板**，不引入新 role 值（新值会让所有 `role` 分支假设失效） |
| `content` | `block_summary` 原文 | 三层结构（标签/叙事/情感）可直接当召回文本 |
| `dialog_group_id` | 组 id | 🔴 原文通道 `GROUP BY c.dialog_group_id` 自动归组 |
| `is_summary` | **1** | 主历史查询/归档自动排除 |
| `is_compacted` | 0 | 与既有 210 行口径一致，避免被归档压掉 |
| `timestamp` | 组 `last_ts` | 不打乱时间序 |
| `seq_pos` | **避开已占用值**（见 §6.2） | 实测 min 0 / max 19927 / distinct 15748（**已有 912 个重复**） |
| `belong_entity_uuid` | 组的值（100% 合法） | 户籍闸门 |
| `is_test` | 0 | 测试隔离 |
| `namespace` | 与该组原文行一致 | 测试隔离第二道 |
| `topic` / `entity_names` | 从组的原文行继承 | 保持检索面一致 |

**物理位置**：仍在 `conversations` —— 即「归到主通道数据库」，不新建表（新建表 = 又一条通道）。

### 2.2 🔴 核心矛盾：摘要行既要能召回，又不能污染命中计数

原文通道现在按 `hit_rows / u_hit / a_hit` 计数，而 `convDensity = max(u_hit,a_hit)/turn_count`。
若摘要行（`role='assistant'`）被计入 `a_hit`，**每组会凭空多出 1 个「命中轮」，密度虚高**。

**解法：同一条 SQL，分列计数**（仍是**一条**通道，不拆成两路）：

```sql
SELECT c.dialog_group_id AS gid,
       COUNT(CASE WHEN COALESCE(c.is_summary,0)=0 THEN 1 END)                    AS hit_rows,
       SUM (CASE WHEN COALESCE(c.is_summary,0)=0 AND c.role='user'     THEN 1 ELSE 0 END) AS u_hit,
       SUM (CASE WHEN COALESCE(c.is_summary,0)=0 AND c.role='assistant' THEN 1 ELSE 0 END) AS a_hit,
       MAX (CASE WHEN COALESCE(c.is_summary,0)=1 THEN 1 ELSE 0 END)              AS hit_summary_rows
  FROM conversations c
 WHERE c.dialog_group_id IS NOT NULL
   AND (c.is_test IS NULL OR c.is_test = 0)
   AND c.belong_entity_uuid IN (${uuidPhs})
   AND (c.content LIKE ? OR ...)          -- 摘要行与原文行同一围栏，一条 SQL
 GROUP BY c.dialog_group_id
```

- `channels.content = max(u_hit, a_hit)` —— **只算原文轮**，摘要行不参与 ✅
- `channels.summary` —— 由 `hit_summary_rows` 触发，回表取该组 `is_summary=1` 行的 `content`，
  用既有 `countHitShards` 算分片数 ⇒ **量纲不变**，`min(1, summary/10)` 与法典 §12.2.3 一致，
  **`ADR_010_SUMMARY_DENSITY_CAP` 不用改**
- 摘要行命中但原文没命中 ⇒ `content=0, summary>0` ⇒ 走 `summaryDensity` 分量，仍进候选集 ✅

> 这样「一条通道」成立，且计数不虚高、法典分母不改。
