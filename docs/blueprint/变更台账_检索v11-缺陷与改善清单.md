### F-14 ✅（2026-10-28 关闭）`Backfill.ts` 默认 `topK` 随常量变 50，弱化 S3-B6「100% 命中率」

**原判**：B6 要求「按 id **逐条**核，非抽样」。回捞时用 top-K=50 截断，
则**只核了前 50 条**，「100%」的分母被缩小，判据被弱化。
**归因层**：`m4/retrieval/Backfill.ts`。

**实测定性（2026-10-28）**：不是「分母被缩小」，是**判据集合被偷换**。
`checked` 从来都是全量逐条（421 条一条不落），被截断的是**每条的判定范围** ——
`scoreAndRank(hits, nowMs).slice(0, topK)` 把「精排结果集」换成了「精排 top-K」。
实测 id=14694：围栏池第 183/500 位（进池）→ 精排第 53/500 位 → 被 `slice(0,50)`
切掉 → 误判「未命中」。同 UUID 含「诗雨」的对话 3341 条，内容同质导致排序天然挤压。
该行 `is_test=0`、`belong=TXS-000000007`、`calcium_score=0.40905`，是正常生产数据。

**根因与 §7.1 同源**：2026-10-28 上午修的 §7.1 也是 `ranked.slice(0, RERANK_TOP_K)`
冒充「候选集」。**同一个形态的第二处**，两次都无测试保护。

**实现路径与原决议的偏差（必须留档）**：
| | 原决议（本节排期） | 实际落地 |
|---|---|---|
| 方案 | 跑 B6 前**显式传大 `topK`**（配置层） | **改判据定义本身**（代码层），去掉 `.slice(0, topK)` |
| 效果 | 走全候选 | 走全候选（同向） |
| 依赖 | 操作纪律：下次跑必须记得传 | 不依赖纪律，判据定义即正确 |

**为何偏离原决议**：① 依赖纪律的方案必然复发（本 bug 已出现两次）；
② 原方案要传多大才够？实测 `candidates_out` max=1000，传多大都可能不够，且阈值本身
就不是判据该有的概念；③ `RERANK_TOP_K` 是**生产注入量约束**，为验收去动它会触碰
任务书 §S5 D4「度量口径不是过滤开关」。业主 2026-10-28 裁决「**按候选集判，与 §7.1 对齐**」，

## 八点五、2026-10-27 第二轮实测缺陷明细（业主群聊原文取证）

> 业主原话：「**问题基本一样，人物也窜的厉害，结构不人性化，加减人不方便，不符合一般真人习惯**」。

### F-22 🔴 一轮塞两个人（最严重）

**证据**（同一条回复内出现两个发言人）：

```
【罗珍思】徐诗雨：（诗雨应了一声，把包带往肩上顺了顺）
诗雨这边就回宿舍拿点东西，没别的。
罗珍思：（阿珍应了一声，把手里的东西归拢好）
阿珍这边没什么要拿的，就一个包，早收拾好了。
```

第二处：`【罗珍思】徐诗雨：（诗雨应了一声，抬起头）… 罗珍思：（阿珍应了一声…）`

**根因**：`src/m5/group/outputGuard.ts:51 extractSpeakerHeader()`
- 逐行只扫**头部 ≤4 行**，且要求首字段是 `speaker:`；**正文内的 `【名】` / `名：` 一律不解析**；
- `validateReplyIdentity()` 的返回是**单个 `assignedSpeaker`** ⇒ 结构上就不支持一轮多人；
- 头缺失时走**情况 0 按粘性归属** ⇒ 整条（含徐诗雨的台词）记给上一轮的 `罗珍思`。

**修法方向**（待定，需业主确认）：
- 方案 A：**轮内分段归属**——按 `【名】` / `名：` 切段，每段独立走 `validateReplyIdentity`，渲染时逐段挂名；
- 方案 B：**单轮单发言人**——提示词强约束一轮只能一个人说话，输出守卫检测到多发言人即拒绝/重生成；
- 方案 C：A+B 组合（生成侧约束 + 解析侧兜底）。
> ⚠️ 方案 B 有二次 LLM 成本；方案 A 是纯解析、零 LLM（符合 ADR-013 第七层「默认 +0 次 LLM」）。

### F-23 🔴 零主语自称漏检，身份冲突静默放行

**证据**（`罗珍思` 名下自称「诗雨」，3 处）：
- `罗珍思：诗雨这边就回宿舍拿点东西…`
- `罗珍思：公寓楼下等你，是吧？诗雨记着了。`
- `罗珍思：诗雨要上去一趟，阿珍在楼下陪着你等就是，不耽误。`

**根因**：`src/m5/group/outputGuard.ts:99`
```ts
const SELF_IDENT_RE = /(?:^|[，。！？；\s])(?:我|俺|本宫)\s*(?:叫|是)\s*([一-龥]{2,8})/g;
```
- 只认**有主语**的 `我是X / 我叫X`；**零主语自称**（「诗雨记着了」）不匹配；
- 窄判据本身是 **P043 有意为之**（宽判据会把「我和徐诗雨聊过」误判成自称徐诗雨）——
  **不能简单放宽**，否则反向误杀；
- 结果 `conflicting = []` ⇒ 走**情况 0「正常」** ⇒ `ok: true, warn: null`，**连告警都没有**。

**修法方向**（待定）：
- 窄口径补充：**句首零主语 + 已知人名**（`^(?:诗雨|阿珍|玉瑶)…`），且要求**该名 ≠ 声明发言人**才算冲突；
- 或：改为**句首名词与 declared 不一致**即告警（不自动重生成，只记 warn + 交二次校验）；
- 🔴 **必须先跑误报率实测**再上——P043 的教训是保护性判据必须比被保护文本更窄。

### F-24 🟠 三套发言格式并存，头时有时无

**证据**：
- 同一段对话里，约一半轮次带 `【徐诗雨】` 头，一半没有；

### F-25 🔴 停顿标记插进 LLM 动作描写内部（F-05 修复的**残留缺口**）

**证据**：
```
（缓了一下，——（好像在斟酌用词）声音温温的）…（语气放缓了些）
——（好像在斟酌用词）（缓了一下，把包带往肩上提了提）
…（停顿了一下）阿珍身上这身还过得去
```
第一行是**标记被嵌进了 LLM 的动作描写括号里面**。

**根因**：`src/m5/expression/ThinkingPauseInjector.ts:36 BOUNDARY_CHARS` **含 `（`**，
所以「插在 `（` 之后」被判为合法边界 ⇒ 落进 `（…）` 内部。
`3cc56fe` 的边界吸附**没挡这个**——它只保证不劈词，不保证不进括号。

**结构性问题**：**同一个 `（…）` 形状承载三种语义**，代码里已经在互相误判：
| 形态 | 谁产生 | 语义 |
|---|---|---|
| `（语气放缓了些）` | **注入器** | 修饰 |
| `（缓了一下，声音温温的）` | **LLM** | 动作描写 = **答案** |
| `（我该接住…）` | **LLM** | 思维链 = **非答案** |

而 `src/m5/DeepSeekLLMProvider.ts:556 isAnswerSentence()` 的规则 ①
`/^(?:语气\|声音\|…\|放缓\|…)/` **正是把注入器的标记判成「思维链元信息 → 非答案」**——
注入器的输出与 CoT 元信息**在判据上不可区分**。

**修法方向**（待定）：
- 短期：`snapToBoundary` 加**括号深度约束**——只在深度 0 插入，`（…）` 内部一律禁止；
- 短期：与已有的 `（…）` 相邻时不叠加（避免 `——（…）（…）` 连打）；
- 中期：给注入器标记**换一个不可混淆的形状**（如 `…` 裸省略号 + 独立分隔），或在
  `isAnswerSentence` 里显式识别注入器标记池（**池是单一真源，不得两边各写一份正则**）。

### ✅ 先记结论：检索侧已验证可用（这是大改的底盘，不用担心）

| 验证项 | 结果 |
|---|---|
| 真机召回 | 业主问「还记得明天客户来吗」→ 玉瑶完整复述接待安排；问「雷灵叶」→ 阿珍答出老家江苏 / 江南水灵 / 上海财经大学；问「带上那个」→ 诗雨想起具体所指。**三条全中** |
| v11 生产接管 | 重启后 `RetrievalV11` 日志 **0 条** + 无回退告警 ⇒ 影子（挂在旧路出口）未跑 ⇒ **新链路已接管**。接管率计数未 flush（`FLUSH_EVERY=50`）属正常 |

⇒ **会话系统的问题不是检索的问题**。大改时检索层可视为稳定底盘。

### 🔴 问题清单（按严重度）

#### F-38-1 会晤隔离被突破（**最严重**）

**现象**（第二轮实测，业主原话「听不懂啊」）：
玉瑶**退出会议后**被重新唤回，却复述了**只对另一位角色说过的私密安排**，
并把它当成自己的事（「今晚回家的事，玉瑶记着呢——那件也收进包里，不会落下」）。

**性质**：**跨角色上下文泄漏**，不只是「答得不好」——
它把 A 角色的私密对话内容当成 B 角色自己的经历说出来，用户感知就是「听不懂」。

**已知线索**：
- `EntityContextManager.ts:90-106` 组装实体上下文时按 `belongEntityUuid` deny-by-default 过滤
  （无归属章的轮次一律排除）。**但会晤态的上下文似乎走了另一条共享路径**，未受该过滤约束。
- `GroupSession` 维护会话级状态（`SessionStore` 单键 `group_session_state`），
  会议纪要与参会者私密对话**可能共用同一份会话上下文**。
- 🔴 **第一轮误判「隔离成立」的教训**：单一样本不能证明隔离，必须构造
  「角色 A 听到过、角色 B 不该知道」的对照用例。

**建议大改时的验收判据**（不是实现方案）：
> 构造用例：用户对角色 A 说一件私密事 → 退出 → 换角色 B 回来 → 问 B「刚才说了什么」
> ⇒ B **必须不知道**。这条应成为会晤隔离的**回归测试**，而非靠人工聊天碰。

#### F-38-2 发言人标签与实际发言者不一致

**现象**（第二轮实测，业主原话「你是玉瑶还是诗雨，怎么搞的」）：

```
回复正文：…（诗雨愣了一下）鸿艺，诗雨这儿只有诗雨——玉瑶不跟诗雨一处。…
正文里的自称：诗雨   ← 内容正确，确实是诗雨在答
显示标签：【玉瑶】   ← 标签错
```

**根因定位**（已追到函数）：

| 位置 | 逻辑 |
|---|---|
| `server-chat-routes.ts:735` | `attributeReply(reply, participants, sticky)` → 用返回值覆盖 `chat_state.speakerName` |
| `outputGuard.ts:403-404` | `extractSpeakerHeader(reply)` 取发言人头；取不到则 `fallback = headerSpeaker \|\| sticky \|\| null`（**sticky = 上一轮发言人**） |
| `outputGuard.ts:415-434` | `splitSpeakerSegments` 按名单切段；多发言人时每段补 `【发言人】`，单发言人时取 `named[0].speaker` |

**为什么误判**：该段正文里**提到了「玉瑶」多次**（"玉瑶不跟诗雨一处"、"你要找玉瑶"），
而 `extractSpeakerHeader` 只认行首 `speaker:` 格式（`outputGuard.ts:71` 要求首个字段是
`SPEAKER_HEADER_KEY`），取不到头 ⇒ 落到 `sticky` / 分段推断，被文本里的人名干扰。

⚠️ **影响面**：`server-chat-routes.ts` 在 `high_risk_files` 名单内，改动成本高；
且 `attributeReply` 是 `WS_GROUP_V2` 新架构的归因入口，**不能简单删掉**。
大改时应考虑：**标签以「实际生成回复的实体 UUID」为准，而不是从文本反推**。

#### F-38-3 裸退出词在玉瑶态零语义（承 F-36 ①）

**现象**：会晤已结束、回到玉瑶态后，用户说「结束」/「散会」→
分别得到「嗯，在呢。你说。」与「在呀，什么事？」—— 没有任何告别语义。

**根因**（第一轮已定位，此处汇总）：
- `process-stages.ts:174` 的退出判定包在 `ctx._entityMeeting?.isActive()` 内
  ⇒ 玉瑶态下**根本不执行**
- 而唯一权威 `EntityMeeting.detectIntent:773` 的正则
  `/^结束\s*(?:了|吧|啦)?\s*(?:会议|对话|会晤|话题|我们|聊天)?\s*…/`
  **其实认**裸「结束」；`process-stages.ts:171` 的副本却要求 `结束.*会议` —— 两者不一致
- 该文件 `:166-170` 注释已记债：**本仓退出判据共 5 处实现、互不一致、违反不变量 #7**
  （`EntityMeeting._exit1:492` / `_exitTail:496` / `:783` / `process-stages.ts:171` /
   `chat.ts:933` / `PrefrontalCortex:287`）

**⇒ 大改时这条的正确解是「退出判据收敛为单一函数」**，不是给玉瑶态补一条特判。

#### F-38-4 退出后叫名字即唤回（承 F-36 ②）

**现象**：玉瑶退出后用户说「玉瑶呢」→ 玉瑶回来并自圆其说「退出不等于走远」。
**判定**：设计内行为（退出 = 回默认本体，叫名字 = 唤醒）。
**但**：当前语义让用户以为「退出没生效」（第二轮业主即如此质疑），
大改时可重新定义。

#### F-38-5 语气填充语过密（承 F-36 ③）

**现象**：几乎每条都有 `…（语气放缓了些）…（停顿了一下）…（缓了一下）…（好像在斟酌用词）…`。
**判定**：prompt 风格问题。大改时与角色设定一并调。

### 🧭 供大改讨论的三个结构性观察（非结论，供业主参考）

1. **状态机散落**：会晤进入 / 退出 / 发言人 / 隔离四件事分别由
   `EntityMeeting.detectIntent`、`GroupSession`、`outputGuard.attributeReply`、
   `EntityContextManager` 承担，**彼此靠约定同步而非单一状态源**。
   F-38-2 的标签错位正是「两个地方各自维护发言人」的必然结果。
2. **判据多处实现**：退出判据 5 处（F-38-3）、发言人归因 2 处（文本反推 + sticky）。
   不变量 #7「同一规则禁止多处实现」已被反复违反。
3. **隔离靠「排除」而非「隔离」**：`EntityContextManager` 是 deny-by-default
  （排除无归属轮次），但**没有机制保证「B 角色读不到 A 的内容」** ——
   只要上下文里有，就会被读到。F-38-1 的根子在这里：
   **缺的是正向隔离边界，不是过滤规则**。

> 以上三条**不是实施方案**，是「为什么这些问题会反复出现」的结构性解释。
> 具体大改方向待与业主商讨后另立文档。
