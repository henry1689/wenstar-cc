## 二、四项取证（逐项实测）

### 1. `DialogGroupAdapter` 原文路 — 🔴 受影响

- **代码位置（实测）**：`src/m4/retrieval/adapters/DialogGroupAdapter.ts:151-156`（通道①）、`:163-167`（通道②）
- **通道①原文**：
  ```sql
  AND id IN (
    SELECT CAST(source_id AS INTEGER) FROM search_index
    WHERE source_type = 'conversation' AND term IN (${phs})
  )
  ```
- **判定方法**：读候选池 SQL + 追踪 `matched_rows / summary_matched` 两个打分输入的下游用法（`:172-176` 排序键、`search()` 内 0.40/0.30/0.15/0.15 权重）
- **退化后果**：
  - S1 之后新产生的对话**不再进入** `search_index` ⇒ 通道①对新对话块 `matched_rows` 恒为 0；
  - 通道②（`source_type='dialog_group'` 摘要命中）**不受影响**，块摘要仍能独立把该组送进候选；
  - 因此一个对话块只有在「块摘要也无字面命中」时才整组召不回——这是 S1.1 退化窗口的真实损失边界。
- **兜底是否存在**：`:181-188` 的 `catch` 只在 SQL **抛错**时降级为 `last_ts DESC` 时间序；本场景 SQL 正常执行、只是返回 0 行，**不会触发该兜底**。

### 2. `meeting-recall` 倒排路 — 🟠 受影响，有兜底

- **代码位置（实测）**：`src/m4/retrieval/meeting-recall.ts:622-655`
- **实测依据**：`:628` 条件 `s.source_type = 'conversation'`，`:641` `JOIN conversations c ON c.id = CAST(s.source_id AS INTEGER)`
- **判定方法**：读两段式结构 ①倒排索引 → ②时间窗采样，确认 ② 的触发条件是「① 无命中」
- **退化后果**：S1 后新对话无法被字面召回，会直接落到 ② 时间窗采样（`windowDays` 内按时间取，与查询词无关）；S1 之前已建索引的历史对话仍走 ①。
- **兜底是否存在**：✅ `:652-654` catch 落 ②，且 ① 零命中时同样落 ②。不阻断对话，但召回质量下降。

### 3. `UnifiedSearchEngine` n-gram 初筛 — 🟠 受影响，仅降级路径

- **代码位置（实测）**：`src/m4/UnifiedSearchEngine.ts:110-134`（`SOURCE_TYPES` 循环与 `:115` 查询）
- **实测依据**：`:105-107` 注释明确「本函数是 V11 单函数（默认 `WS_SEARCH_V13=true` 时仅 V13 失败降级用）」
- **判定方法**：读调用方 `src/webui/chat/retrieval-stage.ts:1300-1314`，确认 `unifiedSearch` 在 V13 不可用时的降级分支被调用
- **退化后果**：降级发生时 conversation 候选为 0；若其他源（memory/black_diamond/knowledge_base）也无命中，`:136-138` 直接返回空结果。
- **下游连带**：`retrieval-stage.ts:1336`「仅真实 conversation 候选可直取长文」——降级路径下该直取能力同时失效（这是下游表现，不是独立消费方）。

## 四、文档同步摘要（最低要求三项）

### ① 白皮书更新摘要 — 《检索架构 v11 · 结构化召回取代 n-gram 索引》

1. **S1 止血已落地**（2026-10-27，commit `5621b13`）：conversation 的 n-gram 索引写入三侧（启动重建 / 每消息实时写入 / 增量回填）全部停用；`idx_si_term` 从 `schema.sql` 断根，运行库存量随停服窗口 `DROP`。
2. **退化窗口取证结论**：四个消费方中 `DialogGroupAdapter` 通道① 与 `meeting-recall` 倒排路受影响（均有替代通道/兜底），`UnifiedSearchEngine` 仅降级路径受影响，`MemoryRetriever` 不受影响。任务书原对 `DialogGroupAdapter` 的「不受影响」预期被实测推翻，见本文档第一节。
3. **缺口台账口径**：`n_gap` = 当日 `conversations` 中**未被 `search_index` 收录**的行数（`NOT EXISTS` 精确统计，不抽样、不估算）；`cum_gap` 逐日累加；`expected_total = s1_start_conversations_total + cum_gap`，与 `conversations_total` 逐日零误差对账。

### ② 蓝皮书更新摘要 — 《检索架构 v11 蓝皮书 v1》

1. **§8.2 每日缺口台账实现**：`GapLedger` 按 10 字段（`date / s1_started_at / n_gap / cum_gap / conversations_total / expected_total / first_gap_id / last_gap_id / verifier / note`）写 `data/retrieval-v11/gap-ledger.jsonl`，一行一天、追加不覆盖；写入前执行三条自检（算术自洽 / 总量零误差 / 日历连续），任一失败写 `note` 并 `console.error`，**不静默跳过**。
2. **§8.2 调度与开关**：服务层 `initPipeline()` 启动期冻结 `s1_started_at` 与基线总行数（`data/retrieval-v11/gap-ledger.meta.json`），并注册 60 秒轮询的每日任务，**仅在 00:05–00:59 窗口**写前一日记录；进程重启不补写历史日期（断档即验收失败）。

## 五、S1 实施与验收实测（2026-10-27 停服窗口）

**停服窗口执行顺序**（任务书 §S1 六步施工顺序的落地记录）

1. 停服：`pm2 stop wenstar-webui` **并** `pm2 stop harness-mcp` —— 后者实测也持有一条 `server.ts` 进程链（双实例，见 `P119` 缺陷反馈），不停它，它会在后续 save() 时用 sql.js 内存库把 DROP 结果整库覆盖回去；
2. 取「变更前」基线：用 python `sqlite3.connect(f"file:{DB}?mode=ro", uri=True)` **只读**打开 `data/webui/fusion_memory.db`，记录索引对象清单、各 `source_type` 行数、三个典型查询的 `EXPLAIN QUERY PLAN`、`page_count`/文件字节数；
3. `schema.sql:282` 删行（commit `5621b13` 已完成）；
4. 运行库 `DROP INDEX IF EXISTS idx_si_term`（**带 `idx_si_source` 保留守卫**：它不在则整体放弃删除；只删索引、不动任何行）；
5. `pm2 start wenstar-webui` 单实例重启（**未**自动拉起 `harness-mcp`）；
6. 验收复跑同一组 `EXPLAIN QUERY PLAN`。

### 验收判据实测结果

| # | 判据 | 实测值 | 结论 |
|---|---|---|---|
| B1 | `search_index.conversation` 不再增长 | 停止时 **2,031,600** → 重启后 **2,031,600**，期间 `conversations` 14,295 → 14,296 | ✅ |
| B2 | 新对话无对应 `source_id` | `id=14582`（S1 生效后产生）索引行 **0**；对照 `id=14579` 有 108 行、`14577` 有 262 行 | ✅ |
| B3 | `idx_si_term` 已不存在 | `False`，且重启后未被 `schema.sql` 重建 | ✅ |
| B4 | `idx_si_source` 仍在 | `True`；`search_index` 上只剩 `sqlite_autoindex_search_index_1` + `idx_si_source` | ✅ |
| B5 | 执行计划不退化 | 四条典型查询全部 `SEARCH … USING COVERING INDEX sqlite_autoindex_search_index_1 (term=? AND source_type=?)`，**零 `SCAN search_index`**，与变更前逐条一致 | ✅ |
| B6 | 启动索引重建段下降 | **无从对比**，见下方说明 | ⚠️ |

**B6 为什么无法按字面验收**：`server.ts:1256` 只在 `isIndexEmpty()` 为真时才跑 `rebuildAllIndexes`，而索引有 302 万行，本次启动日志里根本没有 `[SearchIndex]` 重建段可供对比。

**收益的真实落点是体积与写放大**：

| 指标 | 变更前 | 变更后 | 差值 |
|---|---|---|---|
| 库文件字节 | 553,414,656 | 501,522,432 | **−51,892,224（49.5 MB）** |
| `page_count` | 135,111 | 122,442 | −12,669 页 |

比任务书估的 ~48 MB 多 1.5 MB。且 sql.js 每次 `save()` 都是**整库重写**，所以这 49.5 MB 同时从每一次落盘的写放大里消失（启动日志中异步落盘体积 524.3 MB → 501.5 MB 可直接印证）。

### 副产品发现（S1 之外，但与退化账目相关）

`id=14580` / `14581` 产生于 S1 **之前**，却同样 0 行索引 —— 说明增量写入路径在 rowid 取不到时原本就在静默跳过（`SearchIndexBuilder.ts` 中 V34 注释记载的已知问题）。停写只是把这条不确定行为变成确定行为，**不是** S1 新引入的退化；但记账时应意识到「S1 之前的索引本就不是全量」。
