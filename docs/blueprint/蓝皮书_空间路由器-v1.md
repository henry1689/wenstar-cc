## 2. 内核函数契约（签名即事实，不含实现）

🔴 **所有入口都显式接收 `ts`，内核不读系统时钟。所有返回值不可变（纯函数），调用方不得就地修改。**

```ts
// ── 内核：src/m5/space/SpaceRouter.ts ──────────────────────────
export function isInTenure(seat: Seat, event: SpaceEvent): boolean;
export function canPerceive(seat: Seat, event: SpaceEvent): boolean;
export function isAddressedTo(event: SpaceEvent, uuid: string): boolean;

export function buildViews(
  state: SpaceState,
  events: readonly SpaceEvent[],
): Map<string, ContextView>;          // key = seatUuid

export function route(state: SpaceState, flow: Flow): RouteResult;
//   RouteResult = { nextState: SpaceState; out: RouteOutput }

export function parseCommand(raw: string): Command;
//   Command = enter{name,asAuditor} | leave{name}
//           | keep_only{name} | clear_all | invalid{reason}

// ── 适配：src/m5/space/adapters/chat-adapter.ts ────────────────
syncFromHistory(history: readonly HistoryTurnLike[], startIndex?: number): void;
syncParticipants(participants: readonly ParticipantLike[]): void;
recordUserSay(text: string): void;
recordAgentSay(uuid: string, text: string): void;
exportSnapshot(): SpaceSnapshot;      // 导出时校验任期不变量，违反即抛错

// ── 接入：src/webui/chat.ts ────────────────────────────────────
async function _runMeetingTransition(): Promise<void>;
//   无参数（闭包捕获 ctx）。函数体逐字搬自原内联状态机，仅抽出调用点。
```

### 2.1 契约要点

| 接口 | 要点 |
|:---|:---|
| `canPerceive(seat, event)` | 唯一判定式；`event` 自带 `ts` 与 `audience`，**不额外传** |
| `buildViews(state, events)` | 返回 **Map**（每个有过任期的席位一份），不是数组；覆盖率是「有过任期」而非「当前在场」 |
| `turnsFor(uuid, pendingText?)` | 方法在**适配器**上，第一参数是**席位 UUID**，不是历史数组；`pendingText` 是临时叠加，**不写状态** |
| `route(state, flow)` | 入参 `state` 不被修改；乱序只告警不纠错 |
| `parseCommand(raw)` | 只做文本→意图，**不碰状态**；失败返回 `invalid` 而非抛错 |

## 3. 需求溯源（实现 ↔ 公理）

每一条实现都必须能指回一条白皮书条款，否则即为**私自新增规则**。

| 实现 | 对应白皮书 | 绑定关系 |
|:---|:---|:---|
| 视图过滤 `WS_SPACE_ROUTER_VIEW` | §2.1 任期公理 · §2.2 标签真实性 | 历史可见性**只由「任期 ∧ audience」判定**；旧的按 `belongEntityUuid` 归属过滤 + 硬标当前发言人被废弃，标签改取事件 `actorUuid` |
| 时序提前 `WS_SPACE_PRE_ROUTE` | §3.2 一条关系一个真源 | 发言权（③）必须在**上下文装配之前**确定，否则装配读的是旧发言人 —— 同一请求内两个时点的真源冲突 |
| 门卫放行 `WS_SPACE_GATE_OPEN` | §1 需求锚点 · §3.3 系统里没有例外 | 「叫谁谁来」是业主主诉；硬拦截换人 = 在路由器之外又制造了第三套说话人判定 |
| 会晤起点锚点修复（§6.1） | §2.3 宁可多看，不可全盲 | 时间锚点数据损坏时退化为「可见更多」，绝不退化为「全部不可见」 |
| 三级开关分级 | —（工程决策） | 无公理对应；目的是让每一级可独立 A/B，避免不可归因 |

**复核方法**：任何后续新增的路由规则，若在上表找不到归属，先回到白皮书确认是否新增公理，而不是直接写进代码。

## 4. 三个开关（🔴 2026-10-30 已删除）

> **第一层固化**：三个开关已从代码与 `.env` 中彻底删除。下表是删除前的形态，仅作历史记录。
> 现在 ① 视图接管、② 路由先于装配、③ 换人放行 是**唯一行为**，没有任何配置可退回旧实现。
> 回退只能 `git revert` 代码 —— 这是刻意的：留一个能退回错误实现的开关，等于把已修好的缺陷留在触手可及处。

| 开关（全称） | 级别 | 删除前默认 | 作用 | 旧路径（已删除） |
|:---|:---:|:---:|:---|:---|
| `WS_SPACE_ROUTER_VIEW` | ① | 关 | **视图层接管**：`enrichedHistory` 改由 `turnsFor(uuid)` 按 `canPerceive` 过滤 | `_ecm.getContextWindow`（按 `belongEntityUuid` 归属过滤 + 硬标当前发言人） |
| `WS_SPACE_PRE_ROUTE` | ② | 关 | **路由先于装配**：`_runMeetingTransition()` 在上下文装配**之前**执行 | 原位的第二个调用点（装配之后） |
| `WS_SPACE_GATE_OPEN` | ③ | 关 | **门卫放行换人**：不再拒绝换人请求，直接把目标换上来 | `_meetingDeny` 整轮短路拒绝分支 |

**读取方式**：`isSpaceViewEnabled(env)` 接受 `1` / `true` / `on`（大小写不敏感），空串与未定义一律视为**关闭**。三个开关互相独立，可任意组合。

### 4.1 为什么必须分级

三级是**可 A/B 的增量**，不是一次性替换。实测：

1. 只开 `WS_SPACE_ROUTER_VIEW`：隔离变干净（"手上没有落成字"），但换人仍被拒。
2. 加开 `WS_SPACE_PRE_ROUTE`：上下文终于读到转换**之后**的身份，但门卫仍拦。
3. 加开 `WS_SPACE_GATE_OPEN`：`[SpaceMode] 门卫放行·换人: → 阿珍`，身份三元组一致。

若一次全开，出问题时无法判断是哪一级引入的。

## 5. 调用时序（`src/webui/chat.ts`）

```
用户消息
  │
  ├─〔② WS_SPACE_PRE_ROUTE=1〕_runMeetingTransition()   ← 会晤状态转换
  │      ↓
  ├─ 上下文装配：enrichedHistory
  │      ├─〔①〕turnsFor(_meetingUuid)                  ← 按任期 ∧ audience 过滤
  │      └─〔①关闭〕旧路径（belongEntityUuid 过滤 + 硬标发言人）
  │      ↓
  ├─ runRetrieval()                                     ← 检索依赖上一步上下文
  │      ↓
  ├─ 意图解析 →〔③〕换人 / 〔③关闭〕门卫拦截
  │      ↓
  └─ LLM 生成回复
```

**② 修复的结构性问题**：原实现中，会晤状态转换发生在**意图解析之后**，而上下文装配在**意图解析之前**——上下文在换人之前就装好了。即使换人成功，本轮喂给模型的仍是旧发言人的上下文。②把转换提前，使 `_activeMeetingName` / `_meetingUuid` / `runRetrieval` 全部读到转换后的身份。

**② 的实现方式**：把原内联状态机整体提升为函数 `_runMeetingTransition()`，**函数体逐字不动**，仅抽出调用点。两个调用点由同一个开关**互斥**，保证任一时刻只执行一次。

## 6. 可观测性与已知故障

### 6.1 日志判读

```
[SpaceView] 对象=熊梓铭 历史=42条 席位=5(在场2) 事件=173 诊断=76
[SpaceView] uuid=... ts范围=... 席位明细: 熊梓铭[在] 徐诗雨[离] ...
```

| 字段 | 判读 |
|:---|:---|
| `对象` | 当前会晤实体名（②开启后应为**转换之后**的目标） |
| `历史=N条` | `turnsFor()` 返回轮数；**为 0 即失忆** |
| `席位=N(在场M)` | 总席位 / 当前在场 |
| `诊断=` | 累积诊断条数，配合明细看 `history_ts_missing` / `history_assistant_unowned` |

**三级联查**：`[SpaceMode] 迁移后对象` == `[SpaceView] 对象` == 意图解析目标。不一致即说明某一级未生效。

### 6.2 已知故障

| # | 现象 | 根因 | 修复 |
|:--:|:---|:---|:---|
| 6.2.1 | `[SpaceView] 历史=0条`，但事件数、席位数正常 | `_meetingStartTs` 只取**首行**时间戳；首行缺失 ⇒ null ⇒ 首次入场锚到「现在」⇒ 会晤内历史全落在任期之前 | 扫描**区间内任一**合法时间戳；全部非法时退化为 `0`（= 可见全量） |
| 6.2.2 | 标签与内容分裂（外层写「玉瑶」，内容全是「诗雨」） | 六个说话人来源并存 + outputGuard 在多人场景直接放弃解析 | 标签来源改为事件 `actorUuid`（①） |
| 6.2.3 | 换人被拒 / 勉强放行后更乱 | 门卫拦截 + 上下文先于换人装配 | ② + ③ |

**6.2.1 的判据方向**：宁可多看，不可全盲。全盲是静默失忆，症状只表现为「角色有点怪」，极难定位。

## 7. 故障分级、幂等与脏数据约束

### 7.1 分级与告警清单

| 级别 | 类别 | 表现 | 处置 |
|:---:|:---|:---|:---|
| **F—致命** | 不变量破坏 | `exportSnapshot()` 抛 `任期非法` / `任期乱序重叠` | 立即停链路排查；**不得吞异常** |
| **E—错误** | 路由不可用 | 内核抛错、`turnsFor` 抛错 | 记录并降级到旧路径，告警 |
| **W—业务告警** | 输入不合法 | `command_invalid`、`command_target_not_found` | 正常反馈用户，**不影响状态推进** |
| **W—业务告警** | 语义冲突 | `ts_out_of_order`（乱序，不纠错） | 记录，供诊断 |
| **I—可容忍脏数据** | 历史缺字段 | `history_ts_missing:index=N`、`history_assistant_unowned:index=N`、`history_truncated_rebuild` | 只记诊断，**不阻断** |
| **I—可容忍脏数据** | 未登记 UUID | `agent_say_unknown_uuid:<uuid>` | 丢弃该轮并记诊断（防僵尸席位） |

**原则**：F/E 必须让人看见；W 必须让用户看见；I 只进诊断缓冲，不刷屏。

### 7.2 幂等性（重试边界）

| 操作 | 幂等性 | 边界 |
|:---|:---|:---|
| 视图查询 `buildViews` / `turnsFor` | ✅ 幂等 | 纯只读，不推进状态；`pendingText` 只参与计算，不落状态 |
| 历史摄入 `syncFromHistory` | ✅ 幂等 | 按 `_ingestedIndex` 增量；重复调用只处理新增部分 |
| 席位同步 `syncParticipants` | ✅ 幂等 | 已在场者跳过；只有**首次**同步才锚定会晤起点 |
| 席位指令 `command` | ⚠️ **不幂等** | 重复下发 `enter`：内核先判 `isOnStage`，**不会产生重叠任期**；但会再发一枚令牌并追加一条 `enter` 事件（事件流如实记录"又说了一次"） |
| 重复下发「换人」 | ✅ 不产生多段重叠任期 | 靠 `isOnStage` 短路；**时序上不重复开任期** |

**重试建议**：席位指令失败（`command_target_not_found`）可安全重试一次（等户籍刷新）；成功后再重试只会追加冗余事件，不改变状态正确性。

### 7.3 脏数据约束

- **乱序 ts 只告警，不修正历史时序**——修正等于篡改历史会话快照，会让回放与审计失去意义（白皮书 I5）。
- **归属未知不猜**——`history_assistant_unowned` 的轮次不进事件流，宁可视图偏窄也不写错归属。
- **不创建未知席位**——`command_target_not_found` 时不新增席位，内核不查 FG。

## 8. 回滚兜底边界

| 保证 | 说明 |
|:---|:---|
| **关闭开关即回到旧逻辑** | 三个 `WS_SPACE_*` 关闭后走旧代码路径，**无需回退代码** |

## 10. 部署拓扑（服务层）

```
             ┌──────────────────────────────┐
 浏览器 ───▶ │ wenstar-webui (pm2 id 6)      │  HTTP :3000
             │  Node/TS · 单进程 · 单实例     │  SSE 流式
             └───────────┬──────────────────┘
                         │ 子进程 / HTTP
             ┌───────────▼──────────────────┐
             │ 天权 RPC (Python)             │  GLOBAL_BUS 127.0.0.1:9100
             │  TIANQUAN_LITE=true           │  跳过 ONNX/HF 重型模型
             └──────────────────────────────┘
                         数据目录
                 D:\tools\wenstar-cc\data\webui\
                   fusion_memory.db（sql.js 整库载入内存）
```

- **数据库形态**：sql.js（WASM），整库载入内存；落盘为**原子替换**——先写 `fusion_memory.db.tmp-<pid>`，再 `rename`。
- **落盘频率**：`TIANQUAN_FLUSH_INTERVAL_MS=120000`。`db.export()` 是同步 CPU 排序（WASM 无法异步），每次阻塞事件循环约 2.5s，故不能过密。
- **并发边界**：v1 **仅支持单进程单实例**。多进程同时读写同一 sql.js 库会触发文件锁冲突与互相覆盖，**不做水平扩展**。多实例方案列入 v2。
- **安全边界**：内核**不做身份鉴权**，只负责状态计算。谁能踢人、谁能否决席位变更，由上层接入层控制（见交互规约 §3）。

### 11.1 `cleanupStaleDbTemps()` — 残留临时库清扫

**背景**：sql.js 落盘是「写 `.tmp-<pid>` → rename」。进程在落盘**途中**被杀（pm2 restart / 崩溃）时 rename 不执行，一个**完整整库副本**留在磁盘上。实测残留一个 = **541 MB**，而每次重启都可能撞上 500MB 全量落盘。

**覆盖范围（全仓 3 处写点，DS-23 横向扫描结果）**：

| 写点 | 产生的临时文件 |
|:---|:---|
| `src/m2/SQLiteAdapter.ts` | `data/webui/fusion_memory.db.tmp-<pid>` |
| `src/m4/household/FamilyGraph.ts` | `data/webui/knowledge/family_graph.db.tmp-<pid>` |
| `src/app/memory-vault/MemoryVault.ts` | `data/memory-vault/vault.db.tmp-<pid>` |

> 只清主库等于把同一缺陷留在另外两个库里。清扫走 `STALE_DB_TEMP_TARGETS`（目录 + 库名）目标表；
> **新增写 `${dbPath}.tmp-<pid>` 的库时必须同步登记**，否则该库不被覆盖。
>
> **实测（2026-10-30）**：清扫铺开到 3 个库后，重启首跑回收 `family_graph.db.tmp-*` **105 个 / 4071 MB**
> （日志 `[DbTempClean] 共回收 105 个文件 / 4071MB`）。这条数据同时证明：横向扫描不是理论问题。

**五条安全边界**（宁可不删，不可误删）：

1. 只匹配「已知库名 + `.tmp-<数字>`」，其它文件一律不碰；
2. 跳过**当前进程**自己的临时文件（`pid === process.pid`）；
3. `process.kill(pid, 0)` 成功的（**进程还活着**）一律跳过；
4. 修改时间**不足 `STALE_DB_TEMP_MIN_AGE_MS`（10 分钟）**的跳过（可能正在写，或刚被杀而 rename 尚未完成）；
5. 全程 `try/catch`，**清扫失败不得影响启动**。

**日志**：命中时打印 `[DbTempClean] 清理残留临时库 <file> (<N>MB)`，收尾打印合计回收量。

## 13. 运维手册

### 13.1 启用 / 回滚（改完必须重启 `wenstar-webui`）

> 🔴 **2026-10-30 起，配置层已无回退手段。** 三个开关删除后，唯一回退方式是把对应提交


### 13.2 验证清单（每次开启后）

| 检查 | 期望 |
|:---|:---|
| `[SpaceView] 历史=N≥1条` | 不得为 0 |

### 13.3 排查顺序

1. 看 `[SpaceView]` 两行 —— 历史为 0 先查锚点（§6.2.1）；

3. 看 `诊断=` 明细 —— `history_assistant_unowned` 多说明历史缺归属，视图会偏窄；
4. 仍不对，逐级降开关定位到具体级别。

## 13.5 本轮新增行为（2026-10-31）

### 13.5.1 独处态 —— 没人应就不回

| 项 | 内容 |
|:---|:---|
| **判据** | 空间**已经有过任期**（`seats.some(s => s.periods.length > 0)`）**且**当前零人在场 |
| **行为** | 不调 LLM、`reply` 置空、**不产生助手轮**；业主那句话照常写库（记在本体 UUID） |
| **实现** | `chat.ts` 生成块前内联判定 → `persistence-stage.ts` 写完用户轮后提前返回（`soloMode`） |
| **为什么保守** | 只在「有过席位」的空间生效。从未建立席位时维持玉瑶态 —— 否则第一句聊天就会被判成独处，系统看起来像死了 |
| **日志** | `[SoloMode] 无人在场 —— 不生成回复，业主发言照常落库` |

### 13.5.2 耳语 —— 看得见、听不到

| 项 | 内容 |
|:---|:---|
| **识别** | 句中出现 `耳语 / 悄悄 / 私下 / 悄悄话`，且点到一个**当前在场席位**的名字 |
| **内核** | `Flow.user_say.whisperTo` → `audience = {kind:'seat'}` + `publicMeta = {type:'whisper', from, to}` |
| **记录** | `belong_entity_uuid` = **听众本人**（与一对一私聊完全相同）；库里**没有**任何耳语标记 |
| **不共享** | 听众读到正文；其余在场者由 `turnsFor` 生成占位轮「（鸿艺压低声音，跟人耳语了几句——你没听清）」 |
| **占位文本** | **渲染期生成，不写入存储** |
| **日志** | `[Whisper] 本条仅对目标可闻: <uuid>` |
| ⚠️ **已知限制** | 运行时的隔离标记只存在内存，重启后重新摄取会退化为全场可闻（业主裁决：不为此新增状态） |

### 13.5.3 说话人标签 —— 单一真源

| 项 | 内容 |
|:---|:---|
| **缺陷** | 标签取「请求结束时的 speaker」（`buildChatState`），正文由「生成时刻的身份」写出。本轮只要换过人，两者必然错位 |
| **真机症状** | 外层标签「罗珍思」、正文自称「诗雨」；甚至同一条里前后两个名字 |
| **修复** | `ChatResponse.speakerName` = **生成该回复时的身份**；路由层优先用它作标签 |
| **判据** | **标签 = 生成该回复时的身份**，不是请求结束时的状态 |

### 13.5.4 在场感知 —— 把「谁在场」告诉模型

| 项 | 内容 |
|:---|:---|
| **缺陷** | 上下文里从来没有在场名单，模型只能从历史猜。猜错就有两种相反症状：「她这会儿不在这头」「我没听到」 |
| **修复** | `process-stages.ts` 在实体上下文中追加 `【当前在场】` 名单 |
| **注意** | 这不是可见性过滤算错 —— 是**模型没被告知**，过滤无误也照样说错 |

### 13.5.5 停顿标记 —— 降频与去重

| 项 | 内容 |
