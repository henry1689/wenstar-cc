## 一、批次总览

本批次是**四条独立缺陷线**在同一次深挖中被查实并根治。它们表面症状都表现为「聊天有点乱」，但根因分属四个不同层：

| # | 缺陷线 | 层 | 根因一句话 |
|:--:|:---|:---|:---|
| A | 空间路由器只做了「可见性」 | 架构 | 业主主诉是**分配器**（谁接话），实现只做了**过滤器**（谁知道什么） |
| B | LLM 工具型调用静默失败 | LLM 通道 | 思维链剥离器把纯 JSON 输出削成 `[{`；且 `raw` 与 `reply` 共用熔断器 |
| C | 记忆写入三处独立缺陷 | 存储 | 跨 zone 去重误伤 / 验证与写入不同源 / `seq_pos` 三消费者争两个号 |
| D | 服务层两个隐性故障 | 运维 | 残留 541MB 临时库无人清扫；摘要外层超时 20s **短于**内层 45s |

**业主指令**（2026-10-30）：
> 「感觉干净很多，看来改善方向是对的，继续深挖，把各种问题都解决掉，一些细节问题，小问题都根除掉，确保聊天稳定丝滑」

## 二、S1 审计：查实与根因

### 2.1 A 线 — 空间路由器：设计只覆盖三分之一

**真机证据**（2026-10-29）：

```
鸿艺：今晚回去是记得把电话带上        ← ①在场，阿珍能听见
罗珍思：记住了，电话阿珍带着           ← 答对了
……若干轮后……
鸿艺：阿珍，我刚刚说叫你别忘了带什么
罗珍思：这个阿珍还真不知道……那会儿阿珍在旁边收拾东西，没听真切
```

**根因**：内核只有 ① `audience`（谁听得见），没有 ② `address`（冲着谁）和 ③ `focus`（谁答）。阿珍在场，但她无法判断那句话是否**点名对她**——于是模型把"这话不是对我说的"误推广成"这些话我都没听见"。

**第二层根因（结构性）**：上下文在换人之前就装好了。

```
[顺序错误] 装配上下文 → 检索 → 解析意图（才知道点名了谁）→ 换人 → 生成
[正确顺序] 路由 → 装配上下文 → 检索 → 生成
```

### 2.2 B 线 — LLM 通道

| 缺陷 | 事实 |
|:---|:---|
| 剥离器误伤 | 思维链剥离器把**纯 JSON** 输出削成 `[{`（1010 → 3 字符），工具型调用静默失败 |
| 熔断器混用 | 聊天与压缩/工具调用共用同一个 `RetrieverCircuitBreaker`（阈值 3 / 冷却 30s）。压缩任务的超时堆积会把**聊天**的熔断打跳，表现为"聊着聊着不回话" |
| 预算错配 | 推理模型的 `max_tokens` 是**含推理**的总预算；`raw` 通道沿用回复的小预算 ⇒ 推理吃光预算，正文为空 |

### 2.3 C 线 — 记忆写入三处独立缺陷

| # | 缺陷 | 后果 |
|:--:|:---|:---|
| C1 | `_isDuplicateNewWrite` **未按 `leaf_zone` 限定** | 业主说「嗯」、角色也回「嗯」⇒ 角色那句被判为重复而丢弃 |
| C2 | 校验用的文本与写入用的文本**不同源** | 校验说"写成功了"，实际写的是另一份文本 ⇒ 误报 |
| C3 | `seq_pos` **三个消费者争两个号** | 一轮要写 user + assistant + 锚点 = 3 行，而分配器只预留 2 个号 ⇒ 撞号 ⇒ 记忆写入失败 |

> **C3 是业主明确要求"改彻底"的一项**：不给 `writeMemory` 打单点补丁，而是修正**编号语义**——分配时预留 3 个连续可用号，并在写入前对冲突做 `MAX+1` 规避。

### 2.4 D 线 — 服务层

| 缺陷 | 事实 |
|:---|:---|
| 残留临时库 | sql.js 落盘为「写 `.tmp-<pid>` → rename」；进程在落盘途中被杀则 rename 不执行。实测残留 **1 个 = 541 MB**，而每次重启都可能撞上 500MB 全量落盘。**全仓横向扫描（DS-23）：共 3 处独立写点** —— `SQLiteAdapter`（fusion_memory.db）、`FamilyGraph`（family_graph.db）、`MemoryVault`（vault.db），只清主库等于把同一缺陷留在另外两个库 |
| 摘要超时倒挂 | `COMPACTION_SUMMARY_TIMEOUT_MS = 20s`，而 `DeepSeekLLMProvider` 内层超时 **45s**。外层恒先到 ⇒ 只是提前杀死本可成功的调用。本轮 **47 次摘要失败中 46 次是 `compaction summary timeout`**，摘要长期退化成「取前 160 字」 |

## 三、方案与审批（提案审计留痕）

### 3.1 原始局部方案全文

> **方案 P（局部修补，逐条打补丁）**
>
> 1. **A 线**：在 `chat.ts` 装配处加一层 `canPerceive` 过滤，按 `belongEntityUuid` 判断可见性；说话人标签维持现状。
> 2. **B 线**：在剥离器里再加一批正则，过滤掉被误判的 JSON 片段。
> 3. **C 线**：只修最显眼的 C3——在 `writeMemory` 内部，若检测到 `seq_pos` 冲突就重试一次。
> 4. **D 线**：不改代码，运维上手动清理临时文件；摘要超时维持 20s（认为"快失败总比慢失败好"）。

### 3.2 全局优化方案全文

> **方案 G（结构性根治，本批次实际执行）**
>
> **A 线 — 按三关系模型重建，三级独立开关**
>
> 1. 内核补全 ② `address` 与 ③ `focusUuid`，明确**一条关系只有一个真源**；标签改取事件真实 `actorUuid`。
> 2. **第①级** `WS_SPACE_ROUTER_VIEW`：视图层接管，历史可见性严格由「任期 ∧ audience」判定，废弃 `belongEntityUuid` 归属过滤。
> 3. **第②级** `WS_SPACE_PRE_ROUTE`：把会晤状态转换提升为 `_runMeetingTransition()`，**在上下文装配之前**执行（函数体逐字不动，只抽调用点 + 两调用点开关互斥）。
> 4. **第③级** `WS_SPACE_GATE_OPEN`：门卫不再拦截换人，直接把目标换上来。
> 5. 顺带根治**会晤起点锚点**缺陷：扫描区间内任一合法时间戳，全非法时退化为 `0`（宁可多看，不可全盲）。
>
> **B 线 — 通道分流**
>
> 6. 引入 `LlmChannel = 'reply' | 'raw'`；`raw` 通道直接取 `content`（`resolveRawPayload`），**不走**思维链剥离。
> 7. 熔断器**分桶**：`_toolBreaker`（阈值 3 / 冷却 60s / 超时 180s）与 `_llmBreaker` 分离。
> 8. `raw` 通道的 `max_tokens` 下限抬到 2000，`reasoning_effort='low'`。
>
> **C 线 — 三处一起修**
>
> 9. C1：去重查询按 `leaf_zone` 限定（分区局部唯一）。
> 10. C2：校验与写入**用同一份 `cleanReply`**（提升到函数体层级，消除作用域分裂）。
> 11. C3：**修正编号语义**——分配器预留 3 个连续可用号；`writeMemory` 前再查冲突并 `MAX+1` 规避。
>
> **D 线 — 服务层**
>
> 12. 新增 `cleanupStaleDbTemps()`：启动时清扫 `.tmp-<pid>`，五条安全边界（只匹配固定模式 / 跳过自身 pid / 存活进程跳过 / 10 分钟内跳过 / 全程 try-catch）。
> 13. 摘要外层超时对齐为 50s，**严格大于**内层 45s；并在注释中写明「二者是同一件事的两端」。

### 3.3 业主审批选择及理由

| 时间 | 业主原话 | 选择 |
|:---|:---|:---|
| 2026-10-30 | 「要」（批准 Phase C S2 方案） | 批准第②级方案：状态转换提升为函数 + 两个开关互斥调用点 |
| 2026-10-30 | 「要开3」 | 批准第③级上线验证 |
| 2026-10-30 | 「**改，还要改彻底**」 | **否决方案 P 的 C3 局部补丁，采纳方案 G 的编号语义重构** |
| 2026-10-30 | 「你按照这个顺序处理吧」 | 批准 D 线处理顺序：FG TypeError → TTS → LLM 摘要 |
| 2026-10-30 | 「能听到声音，要一并办理」 | TTS 实测通过；一并清理音频残留 |

### 3.4 两方案差异对比矩阵

| 维度 | 方案 P（局部） | 方案 G（全局） | 差异性质 |
|:---|:---|:---|:---|

## 八、方法论教训（写给后来者）

1. **业主的话要拆成两类读**——"可见性"和"分配器"。只做前者，"干净"会骗过自己。
2. **正则追漂移终将失败**——剥离器误伤、说话人来源分裂，最终都是靠**结构判据**（字段边界、唯一真源）解决，不是靠加词表。
3. **先写测试复现，再改代码**——`历史=0条` 缺陷先跑出 3 红 1 绿，才确认测试能抓到问题。
4. **外层超时必须严格大于内层**——否则外层只是提前杀死本可成功的调用。
5. **未验证的项要标注"未验证"**——本台账 §5.4 第二项即如此。
