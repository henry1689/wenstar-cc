## S1 · 止血

> **目标**：立即停止 conversation 写 `search_index`（该路径写入的是**已被判废的 n-gram 索引**），并删除纯冗余索引 `idx_si_term` 消除每次启动 ~48 MB 重建开销。
> **裁决依据**：§S4.2（业主 2026-10-27 裁决：`idx_si_term` 打包进 S1 停服窗口）

### A. 改哪些文件

| # | 文件:行 | 动作 | 说明 |
|---|---|---|---|
| A1 | `src/m4/SearchIndexBuilder.ts:117` | **停写** | `rebuildAllIndexes` 内的 conversation 写入分支，改为 `continue` 跳过 |
| A2 | `src/m4/SearchIndexBuilder.ts:256` | **停写** | `backfillConversationIndex` 内的 conversation 写入，整体函数退化为空操作（保留签名，返回 0） |
| A3 | `src/m2/schema.sql:282` | **删除该行** | `CREATE INDEX IF NOT EXISTS idx_si_term ON search_index(term);` |
| A4 | 运行库 | **DROP** | `DROP INDEX IF EXISTS idx_si_term;`（幂等，随停服窗口执行） |

**六步施工顺序**（严格按序，见 §S4.2）：

1. **停服**（停 webui + 所有 DB 写入进程；确认无 sql.js 内存库覆盖风险）
2. **取证前**：`EXPLAIN QUERY PLAN` 记录三个典型查询的执行计划基线
3. 改 `schema.sql:282` 删行（A3）
4. 运行库执行 `DROP INDEX IF EXISTS idx_si_term;`（A4）
5. **启动复跑**：同一组 `EXPLAIN QUERY PLAN`，确认走 `idx_si_source` 或 PK，**未出现全表扫描退化**
6. **记录体积**：`SELECT page_count*page_size FROM pragma_page_count(), pragma_page_size();` 前后对比，记入变更台账

> A1 / A2 可在同一窗口完成，也可分开（改 A1 不影响 A2 的正确性）。**A3 / A4 必须同一停服窗口内完成**（只删不 DROP 会导致下次启动重建，等于没删）。

### B. 验收判据

| # | 判据 | 核验方式 |
|---|---|---|
| B1 | 启动后 `search_index` 中 `source_type='conversation'` 的行数**不再增长** | 启动前后各查一次 `COUNT(*) WHERE source_type='conversation'`，差值为 0 |
| B2 | 新产生一条对话后，`search_index` 无对应 `source_id` | 造一条测试对话 → 查 `search_index` → 命中 0 行 → 删测试数据 |
| B3 | `idx_si_term` 已不存在 | `SELECT name FROM sqlite_master WHERE type='index' AND name='idx_si_term';` 返回空 |
| B4 | `idx_si_source` **仍然存在** | 同上查 `idx_si_source`，必须返回 1 行 |
| B5 | 三个典型查询执行计划**不退化为全表扫描** | `EXPLAIN QUERY PLAN` 输出中不得出现 `SCAN search_index` |
| B6 | 启动耗时中索引重建段**下降**（≥ 40 MB 量级的重建消失） | 启动日志时间戳对比变更前 |

> **B4 是不可删项**：`idx_si_source(source_type, source_id)` 不是主键最左前缀，删了会让其他 `source_type` 的删除/查询失去索引（蓝皮书 1.3 / §S4.2）。

### C. 回滚方式

| 场景 | 回滚动作 | 影响面 |
|---|---|---|
| A1/A2 需回滚 | `git revert` 对应 commit（单文件） | conversation 恢复写入 n-gram，无副作用 |
| A3/A4 需回滚 | 在 `schema.sql:282` 原位置加回该行；运行库执行 `CREATE INDEX IF NOT EXISTS idx_si_term ON search_index(term);` | 恢复 ~48 MB 重建开销；**索引可重建，不丢数据** |

> 索引删除**不丢任何数据**（索引是派生结构），回滚成本极低——这是本阶段敢放进停服窗口的底气。

### D. 红线

1. ❌ **只能停 conversation 一路写入**。memories / works / knowledge 等 `source_type` 的写入路径**一律不动**——它们仍有存量消费者，由 S4 统一处置。
2. ❌ **不得删除 `idx_si_source`（:283）**。它与 `idx_si_term` 的冗余性论证完全不同。
3. ❌ **不得改 `indexDocument()`（:67）的函数体**。它是多 `source_type` 共用的写入口，停写必须在调用方（A1/A2）做。
4. ❌ **不得在本阶段顺便"优化"任何与检索无关的代码**。一个 commit 只做一件事。
5. ❌ **停服窗口未确认前不得执行 A4**。sql.js 内存库会覆盖离线改库（历史事故：归属脏值三层传播）。

> 🔴 **v1.1 决定 · 分片上限 40 → 12**（业主 2026-10-27 裁决「降到 12，先保预算」）
>
> 原值 40 来自白皮书 §4.2.2「去重后取前 40 个」。真实生产库只读探针实测：
> 40 分片下 `domain='conversation'` 围栏耗时 **84–185ms**，超出蓝皮书 §3.4
> 单域 ≤100ms 预算。按蓝皮书 §3.4 的超预算处置顺序（① 降 LIMIT →
> ② 减分片数 → ③ 收时间窗），取第 ② 项。
>
> | 分片上限 | 围栏 P50 | 围栏 P95 / max | 逐条命中率（退化窗口 12 条真库样本） |
> |---|---|---|---|
> | 40 | ≈160 ms | 185 ms | 12/12 = **100%** |
> | **12** | **63 ms** | **93 ms** | 12/12 = **100%** |
>
> 结论：耗时降到预算内，**召回面零损失**。依据白皮书 §4.2.3「围栏只求全、不求准」，
> 分片减少的精度损失由精排层补回。
> ⚠️ 白皮书 §4.2.2 的「40」须后续同步修订（白皮书优先级高于蓝皮书，见蓝皮书 §0）。

**影子调用硬约束**：

```ts
// 伪代码：影子调用必须整体被 try/catch 包住，且绝不影响返回值
if (Flags.shadowEnabled()) {
  try {
    const shadow = await recallByStructured(/* 同参 */);
    ShadowLog.write({ queryDigest, oldIds, newIds, latencyMs: /*...*/ });
  } catch (e) {
    // 影子失败只记录，不抛出、不影响生产结果
    ShadowLog.error(e);
  }
}
```
