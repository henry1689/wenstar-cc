### 2.3 膨胀机制

`SearchIndexBuilder.ts:30 buildNgrams()`：

```ts
// 2-gram
for (let i = 0; i < cleaned.length - 1; i++) ngrams.add(cleaned.substring(i, i + 2));
// 3-gram
for (let i = 0; i < cleaned.length - 2; i++) ngrams.add(cleaned.substring(i, i + 3));
```

长度 N 的文本 ⇒ 约 **2N 个索引项**（去重后实测 142 项/条）。文字 3 MB ⇒ 索引 436 MB（**177 倍**）。

写入侧 `SearchIndexBuilder.ts:80` 为**每 gram 一条独立 `INSERT OR REPLACE`**（无事务批量）。

### 2.4 落盘的因果链（关键纠正）

`SQLiteAdapter.ts:288` 自述：

> 防抖合并落盘：**`export()` 会序列化整个内存库**（当前 ~96MB），不能每次写入都落盘。

**对照实验**（原生 SQLite `VACUUM INTO`，读全库+重写全库，与 `export()` 成本同构）：

| 库 | 体积 | 耗时 |
|---|---|---|
| 全库（含索引） | 523.9 MB | **3.72 s** |
| 剔除 `search_index` | **88.0 MB** | **1.32 s** |
| 差值 | **−83.2%** | **−64.6%** |

> 🔴 **纠正既有归因**：落盘耗时 ∝ **库体积**，与索引**写入次数**无关。
> 因此「加大写入批量」**不能**解决落盘阻塞；**只有减小库体积才有效**。

### 2.5 召回质量现状

同一查询下，两条路径的召回文档数（`source_type='memory'`）：

| 查询 | n-gram 索引召回 | 分片 LIKE 召回 | n-gram 耗时 | LIKE 耗时 |
|---|---|---|---|---|
| 模具交期 | **3** | **54** | 93 ms | 59 ms |
| 项目进度 | **5** | **56** | 68 ms | 49 ms |
| 心情不好 | **86** | **523** | 75 ms | 55 ms |
| 上次聊天 | **17** | **137** | 78 ms | 51 ms |

> **结论：n-gram 索引的召回能力实际很弱**（"模具交期"仅召回 3 条），
> 却付出 436 MB 空间与 2.4 s/次的落盘代价。

#### 2.5.1 🔴 归因补正（PI 复核提出，实测确认）

**上面「n-gram 召回弱」的表述必须加限定，否则会导致后续调优方向错误。**

实测索引覆盖率：

| 表 | 索引覆盖 | 主表行数 | **未进索引比例** |
|---|---|---|---|
| `memories` | **1,615（11.8%）** | 13,640 | **88.2%** |
| `black_diamond` | **99（2.7%）** | 3,712 | **97.3%** |
| `knowledge_base` | **19（6.7%）** | 282 | **93.3%** |

**正确归因**：
- n-gram 召回弱的**主因是「覆盖缺口」**——绝大多数记忆**从未被写进索引**，倒排自然召不回；
- 而 `LIKE` 全表扫描天然覆盖 **100%**；
- 因此新方案「召回量提升 10–20 倍」的功劳 **属于覆盖面，不属于围栏机制本身**。

> 🔴 **对后续维护的强制提示**：将来若出现召回质量下降，**不得**直接归咎于「围栏设计」而调整权重；
> 必须先查**数据是否在候选池内**（候选覆盖），再查精排。归错方向会越调越差。

**对 S4 的佐证**：既然 88% 的记忆本就没进索引，那么保留这个索引的收益极低 ——
**它在 436 MB 成本下，实际只服务了 12% 的数据**。这是 S4 删除的最有力理由。

## 第三章 · 架构决策

### 3.1 决策总纲

> **以「结构化围栏 + 多信号精排」取代「n-gram 倒排索引」。**
> 围栏负责**缩小候选集**（UUID / 时间 / 钙化度 / 关键词分片）；
> 精排负责**判定相关性**（命中分片数 / 钙化度 / 40D 语义）；
> 全程**不建立任何倒排索引**，检索在候选集上**现算**。

### 3.2 与 V11.0 原设计的对应关系

| V11.0 原设计 | v11 新设计 | 关系 |
|---|---|---|
| n-gram 初筛（围栏） | **结构化围栏**（UUID + 时间 + 钙化度 + 分片 LIKE） | **替代**（更省、召回更全） |
| 32D 语义向量精排 | **40D 语义精排**（40D 是 32D 的法令升级版） | **落地**（原设计从未实现） |
| n-gram 不参与排序 | **分片命中数参与精排**（现算，非预建索引） | **回归原意** |

### 3.3 🔴 关键澄清：n-gram「算法」与「索引」必须分开处置

> **本节是全文最容易被误读的地方，后续维护者必读。**

| 层面 | 定义 | 去留 | 依据 |
|---|---|---|---|
| **n-gram 切分算法** | 把查询串切成 2-gram / 3-gram 片段的**函数**（`buildNgrams`） | ✅ **保留，且为强制** | 召回的**质量来源**。实测：完整词 `LIKE '%模具交期%'` 召回 **0** 条；切成片段后 `LIKE '%模具%' OR '%具交%' OR '%交期%'` 召回 **54** 条 |
| **n-gram 倒排索引** | `search_index` 表（gram→doc 的预建映射，436 MB） | ❌ **废除** | 它是 83% 体积与 +2.4 s 落盘的来源；而同等匹配**现算 < 10 ms** |

#### 3.3.1 为什么不能连切分算法一起去掉

若改为「LLM 提取完整关键词 → `LIKE '%完整词%'`」：
- LLM 提的是**完整词**（"模具"、"交期"）；
- 而记忆原文中该词**未必连续出现** ⇒ 完整词 LIKE 实测召回 **0 条**；
- **n-gram 片段的宽松匹配才是召回率来源。**

⇒ **切分算法承担的是「召回覆盖面」，索引承担的是「预计算加速」。前者不可去，后者不必要。**

#### 3.3.2 本文档中「拆掉 n-gram」的确切含义

本文件全文出现的「拆掉 / 废除 / 取代 n-gram」，**一律仅指废除倒排索引（`search_index` 表及其写入链路）**，
**绝非**指删除 `buildNgrams` 切分算法。该算法在 v11 中**保留并承担更重要的角色**
（从"建索引用"变为"生成 LIKE 分片 + 精排命中数计算用"）。

#### 3.3.3 等价性说明

| 环节 | V11.0（旧） | v11（新） | 结果 |
|---|---|---|---|
| 切分 | `buildNgrams(query)` | `buildNgrams(query)` | **完全相同** |
| 匹配 | 查预建倒排表 | `LIKE` 扫描正文 | 新路径**召回更全**（54 vs 3） |
| 命中数 | `COUNT(DISTINCT term)` | 候选集内现算 | **语义相同**（现算 <10 ms） |
| 排序 | 由索引查询承担（违反原设计） | 由精排层承担（回归原设计） | 合规 |

#### 3.3.4 🔴 零持久化论证：切分结果**不落盘**，不会重演膨胀

> 这是本方案「不会像之前一样产生庞大数据」的正式论证，后续任何"优化"必须对照本节。

**① 切分对象与规模的根本差异**

| | V11.0（旧） | v11（新） |
|---|---|---|
| 切分对象 | **每一条记忆的正文**（13,640 条 × 平均 222 字） | **用户当前这一句查询**（典型 25 字） |
| 单次切分产出 | 约 142 个片段/条（去重后） | 约 45 个片段/次（截断后用 40 个） |
| 切分结果去向 | **逐条 `INSERT INTO search_index`** | **仅存在于内存，函数返回后即释放** |
| **持久化行数** | **283,048 行**（`memory` 类，另有 conversation 203 万行） | **0 行** |

**② 膨胀的因果归属（必须写清）**

> 膨胀**不是** `buildNgrams` 造成的 —— 它是**纯函数**，返回数组即结束，不碰数据库。
> 膨胀来自 `indexDocument()`（`SearchIndexBuilder.ts:80`）：它**把片段逐条写入表**。
> **v11 删除的是这条写入链路，不是切分函数**（见 §3.3.2 / RA-8）。

**③ 三条防复发约束**

| 约束 | 内容 |
|---|---|
| **RA-1** | 禁止建立全量倒排索引 |
| **第五章禁止事项** | 新增任何 `INSERT INTO search_index` 写入 ⇒ 违规 |
| **本节** | 🔴 **「内存索引 / 进程内缓存 / 预计算表」同样视为违规** —— 任何"为了加速而把 gram→doc 映射预先算好保存"的做法，无论存在磁盘表、内存 Map、还是独立文件，**一律等同于重建倒排索引**，必须走白皮书修订流程并重新论证体积代价。 |

**④ 唯一会增长的持久化项（如实登记）**

| 项 | 增长量 | 说明 |
|---|---|---|
| **检索日志**（§8.1 埋点） | 每次检索 **1 行文本**（约 150 字节） | **必须保留** —— 它是事后归因「为什么这条没召回」的唯一线索；走既有日志轮转机制，不入库。 |

**⑤ 体积趋势承诺**

v11 生效后，库体积**只降不升**：535 MB → 约 88 MB（见 §2.4 实测）。
**任何使库体积回升的改动，视为架构回退，须重新评审。**

### 3.4 架构铁律（不可违反）

| 编号 | 铁律 |
|---|---|
| **RA-1** | **禁止建立全量倒排索引**。检索必须在候选集上现算，不得预建 gram→doc 的倒排表。 |
| **RA-2** | **围栏与精排职责分离**。围栏只缩小候选集，不得承担排序；排序只由精排层决定。 |
| **RA-3** | **UUID 血缘优先**。任何召回必须先过归属闸门（`UUIDPoliceFilter`），不得跨实体召回。 |
| **RA-4** | **能合并则合并**。多个查询条件必须合并为**单次 SQL**，禁止逐条件循环查询（实测：5 词合并 74ms vs 逐个 260ms）。 |
| **RA-5** | **零成本信号优先**。精排优先使用已存在的现成字段（钙化度、40D、时间），LLM 精排为**最后手段**且必须有开关。 |
| **RA-6** | **不删有用信息**。任何优化不得删除记忆、对话、知识库内容。索引可重建，记忆不可。 |
| **RA-7** | **落盘时延 ∝ 库体积**。性能优化必须作用在体积上；增大写入批量不解决落盘阻塞。 |
| **RA-8** | 🔴 **n-gram 切分算法（`buildNgrams`）不得删除**。被废除的只是倒排索引；切分算法是召回覆盖面的来源（见 §3.3）。任何删除该算法、或以其"已被取代"为由移除的改动，**一律驳回**。 |

### 4.1 总体流程（五段）

```

   │
   ├─[0] 查询向量获取（零成本）
   │     M3 已产出 decision.enhanced.perceptionV40（chat.ts:891）

   ├─[1] 围栏层（目标：候选 ≤ 500 条）

   │     ③ 关键词分片 LIKE（合并单次 SQL，RA-4）
   │
   ├─[2] 精排层（目标：候选 → top-K，K 默认 12）
   │     信号① 分片命中数（现算，替代 n-gram COUNT(term)）
   │     信号② 钙化度（现成字段）

   │     触发条件：K 条候选的分数方差低于阈值（即"难分伯仲"）
   │     或候选数 > 阈值且需语义判断
   │
   ├─[4] 🔴 五级闸门 G2→G5（强制，不可跳过）
   │     v11 五段流程定位为 **G1（候选生成 + 初筛）的实现规范**。
   │     五段出口 = **G1 完成点**，其后必须继续挂载：
   │       G2 时空一致性 → G3 仿生遗忘 → G4 意图区分 → G5 话题壁垒
   │     挂载方式：以 **P071 §5.3 既定方案**为准
   │     （`getFiveStageGate()` 提升为 `retrieveMultiRank` 共享出口）。
   │
   └─[5] 注入层 → 交 PromptAssembler（沿用既有 MCIP 契约，不变）
```

### 4.1.1 🔴 五级闸门法理（本方案不得成为旁路）

《蓝皮书 V3.0》红线 6 规定：**五级闸门是唯一读取通道，不可关闭、无旁路**。

**本白皮书对此的立场**：

### 4.2 第一层：围栏（召回）

#### 4.2.1 围栏条件（按序应用，任一为空则跳过）

| 序 | 条件 | 来源 | 成本 |
|---|---|---|---|
| 1 | `belong_entity_uuid IN (...)` | `UUIDPoliceFilter.buildSqlClause` | 索引命中，< 5 ms |
| 2 | `created_at >= ?`（时间窗） | 调用方传入（默认不限） | 索引命中 |
| 3 | `calcium_level >= ?`（重要度下限） | 调用方传入（默认不限） | 索引命中 |
| 4 | `namespace <> 'test'`（测试隔离） | 固定 | 索引命中 |
| 5 | 分片 LIKE（见 4.2.2） | 查询串分级生成 | 全表扫描 **38–60 ms** |

#### 4.2.2 关键词分片生成

**规则**：对查询串生成 **2-gram + 3-gram 分片**（与 `buildNgrams` 相同的切分逻辑，但**不建索引**），
去重后取前 **40** 个（沿用既有上限）。

**合并查询（RA-4 强制）**：

```sql
SELECT id, raw_input, calcium_score, calcium_level, created_at,
       perception_40d, belong_entity_uuid
FROM memories
WHERE belong_entity_uuid IN (?, ...)          -- 围栏 1
  AND (raw_input LIKE ? OR raw_input LIKE ? …) -- 围栏 5（一次 OR，禁止循环）
LIMIT 500
```

**实测**：5 个分片合并 OR + UUID 围栏 = **38 ms**；无围栏 = 74 ms。

#### 4.2.3 高召回原则

围栏**只求全、不求准**。实测分片 LIKE 召回量为 n-gram 索引的 10–20 倍
（"心情不好"：523 vs 86），这是**设计意图而非缺陷** —— 精度由精排层保证。

#### 4.2.4 空候选兜底

若关键词围栏返回 0 条（如纯情绪表达、无实词），**降级为结构化围栏**：
按 UUID + 钙化度排序取 top-N。**保证每轮必有候选**，绝不返回空。

#### 4.2.5 🔴 对话组召回（dialog_group 主路 + conversations 兜底）

> 补 PI C2 指出的覆盖空白。`DialogGroupAdapter` 出现在生效范围，必须给出替代条文。

**背景**：旧架构下对话组召回是双路 ——
① 原文命中归组（查 `search_index` 的 `conversation` 类）
② 组摘要命中（查 `dialog_group` 类）。
两类合计占 `search_index` 的 **88.4%**（222 万 + 69.6 万行）。S4 删表后**双路会同时死掉**。

**v11 替代设计（与 V36 对话块地基 / V38「块可被检索」对齐）**：

| 路径 | 数据源 | 行数 | 实测耗时 | 定位 |
|---|---|---|---|---|
| **主路** | `dialog_groups.block_summary` | **2,779** | **10 ms** | **「块 = 检索单元」** —— 扫摘要比扫 14,295 条对话更省，且符合原生设计 |
| **兜底** | `conversations.content` | 14,295 | 36 ms | 仅当主路无命中时，逐字兜底 |

**条文**：
1. 对话召回**默认走块摘要（`block_summary` + `narrative_tag`）**，命中后按 `dialog_group_id` 展开其成员对话；
2. **`conversations` 全文 LIKE 仅作兜底**，不得作为主路径；
3. 理由：块摘要已聚合语义，粒度合适；全文扫描成本高且噪音大；
4. **禁止**任何形式的「原文→预建映射」（违反 RA-1/§3.3.4）。

#### 4.2.6 五表单库围栏成本基线（实测）

|---|---|---|---|
| `memories` | 13,640 | **48 ms** | 主记忆库 |
| `conversations` | 14,295 | **36 ms** | 仅兜底 |

### 4.3 第二层：精排

#### 4.3.1 得分公式

```
score = w_hit × 归一化分片命中数
      + w_calcium × 归一化钙化度
      + w_recency × 归一化时间近因
      + w_semantic × 40D 余弦(查询向量, 记忆向量)      [可选]
```

**默认权重（v11.0 初值，可经蓝皮书调整）**：

| 权重 | 初值 | 依据 |
|---|---|---|
| `w_hit` | **0.45** | 分片命中数直接替代 n-gram 的 `COUNT(term)`，是原设计的核心排序信号 |
| `w_calcium` | **0.30** | 钙化度=重要性，实测精排可使 top10 平均钙化度 **+170%** |
| `w_recency` | **0.15** | 时间近因（会话上下文连续性） |
| `w_semantic` | **0.10** | 40D 余弦；**开关关闭时此权重并入 w_hit** |

> 🔴 **权重调整必须经蓝皮书修订并记录理由**，禁止代码内硬编码魔数。

#### 4.3.2 分片命中数（核心信号）

对每条候选，计算其 `raw_input` 命中了查询分片中的几个：

```
hit(doc) = |{ g ∈ 查询分片 : g ⊂ doc.raw_input }|
```

**这就是 n-gram 索引原本 `COUNT(DISTINCT term)` 做的事，改为现算。**
实测 500 条候选的现算耗时 **< 10 ms**。

#### 4.3.3 40D 语义余弦（可选通道）

> 🔴 **法律前置（P072 业主立法级裁决，2026-10-23，本文件不得变更）**：
> **「除 40D 外其它都是违法」** —— 全系统**唯一合法相似度 = `cosineSimilarity40D`（全 40 维扇区加权）**，
> **禁止任何子维度切片变体**（含 20 维「语义扇区」、14 维「共振扇区」等）。
> 原 `cosineSimilarity40DSemantic` / `resonanceVector40D` **已被删除**
> （`PerceptionVector40DCodec.ts:291-296`）；现行合法调用见 `MemoryRetriever.ts:703/760`。
>
> **本条优先于任何优化建议**：即使某次实测显示某个子维度切片的 P@10 更高，
> **也不得**在本方案中采用 —— 那属于立法变更，必须走业主正式裁决流程，不得夹带在实现中。

> **法令溯源（防止误读为「新立法」）**：`《40D 量纲统一法令 V1.0》`（WS-DECREE-40D-V1.0）**第二条「违法量纲清单」末行原文**已载明——
> 「任何 N 维子切片（14D 共振切片、20D 语义扇区变体等）……**删除**：禁止以任何子维度切片作为独立量纲存在
> （**扇区加权是 40D 内部的相似度权重，不是独立量纲，合法**）」。
> 因此业主 2026-10-26「扇区加权合法，不予禁止」的裁决，**是对该既有条文的适用与释义，不构成新的立法**，
> 亦不构成对 P072 前置裁决的任何松动；下文判据仅为把条文落到可核验的工程口径上。

**扇区加权 ≠ 子维度切片（业主裁决 2026-10-26：合法加权，不予禁止）**

`PERCEPTION_40D_SECTOR_WEIGHTS`（`src/m3/types/perception-40d.ts:141`）当前对
`physical_body` / `spatiotemporal` / `dynamic_growth` 三个扇区赋权 **0.0**，
这不构成 P072 所禁的「子维度切片」，判据如下（三条须同时成立）：

| 判据 | 切片 | 加权 | 本系统实测 |
|---|---|---|---|
| 向量完整性 | 存储/传输时**丢弃**部分维度 | 向量本体始终完整 40 维 | ✅ `dims` 恒为 40，codec 硬校验 len≠40 拒绝 |
| 可逆性 | **不可逆**的结构性删减 | 权重是配置，可随时恢复 | ✅ 三扇区权重 0 系「P3 前无数据源」的**阶段性**状态，瑶灵/瑶光通道上线后恢复 |
| 实现唯一性 | 需新增切向量函数 | 复用同一 `cosineSimilarity40D` | ✅ 全系统仅此一处合法相似度，无第二个实现 |

**法理表述（供后续文件引用）**：

> 40D 的完整性由**向量本身**保证，不由权重保证。
> 权重只改变各维度在加权内积中的贡献系数，不改变向量维度、不改变存储形态、不改变编解码契约。
> 因此扇区加权属于 `cosineSimilarity40D` 的**内部参数**，是《40D 量纲统一法令》允许的实现自由度；
> 而子维度切片会派生出一个维度数 < 40 的新量纲，属法令所禁。
> **红线**：任何时候不得以「权重为 0」为由，在存储或接口层把 40 维截断为更少维度。

- `memories.perception_40d` 为 `{ __v, dims[40] }`，**覆盖 100%**；
- 查询向量取 `decision.enhanced.perceptionV40`（M3 已产出，零额外成本）；
- **实测成本**：取 200 条 4 ms + JSON 解析 2 ms + 余弦排序 3 ms = **9 ms**；
- **能力边界（重要）**：40D 是**情感/生理感知向量**（D1–D32 五类 + D33–D40 亲密纹理，
  如 `D07 躯体自愈`），**不是语义向量**。它衡量「情绪/场景共鸣」，
  **不能单独承担「话题事实」相关性** —— 故权重上限设为 0.10，且必须与 `w_hit` 并用。
- **验证状态**：`⚠ 未完成有效验证`。离线测试因查询向量为伪造（用候选首条冒充），
  结果不采信。**必须在双跑阶段用真实用户消息向量验证后，方可启用该通道。**

#### 4.3.4 LLM 精排（兜底，默认关闭）

- **触发**：`w_semantic` 关闭 **且** top-K 边界分数方差 < 阈值（难分伯仲）；
- **输入**：top 20 候选的正文（截断至每条约 200 字）；
- **输出**：重排后的 top-K；
- **成本**：一次 LLM 调用，约 5–10k token；**必须可开关、可降级**；
- **降级**：LLM 失败/超时 → 直接使用规则精排结果（fail-open，不得因精排失败而丢召回）。

#### 4.3.5 语义块粒度与 40D 语义向量刺的对应关系（业主裁决 2026-10-27：原子 + 组合两层）

> 依据：《DNA 双螺旋完整编码规范 V2.0》§2.2「海胆不仅是存储单元，更是**组合基元**」。
> 本节把「海胆可大可小」的直觉，落成不违反「原子不可分割」的法定表述。

> 🔴 **术语定名（全仓唯一口径，定义源见蓝皮书第一章）**：
> 本文所称「**语义向量刺**」（英文 **Semantic Vector Spines**，正文简称「**刺**」），
> 指 40D 感知向量 40 个分量的统称——**一根刺 = 一个维度**。
> 早期文档与代码注释中的「语义刺」「刺向量」「spine」均指此物；自本版起统一规范全称为「语义向量刺」，
> 正文首次出现用全称、其后可用简称「刺」。**蓝皮书第一章为本术语的唯一定义源**，
> 其他文件引用时不得再发明同义词，也不得把「刺」重新定义成别的粒度。

**两级模型**

```
原子海胆（一次交互）—— 不可分割、不可拆解，必有完整 40 根语义向量刺，落库为真值
      │                     真源：memories.perception_40d（单行单向量）
      │  组合（可拆、可重组、可跨会话）
      ▼
组合海胆（对话组 / 话题段 / 文章 / 作品）—— 壳肉为聚合摘要，语义向量刺为聚合派生（不落盘）
```

**关键裁定**：**不为 conversations / dialog_groups / works 新增 40D 列。**
组合海胆的语义向量刺由成员原子海胆现算聚合，理由见下文三条。

**现状实测（生产库 2026-10-26，只读核验）**

| 粒度 | 表 | 行数 | 40D 语义向量刺 | 壳肉字段 | 备注 |
|---|---|---|---|---|---|
| 原子（一次交互） | `memories` | 13,640 | ✅ **100%**（`perception_40d`） | `raw_input` | 唯一真值载体 |
| 消息 | `conversations` | 14,295 | ❌ 无此列 | `content` | 只有 `perception_summary` 文本 |
| 对话组 | `dialog_groups` | 2,779 | ❌ 无此列 | `block_summary`（2,335 条 / 84%） | 有 `primary_emotion` 标签 + `emotion_curve` 标量序列 |
| 作品 | `works` | 188 | ❌ `semantic_vector` **188 行全空** | `full_text` | 无刺 |
| 黑钻 | `black_diamond` | 3,712 | ✅ 96.4%（`emotion_vector`） | `summary` | 独立珍藏层 |
| 知识库 | `knowledge_base` | 282 | ✅ 96.5%（`emotion_vector`） | `content` | 独立知识层 |

> **这条表解释了 §4.2.5 为什么必须走 `block_summary`**：
> 对话组没有向量，`cosineSimilarity40D` 无从作用，文本摘要召回是**唯一可行主路**，不是次优选择。

**组合语义向量刺的定义（不落盘）**

```
spine(组合海胆 G) = Σ_{i∈G} w_i · spine(成员 i) / Σ_{i∈G} w_i ,   w_i = calcium_score_i
```

- 结果各维钳制到合法值域（D01–D35、D38–D40 取 [0,1]；D36/D37 取 [-1,1]）；
- **纯计算、零 LLM、零新增存储**；
- 只在需要时现算（单个对话组平均 `turn_count` = 2.1，成员极少，成本可忽略）。

**为何不落盘（三条，须写进实现说明）**

1. **ADR-013 ① 禁冗余派生字段**：组合语义向量刺可由成员完全重建，存下来就是冗余；
2. **陈旧风险**：成员入组/离组、钙化衰减都会改变聚合结果，落盘必然产生「过期的刺」，
   且没有任何机制能保证同步刷新 —— 这正是历史上 `perception_v40_direct` / `works.semantic_vector`
   两列**全空至今**的同一类失败模式；
3. **ADR-013 ② 状态只有一处写**：落盘即制造第二处写入口。

> **ADR-013 豁免声明**：组合语义向量刺**不进入存储层**，故不构成「派生字段」这一 ADR-013 所约束的对象；
> 本裁决不修改 ADR-013，仅明确其适用范围止于**持久化字段**。

**红线（本节生效后不得违反）**

- 🔴 **禁止**为 `conversations` / `dialog_groups` / `works` 新增任何 40D/向量列来「补齐刺」——
  那会同时违反 ADR-013 ①②与本节的裁定；
- 🔴 **禁止**把组合刺写进 `search_index` 或任何缓存表 —— 现算成本已可忽略，缓存只会引入一致性问题；
- 🔴 **禁止**在组合刺上做任何 40 维以下的截断（见 §4.3.3）。

**已知技术债（记录，不阻塞 v11）**

| 项 | 现状 | 处置 |
|---|---|---|
| `memories.perception_v40_direct` | 13,640 行**全空**（P074 直产承诺未落地） | 不入 v11 范围；待 M3 直产改造时一并处理 |
| `works.semantic_vector` | 188 行**全空** | 作品级不造刺；召回走全文切块 + 壳肉溯源（`SearchIndexBuilder.indexWorkChunks` 的 800 字切块语义保留，但不建倒排） |

### 5.1 检索入口签名

```ts
interface RetrievalRequest {

  topK?: number;                    // 默认 12

    score: number;

  diagnostics: {
```

#### S4.2 附带处置：`schema.sql:282` 索引重建问题（业主裁决 2026-10-27：打包进 S1 停服窗口）

PI 实测发现：`idx_si_term` 被 `src/m2/schema.sql:282` 在**每次重启时重建**，
这是 10-15 v19 迁移声称「已断根」却**从未提交**的遗留，单次启动耗时/体积约 **48 MB**。

**冗余论证（为何可删而不损任何查询）**：

| 事实 | 依据 |
|---|---|
| 该索引**不是**任何查询的计划依赖 | `search_index` 主键为 `PRIMARY KEY (term, source_type, source_id)`（`schema.sql:280`） |
| `idx_si_term(term)` 恰是主键的**最左前缀** | SQLite 为复合主键建隐式索引，其前缀即可服务 `WHERE term = ?` / `WHERE term LIKE 'x%'` |
| 故它是**纯冗余索引**：零查询收益、纯写入放大 | 每次 `INSERT` 多维护一棵 B-tree，且每次启动重建约 48 MB |

**处置（选定：S1 窗口，不推迟到 S4）**：

- **为何放 S1**：S1 已是停服窗口（关写入、改 schema），且此改动与 S4 删表**无耦合**；
  拖到 S4 会让 48 MB/启动 的浪费在 S1–S3 期间继续累积（双跑期长达 ≥7 天）。
- **施工顺序（六步，不可调换）**：
  1. 停服——关掉 webui 全进程链，防 sql.js 内存库覆盖离线改库（见「归属脏值三层传播」教训）；
  2. `EXPLAIN QUERY PLAN` 取证：对 `SELECT ... WHERE term = ?` 记录删除前的执行计划，
     确认实际走的是主键隐式索引而非 `idx_si_term`；
  3. 删除 `src/m2/schema.sql:282` 这一行（不动表、不动主键）；
  4. 对现存库执行 `DROP INDEX IF EXISTS idx_si_term;`；
  5. 启动，复跑步骤 2 的同一 `EXPLAIN QUERY PLAN`，确认执行计划**未劣化**；
  6. 记录库文件体积变化，写入 S1 的 S7 归档。
- **回滚**：把该行加回 `schema.sql`（`CREATE INDEX IF NOT EXISTS` 幂等）；已被 `DROP` 的索引下次启动自动重建。**回滚不涉及数据，零风险。**
- **红线**：仅在本窗口内、仅删这一行；**不得**顺带改动 `search_index` 的列 / 主键 / 其他索引（那些属 S4 删表范围）。

## 附录 B · 术语表

| 术语 | 定义 |
|---|---|
| **围栏**（enclosure） | 缩小候选集的过程，不承担排序职责 |
