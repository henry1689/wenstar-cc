### 8. 🔴 系统不变量（任何修复不得违反）

以下规则是系统宪法，优先级高于一切 bugfix：

| # | 不变量 |
|---|--------|
| 1 | **角色扮演时禁止向主 FG 写入**（退出角色后数据自动消失） |
| 2 | **FG 真人绝不可被角色扮演**（`relation_to_user` 非空 → 封锁） |
| 3 | **分支数据隔离**（角色分支没有的人绝不能从主 FG 查） |
| 4 | **状态单一 owner**（每个状态字段只有一个模块有权修改） |
| 5 | **公共 API 变更 = 契约+类型+Mock+测试同步更新** |
| 6 | **禁止静默吞错误**（catch 必须有日志或明确注释说明为什么可以忽略） |
| 7 | **禁止同一业务规则在多个地方重复实现** |
| 8 | **UI 层不含业务逻辑，领域层不依赖 UI** |

**每次修复前必须确认**：列出本次修复涉及哪些不变量，确认方案不违反。

### 9. 🔴 危险信号 —— 立即停止

当你看到 Claude 说出以下话，**立刻叫停，回到闸门 1**：

| 危险信号 | 为什么是问题 |
|----------|------------|
| "我加了一个 fallback" | 没追根因为什么缺失 |
| "这里先 catch 住避免报错" | 在掩盖而非修复 |
| "为了兼容这种情况，我加了一个判断" | 新增条件分支 = 补丁 |
| "我顺便清理了相关逻辑" | 扩大改动范围 |
| "我修改了测试让它匹配新行为" | 测试应符合规格，不应追着代码跑 |
| "这个字段有时候不存在，所以设为 optional" | 没追问什么时候不存在、为什么 |
| "我改了多个模块以确保一致" | 可能同时在多处打补丁 |
| "我发现还有其他问题，也一起修了" | 边界失控 |


### 10. 🔴 禁止打补丁，只做架构性修复


判定标准：
| 补丁行为 | 架构修复 |
|---------|---------|
| `if (这个场景) 注入这个` | 改为数据驱动，无条件分支 |
| 在现有函数中加一个 else 分支 | 重新设计函数使其不需要条件判断 |
| 复制一段代码改几个参数 | 提取参数化函数 |
| 在调用链中间加一层检查 | 重新设计调用链使其自然覆盖 |

**铁律**：每遇到一个新场景暴露出的问题，不是往现有代码加一个 if，而是改设计让这个 if 变得不必要。
