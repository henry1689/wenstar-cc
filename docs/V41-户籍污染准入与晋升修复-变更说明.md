## 二、白皮书更新摘要

**标题：户籍实体的准入闸门与晋升机制 —— 「没判过」不再等于「已确认」**

1. **写入侧串联第二道 person 判据**（准入收紧）。
   原 FG 建节点走 `GarbageEntityGuard.checkEntity`，而 `EntityWriteGate.checkPersonEntity`
   具备它**没有的** `CHAT_RESIDUE`（虚词拦截）/ `PERSON_MAX_LEN` / `ENTITY_BLACKLIST`。
   **实测两个闸门对同一批名字的判定不一致**：

   | 名字 | `checkPersonEntity` | `GarbageEntityGuard.checkEntity`（FG 实际用） |
   |---|:--:|:--:|
   | `东坑这`（含虚词「这」） | ❌ 拒 | ✅ **放行** |
   | `公明这` | ❌ 拒 | ✅ **放行** |
   | `那两个` | ❌ 拒 | ❌ 拒 |

   而 `CHAT_RESIDUE` 在 `GarbageEntityGuard.ts` 中出现次数 = **0**。
   `EntityWriteGate.ts:18` 的注释本就自陈「与 GarbageEntityGuard.FG_EXTRA_BLOCK 对齐」——
   **注释写的才是对的，实现没对齐**。本批在最危险的写入路径（FG `addNode`）先串上强判据。

2. **闸门异常由「静默放行」改为 fail-closed**。
   原 `catch { /* guard不可用不阻塞 */ }` 意味着闸门一旦抛错（查询失败/懒加载失败/判据自身 bug），
   **所有 person 节点都能畅通无阻写进户籍** —— 守卫形同虚设。按户籍管理法「无户口写入拒绝」，
   现改为告警 + 拒绝本次写入（故障会暴露，而非静默放行垃圾）。

3. **滑窗直通必须叠加闸门校验**（`ChatEntry`）。
   `slideDetected` 是 L3 滑窗（2-3 字 n-gram）打的标记，原 `|| slideDetected` 是**无条件直通** ——
   地名片段同样带此标记，据此绕过下游**全部**闸门。
   现改为「`slideDetected` **且** 通过 `checkPersonEntity`」双条件：既保住原意
   （LLM 常遗漏新姓名，如 `安琪` 能过姓氏校验），又不让地名虚词片段搭便车。

4. **正名「没有 status ≠ 已确认」** —— 存量补齐 `status IS NULL → active` 改为 `→ candidate`
   （原语义等于「从没走过任何判定就直接转正」）。实测 `程序`/`周末`/`许多`/`都还`/`容易`/
   `方式`/`颜色`/`高兴` 等垃圾节点的 `properties.evidence` **完全为空**，却是 `active` ——
   正是被这条存量补齐批量转正的。

5. **⚠️ 一条被否决的改动（如实记录）：观察区晋升阈值 3 → 6 已回滚。**
   诊断阶段我判断「`CANDIDATE_PROMOTE_SCORE = 3` 配合 `每次提及 ×1` 实际是
   「提及 3 次即晋升」，构成反向选择器」—— 实测证据确凿（`经常` `明白` `文档` `麻烦` `国庆`
   均 count=3 晋升；而徐诗雨/玉瑶/熊梓铭/王全芬 的 `evidence` **全部为空**，因为她们走直接
   建档路径、根本不经过这条流水线）。**调高到 6 后 `candidate-zone.test.ts` 挂了 5 个断言**：

   | 测试 | 期望 |
   |---|---|
   | `:162` | 首次提及带介绍句 → **必须立即** active |
   | **`:198`** | **「candidate 被提及 3 次 → 晋升 active」—— 测试直接固化了 count=3 即晋升** |
   | `:213` | 2 次弱上下文应晋升 |
   | `:223` | 强上下文 1 次晋升 |
   | `:231` | 关系词上下文应晋升 |

   ⇒ **3→6 与 P2-6 设计意图直接冲突，不是可调旋钮**，故回滚至 3，计分公式不动。
   **根因诊断随之修正**：垃圾能晋升不是因为门槛低，而是**它们本就不该进观察区** ——
   缺陷在**准入**（滑窗产物经 `slideDetected` 无条件直通），不在**晋升**。
   本批因此只改 A（准入）与 C（status 语义），B 保留原状；存量中已晋升的垃圾另走
   `status='void'` 软清理。真人名 evidence 为空这一事实作为**未解决问题**登记（见三·3）。

2. **已知局限（如实登记，不夸大效果）**：
   实测用 `checkPersonEntity` 对存量 594 个 person 节点跑一遍，**仅拒绝 50 个**（含虚词的那些）：
   ```
   active   96 → 闸门拒 7   （别人/后你想/后我们/水多/满足我/许多/越多）
   candidate 498 → 闸门拒 43 （东坑这/公明这/于是我/全了解/关心我/后就这/杭州这 …）
   ```

   而 `公明` `杭州` `容易` `明白` `文档` `程序` `毛巾` `万物生` `充满浪` `全去享` `全是水`
   这类**不含虚词的整词地名/普通名词/滑窗碎片** —— **闸门拦不住**。
   这与系统自身注释的判断一致（`FamilyGraph:2745`）：
   > 「中文人名与滑窗片段在字面特征上不可分 → 唯有用行为/上下文判定」

   ⇒ 本批的准入修复**只覆盖「含虚词的碎片」**，不覆盖「整词地名」。
   后者靠 ① 晋升阈值提高（不再转正）② 存量清理（见五）③ 缺陷 D（后续批次）三者共同处置。
   **不声称 A 能拦下全部** —— 这是诚实的能力边界。

3. **缺陷 D 登记为后续批次（本批不改）**：
   `getAllPersonNames(): status != 'void'` 使 **495 个 candidate 全部参与召回**，仅靠手写

   约一半**必须看到 candidate**：

     `process-stages:125/175`、`chat.ts:914`、`retrieval-stage:370/373/566/860`、
     `EntityContextBuilder:183`、`ChatEntry:172`、`post-process:58`
   - **需要全量含 candidate**（约 15 个）：UUID 回填/档案采集/拓扑/健康检查 ——
     `UuidBackfillService:171`、`EntityUUIDBackfill:60`、`EntityOwnershipResolver:89`、
     `ProfileAcquisitionEngine:311`、`FamilyGraphSync:52/136`、`L3EntityAnnotator:363/395`、
     `EntityTopologyManager:262/277`
   - 直接改 `getAllPersonNames()` 会**破坏后一半依赖**；新增 `getActivePersonNames()` 并逐一
     改 15 个调用点则文件集爆炸（15+ 文件，含 `chat.ts`/`process-stages.ts` 等高风险文件）。
     ⇒ 需独立批次系统梳理两类语义，本批不做。

## 八、方法论记录

**方案被自己的实测推翻两次（如实记录）**：

1. 首版方案称「闸门能拒 `东坑这`/`公明这`/`那两个`，它们却进了 FG ⇒ 闸门没接线」。
   **错** —— 那测的是 `EntityWriteGate.checkPersonEntity`，而 FG 实际走
   `GarbageEntityGuard.checkEntity`，**用错了闸门**。正确闸门对 11 个垃圾**放行 10 个**。
   真实病因不是「没接线」，而是「**两个闸门判据不一致**」。
2. 首版拟在 `L3EntityAnnotator`（滑窗源头）加闸门，但那会引入 `m1 → m4` 运行时依赖
   （与 `FamilyGraph → m1/types` 的 type-import 构成潜在环）。改为在 `ChatEntry`
   （webui 层，跨层 import 有 `post-process.ts:12` 先例）收紧出口。

⇒ 教训：**判据类结论必须用实际调用的那个实现去测，不能用同名/相邻的另一个。**

3. **一处测试数据被改动（如实记录）**：`candidate-zone.test.ts` 的占位名
   `批12验证壬`（**6 字**）→ `批12验证`（**5 字**）。
   原因：写入闸门的 person 长度上限是 `EntityWriteGate.PERSON_MAX_LEN = 5`（**既有设计**，
   理由是防整段描述被当人名，注释举例 `大眼睛又圆又亮`）。修复3 串联该闸门后，
   6 字占位名被**正确拒绝** → 节点未创建 → 「首次提及即晋升」断言无从谈起。
   **改的是测试数据而非闸门**：该用例的意图（首次提及 + 介绍句 → 立即晋升）与名字长度无关，
   占位名需同时满足「库中不存在」与「合乎人名长度约束」两个条件。

4. **一次 Edit 落空的根因**：`status 存量补齐` 那处改动曾「Edit 返回成功但文件未变」。
   根因是把**同文件的两个 Edit 放进了同一条消息** —— 它们实际并行执行，后一个基于
   「不含前一个改动」的快照写入，把前者**覆盖**了。后改为串行发出并立即 grep 验证存活。
   ⇒ 同一文件的多次修改必须**串行**发出，且改完立即验证。
